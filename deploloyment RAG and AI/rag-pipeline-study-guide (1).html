Enterprise RAG Pipeline: Topic Guide

A brief explanation of every module in the learning path, from ingestion to production monitoring. Open a topic to see what it is, why it matters, and the key tools.

How the pieces fit together

Offline path (index time): Sources → Ingestion → Parsing → Cleaning → Chunking → Metadata → Embeddings → Vector DB.

Online path (query time): Query → Preprocess → Transform → Hybrid retrieval → Rerank → Compress → Prompt → LLM → Validate → Cited answer.

Evaluation, caching, security and monitoring wrap around both paths.

M1Architecture and data flow

The map of the whole system. A RAG app has an offline path that prepares knowledge and an online path that answers questions.

  • Sync vs async: sync answers inside the request; async queues heavy work such as ingestion.
  • Batch vs real-time: batch re-indexes on a schedule; real-time updates on every change.
  • Stateless vs stateful: stateless services scale easily; stateful ones keep chat memory.

M2Document ingestion

Getting documents from many sources into the pipeline safely. Production ingestion must handle huge files, scanned PDFs, corrupted files, duplicates and incremental updates.

  • Formats: PDF, DOCX, TXT, CSV, Excel, HTML, Markdown, JSON, databases, APIs, web crawls, SharePoint.
  • Use content hashes to skip duplicates; process only new or changed files.
  • Quarantine bad files instead of failing the whole batch.

Methods to use in this module

  • Docling (PDF, DOCX): DocumentConverter().convert(path).document, then export_to_markdown()
  • PyMuPDF (PDF, fast): pymupdf.open(path), loop for page in doc: page.get_text()
  • Unstructured (many formats): partition(filename=path); partition_pdf(strategy="hi_res") for scans; partition_docx, partition_html
  • CSV / Excel (pandas): pd.read_csv(path, chunksize=50000); pd.read_excel(path, sheet_name=None) reads all sheets
  • JSON: LangChain JSONLoader(file_path, jq_schema=".items[]")
  • HTML / Web: WebBaseLoader(urls).load(); RecursiveUrlLoader to crawl; Playwright for JavaScript-heavy pages
  • Markdown: UnstructuredMarkdownLoader or read text then split with MarkdownHeaderTextSplitter
  • Database: pd.read_sql(query, engine) with SQLAlchemy, or LangChain SQLDatabaseLoader
  • SharePoint / enterprise: LangChain SharePointLoader or Microsoft Graph API with delta queries for changes
  • Any format fallback: Apache Tika parser.from_file(path)
  • Large files: loader.lazy_load() (generator), page-by-page processing, batch size limits
  • Scanned PDFs: Docling PdfPipelineOptions(do_ocr=True), or render page.get_pixmap(dpi=300) then pytesseract.image_to_string()

Step by step (how to explain it)

  1. Discover: list new and changed files with Path.rglob("*"), S3 list_objects_v2, or a Graph API delta query for SharePoint.
  2. Fingerprint: hashlib.sha256(file_bytes).hexdigest(); for S3 you can also compare the ETag and last-modified time.
  3. Compare to the registry: look up the doc in a Postgres table; same hash means skip, different hash means update, missing means new.
  4. Route by type: pick a parser from the file extension or MIME type (for example with mimetypes.guess_type).
  5. Parse: call the right method from the list above; process large files page by page or with lazy_load().
  6. Handle failure: wrap in try/except, retry transient errors, and move unreadable files to a quarantine folder with the error saved.
  7. Queue and record: send work to Celery with .delay() and save status (queued, parsed, indexed, failed) per document.

Interview line: "Ingestion is idempotent: the hash decides whether a file is new, unchanged or modified, so reruns never duplicate data and failures are isolated per document."

M3Parsing and cleaning

Turns raw files into clean, structured text. Bad parsing (wrong reading order, broken tables, repeated headers) silently ruins retrieval, so quality here caps quality everywhere else.

  • Layout-aware parsing and table extraction keep structure intact.
  • OCR for scanned pages; multilingual handling for non-English content.
  • Remove headers, footers, page numbers; normalize whitespace and special characters.

Methods to use in this module

  • Docling: PdfPipelineOptions(do_ocr=True, do_table_structure=True); iterate doc.iterate_items() and skip items labeled page header or footer
  • Unstructured: filter elements: [e for e in elements if e.category not in ("Header", "Footer")]

  • OCR: pytesseract.image_to_string(img, lang="eng+hin"); PaddleOCR for layout-heavy or multilingual pages
  • Debugging reading order: export page.get_text("blocks") and compare with the rendered page image
M4Chunking

Splitting documents into pieces that are small enough to retrieve precisely and large enough to keep meaning. Large chunks dilute relevance; tiny chunks lose context.

  • Fixed, recursive, token, sentence, semantic, document-based.
  • Parent-child and hierarchical: search small chunks, return larger parents.
  • Agentic and contextual chunking add LLM-generated context to each chunk.
  • Tune size and overlap by measuring retrieval, not by guessing.

  • Tables: keep a table as one chunk in Markdown with its caption, never split rows mid-table
M5Metadata and document versioning

Every chunk carries identity and context: document ID, chunk ID, page, source, timestamp, version, department, permissions and content hash. This enables filtering, access control and safe updates.

  • Detect new, unchanged, modified or deleted documents by comparing hashes.
  • Remove stale vectors so old content never answers new questions.
  • Reindex only changed pages or chunks.

Methods to use in this module

  • Hashing: hashlib.sha256(text.encode()).hexdigest() for document and chunk hashes
  • Postgres registry: INSERT ... ON CONFLICT (doc_id) DO UPDATE for doc_id, version, hash, status, ACL
  • Change detection: compare stored hash with new hash: missing means new, equal means unchanged, different means modified; ids missing from the source mean deleted

  • Deterministic IDs: uuid.uuid5(NAMESPACE_URL, f"{doc_id}:{chunk_index}") so reruns overwrite instead of duplicate
M6Embedding generation

Embeddings convert text into vectors so similar meanings sit close together. Choice of model, dimension and similarity metric affects both quality and cost.

  • Dense vs sparse; cosine, dot product, Euclidean; normalization.
  • Batch and async generation, caching, retries and rate-limit handling.
  • Version your embeddings: changing the model means re-embedding everything.

M7Vector database and indexing

Stores vectors and finds nearest neighbors fast. Index type trades speed, memory and accuracy.

  • HNSW: fast, high recall, memory heavy. IVF: clustered, memory efficient. Flat: exact but slow at scale.
  • Payload indexes for metadata filtering; upsert, delete, backup and recovery.
  • Multi-tenancy via collections, namespaces or filters; zero-downtime reindexing with aliases.

  • Qdrant tuning: hnsw_config (m, ef_construct) at creation; search_params=SearchParams(hnsw_ef=128) at query time

  • Backup: Qdrant snapshots via client.create_snapshot(); Postgres pg_dump or managed backups
M8Retrieval

Finds the right chunks for a question. Dense search understands meaning; BM25 matches exact terms such as product IDs. Hybrid search combines both.

  • Reciprocal Rank Fusion (RRF) merges ranked lists without score tuning.
  • Query rewriting, multi-query, expansion and HyDE improve weak queries.
  • Self-query turns natural language into metadata filters.
  • Tune top-K, fetch-K and similarity thresholds; more is not always better.
LangChainQdrantBM25RRF

Methods to use in this module

  • LangChain dense: vectorstore.as_retriever(search_type="mmr", search_kwargs={"k": 5, "fetch_k": 30})
  • LangChain hybrid: BM25Retriever.from_documents(docs) + EnsembleRetriever(retrievers=[bm25, dense], weights=[0.5, 0.5])
  • Qdrant hybrid: query_points(prefetch=[dense, sparse], query=FusionQuery(fusion=Fusion.RRF))
  • Query transformation: MultiQueryRetriever.from_llm(); HyDE via HypotheticalDocumentEmbedder; SelfQueryRetriever for metadata filters
  • Keyword scoring: BM25Okapi(tokenized_corpus).get_scores(query_tokens) from rank_bm25
  • Parent expansion: ParentDocumentRetriever
M9Reranking

A second, more accurate pass over the top candidates. Bi-encoders are fast but coarse; cross-encoders read the query and chunk together for better ordering.

  • Retrieve about 20 to 100 candidates, rerank, keep the best few.
  • Cost is latency; reduce it with fewer candidates, smaller models or caching.
  • Skip reranking when the corpus is tiny or latency is critical.

Methods to use in this module

  • Sentence Transformers: CrossEncoder("BAAI/bge-reranker-v2-m3").predict([(query, chunk), ...]) then sort by score
  • FlashRank: Ranker().rerank(RerankRequest(query=q, passages=p))
  • Cohere: co.rerank(model=..., query=q, documents=docs, top_n=5)
  • LangChain: ContextualCompressionRetriever(base_compressor=CrossEncoderReranker(model=HuggingFaceCrossEncoder(...), top_n=5), base_retriever=r)
  • Latency: rerank only 30 to 50 candidates, batch pairs, cache scores by (query hash, chunk id)
M10Context compression and management

Fits the best evidence into a limited context window. Too much context raises cost and can bury the answer.

  • Token budgeting, deduplication, filtering and prioritization.
  • Expand to parent context when a small chunk matched.
  • Lost-in-the-middle: models miss content in the center, so place key chunks first or last.
ContextualCompressionRetrieverToken budgets

Methods to use in this module

  • LangChain: EmbeddingsFilter(embeddings, similarity_threshold=0.75); LLMChainExtractor.from_llm(llm); DocumentCompressorPipeline(transformers=[...])
  • Lost in the middle: LongContextReorder().transform_documents(docs)
  • Token budget: count with tiktoken.encoding_for_model(...).encode(text) and add chunks until the budget is reached
  • Deduplication: drop chunks with the same hash or with cosine similarity above 0.95 to a chunk already chosen
M11Prompting and generation

Instructs the LLM to answer only from retrieved context, cite sources and say "I don't know" when evidence is missing.

  • System prompts, context injection, structured output with Pydantic.
  • Citations tied to chunk IDs so claims are verifiable.
  • Defend against prompt injection hidden inside retrieved documents.
  • Version and test prompts like code.
LangChainPydanticAbstention

Methods to use in this module

  • Prompt: ChatPromptTemplate.from_messages([("system", rules), ("human", "{context}\n\n{question}")])
  • Structured output: llm.with_structured_output(AnswerModel) where the Pydantic model has answer, citations and confidence
  • Citations: label each chunk [doc_id:chunk_index] in the context and validate returned citations against retrieved ids
  • Abstention: if the retriever returns nothing above threshold, return "not found" without calling the LLM
  • Prompt versions: Langfuse langfuse.get_prompt("rag-answer")
  • Injection defense: wrap context in delimiters and instruct the model to treat it as data, never as instructions
M12Evaluation

Measures whether the system actually works, separately for retrieval and generation, so you know what to fix.

  • Retrieval: Recall@K, Precision@K, MRR, Hit Rate, nDCG.
  • Generation: faithfulness, answer relevancy, context precision and recall.
  • Build golden datasets, compare chunking, embeddings and retrievers, set quality thresholds, and catch regressions in CI.

M13Advanced RAG architectures

Patterns that go beyond a single retrieve-then-generate step.

  • Naive / Advanced / Modular: from simple to pluggable pipelines.
  • CRAG: grades retrieved results and corrects or falls back. Self-RAG: model decides when to retrieve and critiques itself.
  • Adaptive: routes by query complexity. Agentic: an agent plans tools and retrieval steps.
  • Graph RAG: uses entity relationships. Multi-hop: chains retrievals for composite questions.
  • Hierarchical / Query-focused: summarize or navigate by level and focus.

Methods to use in this module

  • Multi-hop: loop: retrieve, extract sub-question, retrieve again, with a max step count
M14Caching and performance

Cuts latency and cost by reusing work.

  • Exact-match and semantic caches for queries and LLM responses; embedding and retrieval caches.
  • Cache keys include query, filters, user permissions and index version.
  • Invalidate on document updates; use TTLs to limit stale answers.
  • Async I/O, connection pooling and parallel retrieval for concurrency.

Production Deployment Guide

How any project goes from a laptop to a production server. Each topic is written so you can explain it in an interview.

D1What deployment is, environments and the standard flow

Deployment means packaging code, running it on production infrastructure, exposing it safely to users, then monitoring it and rolling back if it breaks. (Laptop par chalne wale code ko internet par stable chalana.)

Environments: Dev (build and test), Staging/UAT (production-like copy for final testing), Production (real users). Code moves dev → staging → production, and staging should mirror production.

  1. Source control: code in Git (GitHub, GitLab, Bitbucket) with pull requests and review; deploy from main or a tag.
  2. Build: install pinned dependencies and produce an artifact (Docker image, .jar, frontend build folder).
  3. Test: unit and integration tests, linting, security scans (Trivy, Snyk, Bandit). Any failure stops the release.
  4. Package and store: push the image to a registry (Docker Hub, ECR, GCR, GHCR, ACR) with a version tag or git SHA, never just latest.
  5. Provision infrastructure: servers, network, database, load balancer, ideally as code with Terraform or CloudFormation, configured with Ansible.
  6. Configure: environment variables and secrets from a secrets manager, never from Git.
  7. Deploy: release using rolling, blue-green or canary strategy.
  8. Verify: health check, smoke test, watch error rate and latency.
  9. Monitor and alert: metrics, logs, traces; alerts to Slack or PagerDuty.
  10. Roll back if needed: redeploy the previous tag; database migrations must be backward-compatible.
D2Static website (React, Vue, Angular, plain HTML)

No server logic, so it is cheap, fast and highly scalable.

  1. Build: npm run build creates static files.
  2. Upload to AWS S3, Netlify, Vercel, GitHub Pages, or serve with Nginx.
  3. Put a CDN in front (CloudFront, Cloudflare) for speed and caching.
  4. Point a domain with DNS (Route 53, Cloudflare) and enable HTTPS.
  5. Invalidate the CDN cache on every release.
D3Backend API on a Linux server (EC2, DigitalOcean, on-prem)

Used for Django, Flask, FastAPI, Node.js or Spring Boot on a plain VM.

  1. Provision an Ubuntu VM; log in with SSH keys and disable password login.
  2. Secure it: firewall (UFW or security groups) open only on 22, 80, 443; non-root user; Fail2ban.
  3. Install runtime (Python, Node or Java), pull the code, create a virtualenv, install requirements.
  4. Run with a production app server: Gunicorn or Uvicorn for Python, PM2 for Node. Never use the dev server.
  5. Keep it alive with systemd so it restarts after a crash or reboot.
  6. Nginx as reverse proxy: receives traffic on 80/443, handles SSL, compression and static files, forwards to the app server.
  7. HTTPS with free Let's Encrypt certificates (Certbot, auto-renew).
  8. Logs: to files or journald, rotated with logrotate.

Flow: User → DNS → Nginx (SSL) → Gunicorn/Uvicorn → App → Database.

D4Docker and Docker Compose

Containers package the app with its environment, which removes "works on my machine".

  1. Write a Dockerfile: slim base image, multi-stage build, non-root user.
  2. Build and tag the image, scan it, push it to a registry.
  3. On the server, pull and run it, or use Docker Compose to run app, database, Redis and Nginx together.
  4. Use volumes for persistent data; inject config through environment variables or secrets.
  5. Add health checks and a restart policy (restart: always).

Docker vs VM: containers share the host kernel, so they are lighter and start faster; a VM runs a full OS each.

D5Kubernetes (microservices and large scale)

Use it for many services, autoscaling and self-healing. For one small app it is overkill.

  1. Push images to a registry.
  2. Write manifests or a Helm chart: Deployment (replicas), Service (stable internal address), Ingress (external routing and TLS), ConfigMap/Secret, HPA (autoscaling), PersistentVolumeClaim (storage).
  3. Add readiness probes (receive traffic or not) and liveness probes (restart if stuck).
  4. Run on EKS, AKS, GKE, or self-managed with kubeadm or k3s.
  5. Deploy with kubectl apply, Helm, or GitOps tools (ArgoCD, Flux) where Git is the source of truth.
  6. Rolling updates are automatic; kubectl rollout undo rolls back.
D6Serverless, databases, batch jobs and mobile backends

Serverless: AWS Lambda + API Gateway, Azure Functions, Cloud Functions, Cloud Run. Package the function, define a trigger (HTTP, queue, schedule), deploy with Serverless Framework, SAM or Terraform. Scales automatically and bills per execution; watch cold starts and time limits.

Database:

  1. Prefer managed services: RDS/Aurora, Cloud SQL, Azure SQL, MongoDB Atlas.
  2. Keep it in a private subnet; allow only the app through security groups.
  3. Apply schema changes through migrations (Alembic, Flyway, Liquibase) in the pipeline.
  4. Enable automated backups and point-in-time recovery; add read replicas for scale.
  5. Test restores regularly.

Batch jobs: Airflow, Prefect, cron, Kubernetes CronJobs. Jobs must be idempotent, retry on failure and alert.

Mobile backends: backend follows D3 to D5; the app ships via App Store and Google Play using Fastlane or Codemagic. Version APIs (/v1/) because old app versions stay in use.

D7Deploying a RAG / LLM application
  1. Wrap the pipeline in FastAPI and containerize it.
  2. Run dependencies as separate services: Qdrant or pgvector, Redis, PostgreSQL.
  3. Load models once at startup, not per request; use GPU nodes and vLLM, Triton or TorchServe for heavy models.
  4. Run ingestion as a separate worker (Celery, RQ) or scheduled job, not inside the API.
  5. Deploy with Docker Compose (small) or Kubernetes (large); version models with MLflow or a model registry.
  6. Observe with Langfuse for LLM traces and Prometheus + Grafana for system metrics.
  7. Cache embeddings and answers in Redis; handle LLM rate limits with retries, backoff and fallback models.
  8. Enforce access control at retrieval time and keep API keys in a secrets manager.
D8CI/CD tools

CI builds and tests every push. CD releases passing builds automatically (delivery may need manual approval; deployment is fully automatic).

  • GitHub Actions: YAML pipelines inside the repo, easiest start.
  • GitLab CI: built into GitLab, strong all-in-one.
  • Jenkins: self-hosted and highly customizable, needs maintenance.
  • CircleCI, Azure DevOps, AWS CodePipeline: managed alternatives.
  • ArgoCD / Flux: GitOps delivery to Kubernetes.

Typical flow: checkout → set up runtime → install → test → build image → push to registry → deploy via SSH, kubectl or Helm → smoke test.

D9Release strategies and zero downtime
  • Recreate: stop old, start new. Simple but causes downtime.
  • Rolling: replace instances gradually; Kubernetes default.
  • Blue-green: run old and new side by side, switch traffic at once; instant rollback but double cost.
  • Canary: send 5% of traffic to the new version, watch metrics, then increase; safest for risky changes.
  • Feature flags: ship code turned off, enable gradually (LaunchDarkly, Unleash).

Zero downtime needs: rolling or blue-green, readiness probes, backward-compatible DB migrations and graceful shutdown.

D10Cloud platforms, configuration, secrets and security

AWS: EC2, ECS/Fargate, EKS, Lambda, RDS, S3, CloudFront, Route 53, ALB, IAM, CloudWatch. Azure: VMs, App Service, AKS, Functions, Azure SQL. GCP: Compute Engine, Cloud Run, GKE, Cloud SQL. Simpler: DigitalOcean, Render, Railway, Fly.io, Heroku.

  1. Config lives in the environment, not in code (twelve-factor); use .env only locally.
  2. Production secrets come from AWS Secrets Manager, SSM, Vault or Kubernetes Secrets; rotate them and use least-privilege IAM roles.
  3. HTTPS everywhere (Let's Encrypt, ACM).
  4. Load balancer (Nginx, HAProxy, ALB) spreads traffic; databases stay in private subnets.
  5. WAF and rate limiting (Cloudflare, AWS WAF); API authentication with JWT, OAuth2 or API keys.
  6. Patch regularly and scan images and dependencies.
  7. Plan disaster recovery: RPO is how much data you can lose, RTO is how long you can be down.
D11Monitoring, scaling and troubleshooting
  • Metrics: Prometheus + Grafana, CloudWatch, Datadog, New Relic (CPU, memory, request rate, errors, p95/p99 latency).
  • Logs: ELK/EFK or Loki, structured JSON.
  • Tracing: OpenTelemetry with Jaeger or Tempo.
  • Errors: Sentry. Alerts: Alertmanager, PagerDuty, Slack. Uptime: UptimeRobot, Pingdom.

Scaling: vertical means a bigger machine; horizontal means more instances behind a load balancer and needs a stateless app (sessions in Redis, files in S3). Add autoscaling (ASG, HPA), caching, queues (RabbitMQ, Kafka, SQS), read replicas and connection pooling (PgBouncer). For reliability use health checks, retries with backoff, timeouts, circuit breakers and multi-AZ.

When a deployment fails:

  1. Check pipeline logs: build, test or deploy stage?
  2. Check app logs (journalctl, docker logs, kubectl logs).
  3. Check health endpoints, ports and the Nginx error log.
  4. Check config and secrets; a wrong env var is the most common cause.
  5. Check dependencies: DB connectivity, security groups, DNS.
  6. Check resources: CPU, memory (OOM kills), disk.
  7. If not fixed quickly, roll back first and investigate after.
D12Interview-ready answer and common questions
30-second answer: I containerize the app with Docker and push the image to a registry through a GitHub Actions pipeline that runs tests and security scans. Infrastructure is created with Terraform. In production the app runs behind a load balancer and Nginx with HTTPS, on Kubernetes or ECS, with secrets from a secrets manager. I use rolling or canary releases with health checks for zero downtime, monitor with Prometheus, Grafana and centralized logs, and keep versioned images so I can roll back quickly.
  • Why Nginx in front of Gunicorn? SSL termination, static files, buffering slow clients, load balancing, security.
  • Blue-green vs canary? Blue-green switches all traffic instantly; canary shifts it gradually based on metrics.
  • Compose vs Kubernetes? Compose for one host and small apps; Kubernetes for multi-node, autoscaling and self-healing.
  • How do you handle secrets? Secrets manager or Vault, injected at runtime, never in Git or images.
  • New release breaks production? Roll back to the previous image tag, then investigate with logs and traces.
  • CI vs CD? CI builds and tests every change; CD releases it automatically.

D14How to explain any tool in an interview

Use this five-part pattern for every tool so your answer sounds structured:

  1. Problem: what pain existed without it.
  2. Tool: what you used and what it does in one line.
  3. Why this one: the deciding factor (cost, team skill, ecosystem, scale, existing stack).
  4. Trade-off: an honest weakness.
  5. Example or result: something real from your project.
Example (Nginx): "Gunicorn can run the app but is not built to face the internet. So I put Nginx in front for SSL termination, static files, buffering slow clients and load balancing. I chose Nginx because it is lightweight, battle tested and our team already knew it. The trade-off is manual config; Caddy gives automatic HTTPS if we wanted simpler. In our project it reduced app server load because static and slow connections never reached Gunicorn."

Tips: never say "because everyone uses it"; tie the choice to a requirement. Mention one alternative and when you would pick it. Say only what you have actually used, and label the rest as "I understand the concept".

D15Cross-question bank: "why this tool only?"

Why Docker? Identical environment from laptop to production, fast startup, versioned images enable instant rollback, and dependencies stop clashing.

Cross-question: "Containers are not needed for a simple app, right?" Agree partly: for one small app a VM with systemd works. Docker still pays off once you have more than one environment or developer, because it removes setup drift.

Why Kubernetes and not just Docker Compose or ECS? We needed autoscaling, self-healing and rolling updates across several services and nodes.

Cross-question: "Is Kubernetes overkill?" Yes for a single service. Say: "For a small team I would start with ECS Fargate or Cloud Run and move to Kubernetes when service count and scaling needs justified the operational cost."

Why Terraform, not Ansible? They solve different jobs. Terraform creates infrastructure (VPC, VM, DB) declaratively with a plan and state; Ansible configures software inside servers.

Cross-question: "Why not click in the console?" Not repeatable, not reviewable, impossible to recreate in disaster recovery. IaC gives version history and consistent environments.

Why GitHub Actions, not Jenkins? No server to maintain, pipeline lives with the code, native GitHub integration.

Cross-question: "When would you pick Jenkins?" Air-gapped or on-prem environments, very custom pipelines, or an existing Jenkins investment. Trade-off: you patch and scale it yourself.

Why Nginx when the app has its own server? App servers are not hardened for public traffic. Nginx handles SSL, slow clients, static files, compression and load balancing.

Cross-question: "Does Kubernetes make Nginx unnecessary?" Not exactly: an Ingress controller (often Nginx or Traefik) plays the same role.

Why Redis? In-memory speed for caching, sessions, rate limiting and queues, shared across all instances.

Cross-question: "What if Redis goes down?" The app should fall back to the database or recompute, with a timeout and circuit breaker; use replicas or a managed Redis with failover. Redis is a cache, so losing it must degrade performance, not correctness.

Why Prometheus and Grafana? Open source, pull-based metrics, strong query language (PromQL), native Kubernetes support, flexible dashboards.

Cross-question: "Why not Datadog?" Datadog is easier and richer but costs more at scale. Choose it if the team lacks time to run monitoring; choose Prometheus for cost control and open standards.

Why a managed database (RDS)? Backups, patching, failover and monitoring are handled for us.

Cross-question: "Why not self-host?" Self-hosting is cheaper and more controllable but needs DBA effort. Choose it for special extensions, cost at very large scale or compliance.

Why Qdrant over pgvector (RAG)? Qdrant is purpose-built: fast filtered search, HNSW tuning, quantization and scaling for large vector counts. pgvector is attractive when data is moderate and you want one database with SQL joins.

Cross-question: "How did you decide?" Number of vectors, filter complexity, latency target and operational overhead. Under a few million vectors pgvector is often enough.

Why not serverless for everything? Cold starts, time limits, and cost at steady high traffic. It suits spiky or event-driven work; long-running or GPU workloads fit containers better.

Why Let's Encrypt or ACM? Free, automated, renewing certificates mean no expired-certificate outages.

D16If the interviewer asks about a tool you have not used

Honesty plus reasoning scores higher than bluffing.

  1. Be honest: "I have not used X in production."
  2. Map it to what you know: "I have used Y for the same purpose, and X is similar because..."
  3. Show the concept: explain the problem it solves and how it would fit the flow.
  4. Show learning ability: "I would read the docs and run it in staging first."
Example: "I have not used ArgoCD in production; we deployed with a GitHub Actions pipeline running Helm. I understand ArgoCD as GitOps: it watches Git and syncs the cluster to match, so Git is the source of truth and rollback is a revert. I would adopt it to get drift detection."

If the question is "what if you cannot use tool X?" (no Kubernetes, no cloud, no CI server):

  • No Kubernetes: Docker Compose on a VM, ECS, or Nomad, with systemd restart and Nginx load balancing.
  • No cloud: on-prem VMs with Ansible, Nginx, self-hosted Postgres and Harbor, backups to NAS.
  • No CI/CD: a deployment script (build, test, push, SSH, restart) triggered by a Git hook, then automate it later.
  • No monitoring stack: health endpoint, structured logs, cron-based checks, then add Prometheus.

Handling cross-questions you cannot answer: pause, restate the question, state the assumption, give the principle ("I would measure first"), and name what you would check. Avoid guessing numbers; say how you would find them.

Common traps: claiming Kubernetes for every case, saying one tool is "best" without context, forgetting rollback, and ignoring cost and team skill.

D21Code example: Docling to chunks to embeddings to Qdrant

One pipeline stage chain using the methods from D20. Check names against your installed versions.

import hashlib, uuid
from docling.document_converter import DocumentConverter, PdfFormatOption
from docling.datamodel.base_models import InputFormat
from docling.datamodel.pipeline_options import PdfPipelineOptions
from docling.chunking import HybridChunker
from sentence_transformers import SentenceTransformer
from qdrant_client import QdrantClient
from qdrant_client.models import VectorParams, Distance, PointStruct, PayloadSchemaType

PATH = "policy.pdf"

# 1. Parse: OCR for scans, table structure on
opts = PdfPipelineOptions(do_ocr=True, do_table_structure=True)
converter = DocumentConverter(
    format_options={InputFormat.PDF: PdfFormatOption(pipeline_options=opts)}
)
doc = converter.convert(PATH).document

# 2. Chunk: structure-aware, respects token limits
chunker = HybridChunker()
chunks = list(chunker.chunk(dl_doc=doc))
texts = [chunker.contextualize(chunk=c) for c in chunks]

# 3. Embed: batched and normalized for cosine similarity
model = SentenceTransformer("BAAI/bge-m3")
vectors = model.encode(texts, batch_size=32, normalize_embeddings=True)

# 4. Index: collection, payload index, deterministic IDs
client = QdrantClient(url="http://localhost:6333")
NAME = "docs_v1"
if not client.collection_exists(NAME):
    client.create_collection(
        NAME, vectors_config=VectorParams(size=1024, distance=Distance.COSINE)
    )
    client.create_payload_index(NAME, "doc_id", PayloadSchemaType.KEYWORD)

doc_id = hashlib.sha256(open(PATH, "rb").read()).hexdigest()
points = [
    PointStruct(
        id=str(uuid.uuid5(uuid.NAMESPACE_URL, f"{doc_id}:{i}")),
        vector=v.tolist(),
        payload={"doc_id": doc_id, "chunk_index": i, "text": t, "source": PATH},
    )
    for i, (t, v) in enumerate(zip(texts, vectors))
]
client.upsert(NAME, points=points)
  1. Parse: table structure on so tables survive as structured content.
  2. Chunk: contextualize adds headings to each chunk's text before embedding.
  3. Embed: keep the chunker's tokenizer consistent with the embedding model to avoid over-long chunks.
  4. Index: deterministic IDs from document hash plus chunk index make re-runs idempotent (upsert replaces, never duplicates).
  5. Update flow: if the document hash changes, delete old points with a doc_id filter, then upsert the new ones.
Interview line: "I derive chunk IDs from the document hash and chunk index, so reprocessing is idempotent, and I store doc_id in an indexed payload field so I can delete or filter all chunks of a document quickly."

S3Worked capacity estimate: 10 million documents

State assumptions out loud, then calculate.

  1. Chunks: 10M documents x 20 chunks each = 200M chunks.
  2. Raw vectors: 200M x 1,024 dims x 4 bytes = about 819 GB (float32).
  3. Compression: int8 scalar quantization is about 4x smaller (about 205 GB); binary quantization about 32x (about 26 GB) but lower accuracy, so rerank with full vectors.
  4. Index overhead: HNSW graph adds memory on top, so plan extra headroom; shard across several nodes and keep originals on disk.
  5. Embedding cost and time: 200M chunks at 400 tokens is about 80B tokens; with a self-hosted model on GPUs, batch and parallelize over days, not hours; hosted APIs would be a large bill, so compare.
  6. Query path: target e.g. 300 ms retrieval; dense and BM25 in parallel, rerank 30 candidates, then LLM.
  7. Ingestion: queue-based workers with hash-based incremental updates; backfill once, then process only changes.

The numbers are illustrative assumptions. In the interview, the habit of estimating and justifying matters more than exact values.

S4Senior scenarios with structured answers

Pattern: symptom, evidence to check, root causes, fix, trade-off.

1. Embedding model must change with no downtime.

Plan: create a new collection with a new model name, backfill in batches with rate limits, dual-write new changes to both, evaluate new index on the golden set, shift traffic by alias or percentage, keep the old index for rollback, then delete. Trade-off: double storage and compute during migration. Pitfall: mixing vectors from two models in one index.

2. The right document exists but is not retrieved.

Check in order: was it ingested and parsed correctly, was it chunked badly, is the metadata filter excluding it, is the query poorly phrased, is it in top-100 but ranked low. Fix by cause: reparse, change chunking, fix filters, add query rewriting, add hybrid search or reranking.

3. Recall is high but faithfulness is low.

Retrieval is not the problem. Inspect the prompt, context order and size, conflicting chunks, and model behavior. Fix: stricter grounding prompt, fewer and better chunks, citation validation, abstention, a better model, or an answer verification step.

4. Reranker added 2 seconds.

Reduce candidates from 100 to 30, use a smaller reranker (FlashRank), batch and run on GPU, cache scores, rerank only when top scores are close, or apply it to hard queries only. Check quality loss with the eval set before shipping.

5. System returns outdated answers.

Check ingestion lag, failed update jobs, stale vectors not deleted, and caches serving old answers. Fix: change detection by hash, delete by doc_id on update, include index version in cache keys, alert on ingestion lag.

6. Hybrid retrieval is worse than dense alone.

Likely poor BM25 tokenization, bad fusion weights, noisy sparse results, or an unsuitable eval set. Evaluate each retriever alone, tune weights or RRF constant, fix tokenization, and compare per query type.

7. A user sees another department's document.

Treat as a security incident: contain, find where authorization is missing (filter must be in the retrieval query, not after), audit logs to find exposure, fix, add automated permission tests, report per policy. Cache keys must include permissions.

8. Need to cut token cost by 50%.

Measure where tokens go first. Then: fewer chunks via reranking, compress context, trim prompts, cache repeated answers, route easy queries to a cheaper model, and set output limits. Verify faithfulness on the eval set after each change.

S6Core questions with answers you can speak

RAG or fine-tuning? RAG for fresh, private, citeable knowledge; fine-tuning for style, format or behavior. They combine well. Fine-tuning does not reliably add new facts and cannot enforce per-user permissions.

RAG or long context? Long context is simple for small corpora but costs more per query, hurts latency and loses accuracy in the middle. RAG scales to large, changing data with access control.

Why can bigger chunks hurt retrieval? Multiple topics blur the embedding, so matches become vague and irrelevant text fills the prompt.

Why can increasing top-K reduce quality? More noise and conflicting chunks, higher cost, and the model may miss the right one in the middle.

How do you evaluate without checking every answer? A golden set with expected sources, retrieval metrics, LLM judge metrics calibrated against human samples, production feedback and monitoring for drift.

How do you reduce hallucination? Better retrieval, grounded prompts, citations checked against retrieved ids, abstention, answer verification, and low temperature.

Pre-filter or post-filter in vector search? Filter inside the search (pre-filter with payload indexes) so top-K is taken from allowed data; post-filtering can return too few results or leak data.

How do you handle conflicting documents? Use version and date metadata, prefer authoritative sources, show both with citations when unresolved, and tell the user about the conflict.

HNSW vs IVF? HNSW: higher recall and speed, more memory. IVF: lower memory, needs training and tuning, often with quantization at very large scale.

How do you protect against prompt injection? Treat retrieved text as data, delimit it, scan inputs and outputs, limit tool permissions, validate structured output and never let documents trigger privileged actions.

What would you monitor in production? Latency by stage, error rate, empty retrievals, cache hit rate, token cost, faithfulness samples, ingestion lag, user feedback.

What is your approach when a stakeholder says "the bot is wrong"? Reproduce with the trace, classify as parsing, retrieval, ranking or generation failure, fix, add the case to the regression set.

Interview Question Bank by Module

Five questions per module with speakable answers. B is beginner, I is intermediate, A is advanced.

Q1M1 Architecture questions
  • BWhat are the two paths in RAG? Offline indexing (ingest, chunk, embed, store) and online answering (retrieve, rerank, generate).
  • BWhy RAG instead of only an LLM? Fresh and private data, citations, fewer hallucinations, no retraining.
  • ISync vs async? Query path is synchronous for low latency; ingestion is asynchronous through queues so spikes do not hurt users.
  • IStateless vs stateful? Stateless services scale horizontally; keep chat history and cache in Redis or a database.
  • AHow do you design for failure? Timeouts, retries, circuit breakers, fallbacks such as keyword search or cached answers when the vector DB is down, and separate scaling of ingestion and query.
Q2M2 Ingestion questions
  • BHow do you avoid duplicate ingestion? Hash content, skip identical hashes, and use deterministic chunk IDs.
  • BWhy different loaders per format? Formats differ in structure; one generic parser loses tables and layout.
  • IHow do you handle scanned PDFs? Detect pages without a text layer and OCR only those (Docling, Tesseract, PaddleOCR), storing confidence.
  • IHow do you handle corrupted PDFs? try/except, retry, fallback parser (PyMuPDF then Tika), quarantine with the error, alert, and never fail the whole batch.
  • ADesign ingestion for 10M documents. Object storage plus queue, idempotent workers, hash registry, dead-letter queue, backpressure, metrics, and a change feed for incremental updates.
Q3M3 Parsing and cleaning questions
  • BWhy does parsing quality matter? Bad text produces bad chunks and embeddings, and later steps cannot fix it.
  • BHow do you remove headers and footers? Use parser labels, or find lines repeated across pages and strip them.
  • IWrong reading order? Compare extracted blocks with the page image, switch to a layout-aware parser, and handle multi-column ordering.
  • ITables and paragraphs together? Extract the table as Markdown or HTML with its caption and section heading as metadata, keep it as one chunk.
  • A500-page document efficiently? Parallel page batches, OCR only needed pages, per-page hash caching, and reprocess only changed pages.
Q4M4 Chunking questions
  • BWhat is chunk overlap? Shared text between neighbors so boundaries do not cut context; usually 10 to 15 percent.
  • BWhy not index whole documents? The embedding blurs many topics and the prompt fills with irrelevant text.
  • IHow do you choose chunk size? Start at 300 to 500 tokens, test sizes on the golden set using Recall@K and answer quality, and respect the embedding model limit.
  • IWhat is parent-child retrieval? Search small child chunks, return the larger parent for context.
  • ADocuments that change often? Hash per page or chunk, re-chunk only modified sections, deterministic IDs, delete removed chunks, prefer structure-based chunking so edits do not shift every chunk.
Q5M5 Metadata and versioning questions
  • BWhich metadata per chunk? doc_id, chunk_id, page, source, version, timestamp, hash, permissions.
  • BWhy a content hash? Cheap change and duplicate detection.
  • IDetect new, unchanged, modified, deleted? Compare current hashes with the registry; ids missing from the source are deleted.
  • IPrevent stale embeddings? On update delete by doc_id and upsert new chunks, monitor ingestion lag, and invalidate caches.
  • ADocument-level permissions? Store ACL groups in payload, filter inside the search, sync from the identity provider, and test with automated permission tests.
Q6M6 Embeddings questions
  • BWhat is an embedding? A vector that captures meaning, so similar text is close together.
  • BCosine vs dot product? Cosine ignores magnitude; on normalized vectors they give the same ranking.
  • IChanging the embedding model? Everything must be re-embedded; use a new collection, backfill, and switch by alias.
  • IAPI rate limits? Batching, exponential backoff, concurrency limits, queues and caching by content hash.
  • AWhy do similar sentences score low? Domain or language mismatch, missing model prefixes (E5), negation, unnormalized vectors, or a weak model; verify on an eval set.
Q7M7 Vector database questions
  • BWhat is ANN and why use it? Approximate search trades a little recall for much more speed than exact search.
  • BHNSW vs Flat? Flat is exact but slow; HNSW is fast with high recall but uses more memory.
  • IIsolate customer data? Collection per tenant for strict isolation, or one collection with an indexed tenant_id filter for scale.
  • IReindex without downtime? Build a new collection, backfill, validate, switch the alias, keep the old one for rollback.
  • A100M vectors and slow search? Check ef settings, payload indexes, quantization, sharding and replicas, memory vs disk, filter selectivity, and trace the latency.
Q8M8 Retrieval questions
  • BDense vs BM25? Dense matches meaning; BM25 matches exact words.
  • BWhat is top-K? The number of results returned from retrieval.
  • ICombine BM25 and dense? Run both and merge with RRF or weighted scores, tuned on the eval set.
  • IExact product IDs fail in semantic search? Add BM25 or exact-match filters and use hybrid retrieval.
  • ACorrect document exists but is not returned? Check ingestion and chunking, filters, query phrasing, top-K, embeddings, then add hybrid and reranking; look at the document's rank in top 100.
Q9M9 Reranking questions
  • BBi-encoder vs cross-encoder? Bi-encoder embeds separately (fast); cross-encoder reads query and chunk together (accurate, slower).
  • BWhy rerank? To fix ordering of the top candidates before generation.
  • IHow many candidates? Usually 30 to 100; test candidate recall against latency.
  • IWhen avoid reranking? Tiny corpus, strict latency limits, or already high precision.
  • AReduce reranker latency? Fewer candidates, smaller model, batching on GPU, score caching, and reranking only ambiguous queries.
Q10M10 Context management questions
  • BWhat is context compression? Reducing retrieved text to the relevant parts before the LLM.
  • BLost in the middle? Models use the start and end of the context better, so put the best chunks there.
  • I50 chunks, small window? Rerank, threshold, dedupe, apply a token budget, and expand parents only for the top few.
  • IRemove redundancy? Hash or similarity dedupe, and MMR.
  • ACompress without losing details? Prefer extractive over abstractive, keep numbers and entities, test on the eval set, and fall back to full chunks for critical queries.
Q11M11 Prompting and generation questions
  • BWhat is in a RAG prompt? Instructions, retrieved context, the question, and rules for citations and abstention.
  • BWhy abstention? It prevents invented answers when evidence is missing.
  • IMake the LLM answer only from documents? Strict system prompt, low temperature, structured output with citations, and refusal when no context passes the threshold.
  • IVerifiable citations? Label chunks with ids, require the model to return them, and validate against what was retrieved.
  • AContext is right but answer is wrong? Inspect prompt, chunk order, conflicting chunks, model choice, parsing and temperature; measure faithfulness and add a verification step.
Q12M12 Evaluation questions
  • BWhat is Recall@K? The share of relevant documents found in the top K.
  • BWhat is faithfulness? Whether the answer is supported by the retrieved context.
  • IBuild a golden dataset? Real questions with expected sources and answers, reviewed by experts, including hard cases; extend with synthetic questions.
  • ICompare two pipelines? Same dataset and metrics, paired comparison, plus latency and cost.
  • AGood on 20 questions, bad in production? The set is small and unrepresentative; sample real traffic, include permissions and scale, and feed failures back into the set.
Q13M13 Advanced architecture questions
  • BWhat is CRAG? Retrieval is graded and corrected (query rewrite or web search) when quality is low.
  • BNaive vs advanced RAG? Naive is embed, retrieve, generate; advanced adds rewriting, hybrid search, reranking and compression.
  • IWhen use Graph RAG? Relationship and multi-hop questions where entities connect across documents.
  • IDownside of agentic RAG? Higher latency, cost and unpredictability; needs step limits and guardrails.
  • AHow choose an architecture? Start simple, classify failure types with evaluation, and add the component that fixes that failure.
Q14M14 Caching and performance questions
  • BExact vs semantic cache? Exact needs the same string; semantic matches similar meaning.
  • BWhat is TTL? How long a cache entry stays valid.
  • IInvalidate after a document update? Include the index version in the key or delete keys by doc_id, and use short TTLs.
  • ICache key design? Normalized query, filters, user permissions, and index, prompt and model versions.
  • AScale to 10,000 concurrent users? Async stateless replicas, autoscaling, connection pooling, caching, rate limiting, load tests, and watch LLM provider limits as the usual bottleneck.
Q15M15 Security questions
  • BDirect vs indirect prompt injection? Direct comes from the user; indirect is hidden in retrieved documents.
  • BWhy detect PII? To avoid sending sensitive data to external LLMs and to meet compliance.
  • IPrevent cross-department retrieval? Apply the ACL filter inside the vector query, not after.
  • IMulti-tenant isolation? Collection per tenant or tenant filter, row-level security, separate credentials, and automated tests.
  • AA document contains malicious instructions? Scan at ingestion, quarantine, treat context as data, limit tool permissions, validate outputs and keep audit logs.
Q16M16 Deployment and observability questions
  • BWhy Docker? Same environment from laptop to production.
  • BLiveness vs readiness? Liveness restarts a stuck container; readiness decides whether it receives traffic.
  • ITrace a query across stages? Propagate a trace ID and create spans for retrieve, rerank and generate with Langfuse or OpenTelemetry.
  • ILLM provider rate-limits you? Backoff retries, queue, fallback model, caching, circuit breaker and quota management.
  • AAPI is down, how do you troubleshoot? Check health and recent deploys, logs, resources (OOM), dependencies (DB, vector DB); roll back first, investigate after.
