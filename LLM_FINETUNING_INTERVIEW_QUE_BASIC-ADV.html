01SECTION 1: LLM FINE-TUNING FUNDAMENTALS

🟢 Beginner

Q1. What is fine-tuning of an LLM?

▶ Answer Fine-tuning means continuing to train a pretrained model on a smaller, targeted dataset so its weights adapt to a specific task, domain, style, or output format.

Analogy: pretraining is medical school (broad knowledge); fine-tuning is a residency in cardiology (specialised behaviour on top of what you already know).

┌──────────────────┐      ┌──────────────────────┐      ┌───────────────────┐
│  PRE-TRAINING    │      │    FINE-TUNING       │      │  SPECIALISED LLM  │
│  trillions of    │ ───▶ │  1K – 1M curated     │ ───▶ │  your task, tone, │
│  raw tokens      │      │  examples            │      │  format, policy   │
│  (general skill) │      │  (targeted skill)    │      │                   │
└──────────────────┘      └──────────────────────┘      └───────────────────┘

💡 Memory trick: pretraining teaches the model language and world knowledge; fine-tuning teaches it how to behave.

Q2. What is the difference between pre-training and fine-tuning?

▶ Answer

Aspect Pre-training Fine-tuning
Data Trillions of tokens, mostly unlabeled web/books/code Thousands to millions of curated examples
Objective Next-token prediction on raw text Next-token prediction on demonstrations (SFT) or preference/reward objectives
Compute Thousands of GPUs for weeks/months 1 – 64 GPUs for hours/days (less with LoRA)
Goal General capability Specific behaviour, format, domain
Who does it A handful of labs Almost any team

🎯 Interviewer's intent: do you understand that the loss is the same in SFT (next-token cross-entropy) — what changes is the data and which tokens are scored.

Q5. When should you NOT fine-tune?

▶ Answer

  • Prompting or few-shot already reaches the quality bar — fine-tuning adds cost and maintenance.
  • The knowledge changes frequently (you would retrain forever).
  • You need citations/traceability — fine-tuned weights cannot point to a source.
  • You have no evaluation set — you cannot prove the tuned model is better (or that it did not regress).
  • Fewer than ~100 clean examples and the task is not trivially format-only.
  • Data has unresolved privacy/licensing problems (models can memorise training data).
  • You are on a frontier API model that is already strong at the task and the provider's fine-tuning is unavailable or more expensive than prompting.

Q6. Should you start from a base model or an instruct/chat model?

▶ Answer

Start from Pros Cons
Base Full control; no baked-in chat template or refusal behaviour; best when you have lots of data (10K+) You must teach instruction-following + template + stopping from scratch
Instruct / chat Works with small data (hundreds–few thousand); keeps safety and general ability Must match its chat template exactly; can fight your target style; harder to remove unwanted behaviours

Rule of thumb: small data or narrow tweak → instruct model. Large data, new format, or research/control → base model.

Q7. What is the difference between full fine-tuning and parameter-efficient fine-tuning (PEFT)?

▶ Answer

  • Full fine-tuning updates all weights. Highest capacity, but needs memory for weights + gradients + optimizer states (~16 bytes/param with mixed-precision AdamW) and produces a full-size checkpoint per task.
  • PEFT freezes the base model and trains a tiny set of extra parameters (e.g., LoRA adapters — typically 0.1–2 % of parameters). Memory drops massively, and checkpoints are tens of MB.
Full FT PEFT (LoRA)
Trainable params 100 % ~0.1 – 2 %
GPU memory Very high Low (esp. with QLoRA)
Storage per task Full model (GBs) Adapter (MBs)
Quality ceiling Highest Slightly lower on hard/large-shift tasks
Forgetting More Less

Q8. What is transfer learning and why does it work so well for LLMs?

▶ Answer Transfer learning reuses representations learned on one large task for another. Pretraining forces the model to learn syntax, semantics, reasoning patterns and world knowledge, so fine-tuning only needs to re-route existing capabilities toward the target behaviour rather than learn everything from scratch. That is why 1,000 good examples can change behaviour dramatically while training from scratch would need billions of tokens.

Q9. Describe the end-to-end LLM fine-tuning pipeline.

▶ Answer

 1. DEFINE        task, success metric, failure modes, baseline (prompted model)
      ▼
 2. DATA          collect → clean → dedup → format (chat template) → split
      ▼
 3. CHOOSE        base model + method (SFT / LoRA / QLoRA / DPO) + hardware
      ▼
 4. TRAIN         small pilot run → sweep LR → full run, log loss + evals
      ▼
 5. EVALUATE      task metrics, LLM-judge, human review, regression + safety suite
      ▼
 6. ITERATE       fix data (most gains live here), retrain
      ▼
 7. DEPLOY        merge or hot-swap adapter, serve, canary, monitor
      ▼
 8. FEEDBACK LOOP production logs → new training data → retrain

💡 Rule: in practice ~80 % of the improvement comes from steps 2 and 6 (data), not from hyper-parameter tricks.

Q10. What can fine-tuning reliably teach a model — and what can't it?

▶ Answer Reliable: output format and schema, tone/persona, domain jargon usage, task-specific skills (classification, extraction, routing), tool-calling patterns, refusal/safety policy, style of reasoning.

Unreliable: injecting large amounts of new factual knowledge. Research (e.g., Gekhman et al., 2024) found that models learn new facts from SFT slowly, and that examples introducing unknown facts can increase hallucination on other questions. For knowledge, prefer RAG or continued pre-training on large corpora.

🎯 Interviewer's intent: separating "behaviour" from "knowledge" shows real-world judgement.

Q11. What is the "Superficial Alignment Hypothesis" (LIMA)?

▶ Answer The LIMA paper ("Less Is More for Alignment") fine-tuned a 65B LLaMA on just ~1,000 carefully curated prompt/response pairs and got competitive chat behaviour. The hypothesis: nearly all knowledge and capability come from pretraining; alignment mostly teaches the style and format of a helpful response.

Implication: for SFT, data quality and diversity beat quantity. It is also why small, clean datasets often work — and why SFT alone will not add deep new capabilities.

02SECTION 2: TRAINING MECHANICS YOU MUST KNOW

🟢 Beginner

Q12. What loss function is used to fine-tune a causal LLM?

▶ Answer Token-level cross-entropy for next-token prediction:

L = − (1/N) Σ_t  log P_θ( x_t | x_<t )         (only over tokens included in the loss)

Perplexity = exp(L) — the average "branching factor" the model is uncertain about. Lower is better, but perplexities are only comparable across models that share the same tokenizer and data.

Q13. What is loss masking (train on completions only) and why does it matter?

▶ Answer In SFT each example is prompt + response. If you compute loss on the prompt too, the model wastes capacity learning to predict user text and can drift toward echoing instructions. Standard practice: set labels for prompt tokens to -100 (ignored by PyTorch cross-entropy) so only assistant tokens are scored.

tokens : <user> Summarise this… </user> <assistant> The report says… <eos>
labels :  -100   -100  -100  …   -100     -100      The report says… <eos>
                                                     └── loss computed here only ──┘

⚠️ Common mistake: masking the EOS token (e.g., by setting pad_token = eos_token and masking all pad positions) — the model then never learns to stop.

Q14. What is a chat template and why can a mismatch silently ruin results?

▶ Answer A chat template converts a list of messages into the exact token string a model was trained with (role markers, special tokens, system prompt position). Different families differ (ChatML, Llama-3 header tokens, Mistral [INST], Gemma turns…).

If you fine-tune with template A and serve with template B (or forget add_generation_prompt), quality drops with no error message. Always build both training data and inference prompts with tokenizer.apply_chat_template(...).

msgs = [{"role": "system", "content": "You are a helpful assistant."},
        {"role": "user", "content": "Hi"}]
text = tokenizer.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True)

Q15. Explain batch size, gradient accumulation and effective batch size.

▶ Answer

effective_batch = per_device_batch × gradient_accumulation_steps × num_GPUs

Gradient accumulation runs several small forward/backward passes and sums gradients before one optimizer step, giving a large effective batch without the memory of a large physical batch.

Example: per_device=2, grad_accum=16, GPUs=1 → effective batch 32 sequences. Measure it also in tokens per step (batch × sequence length) since sequence lengths vary.

Q16. How many epochs should you fine-tune for?

▶ Answer

  • SFT: typically 1–3 epochs. Large datasets (>50K): often 1–2. Small curated sets (~1K): more epochs can be fine (LIMA used 15) but watch for overfitting.
  • DPO / preference tuning: usually 1 epoch.
  • Decide with validation task metrics, not train loss. Validation loss often starts rising in epoch 2 while task quality is still improving, so trust the eval that reflects the real task.

Q17. Compare fp32, fp16 and bf16 for fine-tuning.

▶ Answer

Format Bits Exponent / mantissa Notes
fp32 32 8 / 23 Safe but 2× memory of 16-bit
fp16 16 5 / 10 Small range → needs loss scaling to avoid underflow/overflow
bf16 16 8 / 7 Same range as fp32, lower precision; no loss scaling; default on Ampere+ GPUs

Mixed precision keeps fp32 master weights and optimizer states while doing forward/backward in 16-bit. If your GPU supports it (A100/H100/RTX 30/40), use bf16.

Q18. How much memory does the AdamW optimizer need, and how do you reduce it?

▶ Answer AdamW stores two fp32 states per parameter (first and second moments). In mixed-precision full FT the per-parameter budget is:

fp16/bf16 weights   2 B
fp16/bf16 gradients 2 B
fp32 master weights 4 B
Adam m (fp32)       4 B
Adam v (fp32)       4 B
──────────────────────
                   16 B / parameter   (+ activations)

Reductions: 8-bit Adam (bitsandbytes), paged optimizers, Adafactor, optimizer-state sharding (ZeRO/FSDP), GaLore (low-rank gradient projection), or simply PEFT (optimizer states only for the adapter weights).

Q19. What are gradient checkpointing and FlashAttention, and why are they used in fine-tuning?

▶ Answer

  • Gradient checkpointing stores only some activations and recomputes the rest during backward. Cuts activation memory dramatically for ~20–30 % extra compute.
  • FlashAttention computes exact attention in tiles using fast on-chip SRAM, avoiding materialising the N×N attention matrix: memory becomes O(N) instead of O(N²) and it is faster.

Together they allow long sequences and bigger batches on the same GPU.

Q20. Explain learning-rate warmup and decay schedules.

▶ Answer

  • Warmup (linear ramp over first ~3–10 % of steps) avoids unstable big updates while Adam's moment estimates are still noisy.
  • Decay (cosine or linear to ~0–10 % of peak) lets the model settle into a good minimum.
  • Typical: lr_scheduler_type="cosine", warmup_ratio=0.03.

Constant LR with short warmup is also common for LoRA on small data. Too high a peak LR is the #1 cause of loss spikes and forgetting.

Q22. How much data do you need for fine-tuning?

▶ Answer There is no universal number — it depends on task difficulty and distribution shift:

Goal Rough scale
Output format / style / persona 100 – 1,000 high-quality examples
Narrow task (classification, extraction, routing) 1K – 10K
Domain-specific assistant 10K – 100K
Broad general instruction tuning 100K – 1M+
Continued pre-training Hundreds of millions to billions of tokens

Best practice: start small (a few hundred), evaluate, plot a learning curve (train on 25 %, 50 %, 100 %). If the curve is flat, more data of the same kind will not help — improve quality or coverage instead.

Q23. Quality vs quantity — which matters more?

▶ Answer Quality and diversity. LIMA (1K curated examples) and later work on data selection showed small clean sets can beat much larger noisy ones. Noisy or inconsistent responses teach the model the noise: the model learns to imitate whatever is in the targets, including mistakes, verbosity, and hallucinated facts.

Quality checklist: correct, consistent style, complete answers, follows the system prompt, diverse prompts, realistic distribution (matches production traffic), no contradictions between examples.

Q24. Walk through a data-cleaning pipeline for fine-tuning data.

▶ Answer

raw data
  ▼  1. Schema/format validation (drop malformed rows, empty targets)
  ▼  2. Language / length filters (too short, too long, truncated answers)
  ▼  3. PII & secrets scrubbing (emails, phone, keys) + licence check
  ▼  4. Deduplication   exact hash → near-dup (MinHash-LSH) → semantic (embeddings)
  ▼  5. Quality scoring  heuristics, reward model / LLM-judge, perplexity filters
  ▼  6. Decontamination  remove overlap with eval/benchmark sets (n-gram match)
  ▼  7. Balance & mix    cap over-represented tasks, add general "replay" data
  ▼  8. Split            train / val / test (group-aware!)

⚠️ Common mistake: splitting after augmentation or by random row when rows come from the same conversation/document → near-duplicates leak from train into validation and inflate scores.

Q25. How do you deduplicate a training set, and why does it matter?

▶ Answer Duplicates make the model over-weight repeated content, increase memorisation (and privacy risk), and contaminate validation splits.

  • Exact: hash the normalised text.
  • Near-duplicate: MinHash + LSH on shingles (Jaccard similarity).
  • Semantic: embed prompts, cluster, keep one or a few per cluster (also improves diversity).

Q26. How do you build synthetic training data with a stronger model?

▶ Answer Common recipes: - Self-Instruct / Evol-Instruct: seed tasks → LLM generates new instructions → evolve them to be harder/more varied. - Distillation: teacher model answers your prompts; student trains on teacher outputs (black-box distillation). - Rejection sampling: sample N answers, keep those that pass a verifier (unit tests, exact-match, judge score). - Back-translation: generate the instruction for existing high-quality text. - Persona / scenario prompting to increase diversity.

Guardrails: human-review a sample, use a judge + programmatic checks, deduplicate, and check the teacher's licence/ToS (some forbid training competing models). Avoid training repeatedly on your own outputs — that risks model collapse (loss of diversity).

Q27. What is data contamination/decontamination?

▶ Answer Contamination = benchmark or evaluation items appear in the training data, so scores measure memorisation. Detect by n-gram overlap (commonly 8–13-gram) or embedding similarity between train and eval sets, then remove the matches. Do it for your private test set too — especially when using synthetic or scraped data.

Q28. How do you split data for train / validation / test?

▶ Answer

  • Typically 90/5/5 or 80/10/10 (for small sets keep at least ~100–200 test items).
  • Group-aware split: keep all rows from the same user, document, conversation or template together.
  • Stratify by task/intent so rare categories appear in every split.
  • Freeze the test set early; never tune on it. Keep a separate small "golden" set curated by domain experts.

Q29. What is sequence packing and what are its risks?

▶ Answer Packing concatenates several short examples into one fixed-length sequence (e.g., 4096 tokens) to avoid wasting compute on padding — often 2–5× throughput on short data.

Risks: without proper attention masking / position-id reset (e.g., FlashAttention varlen), examples can attend to each other (cross-contamination). Also make sure EOS separators are present and loss masking still applies to each example correctly.

Q30. How do you mix domain data with general data?

▶ Answer To reduce forgetting, blend in general instruction data (replay/rehearsal): commonly 10–30 % general data with domain data, tuned by watching regression on general benchmarks. Domain data can be up-sampled if small. For continued pre-training, use mixtures like 70–90 % domain + 10–30 % general text.

Q31. How do you handle class imbalance or skewed task distribution in SFT data?

▶ Answer Cap dominant tasks, up-sample rare-but-important ones (or generate more), and stratify evaluation per task. Report per-slice metrics — an average score can hide that a rare but critical intent regressed.

Q32. What PII, safety and legal issues arise in fine-tuning data?

▶ Answer

  • PII/secrets can be memorised and regurgitated — scrub with regex/NER and audit outputs with extraction probes.
  • Licences: check dataset licence (e.g., non-commercial), model licence (Llama-family community licence, Apache-2.0 Qwen/Mistral variants, etc.), and provider ToS on using API outputs.
  • Consent/retention/GDPR: user logs may need consent and deletion paths; retraining is how you "delete" something from weights.
  • Safety data: even benign fine-tuning can erode safety behaviour (Qi et al., 2023), so include refusal/safety examples and run a safety eval before release.

Q33. Explain data selection methods such as IFD, DEITA and coreset/diversity selection.

▶ Answer Rather than using everything, score examples and keep the most useful: - IFD (Instruction-Following Difficulty): how much the instruction helps the model predict the response (compare loss with vs without the instruction); moderately hard examples give the most learning. - DEITA: combine complexity score, quality score and diversity (embedding-space distance) to pick a small, high-value subset. - Diversity / coreset selection: cluster embeddings and sample across clusters (k-center greedy).

🎯 Interviewer's intent: you know that "less but better data" can be systematically selected, not just eyeballed.

Q34. What is rejection sampling fine-tuning (RFT / STaR) and when is it useful?

▶ Answer Generate multiple candidate solutions per prompt from the current model, keep only those that pass a verifier (correct final answer, passing unit tests), and fine-tune on the survivors. Repeat. It bootstraps reasoning/coding skill without human labels and is a simple precursor to RL with verifiable rewards.

Q35. How do you create multi-turn and tool-calling training data?

▶ Answer

  • Multi-turn: include full conversations; compute loss on every assistant turn (or only the last, depending on goal), keep the system prompt consistent.
  • Tool calling: the assistant message contains a structured call (name + JSON args); a tool role message holds the result; then the assistant answers. Train (compute loss) on assistant tool-call and final-answer tokens but mask tool outputs, since the model should not learn to predict tool results.
  • Include negative examples: when not to call a tool, invalid-argument recovery, and multi-call sequences.

04SECTION 4: FULL FINE-TUNING, MEMORY MATH & DISTRIBUTED TRAINING

🔴 Advanced

Q36. Estimate the GPU memory needed to fully fine-tune a 7B model.

▶ Answer

weights (bf16)            7B × 2 B  =  14 GB
gradients (bf16)          7B × 2 B  =  14 GB
optimizer: fp32 master    7B × 4 B  =  28 GB
           Adam m + v     7B × 8 B  =  56 GB
────────────────────────────────────────────
subtotal                   ≈ 112 GB   (16 B/param)
+ activations (depends on batch × seq_len; reduced by checkpointing)

So full FT of a 7B model does not fit on one 80 GB GPU without tricks — use ZeRO/FSDP sharding, offloading, 8-bit optimizers, or PEFT.

💡 Shortcut: full FT ≈ 16 × params (bytes), inference in fp16 ≈ 2 × params, QLoRA ≈ ~0.5–0.7 × params + adapters + activations.

Q37. Explain DDP, ZeRO stages and FSDP.

▶ Answer

Strategy What is sharded across GPUs Memory per GPU
DDP Nothing — full model replicated; only data is split, gradients all-reduced Highest
ZeRO-1 Optimizer states ↓
ZeRO-2 + Gradients ↓↓
ZeRO-3 / FSDP (FULL_SHARD) + Parameters (gathered on demand per layer) ↓↓↓
ZeRO-Offload / Infinity Moves states to CPU RAM / NVMe Lowest GPU, slower

Higher stages save memory but add communication. FSDP (PyTorch-native) is roughly ZeRO-3; DeepSpeed provides ZeRO 1/2/3 + offload.

Q38. What are tensor, pipeline and sequence parallelism, and when do you need them for fine-tuning?

▶ Answer

  • Tensor parallel: split individual matrices across GPUs (needs fast NVLink).
  • Pipeline parallel: split layers into stages; micro-batches flow through.
  • Sequence/context parallel: split the sequence dimension for very long contexts.

For most fine-tuning (≤70B) FSDP/ZeRO-3 + LoRA/QLoRA is enough. 3D parallelism (data + tensor + pipeline) is mainly for pre-training or very large models.

Q39. How do you fine-tune a large model on limited GPU memory? List the levers.

▶ Answer

  1. Use PEFT (LoRA) instead of full FT.
  2. Quantise the frozen base (QLoRA, 4-bit).
  3. Gradient checkpointing + FlashAttention.
  4. Smaller micro-batch + gradient accumulation.
  5. 8-bit / paged optimizers.
  6. Shorter max sequence length, packing to avoid padding waste.
  7. ZeRO/FSDP sharding, CPU offload.
  8. Liger-/Unsloth-style fused kernels, chunked cross-entropy (large vocab logits are a hidden memory hog).

Q40. How do you estimate training time and cost?

▶ Answer For full training, FLOPs ≈ 6 × N (params) × D (tokens); with LoRA, backward skips weight-gradients of frozen weights so compute is roughly ~4 × N × D; gradient checkpointing adds ~⅓ more.

Example: 7B model, 50M tokens, full FT
FLOPs  = 6 × 7e9 × 5e7           = 2.1e18
A100 bf16 peak 312 TFLOPs, ~40 % MFU ≈ 125 TFLOPs effective
time   = 2.1e18 / 1.25e14        ≈ 1.7e4 s ≈ 4.7 GPU-hours (per GPU-equivalent)

Then multiply by GPU-hour price and add 2–3× for experiments, sweeps and failed runs.

Q41. What is MFU (Model FLOPs Utilisation) and why do you track it?

▶ Answer MFU = achieved model FLOPs / hardware peak FLOPs. Well-tuned training reaches ~35–55 % on modern GPUs. Low MFU signals bottlenecks: data-loader stalls, tiny batches, padding waste, communication overhead, or missing fused kernels/FlashAttention. It is the quickest way to tell "GPU is idle" from "model is just expensive".

Q42. What does gradient clipping do and what value is typical?

▶ Answer It rescales gradients when their global norm exceeds a threshold (max_grad_norm, typically 1.0), preventing rare huge gradients from wrecking the weights. Logging grad-norm is a top debugging signal: sudden spikes precede loss spikes and NaNs.

Q43. How do you make fine-tuning runs reproducible?

▶ Answer Fix seeds (Python/NumPy/PyTorch, data-loader shuffling), pin library versions and CUDA, log the full config, dataset hash/version and git commit, save checkpoints + optimizer state. Note that bit-exact reproducibility across different GPU counts or non-deterministic kernels is not guaranteed — track metric variance across 2–3 seeds before claiming an improvement.

05SECTION 5: PARAMETER-EFFICIENT FINE-TUNING (PEFT) & LORA

🟡 Intermediate

Q44. What is PEFT and which methods exist?

▶ Answer PEFT trains a small number of parameters while freezing the pretrained model.

Q45. Explain LoRA and its math.

▶ Answer Instead of updating a big weight matrix W₀ ∈ ℝ^(d×k) directly, LoRA learns a low-rank update ΔW = B·A with B ∈ ℝ^(d×r), A ∈ ℝ^(r×k) and r ≪ min(d,k):

h = W₀ x + (α / r) · B A x

           ┌──────────── W₀ (frozen, d×k) ───────────┐
   x ─────▶│                                          ├──(+)──▶ h
   │       └──────────────────────────────────────────┘   ▲
   │       ┌── A (r×k) ──▶ r-dim ──▶ B (d×r) ──▶ ×(α/r) ──┘
   └──────▶│   trainable      bottleneck   trainable
  • Init: A random (Kaiming/Gaussian), B = 0 → ΔW = 0 at the start, so training begins exactly at the base model.
  • Trainable parameters per adapted matrix: r·(d + k) instead of d·k.
  • Why it works: weight updates during adaptation have low "intrinsic rank" (Aghajanyan et al.; Hu et al.).
  • After training: W = W₀ + (α/r)·BA → merge → no inference overhead.

Q47. What do rank (r) and alpha (α) control, and how do you pick them?

▶ Answer

  • r = capacity of the update. Typical 8–64; use higher (64–256) for complex tasks, new domains or code/math with large data.
  • α with scaling α/r sets the magnitude of the update — behaves like a learning-rate multiplier for the adapter. Common choices: α = r or α = 2r.
  • Changing r while keeping α fixed changes the effective scale, so tune them together (or use rsLoRA, which scales by α/√r so higher ranks stay stable).

Starting point: r=16, α=32, dropout=0.05, all linear layers, LR ~2e-4. Sweep LR first, r second. The QLoRA paper found the choice of target layers mattered more than rank.

Q48. Which modules should LoRA target?

▶ Answer The original paper adapted only attention q_proj/v_proj. Later evidence (QLoRA paper; subsequent analyses) shows adapting all linear layers — attention (q,k,v,o) and MLP (gate, up, down) — is needed to match full-FT quality. In PEFT: target_modules="all-linear". Do not adapt embeddings/lm_head unless you added tokens (then use modules_to_save).

Q49. LoRA vs full fine-tuning — what does the research say?

▶ Answer "LoRA Learns Less and Forgets Less" (Biderman et al., 2024): on hard domains like code and math with large datasets, full FT learns more; LoRA is more conservative and preserves base-model abilities better (acts as a regulariser). With all layers targeted and small-to-medium datasets, LoRA typically matches full FT. LoRA usually needs a ~10× higher LR than full FT.

Choose When
LoRA Limited GPUs, many task-specific variants, want low forgetting, data ≤ ~100K examples
Full FT Big distribution shift, very large datasets, maximum quality, plenty of compute

Q50. What is LoRA merging, and when should you merge vs keep the adapter separate?

▶ Answer Merge (W ← W₀ + (α/r)BA): single standard checkpoint, zero latency overhead, works in any inference engine. Keep separate: hot-swap many task/tenant adapters on one base model (vLLM, LoRAX, S-LoRA), A/B test versions, cheap storage, easy rollback.

⚠️ Merge into a bf16/fp16 base, not into a 4-bit-quantised one — merging into quantised weights loses precision.

Q51. Name LoRA variants: DoRA, rsLoRA, LoRA+, AdaLoRA, LoftQ, PiSSA.

▶ Answer

Variant Idea
DoRA Split weight into magnitude and direction; apply LoRA to direction, train magnitude separately → closer to full-FT behaviour
rsLoRA Scale by α/√r (instead of α/r) so larger ranks learn stably
LoRA+ Use a higher learning rate for B than for A → faster, better convergence
AdaLoRA Allocate rank adaptively per layer via SVD-style importance
LoftQ / QLoRA-init Initialise adapters to compensate quantisation error

Q52. How do prompt tuning, prefix tuning and adapters differ from LoRA?

▶ Answer

  • Prompt tuning: learns k "virtual token" embeddings at the input; extremely few params, but weaker on small models and reduces usable context.
  • Prefix / P-tuning v2: learns virtual K/V at every layer; stronger than prompt tuning.
  • Adapters: insert trainable bottleneck layers in series → extra latency that cannot be merged away.
  • LoRA: adds a parallel low-rank path that merges into W → no latency; usually the best quality/efficiency trade-off.

Q53. How do you serve many LoRA adapters efficiently?

▶ Answer Keep one copy of the base model in GPU memory and load small adapters on demand; batch requests for different adapters in the same forward pass using specialised kernels (Punica/S-LoRA; supported in vLLM enable_lora, LoRAX, TensorRT-LLM). Cache hot adapters, evict cold ones. This turns "one model per customer" from GPU-prohibitive into cheap multi-tenancy.

Q54. Can you combine or interpolate multiple LoRA adapters?

▶ Answer Yes — weighted sum of adapters (ΔW = Σ wᵢ BᵢAᵢ) or LoRA merging via TIES/DARE-style methods. Works best when adapters were trained on the same base and their tasks don't conflict; otherwise you get interference. Always re-evaluate the merged result.

Q55. Why is B initialised to zero and A random (not both random or both zero)?

▶ Answer

  • Both zero → gradients to both are zero (product rule) → never learns.
  • Both random → ΔW ≠ 0 at step 0 → you disturb the pretrained model before any learning.
  • B = 0, A random → ΔW = 0 at start (safe), and gradient w.r.t. B is non-zero because A is non-zero, so learning starts immediately.

Q56. What are the limitations of LoRA?

▶ Answer

  • Capacity-limited on very large datasets or big domain shifts.
  • Sensitive to which layers are targeted and to LR/α.
  • Cannot easily add new knowledge or change the tokenizer/embeddings without modules_to_save.
  • Multiple adapters can interfere when merged.
  • Compute is only ~30 % lower than full FT (you still backprop through the frozen weights); the big saving is memory and storage, not FLOPs.

06SECTION 6: QUANTIZATION & QLORA

🔴 Advanced

Q57. What is quantization and how does it help fine-tuning and inference?

▶ Answer Quantization stores weights (and sometimes activations) in lower precision (8-, 4-bit) instead of 16-bit. A 7B model shrinks from ~14 GB (bf16) to ~3.5–4 GB (4-bit), letting you fine-tune or serve on a single consumer GPU.

  • PTQ (post-training quantisation): quantise a finished model (GPTQ, AWQ, GGUF k-quants, bitsandbytes).
  • QAT (quantisation-aware training): simulate quantisation during training for better low-bit accuracy.

Q58. Explain QLoRA — its three innovations.

▶ Answer QLoRA (Dettmers et al., 2023) fine-tunes a frozen 4-bit base model with 16-bit LoRA adapters:

 4-bit NF4 base weights (frozen)  ──dequantise on the fly to bf16──▶ matmul
                                                                       │
 LoRA adapters (bf16, trainable) ────────────────────────────────────(+)──▶ output
 gradients flow *through* the frozen 4-bit weights into the adapters only
  1. NF4 (4-bit NormalFloat): a data type whose quantisation levels are optimal for normally distributed weights.
  2. Double quantisation: quantise the quantisation constants themselves (saves ~0.37 bit/param).
  3. Paged optimizers: use unified memory to page optimizer states to CPU during memory spikes (avoids OOM on long sequences).

Result: fine-tune a 65B model on a single 48 GB GPU with quality close to 16-bit LoRA.

Q59. How does NF4 differ from plain INT4 or FP4?

▶ Answer INT4 uses evenly spaced levels; pretrained weights are roughly normally distributed (most values near zero). NF4 places levels at the quantiles of a normal distribution, so each level represents equal probability mass — less error for the same 4 bits. Weights are quantised block-wise (e.g., 64 values per block) with a per-block scale.

Q60. What is the accuracy trade-off of QLoRA vs LoRA?

▶ Answer Usually small — the QLoRA paper reports parity with 16-bit fine-tuning on their benchmarks — but quantisation noise can matter on delicate tasks (math, code, long-context, small models). Training is also ~20–40 % slower due to dequantisation. Validate on your task; if there is a gap, try 8-bit or bf16 LoRA.

Q61. Compare GPTQ, AWQ, GGUF and bitsandbytes.

▶ Answer

Q62. How do you export a QLoRA-trained model for deployment?

▶ Answer

  1. Reload the base model in bf16/fp16 (not 4-bit).
  2. Load the adapter with PEFT and merge_and_unload().
  3. Save the merged model and tokenizer.
  4. Optionally quantise the merged model with AWQ/GPTQ/GGUF for serving.

Merging directly into the 4-bit weights adds rounding error; the merged model may differ slightly from what you evaluated, so re-run your eval on the final artifact.

Q63. What is FP8 training/fine-tuning and when is it worth it?

▶ Answer FP8 (E4M3/E5M2) halves memory and roughly doubles matmul throughput on H100/H200/Blackwell GPUs, using per-tensor scaling to control range. It is worthwhile for large-scale full fine-tuning where throughput matters; it needs careful scaling and kernel support (Transformer Engine), so for small LoRA jobs the complexity rarely pays off.

Q64. Why must quantised base weights stay frozen in QLoRA?

▶ Answer 4-bit integers/codebook values are not differentiable parameters you can nudge by small gradient steps. Freezing them and learning higher-precision LoRA deltas keeps the update precise, while the frozen quantised weights simply provide the (slightly noisy) base function.

07SECTION 7: SUPERVISED FINE-TUNING (SFT) & INSTRUCTION TUNING

🟡 Intermediate

Q65. What is SFT and how does it differ from instruction tuning?

▶ Answer SFT = supervised training on (input → desired output) demonstrations with next-token loss. Instruction tuning is SFT on a broad, diverse mixture of tasks phrased as instructions (FLAN, T0, Alpaca, OpenHermes, Tulu…) so the model generalises to unseen instructions. Task-specific SFT (e.g., invoice extraction) is narrower and optimises one behaviour.

Base LM ──SFT/instruction tuning──▶ Instruct model ──preference tuning (RLHF/DPO)──▶ Aligned chat model
(predicts text)   (follows format)       (helpful)            (preferred, safer answers)

Q66. Why is SFT usually done before preference tuning (DPO/RLHF)?

▶ Answer Preference methods refine a model that can already produce reasonable candidates: DPO needs a sensible reference policy, and PPO/GRPO need to sample decent outputs to get a learning signal. SFT gives the model the format, template and basic competence; preference tuning then shifts probability mass toward better answers among plausible ones.

Q68. How do you fine-tune for structured output (JSON) reliably?

▶ Answer

  1. Train on many examples whose assistant turn is only the valid JSON (schema-consistent, with edge cases: nulls, missing fields, long inputs).
  2. Validate every training target with a JSON-schema validator.
  3. At inference add constrained decoding (grammar/JSON-schema guided decoding in vLLM, Outlines, XGrammar) — guarantees syntactic validity even if the model slips.
  4. Evaluate with a parse rate and field-level accuracy.

Fine-tuning fixes semantic consistency; constrained decoding fixes syntactic validity. Use both.

Q69. How do you fine-tune a model for function/tool calling?

▶ Answer Format tool schemas in the system/developer message, and train assistant turns that emit the call in the exact format the serving stack parses (e.g., JSON with name + arguments). Include: multiple tools, parallel calls, no-tool-needed cases, missing/ambiguous parameters (ask a clarifying question), error recovery from tool failures. Compute loss on the assistant's tool-call and final-answer tokens, mask the tool output tokens.

Q70. What is multi-task SFT and how do you avoid task interference?

▶ Answer Training on several tasks at once shares skills but tasks can conflict (different styles/formats). Mitigate with: clear task prefixes/system prompts, balanced or temperature-sampled mixing, per-task evals to catch regressions, or separate LoRA adapters per task (then route or merge).

Q71. How do you distill reasoning (chain-of-thought) into a smaller model?

▶ Answer Collect teacher solutions with reasoning traces, filter by correctness (verifier/majority vote), and SFT the student on prompt → reasoning + answer. Distilled small models (e.g., R1-distilled Qwen/Llama variants) gain large reasoning improvements this way. Caveats: student copies the style of reasoning even when it is not faithful; quality of filtering is critical; check teacher licence.

Q72. Should the system prompt be included in training data?

▶ Answer If the deployed system prompt is fixed, training with it teaches the model to rely on it; training without it "bakes in" the behaviour so you can drop the prompt tokens at inference (lower cost/latency) — but the model then cannot be steered by new system prompts as easily. For robust products, train with varied system prompts and include a few examples with none.

08SECTION 8: ALIGNMENT: RLHF, DPO, GRPO & PREFERENCE TUNING

🔴 Advanced

Q73. Explain the RLHF pipeline (InstructGPT).

▶ Answer

Step 1  SFT           human demonstrations ──▶ supervised policy π_SFT
Step 2  Reward model  humans rank K outputs per prompt ──▶ train RM r_φ(x,y)
Step 3  RL (PPO)      maximise  E[ r_φ(x,y) − β · KL(π_θ ‖ π_ref) ]
                      policy generates → RM scores → PPO update
  • RM loss (Bradley–Terry): L = −log σ( r(x, y_w) − r(x, y_l) )
  • KL penalty keeps the policy near the reference so it doesn't drift into gibberish that fools the RM.
  • InstructGPT's headline: a 1.3B RLHF model was preferred over the 175B GPT-3 — alignment can matter more than raw scale.
  • PPO needs 4 models in memory: policy, reference, reward model, value (critic).

Q74. Why use a KL penalty in RLHF?

▶ Answer Without it, the policy exploits weaknesses in the reward model (reward hacking): long, flattering, or weird outputs that score high but are not good. The KL term β·KL(π_θ‖π_ref) anchors the policy to the SFT model, preserving fluency and general capability. Larger β → safer but less improvement; smaller β → more reward, more hacking risk.

Q75. Explain DPO — how does it avoid a separate reward model and RL?

▶ Answer DPO (Rafailov et al., 2023) shows that the KL-regularised RLHF objective has a closed-form optimal policy, so the reward can be written implicitly as β·log(π_θ/π_ref). Plugging that into Bradley–Terry gives a simple classification-style loss on preference pairs:

L_DPO = − E log σ( β · [ log π_θ(y_w|x)/π_ref(y_w|x)  −  log π_θ(y_l|x)/π_ref(y_l|x) ] )

Intuition: increase the relative likelihood of the chosen response and decrease the rejected one, measured against a frozen reference, with β controlling how far you may move (typ. 0.1–0.5).

No reward model, no sampling loop, no critic → 2 forward passes, stable and cheap.

Q76. DPO vs PPO (RLHF) — trade-offs?

▶ Answer

DPO PPO/RLHF
Components Policy + frozen reference Policy, reference, reward model, value model
Data Offline preference pairs Online samples scored by RM
Stability / simplicity High Finicky (many hyper-parameters)
Compute Low High
Exploration None — limited to dataset distribution Explores new outputs
Ceiling Often good; can plateau/over-optimise Typically stronger on hard, verifiable or open-ended goals when well tuned

Practical view: DPO-family is the default for style/quality/safety preferences; online RL (PPO/GRPO) is preferred when you have a reliable reward (math, code, tool success).

Q77. What are common failure modes of DPO?

▶ Answer

  • Likelihood displacement: both chosen and rejected log-probs fall; the model can become less likely to produce either, harming quality.
  • Length exploitation / verbosity if chosen answers are systematically longer.
  • Off-policy mismatch: preference data from other models differs from what your SFT model generates → weak signal. Prefer on-policy pairs (sample from your SFT model, label them).
  • Sensitivity to β and LR (full-FT DPO LR is tiny, ~5e-7; LoRA ~5e-6).
  • Noisy labels: near-identical pairs teach little; filter them.

Fixes: SFT-loss term on chosen (RPO), IPO/SimPO variants, iterative/online DPO, careful data curation.

Q78. Compare IPO, KTO, ORPO and SimPO.

▶ Answer

Method Key difference
IPO Squared-error objective instead of log-sigmoid → resists overfitting when preferences are near-deterministic
KTO Needs only binary good/bad labels (thumbs up/down), based on prospect theory — no pairs required
ORPO Reference-free, single-stage: SFT loss + odds-ratio penalty on rejected responses
SimPO Reference-free: reward = length-normalised average log-prob, plus target margin γ; mitigates length bias

Q79. What is GRPO and why did it become popular for reasoning models?

▶ Answer Group Relative Policy Optimisation (DeepSeekMath / DeepSeek-R1) is a PPO variant without a value network. For each prompt sample a group of G outputs, score each with a reward function, and use the group-normalised reward as the advantage:

A_i = ( r_i − mean(r_1..r_G) ) / std(r_1..r_G)
loss = − E[ clipped_ratio_i · A_i ]  +  β · KL(π_θ ‖ π_ref)

Benefits: no critic (saves memory), simple, works with rule-based verifiable rewards (answer correctness, unit tests, format checks). This is RL with verifiable rewards (RLVR); it drives "aha-moment" longer reasoning behaviours.

Q80. What is RLVR (reinforcement learning with verifiable rewards) and what are its pitfalls?

▶ Answer Reward comes from a programmatic checker (exact-match on math, tests passing, schema validity) instead of a learned RM, so it is hard to fool and cheap. Pitfalls: reward hacking of the checker (e.g., hard-coding test outputs), format-only gaming, sparse rewards on hard prompts (filter prompts to medium difficulty), length blow-up, and it only helps where verification is possible.

Q81. What is RLAIF and Constitutional AI?

▶ Answer RLAIF replaces human preference labels with an AI judge. Constitutional AI (Anthropic): (1) the model critiques and revises its own answers using a written set of principles (supervised stage), then (2) preferences are generated by an AI comparing responses against those principles and used for RL. Benefit: scalable, transparent principles; risk: inherits the judge's biases — validate against humans.

Q82. What is reward hacking / reward over-optimisation and how do you mitigate it?

▶ Answer The policy exploits imperfections in the proxy reward (verbosity, flattery, formatting tricks, sycophancy). Gao et al. showed true quality first rises then falls as you optimise the proxy further.

Mitigations: KL penalty/early stopping, stronger or ensembled reward models, length-controlled rewards, adversarial/fresh prompts, periodic human or held-out judge evaluation, and verifiable rewards where possible.

Q83. How do you collect good preference data?

▶ Answer

  • Sample several responses from the current (SFT) policy — on-policy pairs give the best signal.
  • Have humans (or a strong judge with a rubric) pick the better one; include ties/"both bad".
  • Ensure pairs differ meaningfully; drop near-duplicates.
  • Measure inter-annotator agreement (InstructGPT reported ~73 % between labelers) and audit for biases (length, position, style).
  • Keep a held-out human-labelled set to sanity-check the LLM judge.

Q84. What are sycophancy and length bias in aligned models, and how do they arise?

▶ Answer Human and LLM judges tend to prefer longer, agreeable, confident answers, so preference optimisation amplifies verbosity and sycophancy (agreeing with the user's wrong claims). Mitigate with length-controlled evaluation/rewards, SimPO-style normalisation, training on data where correct disagreement is rewarded, and explicit sycophancy test suites.

Q85. What are process reward models (PRM) vs outcome reward models (ORM)?

▶ Answer

  • ORM: scores only the final answer. Cheap, sparse credit assignment.
  • PRM: scores each reasoning step, giving dense feedback and better search/selection (best-of-N, tree search) but requires step-level labels (expensive, or generated by Monte-Carlo rollouts).

Q86. Best-of-N sampling vs RL — when is each appropriate?

▶ Answer Best-of-N (sample N, pick the highest reward) needs no training but costs N× at inference. RL amortises that cost by training the policy to produce good answers in one shot. Best-of-N is also used offline to create better training data (rejection sampling) before or alongside RL.

Q87. What is iterative / online DPO?

▶ Answer Repeat: (1) sample from the current policy, (2) label pairs with a judge/RM, (3) run DPO, (4) repeat with the new policy. It fixes DPO's off-policy weakness and gets closer to online RL benefits with simpler infrastructure. Watch for reward-model drift and diversity collapse across rounds.

Q88. Describe a modern full post-training recipe (e.g., Tulu-3 style).

▶ Answer

Base model
  ▼ 1. SFT           curated, diverse instruction + reasoning + safety data
  ▼ 2. Preference    on-policy pairs judged by strong LLM → DPO (length-normalised)
  ▼ 3. RLVR          GRPO/PPO with verifiable rewards on math, code, instruction-following
  ▼ 4. Eval + safety benchmark suite, decontamination, red-teaming

Most open recipes follow this SFT → preference → RL order, adjusting the data mixture at each stage.

Q90. How do you tune the learning rate efficiently?

Pick the largest LR that trains smoothly (no spikes) and gives the best validation task metric; then lower slightly for the full run. LR interacts with batch size (roughly, scale LR ~√ or linearly with batch) and with LoRA α.

Q91. How do you read training and validation loss curves?

▶ Answer

Q92. What signs tell you the model is overfitting during fine-tuning?

▶ Answer Validation loss increases while training loss falls; generations become repetitive or copy training phrases verbatim; performance drops on out-of-distribution prompts; general benchmarks regress; near-zero training loss. Remedies: fewer epochs, early stopping / best-checkpoint selection, more diverse data, lower LR or LoRA rank, dropout, weight decay, mixing in general data.

Q93. What is the role of batch size in fine-tuning quality?

▶ Answer Larger batches give lower-variance gradient estimates and allow higher LRs, but fewer update steps per epoch. With small datasets, huge batches mean only a handful of steps (under-training). Typical effective batches of 16–128 work; for tiny data reduce it so you get a few hundred optimizer steps.

Q94. Weight decay, dropout and label smoothing — do they matter for LLM fine-tuning?

▶ Answer Mildly. Weight decay (0–0.1) is standard in AdamW. LoRA dropout (0.05–0.1) helps small datasets. Label smoothing is uncommon (it hurts calibration and generation). The biggest regularisers are fewer epochs, lower LR, and more diverse data.

Q95. How do you pick a checkpoint to ship?

▶ Answer Save periodic checkpoints (every N steps), evaluate each on the task validation set + regression suite, and choose the best by task metric, not necessarily the lowest val loss or the final step. Consider averaging weights of the last few checkpoints (EMA/SWA) for a small robustness gain.

Q96. How much do random seeds matter, and how do you report improvements honestly?

▶ Answer On small datasets, seed variance can be several metric points. Run 2–3 seeds for key comparisons, report mean ± std, and use paired tests or bootstrap confidence intervals. Avoid claiming a win from a single lucky run.

Q97. What is a good hyper-parameter search strategy under a compute budget?

▶ Answer

  1. Fix the data first (largest lever).
  2. Sweep LR (coarse log grid) on a small subset.
  3. Then LoRA rank/α and target modules, epochs.
  4. Only then explore exotic knobs (schedulers, weight decay). Use Optuna/W&B sweeps with early-pruning of bad runs; keep a leaderboard of runs with dataset hash + config.

10SECTION 10: EVALUATING FINE-TUNED MODELS

🔴 Advanced

Q98. How do you evaluate a fine-tuned LLM end-to-end?

▶ Answer

┌── Layer 1  Automatic, task-specific metrics  (exact match, F1, ROUGE, pass@k, JSON parse rate)
├── Layer 2  LLM-as-judge / pairwise win-rate vs baseline on a rubric
├── Layer 3  Human review of a stratified sample (domain experts)
├── Layer 4  Regression suite: general benchmarks + safety + prior-fixed bugs
└── Layer 5  Online: canary / A-B test with business metrics, guardrails, logs

Always compare against two baselines: the base/instruct model with a good prompt, and the previous production model. If the fine-tuned model doesn't beat a well-prompted baseline, it isn't worth shipping.

Q99. What are the limits of perplexity as an evaluation metric?

▶ Answer Perplexity measures how well the model predicts held-out text — useful for continued pre-training and sanity checks, but it does not measure helpfulness, correctness, format adherence or safety, and cannot be compared across different tokenizers. Two models with similar perplexity can differ hugely in instruction following.

Q100. Which benchmarks are commonly used and what do they measure?

Q101. What are the biases of LLM-as-a-judge and how do you reduce them?

▶ Answer

  • Position bias: prefers the first (or second) answer → randomise/swap order and average.
  • Verbosity bias: prefers longer answers → length-controlled win rate, rubrics penalising padding.
  • Self-preference: prefers outputs of its own family → use a different/neutral judge or multiple judges.
  • Style over substance → use reference answers and explicit rubrics.

Calibrate the judge against a small human-labelled set (report agreement), and re-check periodically.

Q102. How do you design a golden evaluation set?

▶ Answer Collect real-distribution prompts, stratify by intent/difficulty/edge cases (including adversarial and out-of-scope), have domain experts write or verify reference answers, freeze it, version it, and keep it out of training (decontaminate). 200–1,000 items is often enough for reliable A/B decisions; add a rolling set for newly observed failures.

Q103. How do you test for statistical significance when comparing two models?

▶ Answer Use paired comparisons on the same prompts: bootstrap confidence intervals of the score difference, McNemar's test for binary correctness, or sign test for win-rates. With small n (<200) differences under ~5 points are often noise. Report per-slice results.

Q104. How do you evaluate capability retention and safety after fine-tuning?

▶ Answer Run a fixed regression suite before and after (MMLU/GSM8K/IFEval subset + your legacy tasks) and a safety suite (refusal on harmful prompts, jailbreak resistance, toxicity, PII leakage probes). Benign fine-tuning can weaken safety (Qi et al., 2023), so safety evaluation is mandatory even for "harmless" datasets.

Q105. How do you evaluate generation tasks without a single right answer (summaries, chat)?

▶ Answer Combine: pairwise LLM-judge with rubric (faithfulness, completeness, tone), reference-based metrics as weak signals (ROUGE/BERTScore), targeted factuality checks (claim-level verification against source), and human review on a sample. Track disagreement between judge and humans.

Q106. How do you A/B test a fine-tuned model in production?

▶ Answer Shadow mode first (log outputs, no user impact), then a canary (1–5 % traffic) with guardrail metrics (error rate, refusal rate, latency, cost, thumbs-down), then a proper randomised A/B on business KPIs. Keep instant rollback (route traffic back to the previous model/adapter).

11SECTION 11: CATASTROPHIC FORGETTING & OVERFITTING

🔴 Advanced

Q107. What is catastrophic forgetting and why does it happen?

▶ Answer Fine-tuning shifts weights to minimise loss on the new data; if those changes overwrite directions important for earlier capabilities (general knowledge, safety, other languages), old skills degrade. Risk grows with high LR, many epochs, narrow data, full-parameter updates and large distribution shift.

Q108. List practical techniques to mitigate catastrophic forgetting.

▶ Answer

  1. Lower LR / fewer epochs; early stopping.
  2. PEFT (LoRA) — smaller, more constrained update ("learns less, forgets less").
  3. Replay / rehearsal: mix general data (10–30 %) into training.
  4. KL/regularise toward the base (as in RLHF) or add an SFT-on-general loss.
  5. Weight interpolation (WiSE-FT): θ = (1−α)·θ_base + α·θ_ft, choose α by eval.
  6. Model merging (task arithmetic/TIES/DARE) of base + fine-tuned.
  7. EWC (elastic weight consolidation): penalise changes to weights with high Fisher information.
  8. Freeze lower layers / embeddings.
  9. Self-distillation / self-generated rehearsal data: let the base model generate the "old-skill" examples.

Q109. Explain Elastic Weight Consolidation (EWC).

▶ Answer EWC adds a quadratic penalty Σ_i (λ/2)·F_i·(θ_i − θ*_i)² where F_i is the diagonal Fisher information estimating how important weight i was for the old task. Important weights are "anchored"; unimportant ones are free to move. Works in theory and small models; for LLMs it is memory-heavy and rarely used compared with LoRA + replay + interpolation.

Q110. How is memorisation different from overfitting, and why does it matter?

▶ Answer Overfitting hurts generalisation; memorisation means the model can reproduce specific training sequences verbatim (privacy/copyright risk) — possible even with good validation loss. Duplicated data and many epochs increase it. Mitigate with deduplication, PII scrubbing, fewer epochs, lower capacity, and extraction-attack testing (prompt with prefixes of training samples).

Q111. Why can fine-tuning on benign data weaken safety alignment?

▶ Answer Safety behaviours are a relatively thin layer on top of the base model; gradient updates on unrelated data can shift the same weights and reduce refusals (Qi et al., 2023 showed even benign fine-tuning degraded safety, and a few adversarial examples could remove it). Mitigate: mix in safety/refusal data, use LoRA with low LR, evaluate safety before release, and gate who can fine-tune via API.

Q112. How do you measure how much a model has forgotten?

▶ Answer Evaluate before/after on a capability probe set: general benchmarks, prior-task golden sets, perplexity on general text (e.g., a held-out web slice), multilingual prompts, and safety prompts. Report relative retention (after/before) per slice so small losses in critical skills are visible.

12SECTION 12: DOMAIN ADAPTATION, CONTINUED PRE-TRAINING & LONG CONTEXT

🔴 Advanced

Q113. What is continued pre-training (CPT) and how is it different from SFT?

▶ Answer CPT continues the unsupervised next-token objective on a large raw domain corpus (legal, medical, code, a new language) to absorb vocabulary, style and facts. SFT then teaches the model to follow instructions in that domain.

Base LLM ─▶ CPT on domain text (1B+ tokens) ─▶ SFT on domain instructions ─▶ (DPO) ─▶ Domain assistant

Use CPT when the domain is far from web text and you have lots of unlabeled text; skip it if the base model already handles the domain well.

Q114. What learning-rate and data-mixing practices apply to CPT?

▶ Answer Use a lower peak LR (e.g., 1e-5–5e-5, re-warmed and decayed), include replay of general data (10–30 %) to limit forgetting, up-sample high-quality sources, deduplicate, and monitor both domain perplexity and general benchmarks. Train on many tokens (hundreds of millions to billions) — small corpora do not justify CPT.

Q115. How do you extend a tokenizer for a new domain or language?

▶ Answer

  1. Train/choose new tokens (from domain corpus) and add them to the tokenizer.
  2. model.resize_token_embeddings(len(tokenizer)).
  3. Initialise new embeddings sensibly (mean of the constituent sub-token embeddings).
  4. Train the embedding and output layers (in LoRA: modules_to_save=["embed_tokens","lm_head"]) plus the model — usually via CPT first.

Benefit: shorter sequences → lower cost and better quality for morphologically rich or low-resource languages. Risk: mismatched tokenizer breaks compatibility with existing adapters and tooling.

Q116. How do you fine-tune for a low-resource language?

▶ Answer Check base-model coverage; if weak: extend tokenizer, do CPT on monolingual text, then SFT on translated + native instruction data (translate with strong MT/LLM, filter for quality), mix in high-resource-language data to keep transfer, and evaluate on native-speaker-reviewed sets, not only translated benchmarks.

Q117. How do you extend an LLM's context window via fine-tuning?

▶ Answer Change the position encoding scaling and then train briefly on long sequences: - Position Interpolation: linearly compress positions into the trained range. - NTK-aware / YaRN: adjust RoPE frequencies non-uniformly for better extrapolation. - Fine-tune (often with LoRA, e.g., LongLoRA's shifted sparse attention) on long documents; keep some short data.

Validate with needle-in-a-haystack and real long-document tasks; long-context accuracy often degrades in the middle of the window.

Q118. Should knowledge be injected via CPT, SFT or RAG?

▶ Answer CPT is the only one that reliably increases parametric knowledge but is costly and can't be updated cheaply. SFT primarily teaches behaviour. RAG gives up-to-date, cited, editable knowledge. Best systems combine them: CPT/SFT for domain fluency and behaviour + RAG for facts, which also lets you fine-tune the generator to use retrieved context faithfully (RAFT-style training with distractor documents).

🔴 Advanced

Q119. What is model merging and which methods should you know?

▶ Answer Merging combines the weights of several models fine-tuned from the same base — no training, no extra inference cost.

Method Idea
Weight averaging / model soups Average checkpoints (often improves robustness)
Task arithmetic Task vector τ = θ_ft − θ_base; add scaled vectors: θ = θ_base + Σ λᵢτᵢ
SLERP Spherical interpolation between two models (preserves weight norm/geometry)
TIES Trim small deltas, elect sign per parameter, merge only agreeing values → reduces interference
DARE Randomly drop a large fraction of delta weights and rescale the rest, then merge

Tools: mergekit. Always re-evaluate — merges can silently break behaviours.

Q120. Explain knowledge distillation for LLMs (white-box vs black-box).

▶ Answer

  • Black-box (sequence-level): teacher only provides text; student does SFT on teacher outputs (Alpaca, R1-distills). Simple; works with APIs.
  • White-box (logit-level): student minimises KL divergence to the teacher's full token distribution (soft labels carry more information than one-hot text). Requires teacher logits and the same/aligned tokenizer.
  • Variants: on-policy distillation (student samples, teacher scores), reverse-KL for mode-seeking.

Use it to compress a large model's narrow skill into a cheap small model. Check ToS/licences.

Q121. How do you fine-tune embedding models and rerankers (e.g., for RAG)?

▶ Answer

Embedding model (bi-encoder)  →  contrastive loss with in-batch negatives
   query ─▶ enc ─▶ q ┐
                     ├─ cosine ─▶ pull (q, d⁺) together, push (q, d⁻) apart
   doc   ─▶ enc ─▶ d ┘
Reranker (cross-encoder)      →  classify/score (query, doc) pairs jointly
  • Data: (query, relevant passage) pairs — from clicks/labels or synthetic queries generated by an LLM from your docs.
  • Use hard negatives (top BM25/dense results that are not relevant).
  • Losses: MultipleNegativesRankingLoss (InfoNCE), triplet loss; Matryoshka loss for truncatable embeddings.
  • Frameworks: sentence-transformers. Re-index all documents after changing the embedder.

This is often the highest-ROI fine-tune in a RAG system — more than tuning the generator.

Q122. What is RAFT (Retrieval-Augmented Fine-Tuning)?

▶ Answer Fine-tune the generator on examples that include the question, the oracle document plus distractor documents, and a chain-of-thought answer that cites the relevant passage. Sometimes the oracle is omitted so the model learns to rely on parametric knowledge or abstain. Result: a model that is robust to noisy retrieval, ignores irrelevant chunks, and quotes evidence.

Q123. How does multimodal (vision-language) fine-tuning work?

▶ Answer LLaVA-style: a vision encoder (e.g., CLIP/SigLIP) → projector → LLM. Stage 1: train only the projector on image-caption pairs (feature alignment). Stage 2: visual instruction tuning — fine-tune projector + LLM (often with LoRA) on image-instruction data. Domain adaptation (charts, medical imaging) usually uses LoRA on the LLM plus optionally the projector; data quality (accurate grounded captions/QA) dominates results.

Q124. What is special about fine-tuning Mixture-of-Experts (MoE) models?

▶ Answer MoE fine-tuning can be unstable: routers may collapse to a few experts or overfit; load-balancing auxiliary loss must be kept; small datasets overfit easily. Practices: lower LR, freeze or lightly train the router, LoRA on attention + selected experts, or expert-specialised fine-tuning that trains only experts relevant to the task. Memory is high (all experts must be loaded) even though compute per token is low.

Q125. What are GaLore and LISA — memory-efficient *full-parameter* training?

▶ Answer

  • GaLore: projects gradients into a low-rank subspace so optimizer states are tiny, while still updating all weights (unlike LoRA which restricts the weight update itself).
  • LISA: randomly unfreezes a few layers each step (layer-wise importance sampling), so only a subset has gradients/optimizer states at a time.

They let you approximate full fine-tuning on consumer-scale memory, useful when LoRA's capacity limits hurt.

Q126. How would you use an LLM for classification — generative prompting, classification head or embeddings?

▶ Answer

Approach Pros Cons
Generative (SFT outputs the label) Simple; can output rationale/JSON Must constrain/parse output; slower
Classification head (AutoModelForSequenceClassification + LoRA) Fast, calibrated probabilities, no parsing Fixed label set; needs retraining for new labels
Embeddings + logistic regression Cheapest; good baseline Lower ceiling

For high-throughput production classification, a small LLM with a classification head (or even a fine-tuned encoder) is often 10–100× cheaper than generation with a large model.

Q127. What is model editing and machine unlearning?

▶ Answer

  • Model editing (ROME, MEMIT) changes specific facts by rank-one updates to MLP weights without full retraining; can degrade neighbours and doesn't scale to many edits.
  • Unlearning tries to remove data/behaviours (gradient ascent, preference-based "refusal" training, representation methods). It is not guaranteed to erase information — the knowledge may be recoverable. For strict deletion requirements retrain without the data.

Q128. Does data ordering or curriculum matter in SFT?

▶ Answer Modestly. Mixing tasks uniformly at random is the safe default. Curricula (easy → hard) or placing high-quality data late ("annealing" on curated data) can give small gains, especially in pre-training/CPT. For SFT, data quality/diversity effects usually dwarf ordering effects; measure with seeds before adopting fancy schedules.

Q129. What scaling behaviours matter for fine-tuning?

▶ Answer Fine-tuning data needs grow with task difficulty but far less than pre-training; larger base models are more sample-efficient (need fewer examples for the same quality). LoRA capacity saturates on very large datasets, while full FT continues to improve. When choosing between "bigger base + light tuning" and "smaller model + heavy tuning", evaluate cost per quality point, including inference cost.

Q136. Implement LoRA from scratch in PyTorch (including merge).

▶ Answer

import math, torch, torch.nn as nn

class LoRALinear(nn.Module):
    def __init__(self, base: nn.Linear, r=8, alpha=16, dropout=0.0):
        super().__init__()
        self.base = base
        for p in self.base.parameters():
            p.requires_grad = False                       # freeze W0
        dev, dt = base.weight.device, base.weight.dtype
        self.scale = alpha / r
        self.A = nn.Parameter(torch.empty(r, base.in_features, device=dev, dtype=dt))
        self.B = nn.Parameter(torch.zeros(base.out_features, r, device=dev, dtype=dt))  # B = 0
        nn.init.kaiming_uniform_(self.A, a=math.sqrt(5))                                # A random
        self.drop = nn.Dropout(dropout)

    def forward(self, x):
        # W0 x + (alpha/r) * B A x
        return self.base(x) + (self.drop(x) @ self.A.T @ self.B.T) * self.scale

    @torch.no_grad()
    def merge(self) -> nn.Linear:
        self.base.weight += (self.B @ self.A) * self.scale   # fold delta into W0
        return self.base

def inject_lora(model, targets=("q_proj", "k_proj", "v_proj", "o_proj"), **kw):
    for p in model.parameters():
        p.requires_grad = False                                # freeze everything first
    for _, parent in list(model.named_modules()):
        for name, child in list(parent.named_children()):
            if isinstance(child, nn.Linear) and name in targets:
                setattr(parent, name, LoRALinear(child, **kw))
    return model

import torch

def encode(example, tok, max_len=2048):
    msgs = example["messages"]                                   # last message = assistant target
    prompt_txt = tok.apply_chat_template(msgs[:-1], tokenize=False, add_generation_prompt=True)
    full_txt = prompt_txt + msgs[-1]["content"] + tok.eos_token   # use the template's end-of-turn token
    p_ids = tok(prompt_txt, add_special_tokens=False)["input_ids"]   # template already has BOS
    f_ids = tok(full_txt, add_special_tokens=False)["input_ids"]
    labels = [-100] * len(p_ids) + f_ids[len(p_ids):]           # loss only on the response (+EOS)
    return {"input_ids": f_ids[:max_len], "labels": labels[:max_len]}

def collate(batch, pad_id):
    L = max(len(b["input_ids"]) for b in batch)
    ids = torch.full((len(batch), L), pad_id, dtype=torch.long)
    lab = torch.full((len(batch), L), -100, dtype=torch.long)   # pads ignored in the loss
    att = torch.zeros((len(batch), L), dtype=torch.long)
    for i, b in enumerate(batch):
        n = len(b["input_ids"])
        ids[i, :n] = torch.tensor(b["input_ids"])
        lab[i, :n] = torch.tensor(b["labels"])
        att[i, :n] = 1
    return {"input_ids": ids, "attention_mask": att, "labels": lab}   # HF shifts labels internally

Q138. Implement the DPO loss from scratch.

▶ Answer

import torch, torch.nn.functional as F

def seq_logp(logits, labels):
    """Sum of token log-probs of the response. logits [B,T,V], labels [B,T] (-100 = ignore)."""
    logits, labels = logits[:, :-1], labels[:, 1:]              # next-token alignment
    mask = labels != -100
    logp = logits.log_softmax(-1).gather(2, labels.clamp(min=0).unsqueeze(-1)).squeeze(-1)
    return (logp * mask).sum(-1)                                # [B]

def dpo_loss(pi_chosen, pi_rejected, ref_chosen, ref_rejected, beta=0.1):
    # all inputs: sequence log-probs [B]; ref_* computed under torch.no_grad()
    logits = beta * ((pi_chosen - ref_chosen) - (pi_rejected - ref_rejected))
    loss = -F.logsigmoid(logits).mean()
    acc = (logits > 0).float().mean()                           # preference accuracy
    return loss, acc

Log-softmax over the full vocab is memory-heavy; production code computes it chunked or with fused kernels. Track acc, reward margins and chosen/rejected log-probs to spot likelihood displacement.

Q143. Write a GPU-memory estimator for fine-tuning.

▶ Answer

def estimate_gb(params_b, method="lora", seq=2048, batch=1, layers=32, hidden=4096,
                lora_frac=0.006, grad_ckpt=True):
    P = params_b * 1e9
    if method == "full":                       # bf16 w + g, fp32 master + Adam m,v  = 16 B/param
        states = 16 * P
    elif method == "lora":                     # frozen bf16 base + trainable adapters (16 B each)
        states = 2 * P + 16 * (lora_frac * P)
    elif method == "qlora":                    # ~4.5 bits base + adapters
        states = 0.56 * P + 16 * (lora_frac * P)
    else:
        raise ValueError(method)
    # rough activation memory per layer: ~34·s·b·h bytes (no ckpt) vs ~2·s·b·h (full recompute)
    act = layers * seq * batch * hidden * (2 if grad_ckpt else 34)
    return (states + act) / 1e9

for m in ("full", "lora", "qlora"):
    print(m, round(estimate_gb(7, m), 1), "GB (7B, seq 2048, batch 1)")

Rough numbers only — real usage adds CUDA context, fragmentation and the large-vocab logits.

Q144. Write a position-debiased pairwise LLM-judge function.

▶ Answer

def pairwise_judge(judge, question, ans_a, ans_b, rubric="correctness, completeness, concision"):
    """judge(prompt:str)->str. Returns 'a', 'b' or 'tie' after swapping positions to cancel position bias."""
    def ask(x, y):
        prompt = (f"Compare the two answers using: {rubric}.\n"
                  f"[Question]\n{question}\n\n[Answer A]\n{x}\n\n[Answer B]\n{y}\n\n"
                  "Reply with exactly one letter: A or B.")
        return judge(prompt).strip().upper()[:1]
    r1 = ask(ans_a, ans_b)          # original order
    r2 = ask(ans_b, ans_a)          # swapped order
    if r1 == "A" and r2 == "B":     # ans_a preferred in both orders
        return "a"
    if r1 == "B" and r2 == "A":     # ans_b preferred in both orders
        return "b"
    return "tie"                    # inconsistent → treat as tie

Aggregate as win/tie/loss with bootstrap confidence intervals over prompts.

▶ Answer

  • Outputs: format-validity rate, refusal rate, length, toxicity/PII detectors, hallucination checks.
  • Quality: sampled LLM-judge + human audits on real traffic; user feedback (thumbs, edits, escalations).

Q148. How do you decide whether fine-tuning pays off financially?

▶ Answer Compare total cost per successful request:

Prompted large model : (prompt_tokens + output_tokens) × price_big × requests
Fine-tuned small     : training_cost/amortised + (short prompt + output) × price_small × requests + ops
Break-even requests  = training_cost / (cost_per_req_prompted − cost_per_req_tuned)

Fine-tuning wins when volume is high, prompts are long (few-shot + instructions you can bake in), the task is narrow, or latency requirements rule out a huge model. Include engineering time, evaluation, retraining and hosting in the tuned side.

Q149. What security risks are specific to fine-tuning?

▶ Answer

  • Data poisoning / backdoors: malicious samples implant trigger→behaviour ("sleeper agents"); vet data sources, scan for outliers, restrict who can contribute.
  • Safety erosion from fine-tuning (even benign data).
  • Training-data extraction / PII leakage: memorised secrets can be extracted; scrub, dedupe, test with extraction probes; consider differential privacy (utility cost).
  • Model theft / adapter leakage: control access to adapters and weights.
  • Supply-chain: verify base-model and library provenance, use safetensors, pin hashes. Prompt-injection risk is not solved by fine-tuning; keep runtime guardrails.

Q150. How do you make model behaviour auditable and compliant?

▶ Answer Maintain a model card (base model, data sources, licences, intended use, limits, eval results), dataset lineage and consent records, reproducible training configs, evaluation reports including safety/bias slices, change logs per version, and human-in-the-loop for high-risk decisions. Align with the regulations relevant to your domain (GDPR/CCPA, sector rules, EU AI Act obligations).

Q151. How often should you retrain, and what triggers it?

▶ Answer Trigger on evidence, not the calendar: measured drift, quality drop on the rolling golden set, new product requirements/policies, new base-model releases that beat you, or accumulation of enough new high-quality labelled data. Many teams do scheduled light retrains (monthly/quarterly adapters) with full re-evaluation gates.

Q152. When a better base model is released, how do you migrate your fine-tune?

▶ Answer Adapters are tied to a specific base — you must retrain on the new base. Keep data, prompts and evals model-agnostic, re-run your golden suite comparing (a) new base + good prompt, (b) new base + retuned adapter, (c) current prod. Often the new base with prompting already matches your old fine-tune, so the migration might be "delete the adapter".

Q153. What latency/throughput optimisations pair well with fine-tuned models?

▶ Answer Merge adapters, quantise (AWQ/FP8), use continuous batching (vLLM), prefix caching for shared system prompts, speculative decoding (a small draft model; fine-tune the draft on your outputs for higher acceptance), shorter prompts thanks to baked-in instructions, and right-sized (smaller) base models.

Q155. After fine-tuning, the model got worse on general tasks. How do you diagnose and fix it?

▶ Answer

  1. Quantify: run the regression suite before/after; identify which skills dropped.
  2. Check hyper-parameters: LR too high, too many epochs, full FT instead of LoRA.
  3. Check data: too narrow/homogeneous, contains errors, template mismatch, template not applied at eval.
  4. Fixes: lower LR/epochs, LoRA with modest rank, mix 10–30 % general data, weight interpolation with the base (WiSE-FT), model merging, freeze embeddings.
  5. Re-evaluate; keep the best trade-off checkpoint.

Q156. JSON validity is 92 % after SFT, but the product needs ≥99.9 %. What do you do?

▶ Answer

  • Add constrained decoding (JSON schema/grammar) → syntactic validity ≈100 %.
  • Inspect failures: truncation (raise max tokens), long inputs, rare fields → add targeted training examples.
  • Ensure every training target validates against the schema; remove sloppy examples.
  • Train more on hard cases (hard-example mining), possibly larger base model.
  • Add retry-with-repair at runtime and monitor parse rate per input slice.

Q157. You have one 24 GB GPU and want to fine-tune an 8B–13B model. What's your plan?

▶ Answer QLoRA (4-bit NF4 + LoRA r=16, all-linear) → 8B needs roughly 6–8 GB for weights + adapters, leaving room for activations. Use gradient checkpointing, FlashAttention, paged_adamw_8bit, micro-batch 1–4 with gradient accumulation to an effective batch of 32, max_length 1024–2048, and packing if data is short. A 13B fits similarly with smaller micro-batches. Consider Unsloth for speed. Validate with a small pilot before the full run.

Q158. You only have 300 labelled examples. What do you do?

▶ Answer

  1. Verify prompting/few-shot + RAG can't already solve it.
  2. Clean and double-check labels — with tiny data, each error matters.
  3. Augment carefully: paraphrases, LLM-generated variants reviewed by humans, rejection sampling with a verifier.
  4. Fine-tune an instruct model with LoRA (low rank, low LR, 2–4 epochs), hold out ~50 for eval, use cross-validation.
  5. Compare against the prompted baseline; if gains are small, stay with prompting and collect more data.

Q159. Users report hallucinated company facts after you fine-tuned on internal documents. Why, and what now?

▶ Answer Fine-tuning taught the style of confident answers but did not reliably store facts, and unknown-fact examples can even encourage hallucination. Fix: move factual knowledge to RAG with citations, fine-tune (RAFT-style) to answer only from retrieved context and abstain when evidence is missing, add "I don't know"/refusal examples, and evaluate faithfulness at the claim level.

Q160. Your DPO-tuned model became very verbose. Explain and fix.

▶ Answer Preference data probably favoured longer answers (annotator/judge length bias), and DPO's implicit reward rewards raising likelihood of the chosen style. Fix: audit length correlation, length-balance pairs or truncate/rewrite chosen answers, use SimPO/length-normalised objective, add a length penalty in RM-based RL, evaluate with length-controlled win rate, lower β/LR.

Q161. A legal/medical assistant needs high accuracy and compliance. What is your approach?

▶ Answer Base model with strong reasoning + RAG over vetted sources with citations; light SFT for format, tone, disclaimers, and abstention behaviour; domain-expert-written golden sets; safety/compliance evals (unauthorised advice, hallucinated citations); human-in-the-loop review for high-risk outputs; audit logging; PII/PHI controls (HIPAA/GDPR); versioned model card. Do not rely on weights for facts.

Q162. Your app sends a 3,000-token instruction prompt on 5M calls/day. How can fine-tuning help?

▶ Answer Bake the instructions into the model by fine-tuning on (short prompt → desired output). Cutting 2,800 prompt tokens/request saves ~14B input tokens/day, dropping cost and time-to-first-token, and lets you use a smaller model. Validate that behaviour matches the long-prompt baseline on a golden set; keep the ability to update policies via short dynamic snippets or retraining.

The strongest systems mix them: RAG for facts, fine-tuning for behaviour, prompts for per-request instructions.

Q164. SFT vs DPO vs PPO/GRPO — which do you use when?

▶ Answer

  • SFT: you have gold demonstrations; teaches format/skills. Always the first step.
  • DPO family: you have preference pairs (or can generate/judge them); improving quality, tone, safety with low complexity.
  • PPO/GRPO (online RL): you have a reliable reward (verifiable or good RM) and want to push beyond demonstrations (math, code, agents/tool success).

Q165. LoRA vs QLoRA vs full fine-tuning — how do you choose?

▶ Answer

Do you have ≥ 8× the memory full FT needs and a large dataset / big domain shift?  → Full FT
Else, do you have enough VRAM for the bf16 base + activations?                     → LoRA (bf16)
Else (memory-bound)                                                               → QLoRA

QLoRA trades ~20–40 % speed and a small precision risk for a huge memory cut; LoRA is faster; full FT gives max capacity.

Q166. A small fine-tuned model versus a large prompted model — which wins?

▶ Answer For narrow, well-defined tasks with enough data, a fine-tuned 7–8B model often matches or beats a much larger prompted model at a fraction of latency and cost. For broad, open-ended or novel reasoning, large general models win. Decide by benchmarking on your golden set, measuring quality per dollar and per millisecond.

Q167. One multi-task model vs one adapter per task?

▶ Answer

Multi-task model Per-task adapters
Serving simplicity ✔ one artifact Needs routing + adapter serving
Task interference Possible None
Update one task Retrain everything Retrain only that adapter
Cross-task transfer ✔ ✘ (unless merged)

Adapters are attractive for multi-tenant products; a multi-task model for a small, stable task set.

Q168. Human-labelled vs synthetic (LLM-generated) training data?

▶ Answer Human data: highest fidelity for real distribution and subtle judgement, but slow/expensive. Synthetic: cheap, scalable, diverse, controllable, but inherits teacher biases/errors and risks collapse. Best practice: hybrid — humans define rubrics and write/verify a seed + golden set; synthetic scales coverage; filters (verifiers, judges, dedup) ensure quality.

Q169. Online vs offline preference optimisation?

▶ Answer Offline (DPO on a fixed dataset) is simple, stable, cheap but limited by the data's distribution. Online (PPO/GRPO/online DPO) samples from the current policy, so it learns from its own mistakes and can exceed the dataset, at the cost of infra complexity, reward-model dependence and reward-hacking risk.

Q170. LLM-as-judge vs human evaluation?

▶ Answer Judges are fast, cheap and consistent but biased (position, verbosity, self-preference) and can miss domain subtleties. Humans are the gold standard but slow and noisy across annotators. Use LLM judges for breadth and regression, humans for calibration, high-stakes slices and final release decisions.

🏭 Production

Q171. Training loss is not decreasing. What do you check?

▶ Answer

1. Are parameters actually trainable?     print trainable params  (0 → adapters not attached / all frozen)
2. Are labels correct?                    all -100 (fully masked)? shifted twice? wrong template?
3. Is LR sane?                            too low → flat; too high → oscillation/NaN
4. Is data batch varied and shuffled?     duplicates? single task? tiny dataset?
5. Grad-norm logged?                      zero → detached graph / checkpointing without input grads
6. Precision issues?                      fp16 underflow → switch to bf16
7. Optimizer/scheduler wired properly?    warmup too long, LR scheduled to 0

Overfit one small batch first — if the model can't drive loss to ~0 on 8 examples, it's a pipeline bug, not a hyper-parameter problem.

Q172. The loss becomes NaN or Inf. Causes and fixes?

▶ Answer

  • fp16 overflow → use bf16 or proper loss scaling.
  • LR too high / no warmup → lower, add warmup, clip gradients.
  • A batch where every label is -100 → mean over zero tokens → NaN; filter empty targets.
  • Corrupt/extreme data (empty strings, very long sequences, unicode issues).
  • Custom kernels/quantisation instability; try disabling fused ops to isolate.
  • Log grad-norm and find the step where it explodes; dump that batch.

Q173. You hit CUDA out-of-memory. What are your steps, in order?

▶ Answer

  1. Reduce micro-batch size; raise gradient accumulation.
  2. Enable gradient checkpointing and FlashAttention.
  3. Cut max_length / truncate outliers; avoid huge padding (group by length).
  4. Use LoRA → QLoRA; 8-bit/paged optimizers.
  5. Shard with FSDP/ZeRO-3, offload to CPU.
  6. Watch for the vocab-size logits spike (use chunked/fused cross-entropy) and memory fragmentation (PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True).

Q174. After fine-tuning the model never stops generating (or rambles on). Why?

▶ Answer Common causes: (1) EOS not in labels — masked by mistake (pad_token = eos_token + masking pads), (2) template mismatch so the end-of-turn token differs at inference, (3) eos_token_id/generation_config doesn't include the template's end token (e.g., <|eot_id|>), (4) training data lacks proper endings or was truncated. Fix by verifying a decoded training example ends with the end-of-turn token and its label is not -100, and set the stop tokens in generation.

Q175. Validation metrics are great, but production quality is poor. Why?

▶ Answer

  • Train/serve skew: different prompt template, system prompt or preprocessing.
  • Distribution shift: validation not representative of real traffic (or leaked from train).
  • Decoding differences (temperature, max tokens, stop tokens).
  • Metric mismatch: optimising a proxy (loss/ROUGE) rather than user success.
  • Quantisation/merge artefacts in the deployed artifact. Fix: replay real production prompts through the eval harness, compare byte-for-byte prompts, evaluate the deployed artifact.

Q176. The model produces gibberish after merging or quantising the adapter. What happened?

▶ Answer Typical culprits: merged into a 4-bit base (rounding), wrong base model version (adapter trained on a different checkpoint), tokenizer changed/special tokens added but embeddings not saved (modules_to_save), dtype mismatch (fp16 overflow), or corrupted save. Re-merge into the exact original bf16 base, ensure tokenizer + embedding sizes match, then sanity-test before quantising.

Q177. The fine-tuned model behaves just like the base model. What went wrong?

▶ Answer Adapter not loaded/applied (wrong path, is_trainable, forgot PeftModel), LoRA targeting the wrong module names for this architecture, LR far too low or α/r too small, too few steps, loss masked to nothing, inference using a different template than training, or evaluation with a stale checkpoint. Confirm by comparing logits/outputs with adapter enabled vs disabled and by printing trainable parameter counts.

Q178. Generations are repetitive or loop. Fix?

▶ Answer Cause: overfitting/low diversity, missing EOS, greedy decoding on weak signal, tiny/duplicated data. Fix: dedupe and diversify data, fewer epochs/lower LR, verify stop tokens, use decoding controls (repetition penalty/no_repeat_ngram_size, mild temperature/top-p), and check that the loss on the response isn't collapsing to ≈0.

Q179. Training throughput is very slow. How do you profile it?

▶ Answer Check GPU utilisation and MFU. Typical causes: data-loader bottleneck (increase workers, pre-tokenise), heavy padding (length-grouped batching or packing), tiny micro-batch, missing FlashAttention/fused kernels, excessive gradient checkpointing, slow interconnect for FSDP, CPU offload, frequent evaluation/logging, or unnecessary fp32 ops. Use the PyTorch profiler and compare tokens/s against a known reference for your GPU and model size.

Q180. Model got noticeably less safe after fine-tuning. What do you do?

▶ Answer Run a safety benchmark before/after to quantify, then: mix in refusal and safety data (and general instruction data), lower LR/use LoRA, apply safety-focused preference tuning (DPO on refusals vs harmful compliance), add runtime guardrails/classifiers, and gate release on safety evals. Investigate whether some training samples contain unsafe compliance patterns.

Q181. Training loss is suspiciously low from the very first steps. What might be wrong?

▶ Answer Label leakage or masking bug: labels include the prompt (which is often copyable), duplicated tokens between input and target, the answer is present in the prompt, train/val contamination, or the model has already seen this data (base or instruct model was trained on it). Inspect a decoded example with the label mask visualised, and verify against a held-out set.

20SECTION 20: INTERVIEW FOLLOW-UP QUESTIONS

🔴 Advanced

Q182. Walk me through exactly what happens in one training step.

▶ Answer

1. Load a micro-batch → tokenised input_ids, attention_mask, labels
2. Forward pass (bf16; frozen 4-bit weights dequantised on the fly for QLoRA) → logits
3. Cross-entropy on unmasked labels (shifted by one) → scalar loss
4. Backward pass → gradients (only for trainable params; activations recomputed if checkpointing)
5. Repeat 1–4 `grad_accum` times, gradients accumulate (loss divided by accum steps)
6. Clip global grad-norm to 1.0
7. Optimizer step (AdamW updates moments + params) → scheduler step (LR update) → zero grads

Q183. Your LoRA fine-tune didn't beat the prompted baseline. What next?

▶ Answer Investigate before scaling up: (1) is the eval valid and sensitive? (2) inspect failures — data problem or capability problem? (3) sanity-check pipeline (masking, template, EOS, trainable params), (4) improve data (quality, coverage of failure modes, more hard cases), (5) then tune LR/rank/targets, (6) try a stronger base or full FT, (7) accept that prompting/RAG may be the right answer.

Q184. How do you tell whether a problem is due to data or hyper-parameters?

▶ Answer Run controlled experiments: fix hyper-parameters and vary data quality/size (learning curves); fix data and sweep LR/rank. If more data of the same kind doesn't help but a cleaner subset does → data quality. If train loss can't fall or diverges → optimisation/config. Error analysis by category usually points clearly to missing or contradictory data.

Q185. Why not simply raise LoRA rank until it matches full fine-tuning?

▶ Answer Capacity is only one factor; beyond a point extra rank yields diminishing returns, increases memory and overfitting risk, and changes optimal LR/α. Target layers, data quality and LR usually matter more. If LoRA at high rank on all layers still underperforms, you likely need full FT, more/better data, or a bigger base model.

Q186. What is your biggest fear/risk when fine-tuning for production?

▶ Answer Silent regressions: a model that scores well on a narrow validation set but is worse on real traffic, safety, or previously-working behaviour. Mitigate with representative golden sets, regression + safety suites, canary rollouts, monitoring, and instant rollback.

Q187. How would you explain fine-tuning to a non-technical stakeholder?

▶ Answer "The base model is a very well-read new hire. Fine-tuning is on-the-job training with hundreds of examples of how we do things here — our tone, our formats, our rules. It doesn't teach the hire new company facts (we give those via a searchable library — RAG). The quality of the training examples decides the outcome, and we test the trained hire on a fixed exam before letting them talk to customers."

Q188. How do you prevent evaluation leakage when using synthetic data?

▶ Answer Generate synthetic data from seed material disjoint from the eval set, run n-gram/embedding decontamination between synthetic train data and eval items, keep the golden set out of any prompt used for generation, version everything, and prefer human-written eval items. Re-check leakage whenever the pipeline changes.

Q189. What would change if you had 10× more data? 10× more compute? 10× less?

▶ Answer

  • 10× more data: consider full FT or higher rank, curate/select rather than use everything, larger held-out evals, maybe smaller LR/more careful mixing.
  • 10× more compute: bigger base model, longer/online RL, more seeds/sweeps, full FT.
  • 10× less (data or compute): LoRA/QLoRA, instruct base, tighter data curation, heavier reliance on prompting/RAG, smaller model.

21SECTION 21: RAPID-FIRE Q&A

⚡ Rapid Fire

Q191. What does the label value `-100` do?

▶ Answer It is PyTorch's ignore_index for cross-entropy: those positions contribute nothing to the loss (used for prompt tokens and padding).

Q192. What is the LoRA update formula?

▶ Answer W = W₀ + (α/r)·B·A, with B initialised to 0.

Q193. How big is a LoRA adapter for a 7B model at r=16 on all linear layers?

▶ Answer ~40M parameters → ~80 MB in bf16/fp16 (~160 MB in fp32).

Q194. What does NF4 stand for and why?

▶ Answer 4-bit NormalFloat — quantisation levels are placed at quantiles of a normal distribution, matching the distribution of pretrained weights.

Q195. Why is bf16 preferred over fp16?

▶ Answer Same exponent range as fp32 → no loss scaling and far fewer overflow/underflow problems.

Q196. Typical learning rate for LoRA vs full fine-tuning?

▶ Answer LoRA/QLoRA ≈ 1e-4–3e-4; full fine-tuning ≈ 1e-5–2e-5 (about 10× lower).

Q197. What is `paged_adamw_8bit`?

▶ Answer An 8-bit AdamW whose states are paged between GPU and CPU memory to survive memory spikes (QLoRA-style optimizer).

Q198. Why left-pad for batched generation but right-pad for training?

▶ Answer Generation continues from the last token, so real tokens must be at the right end (left padding). Training with right padding + attention mask + -100 labels is simplest.

Q199. What does gradient checkpointing trade?

▶ Answer Extra compute (~20–30 %) for much lower activation memory.

Q200. What does ZeRO-3 shard?

▶ Answer Optimizer states, gradients and parameters across GPUs (gathered layer by layer as needed).

Q201. Does DPO need a reward model? A critic?

▶ Answer Neither. It needs preference pairs and a frozen reference policy.

Q202. What does GRPO remove compared with PPO?

▶ Answer The value/critic network — advantages come from group-normalised rewards over G samples per prompt.

Q203. What does β do in DPO?

▶ Answer Controls deviation from the reference: larger β keeps the policy closer (more conservative), smaller β allows bigger shifts. Typical 0.1.

Q204. Why is the DPO learning rate so small?

▶ Answer The loss operates on log-probability ratios of whole sequences; large steps quickly over-optimise and cause likelihood displacement — typically ~5e-7 (full) to ~5e-6 (LoRA).

Q205. How many models does PPO-based RLHF hold in memory?

▶ Answer Four: policy, reference policy, reward model, value model.

Q206. What is the Bradley–Terry model?

▶ Answer P(y_w ≻ y_l) = σ(r(y_w) − r(y_l)) — a preference probability from a scalar reward; the basis of reward-model training and DPO.

Q207. What is a task vector?

▶ Answer τ = θ_finetuned − θ_base; adding/scaling/negating task vectors edits model behaviour (task arithmetic).

Q208. What is SLERP merging?

▶ Answer Spherical linear interpolation between two models' weights, preserving weight-vector norms better than linear averaging.

Q209. What is rsLoRA's change?

▶ Answer Scales the adapter by α/√r instead of α/r, stabilising learning at high ranks.

Q210. What is `merge_and_unload()`?

▶ Answer Folds the LoRA delta into the base weights and returns a plain model without adapter layers.

Q211. Why call `prepare_model_for_kbit_training` (or `enable_input_require_grads`) with QLoRA + checkpointing?

▶ Answer Frozen embeddings produce outputs without requires_grad, so checkpointed segments would have no gradient path; the helper enables input grads (and casts norms to fp32 for stability).

Q212. Why is `use_cache=False` used during training with gradient checkpointing?

▶ Answer The KV cache stores activations that checkpointing is trying to avoid keeping; the two are incompatible, so the cache is disabled in training.

Q213. What is instruction back-translation?

▶ Answer Take high-quality unlabeled text and have a model generate the instruction that would produce it, creating (instruction, response) pairs.

Q214. How do you compute perplexity from loss?

▶ Answer PPL = exp(mean token cross-entropy).

Q215. What does PPO's clipping do?

▶ Answer Limits how much the policy probability ratio can change per update ([1−ε, 1+ε], ε≈0.2), keeping updates stable.

Q216. What is the architecture of a reward model?

▶ Answer The LLM backbone with the LM head replaced by a scalar head, read at the final token, trained on pairwise preferences.

Q217. What is on-policy data?

▶ Answer Samples generated by the current policy (or a close copy) — the training signal matches the distribution the model will actually produce, which makes preference/RL learning more effective.

Q218. What is the "alignment tax"?

▶ Answer The drop in some capabilities (or benchmarks) that can accompany alignment/preference tuning; mitigated by regularisation, data mixing and careful KL control.

Q219. What is sequence packing?

▶ Answer Concatenating several short examples into one fixed-length sequence to avoid padding waste (requires correct attention/position handling).

Q220. Why is answer-only loss standard in SFT?

▶ Answer So the model learns to produce responses, not to model user prompts, and doesn't waste capacity/echo instructions.

Q221. What is QAT vs PTQ?

▶ Answer QAT simulates quantisation during training (better low-bit accuracy); PTQ quantises a trained model afterwards (cheaper, slight quality loss).

Q222. What is a "sleeper agent"/backdoor in fine-tuning?

▶ Answer Poisoned training samples that make the model behave normally except when a hidden trigger appears — a data-supply-chain risk.

Q223. Why not use fine-tuning as a database?

▶ Answer Facts are stored diffusely, can't be cited or edited reliably, may be hallucinated, and require retraining to update. Use RAG for facts.

Q224. Which decoding settings do you use when evaluating?

▶ Answer Deterministic tasks: greedy / temperature 0. Open-ended or pass@k: temperature ~0.6–1.0 with multiple samples. Keep settings identical across models compared.

Q225. Epoch vs step vs effective batch?

▶ Answer A step = one optimizer update; an epoch = one pass over the dataset; steps/epoch = N / effective_batch.

Q226. What is FlashAttention's main benefit?

▶ Answer Exact attention with O(N) memory and better speed via tiling and avoiding materialising the N×N matrix.

Q227. When does full fine-tuning beat LoRA?

▶ Answer Large datasets, big domain shift (new language, code/math at scale), and when squeezing maximum quality with ample compute.

Q228. Why are larger base models more sample-efficient to fine-tune?

▶ Answer Their pretrained representations already contain the needed skills, so fewer examples are required to elicit them.

Q229. What is RLVR?

▶ Answer Reinforcement learning with verifiable rewards — rewards from programmatic checkers (answers, unit tests) rather than a learned reward model.

Q230. What is model collapse?

▶ Answer Quality/diversity loss when models are trained repeatedly on their own (or other models') generated data without fresh real data.

Q231. What is the first thing to do when a fine-tune misbehaves?

▶ Answer Try to overfit a tiny batch and inspect a decoded training example with its label mask — most bugs are data-format/masking/template issues.
