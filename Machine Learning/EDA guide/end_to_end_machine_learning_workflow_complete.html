6. Outlier analysis and treatment

# Box plot
for col in df.select_dtypes(include=np.number).columns:
    sns.boxplot(x=df[col])
    plt.title(f"Box plot: {col}")
    plt.show()

# IQR rule
col = "fare"
q1, q3 = df[col].quantile([0.25, 0.75])
iqr = q3 - q1
lower, upper = q1 - 1.5 * iqr, q3 + 1.5 * iqr
outlier_mask = (df[col] < lower) | (df[col] > upper)
print("Outlier count:", outlier_mask.sum())

# Z-score (most useful as a rough flag for near-normal data)
z = (df[col] - df[col].mean()) / df[col].std()
z_outliers = z.abs() > 3

# Modified Z-score using median absolute deviation
x = df[col].dropna()
mad = stats.median_abs_deviation(x, scale="normal")
modified_z = 0.6745 * (x - x.median()) / mad if mad else pd.Series(0, index=x.index)
modified_z_outliers = modified_z.abs() > 3.5

# Capping / winsorization demonstration
df["fare_capped"] = df["fare"].clip(lower=lower, upper=upper)

Possible actions: keep valid extreme observations, cap, transform, use robust algorithms, investigate source errors, or remove only when justified. Learn capping thresholds on training data, not the entire dataset.

16. Production preprocessing and model pipeline

This is the recommended pattern: split raw data first, then fit preprocessing and model together. The pipeline ensures the same transformations are applied during training and inference.

from sklearn.compose import ColumnTransformer
from sklearn.pipeline import Pipeline
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import StandardScaler, OneHotEncoder
from sklearn.ensemble import RandomForestClassifier

# Titanic example: remove target and columns unsuitable for this simple example
target = "survived"
drop_features = ["alive", "class"]  # class duplicates pclass information
X = df.drop(columns=[target] + [c for c in drop_features if c in df.columns])
y = df[target]

# Split before fitting any learned preprocessing
X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.2, stratify=y, random_state=42
)

numeric_features = X_train.select_dtypes(include=np.number).columns.tolist()
categorical_features = X_train.select_dtypes(
    include=["object", "category", "bool"]
).columns.tolist()

numeric_pipeline = Pipeline([
    ("imputer", SimpleImputer(strategy="median")),
    ("scaler", StandardScaler())
])

categorical_pipeline = Pipeline([
    ("imputer", SimpleImputer(strategy="most_frequent")),
    ("onehot", OneHotEncoder(handle_unknown="ignore"))
])

preprocessor = ColumnTransformer([
    ("numeric", numeric_pipeline, numeric_features),
    ("categorical", categorical_pipeline, categorical_features)
])

full_pipeline = Pipeline([
    ("preprocessor", preprocessor),
    ("model", RandomForestClassifier(
        n_estimators=300, random_state=42, class_weight="balanced"
    ))
])

full_pipeline.fit(X_train, y_train)
pred = full_pipeline.predict(X_test)
print(classification_report(y_test, pred))
Note about Titanic: This sample intentionally demonstrates a compact baseline. Real production work should assess leakage-prone columns, define a data contract, validate feature semantics and compare preprocessing/model choices using cross-validation.

24. Production-grade FastAPI service Production

The earlier FastAPI example is enough to learn the idea. A real service also needs input limits, probabilities, versioning, structured logs, metrics, and separate health and readiness checks.

app/main.py

import json
import logging
import os
import time
import uuid
from contextlib import asynccontextmanager

import joblib
import pandas as pd
from fastapi import FastAPI, HTTPException, Request, Response
from pydantic import BaseModel, Field
from prometheus_client import (
    CONTENT_TYPE_LATEST, Counter, Histogram, generate_latest
)

MODEL_PATH = os.getenv("MODEL_PATH", "artifacts/titanic_pipeline.joblib")
MODEL_VERSION = os.getenv("MODEL_VERSION", "1.0.0")
THRESHOLD = float(os.getenv("THRESHOLD", "0.5"))
MAX_BATCH = int(os.getenv("MAX_BATCH", "500"))

logging.basicConfig(level=logging.INFO, format="%(message)s")
log = logging.getLogger("ml-api")

REQUESTS = Counter("predict_requests_total", "Prediction rows by outcome", ["status"])
LATENCY = Histogram("predict_latency_seconds", "Model inference time",
                    buckets=(.005, .01, .025, .05, .1, .25, .5, 1, 2.5))
PREDICTIONS = Counter("predictions_total", "Predictions by class", ["label"])

state = {}


@asynccontextmanager
async def lifespan(app: FastAPI):
    state["model"] = joblib.load(MODEL_PATH)   # load once, not per request
    log.info(json.dumps({"event": "model_loaded", "version": MODEL_VERSION}))
    yield
    state.clear()


app = FastAPI(title="Titanic ML API", version=MODEL_VERSION, lifespan=lifespan)


class Passenger(BaseModel):
    pclass: int = Field(ge=1, le=3)
    sex: str = Field(pattern="^(male|female)$")
    age: float | None = Field(default=None, ge=0, le=120)
    sibsp: int = Field(default=0, ge=0, le=20)
    parch: int = Field(default=0, ge=0, le=20)
    fare: float | None = Field(default=None, ge=0)
    embarked: str | None = None
    adult_male: bool = False
    deck: str | None = None
    embark_town: str | None = None
    alone: bool = False


class BatchRequest(BaseModel):
    items: list[Passenger] = Field(min_length=1, max_length=MAX_BATCH)


@app.middleware("http")
async def request_logging(request: Request, call_next):
    request_id = request.headers.get("x-request-id", str(uuid.uuid4()))
    start = time.perf_counter()
    response = await call_next(request)
    response.headers["x-request-id"] = request_id
    log.info(json.dumps({
        "event": "request",
        "request_id": request_id,
        "path": request.url.path,
        "status": response.status_code,
        "latency_ms": round((time.perf_counter() - start) * 1000, 1),
        "model_version": MODEL_VERSION,
    }))
    return response


def run_model(items):
    model = state.get("model")
    if model is None:
        raise HTTPException(status_code=503, detail="Model not loaded")
    frame = pd.DataFrame([i.model_dump() for i in items])
    start = time.perf_counter()
    try:
        proba = model.predict_proba(frame)[:, 1]
    except Exception:
        REQUESTS.labels("error").inc(len(items))
        log.exception("inference_failed")
        raise HTTPException(status_code=500, detail="Inference failed")
    LATENCY.observe(time.perf_counter() - start)
    REQUESTS.labels("ok").inc(len(items))
    results = []
    for p in proba:
        label = int(p >= THRESHOLD)
        PREDICTIONS.labels(str(label)).inc()
        results.append({"prediction": label,
                        "probability": round(float(p), 4),
                        "model_version": MODEL_VERSION})
    return results


@app.get("/health")        # liveness: is the process alive?
def health():
    return {"status": "ok"}


@app.get("/ready")         # readiness: can it serve traffic?
def ready():
    if "model" not in state:
        raise HTTPException(status_code=503, detail="Model not loaded")
    return {"status": "ready", "model_version": MODEL_VERSION}


@app.post("/predict")
def predict(passenger: Passenger):
    return run_model([passenger])[0]


@app.post("/predict/batch")
def predict_batch(req: BatchRequest):
    return {"results": run_model(req.items)}


@app.get("/metrics")
def metrics():
    return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)

What each part is for

  • Load at startup: loading the model inside the request would add seconds to every call.
  • Validated input: range and pattern checks reject bad requests with a clear 422 before they reach the model.
  • Plain def endpoints: scikit-learn is CPU-bound, so FastAPI runs these in a thread pool instead of blocking the event loop.
  • Probability and version in every response: callers can apply their own threshold, and every prediction can be traced to a model.
  • Liveness vs readiness: a pod that is alive but still loading must not receive traffic.
  • Request ID and JSON logs: one ID lets you follow a single request across services.
Privacy: do not log raw personal fields by default. Log the request ID, model version, probability and a hashed or minimal feature set, and set a retention period.

28. Training-serving skew and feature consistency Production

Many models that look excellent offline fail online because the features at serving time are not computed the same way as at training time. This is called training-serving skew.

Common causes

  • Preprocessing written twice (once in the notebook, once in the API) and slowly diverging.
  • Different library versions, category lists, or missing-value handling.
  • Features that use future information or data that is not available at request time (leakage).
  • Training on a clean history but serving on late, partial or corrupted events.

Practical defences

  • Ship one object: a scikit-learn Pipeline that contains all preprocessing, as in section 16. The API passes raw columns and nothing else.
  • Use OneHotEncoder(handle_unknown="ignore") so a new category does not crash inference.
  • Validate every input frame against a schema, in training and in serving.
  • Keep a small golden set of rows with known outputs and assert that offline and online predictions match.
  • For many shared, time-dependent features, use a feature store such as Feast so training and serving read the same definitions.

Population Stability Index (PSI) for numeric drift

import numpy as np
import pandas as pd

def psi(expected, actual, bins=10):
    expected = pd.Series(expected).dropna()
    actual = pd.Series(actual).dropna()
    edges = np.unique(np.quantile(expected, np.linspace(0, 1, bins + 1)))
    edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(expected, edges)[0] / len(expected)
    a = np.histogram(actual, edges)[0] / len(actual)
    e, a = np.clip(e, 1e-6, None), np.clip(a, 1e-6, None)
    return float(np.sum((a - e) * np.log(a / e)))

# Common rule of thumb: < 0.1 stable, 0.1 to 0.25 moderate shift, > 0.25 large shift

31. Security, privacy and governance Production

  • Access control: put the API behind an API gateway or service mesh with authentication (API keys, OAuth/JWT or mutual TLS) and rate limits.
  • Input safety: validate types and ranges, cap batch size and request size, and set timeouts.
  • Trusted artifacts only: joblib and pickle can run code on load. Load models only from your own registry with restricted write access, and consider signed artifacts.
  • Secrets: keep keys and database passwords in a secrets manager or Kubernetes secrets, never in the image, code or notebooks.
  • Supply chain: pin dependencies and scan them and the image regularly.
  • Privacy: collect only needed fields, mask or hash identifiers in logs, define retention, and follow the rules that apply to you (for example GDPR or India’s DPDP Act).
  • Documentation: keep a model card with purpose, training data, metrics, limits, known biases and owner.
  • Fairness and audit: evaluate subgroups, keep an audit trail of who promoted which model and when, and allow human review for high-stakes decisions.

36. Batch scoring pipelines MLOps

Many production models never run behind an API. A scheduled job scores a table and writes results for dashboards, CRM tools or downstream systems. Design it to be safe to re-run.

import os
import joblib
import pandas as pd
import pyarrow.parquet as pq
from datetime import date

MODEL_VERSION = os.getenv("MODEL_VERSION", "1.0.0")
FEATURES = ["pclass", "sex", "age", "sibsp", "parch", "fare", "embarked",
            "adult_male", "deck", "embark_town", "alone"]

def score(input_path: str, out_dir: str, run_date: date):
    model = joblib.load("artifacts/titanic_pipeline.joblib")
    parts = []
    for batch in pq.ParquetFile(input_path).iter_batches(batch_size=50_000):
        df = batch.to_pandas()
        out = df[["passenger_id"]].copy()
        out["score"] = model.predict_proba(df[FEATURES])[:, 1]
        out["model_version"] = MODEL_VERSION
        out["scored_on"] = run_date.isoformat()
        parts.append(out)

    result = pd.concat(parts, ignore_index=True)
    os.makedirs(out_dir, exist_ok=True)
    tmp = f"{out_dir}/part.tmp.parquet"
    final = f"{out_dir}/part.parquet"
    result.to_parquet(tmp, index=False)
    os.replace(tmp, final)          # atomic swap: readers never see half-written files
    return len(result)

if __name__ == "__main__":
    today = date.today()
    n = score("data/input.parquet", f"scores/run_date={today}", today)
    print("scored rows:", n)
  • Idempotent: running the same date twice overwrites the same partition instead of duplicating rows.
  • Chunked: reads in batches so memory stays flat on large tables.
  • Auditable: every output row carries the model version and run date.
  • Checked: compare row counts, null rates and score distribution with the previous run, and fail the job if they look wrong.
  • Scheduled: run it from Airflow, Prefect, Dagster, a cron job, or a cloud scheduler with retries and alerts on failure.

chunks = [
    "A canary release sends a small share of traffic to the new version first.",
    "Blue/green keeps two environments and switches traffic between them.",
    "Shadow deployment copies live traffic to a new model without returning its output.",
]
vectors = embedder.encode(chunks, normalize_embeddings=True).astype("float32")
index = faiss.IndexFlatIP(vectors.shape[1])
index.add(vectors)

# 2. Retrieve
def retrieve(question, k=2):
    q = embedder.encode([question], normalize_embeddings=True).astype("float32")
    scores, ids = index.search(q, k)
    return [(chunks[i], float(s)) for i, s in zip(ids[0], scores[0]) if i != -1]

# 3. Generate with grounding
def answer(question):
    hits = retrieve(question)
    context = "\n".join(f"- {text}" for text, _ in hits)
    prompt = f"Context:\n{context}\n\nQuestion: {question}\nAnswer using only the context. Say if it is not covered."
    resp = client.chat.completions.create(
        model="mistralai/Mistral-7B-Instruct-v0.3",
        messages=[{"role": "user", "content": prompt}],
        temperature=0.1, max_tokens=250,
    )
    return {"answer": resp.choices[0].message.content,
            "sources": [text for text, _ in hits]}

print(f"MAE={mae:.3f}  RMSE={rmse:.3f}  R2={r2:.3f}")

# Residual check by segment
residual = y_test - pred
print(residual.groupby(X_test["segment"]).agg(["mean", "std"]))

Time-series validation and lag features

import pandas as pd
from sklearn.model_selection import TimeSeriesSplit
from sklearn.ensemble import HistGradientBoostingRegressor
from sklearn.metrics import mean_absolute_error

df = df.sort_values("date").reset_index(drop=True)
df["lag_1"] = df["sales"].shift(1)
df["lag_7"] = df["sales"].shift(7)
df["roll_7_mean"] = df["sales"].shift(1).rolling(7).mean()   # shift(1) prevents leakage
df = df.dropna()

X = df[["lag_1", "lag_7", "roll_7_mean"]]
y = df["sales"]

tscv = TimeSeriesSplit(n_splits=5, gap=1)
for fold, (train_idx, val_idx) in enumerate(tscv.split(X)):
    m = HistGradientBoostingRegressor(random_state=42)
    m.fit(X.iloc[train_idx], y.iloc[train_idx])
    mae = mean_absolute_error(y.iloc[val_idx], m.predict(X.iloc[val_idx]))
    print(f"fold {fold}: MAE={mae:.2f}")
Always beat a baseline: for forecasting, compare with "same value as last week". For classification, compare with the majority class or a simple logistic regression. If a complex model cannot beat the baseline clearly, do not deploy it.

42. A/B testing and business impact Production

A better offline metric does not prove a better business outcome. For decisions that affect users, compare the new model with the current one on live traffic.

  1. Choose one primary metric (conversion, revenue per user, loss rate) and a few guardrail metrics (latency, complaints, refund rate).
  2. Compute the sample size before starting, and decide the test duration in advance.
  3. Randomize by user or account, not by request, so one person always sees one variant.
  4. Do not stop early when the result looks good; wait for the planned sample.
  5. Check for sample ratio mismatch (the traffic split matches the plan) before reading results.
from statsmodels.stats.proportion import proportion_effectsize, proportions_ztest
from statsmodels.stats.power import NormalIndPower

# Plan: detect a lift from 12% to 14% conversion
effect = proportion_effectsize(0.14, 0.12)
n_per_group = NormalIndPower().solve_power(effect_size=effect, alpha=0.05, power=0.8, ratio=1)
print("users needed per group:", int(n_per_group) + 1)

# Analyse after the planned sample is collected
conversions = [conv_control, conv_new]
users = [n_control, n_new]
z, p_value = proportions_ztest(count=conversions, nobs=users)
print(f"z={z:.2f}, p={p_value:.4f}")

When traffic is small or risk is high, use shadow mode first, then a small canary, and review business metrics together with model metrics.

Calibration: are probabilities trustworthy?

If a model says 0.8, about 80% of such cases should be positive. Calibration matters whenever you act on the probability itself (pricing, risk, triage).

from sklearn.calibration import CalibratedClassifierCV, calibration_curve
from sklearn.metrics import brier_score_loss

calibrated = CalibratedClassifierCV(estimator=full_pipeline, method="isotonic", cv=5)

proba = calibrated.predict_proba(X_test)[:, 1]
print("Brier score:", round(brier_score_loss(y_test, proba), 4))   # lower is better

for p, f in zip(mean_pred, frac_pos):
    print(f"predicted {p:.2f} to actual {f:.2f}")

Who does what

  • Data scientist: problem framing, features, model, evaluation, model card.
  • ML or MLOps engineer: pipelines, packaging, serving, CI/CD, monitoring.
  • Data engineer: reliable data sources, schemas, feature pipelines.
  • Product owner and domain expert: success metric, thresholds, acceptance, A/B test decisions.
  • Security and compliance: access, privacy, audit.

Cost control

  • Right-size instances from load tests and use autoscaling with sensible minimums.
  • Use batch scoring where real-time is not needed.
  • Use spot or preemptible instances for training; keep serving on stable capacity.
  • Shut down idle endpoints and notebooks; tag resources by project and set budget alerts.
  • Remove old model versions and artifacts under a retention rule.

Quick answers

How do I avoid training-serving skew?

Ship preprocessing and model as one Pipeline, validate input schemas, and test that offline and online predictions match on a golden set.

How do I know when to retrain?

Use drift and rolling performance monitoring, plus a schedule as a safety net. Retrain only after confirming that quality dropped or data has truly changed.

Which deployment should I choose first?

For most teams: a Docker container on a managed service (Cloud Run, ECS, App Runner or a managed ML endpoint). Move to Kubernetes only when you need its control.

How do I deploy safely?

Run tests and model quality gates, deploy to staging, use shadow or canary, watch error rate, latency and prediction distribution, and keep a one-step rollback.

What if I have no labels in production?

Monitor input drift and prediction distribution, sample cases for human labelling, and join real outcomes later when they become available.

Batch or real-time?

Choose batch if decisions can wait. It is cheaper and simpler. Choose real-time only when a decision is needed while the user waits.

How should I handle a model that is too slow?

Profile first, then try a simpler model, feature reduction, ONNX Runtime, batching, caching, and more replicas, in that order.

Can I use pickle or joblib in production?

Yes, if you load only trusted files from a controlled registry and pin library versions. For portability or untrusted environments consider ONNX.

46. Final production checklist

  1. Understand target, business objective and success metric.
  2. Validate schema, types, ranges, duplicates and missingness.
  3. Explore distributions, relationships, outliers and imbalance.
  4. Split data correctly before fitting learned transformations.
  5. Build preprocessing with Pipeline and ColumnTransformer.
  6. Establish a baseline, then compare suitable algorithms.
  7. Use cross-validation and tune hyperparameters on training data.
  8. Evaluate once on an untouched test set with business-relevant metrics.
  9. Check leakage, calibration, subgroup performance and explainability.
  10. Track experiments and save a reproducible, versioned artifact.
  11. Test inference schema and deploy through an API or batch job.
  12. Monitor data quality, drift, latency and real-world performance.
  13. Define rollback, retraining and model approval procedures.

Additional checks for a live system

  1. Pin dependencies and build a versioned, non-root container image tagged with the git SHA.
  2. Separate liveness and readiness checks; load the model once at startup.
  3. Validate inputs at the API edge and again with a data schema; handle unseen categories safely.
  4. Return model version and probability; choose the threshold from the cost of errors.
  5. Add quality gates in CI: data, metric floor, champion comparison, latency and security scans.
  6. Release through shadow or canary stages with automatic rollback on alerts.
  7. Emit structured logs with request IDs and Prometheus metrics; alert on symptoms, not noise.
  8. Join delayed ground truth to track real performance over time.
  9. Protect the API and artifacts: authentication, rate limits, trusted model sources, secrets management.
  10. Minimise and protect personal data in logs; keep a model card and an audit trail.
  11. Load test before launch and size resources from evidence.
  12. Assign an owner, an on-call path and a documented rollback and retraining runbook.
  13. Version data, code, parameters and environment together so any model can be reproduced.
  14. Compare against a simple baseline and test business impact with an A/B test when decisions affect users.
  15. Check calibration and subgroup performance, and keep a model card.
  16. For LLM and RAG systems, keep a quality test set, version prompts and indexes, and track tokens, cost and latency.
