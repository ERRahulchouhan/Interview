Data understanding, validation and leakage (Q1-10)

You have daily sales data with missing dates. How do you handle it?

Say first: I first ask why the dates are missing, because the cause decides the fix.

Steps

  1. Diagnose. A store closure or holiday means real "no sales". A logging or pipeline failure means the value is unknown.
  2. Reindex. Build a full date range and reindex, so every gap shows up as an explicit missing value.
  3. Fill based on cause. True closure: fill with 0. Short gap in a smooth series: interpolate. Seasonal data: use the average of the same weekday. Long gap: drop that window or use a model that handles missing data, like a state-space model.
  4. Flag it. Add an is_missing column so the model knows the value was filled.
  5. Validate. Hide some known values, fill them with each method, and pick the method with the lowest error.

Example

A shop is closed on Sundays, so Sunday gets 0. A server outage on a Tuesday gets the average of other Tuesdays.

Watch out

Filling with the overall mean ignores seasonality. In real-time systems, use only past values to fill, never future ones.

Your sensor data arrives at irregular intervals. How do you model it?

Say first: Most models assume equal spacing, so I either make the data regular or use a model that accepts irregular timestamps.

Steps

  1. Inspect the gaps. Plot the time between readings. Is it small jitter, or bursts and outages?
  2. Resample to a fixed grid (for example, every 1 minute). Aggregate by signal type: mean for temperature, sum for counts, last for status, max for alarms.
  3. Handle small gaps by interpolation, and mark large gaps as missing.
  4. Add features: time since last reading and number of readings per bucket, because the timing itself can carry information.
  5. If resampling loses detail, use models that take real timestamps: Kalman filter, Gaussian process, Neural ODE, or time-aware attention.

Example

A factory sensor sends data only when the value changes. I carry the last value forward and keep "time since last change" as a feature.

Watch out

Pick a bucket smaller than the fastest event you care about. Too coarse hides it, too fine creates many empty buckets.

How do you check whether a series is stationary, and what do you do if it isn't?

Say first: Stationary means the mean, variance and autocorrelation do not change over time. I test it, then fix it only if my model needs it.

Steps

  1. Look first. Plot the series and its rolling mean and standard deviation. A trend or growing spread is a warning.
  2. Run two tests. ADF (null: not stationary), where p < 0.05 suggests stationary. KPSS (null: stationary), where p < 0.05 suggests not stationary. Using both is safer.
  3. Fix it. Trend: first differencing. Seasonality: seasonal differencing (lag 7 or 12). Growing variance: log or Box-Cox first.
  4. Re-test and avoid over-differencing (a strongly negative lag-1 autocorrelation is the sign).
  5. Invert the transformations to get forecasts on the original scale.

Example

Monthly airline passengers: take the log, then difference at lag 1, then at lag 12.

Watch out

ARIMA needs stationarity. Tree models and neural nets do not strictly need it, but differencing helps them extrapolate trends.

ADF says stationary but KPSS says non-stationary. What now?

Say first: A disagreement is useful information. It tells me what kind of non-stationarity I have.

Steps

  1. Read the combination. Both say stationary: fine. Both say non-stationary: difference. ADF stationary but KPSS not: likely difference-stationary, so difference. KPSS stationary but ADF not: likely trend-stationary, so detrend.
  2. Apply the fix and run both tests again.
  3. Check for a structural break (Zivot-Andrews test). A break can fool ADF.
  4. Check sample size. Short series give low test power.
  5. Decide by results. Compare the forecast error of both treatments on a validation set.

Example

Sales with a steady upward drift: KPSS flags the trend, and differencing makes both tests agree.

Watch out

Never trust one test or one p-value. Combine tests, the plot and out-of-sample results.

Your series has huge outliers from a one-off event, such as a viral promotion. What do you do?

Say first: I ask two questions: is it a data error, and will it happen again?

Steps

  1. Verify. Rule out logging errors and confirm the cause with the business team.
  2. One-off event: cap it (winsorize at the 1st and 99th percentile) or replace it with a model estimate, and add an event dummy so the model does not learn it as normal.
  3. Recurring event (Black Friday, Diwali): keep it and add holiday features, including days before and after.
  4. Use robust tools: detect outliers with STL residuals and MAD (median-based) instead of mean and standard deviation, and train with MAE or Huber loss.
  5. Compare model performance with and without cleaning.

Example

A celebrity post makes one product spike 20x for a day. I cap it and flag it, rather than let the forecast assume a spike every week.

Watch out

Clean only the training data. Evaluate on real, uncleaned data.

Variance grows with the level of the series. How do you handle it?

Say first: Growing spread means the effects are multiplicative: the seasonal swing is a percentage of the level.

Steps

  1. Confirm. Plot it, or plot rolling standard deviation against rolling mean. A rising relationship confirms it.
  2. Transform. Use log (or log1p if zeros exist) or Box-Cox, which finds the best power automatically.
  3. Model on the transformed scale with ARIMA, ETS or a GBM.
  4. Back-transform the forecasts. Remember exp of a log forecast gives the median, so apply bias correction if you need the mean.
  5. Alternatives: multiplicative decomposition, or Poisson or Tweedie models with a log link for counts.

Example

Ice cream sales where summer peaks grow as the business grows. After the log, the peaks have equal height.

Watch out

Always report metrics on the original scale, since that is what the business sees.

How do you handle multiple seasonalities (daily, weekly, yearly) in hourly electricity demand?

Say first: Hourly demand has several cycles at once, so I model each one explicitly.

Steps

  1. Detect. Look at the ACF peaks at lag 24 and 168, and at a periodogram.
  2. Decompose with MSTL using periods 24 and 168 to see trend and each seasonal part.
  3. Statistical route: Fourier terms for each period plus ARIMA errors (dynamic harmonic regression), TBATS, or Prophet.
  4. ML route: features like hour, day of week, month, holiday flag, sin/cos encodings, lag 24, lag 168 and temperature.
  5. Deep route: N-BEATS or Temporal Fusion Transformer can learn the cycles directly.
  6. Validate with rolling origins that cover both summer and winter.

Example

Demand peaks at 8 pm daily, is lower on weekends, and rises in summer for air conditioning. Each has its own feature.

Watch out

Use cyclical encoding so hour 23 and hour 0 are treated as neighbors.

How would you handle a structural break, such as COVID, in your training data?

Say first: A break means old patterns may not describe the future, so I detect it, understand it, then decide how to treat it.

Steps

  1. Detect with plots and change-point methods (PELT, Bayesian change-point) or a Chow test.
  2. Understand the cause. Is the shift temporary or permanent?
  3. Temporary shock: add an intervention dummy or mask the period as missing.
  4. Permanent shift: train mainly on post-break data, weight recent data more, or add a regime indicator.
  5. Combine: use long pre-break history for the seasonal shape and post-break data for the level.
  6. Validate on a post-break holdout and keep monitoring for drift.

Example

Travel bookings collapsed in 2020. I mask 2020-21 for a recovery-focused model, and keep 2018-19 only to learn seasonality.

Watch out

Dropping all pre-break data can leave too little history for seasonality. Balance both.

Why can't you use random K-fold cross-validation on time series?

Say first: Time order matters. Random folds let the model train on the future and predict the past.

Steps

  1. Explain leakage. Neighboring points are correlated, so a test point on day 100 has training points on day 99 and 101. The model memorizes instead of forecasting.
  2. Use walk-forward validation. Train Jan-Jun, test Jul. Then train Jan-Jul, test Aug, and so on (expanding window), or slide a fixed window (rolling).
  3. Tools: scikit-learn TimeSeriesSplit, with a gap when features look back over a window.
  4. Keep a final holdout of the most recent period, untouched until the end.
  5. Report the average error across folds and its spread.

Example

Random K-fold gives 5% error. Walk-forward gives 14%. The 14% is the honest number.

Watch out

Fit scalers and imputers inside each fold, using training data only.

Your model has 98% accuracy offline but fails in production. What could be wrong?

Say first: A gap this large usually means the offline setup did not match production, so I audit in a fixed order.

Steps

  1. Leakage check. Look for centered rolling windows, scalers fit on all data, target encoding across time, shuffled splits, or joins that pull in later data.
  2. Availability check. Is every feature available at prediction time with the same delay? Yesterday's sales may arrive late in production.
  3. Train/serve skew. Compare feature code paths and distributions between training and serving.
  4. Drift check. Compare production inputs against training data (PSI, KS test) and watch for concept drift.
  5. Metric check. Compare with a naive baseline. If "same as yesterday" scores 97%, then 98% is not impressive.
  6. Fix. Rebuild validation with walk-forward splits and run the model in shadow mode before launch.

Example

A feature used the full-day average, which is only known at midnight, but predictions were needed at 9 am.

Watch out

When results look too good, suspect leakage before celebrating.

Features and preprocessing (Q51-60)

How do you choose lag features?

Say first: Lags let a tabular model see the past, and I pick them from the data and the forecast horizon, not by guessing.

Steps

  1. Find strong lags with the ACF and PACF plots.
  2. Add seasonal lags: for daily data, 7, 14 and 28; for yearly patterns, 365.
  3. Respect the horizon. For a 7-day direct forecast, use lags of at least 7 days, because newer values won't exist at prediction time.
  4. Test on walk-forward folds and drop lags with low importance or high overlap.
  5. Combine lags with rolling statistics for a fuller picture.

Example

For daily store sales, lag 7 and lag 14 capture the weekly rhythm, and lag 28 captures the monthly one.

Watch out

Too many correlated lags cause overfitting and noise.

How do you pick rolling window sizes?

Say first: Rolling windows summarize recent behavior, so I match their size to the business cycle and use more than one.

Steps

  1. Match the cycle: 7 days covers a week, 28 days covers a month.
  2. Use short and long windows together. Short windows show momentum; long windows show the baseline.
  3. Add several statistics: mean, standard deviation, min, max.
  4. Shift first. Compute y.shift(1).rolling(7).mean() so today's value is never included.
  5. Validate window choices with walk-forward folds.

Example

The 7-day mean tells me recent level; the 28-day mean tells me whether that level is unusual.

Watch out

A centered window uses future values and leaks the answer.

How do you encode cyclical features like hour or month?

Say first: Hour 23 and hour 0 are neighbors, so I encode time on a circle instead of a line.

Steps

  1. Identify the cycle length: 24 for hour, 7 for weekday, 12 for month.
  2. Create two features: sin(2π·x/period) and cos(2π·x/period).
  3. Use both together. Sine alone gives the same value for two different times.
  4. Choose by model: linear and neural models need this encoding; tree models can use the raw integer or categorical value.

Example

With raw hour, 23 and 0 look far apart. With sin/cos, they sit next to each other.

Watch out

Fourier terms with several harmonics are better for longer, smoother seasonal shapes.

How do you scale series for neural networks?

Say first: Neural nets train badly on raw values, and large series would dominate small ones, so I scale per series using training data only.

Steps

  1. Choose a scaler: standardization or min-max, or a log transform for skewed data.
  2. Fit per series (or per window with instance normalization such as RevIN).
  3. Fit on the training period only, then apply to validation and test.
  4. Train and predict on scaled values.
  5. Invert the scaling on outputs to get real units.

Example

A store selling 10,000 units and a kiosk selling 10 get comparable ranges, so the model learns both.

Watch out

Fitting the scaler on all data leaks future statistics.

How do you handle holidays that move every year, like Diwali or Eid?

Say first: Fixed calendar features can't catch moving dates, so I use an explicit holiday calendar with windows around each date.

Steps

  1. Get exact dates for past and future years from a holiday library or calendar.
  2. Add a flag for the holiday itself.
  3. Add window features: days before and after, since demand often builds up and tails off.
  4. Add interactions, such as holiday × weekday.
  5. Check each holiday's error separately in validation.

Example

Sweet shop sales rise 5 days before Diwali, peak the day before, and drop after. A single flag would miss that shape.

Watch out

With only a few years of history, each holiday has few examples, so keep the features simple.

What are the pitfalls when resampling hourly data to daily?

Say first: Resampling changes meaning, so I choose the aggregation, time zone and edge handling carefully.

Steps

  1. Pick the right aggregation: sum for sales or counts, mean for temperature, max for peaks, last for state.
  2. Align time zones so a "day" matches the business day.
  3. Handle partial days at the start and end, or drop them.
  4. Check missing hours. A day with 20 hours of data is not comparable to one with 24.
  5. Confirm the target granularity with the business before aggregating.

Example

Summing hourly temperature would give a meaningless number; the mean or max is right.

Watch out

Aggregating hides intraday patterns you may need later.

How do you handle daylight saving time?

Say first: DST creates days with 23 or 25 hours, so I keep storage in UTC and convert only when building features.

Steps

  1. Store timestamps in UTC. UTC has no jumps and no duplicates.
  2. Convert to local time only to create features like local hour and weekday.
  3. Handle the odd days: in spring one local hour is missing, in autumn one repeats.
  4. Check demand patterns in local time, since people follow the clock.
  5. Test around the change dates specifically.

Example

Morning peak demand moves one hour in UTC when clocks change, but stays at 8 am local. Local-hour features capture that.

Watch out

Local timestamps in storage create duplicate and missing hours that silently corrupt joins.

What do you do about long gaps in sensor data?

Say first: Short gaps can be filled, but long gaps are unknown, so I don't invent data across them.

Steps

  1. Measure gap lengths and find the cause (outage, maintenance, sensor fault).
  2. Fill short gaps by interpolation or forward fill.
  3. Mark long gaps as missing and add a flag feature.
  4. Split into segments so windows never span a long gap, or use models that accept missing values (state-space, GBMs).
  5. Validate by masking known stretches and checking how well your method recovers them.

Example

A 3-day outage on a wind turbine should not be linearly interpolated, since wind varies a lot in 3 days.

Watch out

Interpolating long gaps creates fake smooth data that makes the model look better than it is.

How do you do feature selection for time series?

Say first: I select features with time-aware validation, so I never reward features that only work because of leakage.

Steps

  1. Start with domain knowledge: list features that make business sense.
  2. Remove leakage risks: anything unavailable at prediction time.
  3. Drop redundant features, such as highly correlated lags.
  4. Measure importance with permutation importance on walk-forward folds.
  5. Regularize (L1, or tree-model feature limits) and keep the simplest set that holds accuracy.

Example

Lags 1 to 14 are all correlated; keeping lag 1, 7 and 14 gives the same accuracy with fewer features.

Watch out

Selecting features with random cross-validation can keep leaky ones.

Monthly macro data is joined to daily sales. What is the risk?

Say first: The risk is look-ahead leakage: the data describes a month but was published later.

Steps

  1. Find the release date, not just the reference month.
  2. Join on the release date: a value for March published on April 15 only exists for rows on or after April 15.
  3. Forward-fill the value across days until the next release.
  4. Account for revisions. Use the first-published value that was known then, not the revised one.
  5. Test it: check no feature uses information dated after the prediction time.

Example

An unemployment rate for March joined to every March day lets the model "know" a number the real world didn't have yet.

Watch out

This leak makes offline accuracy great and production accuracy poor.
