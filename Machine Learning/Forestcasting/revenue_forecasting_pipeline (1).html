Quarterly Revenue Forecasting
End-to-end production time-series ML pipeline

Important reality check – only 4 quarters of history. Four data points cannot support a trained ML model (LightGBM, LSTM, Prophet). Any fit will overfit. The pipeline below is built so that it works safely today (baselines + simple statistical models, with wide prediction intervals) and upgrades automatically as data grows. To get real accuracy, do these in parallel:
  • Pull monthly (or weekly) revenue from the ERP/billing system and aggregate to quarters afterwards – 4 quarters becomes 12+ points.
  • Forecast at product / region / customer-segment level and reconcile upward (hierarchical forecasting) – gives many series.
  • Add drivers: pipeline bookings, headcount, pricing, marketing spend, macro indicators, seasonality of your industry.
  • Blend with business judgement (sales leadership overrides) – the pipeline records both.

1. Workflow Diagram

1A. Each Stage Explained Simply

Everyday example: a shop owner planning next quarter's stock from the sales book.

#StageWhat we doWhy we do it
1Data SourcesFind where revenue numbers live: ERP, billing, CRM, Excel.The model can only learn from real company data. Like opening the shop's sales book.
2IngestionA scheduled job copies the data into one safe storage area without changing it.You keep an untouched copy, so you can always check the original numbers.
3ValidationAutomatic checks for missing quarters, negative revenue, duplicates, strange spikes.Bad data gives bad forecasts (garbage in, garbage out). Like checking the sales book for mistakes first.
4Feature BuildTurn raw numbers into clues: last quarter, same quarter last year, growth rate, quarter number.Models learn patterns from clues. Example clue: "Q4 is always big".
5Feature StoreSave those clues in a versioned file or table.Training and forecasting use exactly the same clues, and any past result can be reproduced.
6BacktestingPretend it is the past: train on early quarters, predict the next, compare with the real value, repeat with more data each time.Shows real accuracy before you trust the model. Never uses future data (no cheating).
7Model ZooSeveral models compete: Naive, Seasonal-Naive, ETS, SARIMAX, LightGBM.No model is best for every dataset. Simple models are a safety check; a complex model must beat them.
8Champion SelectPick the model with the lowest backtest error (MASE or WAPE).The choice is based on evidence, not opinion or fashion.
9Model Registry (MLflow)Save the chosen model with settings, scores and version. The best one gets the label "champion".You know which model made which forecast, and you can roll back if a new one is worse.
10Forecast + Confidence RangePredict the next 4 quarters with a low and high range (80% and 95%).Nobody predicts revenue exactly. The range lets finance plan for best, normal and worst cases.
11ServingExpose the forecast through an API or write it to a database table.Other systems and people use it automatically without running Python.
12BI DashboardShow forecast and actuals as charts in Power BI or Metabase.Managers read charts easily, not code.
13Actuals ArriveThe quarter ends and real revenue is recorded.Now you can compare "what we predicted" with "what happened". This is the only true test.
14MonitoringMeasure forecast error and bias, check how often actuals fall inside the range, watch for sudden revenue shifts.Models get worse as the business changes (new product, price change, acquisition). Monitoring catches it early.
15Retrain TriggerRetrain every quarter, or at once if monitoring raises an alert.The model keeps learning from fresh data. The loop returns to stage 2 and repeats.
In one sentence: get clean data → make clues → test models fairly → pick the best → forecast with a range → share → compare with reality → improve and repeat.

5. Data Ingestion & Validation

# src/data.py
import pandas as pd, pandera as pa, yaml
from sqlalchemy import create_engine

def load_config(path="config/config.yaml"):
    return yaml.safe_load(open(path))

def load_raw(cfg, conn_str):
    d = cfg["data"]
    df = pd.read_sql(f"SELECT {d['date_col']}, {d['target_col']} FROM {d['table']}",
                     create_engine(conn_str), parse_dates=[d["date_col"]])
    return df.rename(columns={d["date_col"]: "ds", d["target_col"]: "y"}).sort_values("ds")

schema = pa.DataFrameSchema({
    "ds": pa.Column(pa.DateTime, unique=True, nullable=False),
    "y":  pa.Column(float, pa.Check.ge(0), nullable=False, coerce=True),
})

def validate(df, cfg):
    df = schema.validate(df)
    # gap check: no missing periods
    full = pd.date_range(df.ds.min(), df.ds.max(), freq=cfg["data"]["freq"] + "E"
                         if cfg["data"]["freq"] == "Q" else "ME")
    missing = set(full) - set(df.ds)
    if missing:
        raise ValueError(f"Missing periods: {sorted(missing)}")
    # outlier flag (robust z-score) – flag, do not silently drop
    med, mad = df.y.median(), (df.y - df.y.median()).abs().median() or 1
    df["outlier"] = ((df.y - med).abs() / (1.4826 * mad)) > 4
    return df.set_index("ds").asfreq(cfg["data"]["freq"] + "E" if cfg["data"]["freq"] == "Q" else "ME")

6. Feature Engineering

# src/features.py
import numpy as np, pandas as pd

def build_features(s: pd.Series, season=4, exog: pd.DataFrame | None = None):
    df = s.to_frame("y")
    for k in (1, 2, season):                       # lags (only useful once history grows)
        df[f"lag_{k}"] = s.shift(k)
    df["roll_mean_2"] = s.shift(1).rolling(2).mean()
    df["yoy_growth"] = s.pct_change(season).shift(1)
    df["quarter"] = df.index.quarter
    df["t"] = np.arange(len(df))                   # linear trend index
    if exog is not None:                           # known-in-advance drivers only!
        df = df.join(exog)
    return df

Rule: every feature must be available at forecast time. Lagged actuals and planned drivers (budget, pricing) are fine; future actual drivers cause leakage.

7. Model Zoo

# src/models.py
import numpy as np, pandas as pd
from statsmodels.tsa.holtwinters import ExponentialSmoothing
from statsmodels.tsa.statespace.sarimax import SARIMAX

class Naive:
    name = "naive"
    def fit(self, y): self.last = y.iloc[-1]; return self
    def predict(self, h): return np.repeat(self.last, h)

class SeasonalNaive:
    name = "seasonal_naive"
    def __init__(self, m=4): self.m = m
    def fit(self, y): self.tail = y.iloc[-self.m:].values; return self
    def predict(self, h): return np.resize(self.tail, h)

class Drift:                                       # linear extrapolation – safe with tiny data
    name = "drift"
    def fit(self, y):
        self.last, self.slope = y.iloc[-1], (y.iloc[-1] - y.iloc[0]) / max(len(y) - 1, 1); return self
    def predict(self, h): return self.last + self.slope * np.arange(1, h + 1)

class ETS:
    name = "ets"
    def __init__(self, m=4): self.m = m
    def fit(self, y):
        seasonal = "add" if len(y) >= 2 * self.m else None   # need 2 full cycles
        self.res = ExponentialSmoothing(y, trend="add", damped_trend=True,
                                        seasonal=seasonal, seasonal_periods=self.m if seasonal else None
                                        ).fit(); return self
    def predict(self, h): return self.res.forecast(h).values

class Sarimax:
    name = "sarimax"
    def __init__(self, m=4): self.m = m
    def fit(self, y):
        order, sorder = (1, 1, 0), ((1, 0, 0, self.m) if len(y) >= 3 * self.m else (0, 0, 0, 0))
        self.res = SARIMAX(y, order=order, seasonal_order=sorder).fit(disp=False); return self
    def predict(self, h): return self.res.forecast(h).values

class GBM:                                         # activate only when history is large (≥ 24 points)
    name = "lightgbm"
    def __init__(self, m=4): self.m = m
    def fit(self, y):
        import lightgbm as lgb
        from features import build_features
        d = build_features(y, self.m).dropna()
        self.cols = [c for c in d.columns if c != "y"]
        self.model = lgb.LGBMRegressor(n_estimators=300, learning_rate=0.03, num_leaves=8,
                                       min_child_samples=3, verbose=-1).fit(d[self.cols], d["y"])
        self.hist = y.copy(); return self
    def predict(self, h):                          # recursive multi-step
        from features import build_features
        s, out = self.hist.copy(), []
        for _ in range(h):
            nxt = s.index[-1] + (s.index[-1] - s.index[-2])
            s.loc[nxt] = np.nan
            row = build_features(s.ffill(), self.m).iloc[[-1]][self.cols]
            p = float(self.model.predict(row)[0]); s.loc[nxt] = p; out.append(p)
        return np.array(out)

def candidates(m, n_obs):
    zoo = [Naive(), SeasonalNaive(m), Drift(), ETS(m)]
    if n_obs >= 8:  zoo.append(Sarimax(m))
    if n_obs >= 24: zoo.append(GBM(m))
    return zoo
Data-size gating: candidates() only enables complex models when there is enough history. With 4 quarters you get Naive / Seasonal-Naive / Drift / ETS – honest, stable, explainable.

8. Backtesting & Model Selection

# src/backtest.py
import numpy as np, pandas as pd

def mase(y_true, y_pred, y_train, m=1):
    scale = np.mean(np.abs(np.diff(y_train, n=m))) or 1.0
    return np.mean(np.abs(y_true - y_pred)) / scale

def wape(y_true, y_pred): return np.abs(y_true - y_pred).sum() / max(np.abs(y_true).sum(), 1e-9)

def rolling_origin(y: pd.Series, model, min_train=3, step=1, h=1):
    """Expanding-window CV. Never shuffles. Train strictly before test."""
    rows = []
    for end in range(min_train, len(y) - h + 1, step):
        train, test = y.iloc[:end], y.iloc[end:end + h]
        try:
            pred = model.fit(train).predict(h)
        except Exception as e:
            continue
        rows.append(dict(origin=train.index[-1], mase=mase(test.values, pred, train.values),
                         wape=wape(test.values, pred), err=(test.values - pred).mean()))
    return pd.DataFrame(rows)

def leaderboard(y, models, cfg):
    out = []
    for m in models:
        r = rolling_origin(y, m, cfg["backtest"]["min_train"], cfg["backtest"]["step"])
        if len(r): out.append(dict(model=m.name, mase=r.mase.mean(), wape=r.wape.mean(), folds=len(r)))
    return pd.DataFrame(out).sort_values(cfg["backtest"]["metric"]).reset_index(drop=True)

With 4 quarters you get ≈1 fold – treat the leaderboard as weak evidence and prefer the simplest model unless another wins consistently.

9. Training, Tracking & Registry

# src/train.py
import mlflow, mlflow.pyfunc, pandas as pd, joblib
from data import load_config, load_raw, validate
from models import candidates
from backtest import leaderboard

class Wrapper(mlflow.pyfunc.PythonModel):
    def __init__(self, fitted): self.fitted = fitted
    def predict(self, context, model_input):
        return pd.DataFrame({"forecast": self.fitted.predict(int(model_input["horizon"].iloc[0]))})

def main(conn_str):
    cfg = load_config()
    y = validate(load_raw(cfg, conn_str), cfg)["y"]
    m = cfg["data"]["season_length"]
    mlflow.set_tracking_uri(cfg["mlflow"]["tracking_uri"]); mlflow.set_experiment(cfg["mlflow"]["experiment"])

    zoo = candidates(m, len(y))
    lb = leaderboard(y, zoo, cfg)
    champ_name = lb.iloc[0]["model"]
    champ = next(z for z in zoo if z.name == champ_name).fit(y)    # refit on ALL data

    with mlflow.start_run(run_name=f"train_{y.index[-1]:%Y%m%d}") as run:
        mlflow.log_params({"champion": champ_name, "n_obs": len(y), "last_period": str(y.index[-1])})
        mlflow.log_metrics({"cv_mase": float(lb.iloc[0].mase), "cv_wape": float(lb.iloc[0].wape)})
        lb.to_csv("leaderboard.csv", index=False); mlflow.log_artifact("leaderboard.csv")
        info = mlflow.pyfunc.log_model("model", python_model=Wrapper(champ),
                                       registered_model_name=cfg["mlflow"]["model_name"])
    # promote only if better than current champion
    client = mlflow.MlflowClient()
    client.set_registered_model_alias(cfg["mlflow"]["model_name"], "challenger", info.registered_model_version)
    return champ_name, lb

if __name__ == "__main__":
    import os; print(main(os.environ["DB_URL"]))

Promotion rule: challenger becomes champion alias only if its backtest metric beats the current champion on the same folds, or after manual finance sign-off.

10. Forecasting with Prediction Intervals

# src/predict.py
import numpy as np, pandas as pd

def forecast_with_intervals(model, y, h=4, levels=(80, 95), n_boot=1000, seed=42):
    """Bootstrap one-step residuals → fan-out intervals. Widens honestly with small data."""
    rng = np.random.default_rng(seed)
    point = model.predict(h)
    fitted = np.array([model.__class__().fit(y.iloc[:i]).predict(1)[0] if False else np.nan for i in range(1)])
    # residuals via in-sample naive differences (robust fallback for tiny series)
    resid = np.diff(y.values) - np.mean(np.diff(y.values))
    sigma = np.std(resid, ddof=1) if len(resid) > 1 else 0.1 * abs(y.iloc[-1])
    sims = np.array([point + np.cumsum(rng.choice(resid, h, replace=True)) if len(resid) > 1
                     else point + rng.normal(0, sigma, h) for _ in range(n_boot)])
    idx = pd.date_range(y.index[-1], periods=h + 1, freq=y.index.freq)[1:]
    out = pd.DataFrame({"forecast": point}, index=idx)
    for lv in levels:
        lo, hi = (100 - lv) / 2, 100 - (100 - lv) / 2
        out[f"lo_{lv}"], out[f"hi_{lv}"] = np.percentile(sims, [lo, hi], axis=0)
    return out

Always publish the range, not just the point. Finance should plan on the interval (base / downside / upside scenarios).

13. Monitoring & Drift

# src/monitor.py
import numpy as np, pandas as pd

def forecast_accuracy(forecast_df, actual_df):
    j = forecast_df.join(actual_df, how="inner", rsuffix="_act")
    if j.empty: return None
    wape = np.abs(j.y - j.forecast).sum() / j.y.abs().sum()
    bias = (j.forecast - j.y).sum() / j.y.sum()
    cover95 = ((j.y >= j.lo_95) & (j.y <= j.hi_95)).mean()
    return dict(wape=wape, bias=bias, coverage_95=cover95)

def drift_z(history: pd.Series, new_value: float, window=8):
    h = history.iloc[-window:]
    return (new_value - h.mean()) / (h.std(ddof=1) or 1)

def run_checks(cfg, forecast_df, actual_df, history):
    acc = forecast_accuracy(forecast_df, actual_df)
    alerts = []
    if acc and acc["wape"] > cfg["monitoring"]["max_wape_alert"]: alerts.append(f"WAPE {acc['wape']:.1%}")
    if acc and abs(acc["bias"]) > 0.10: alerts.append(f"Bias {acc['bias']:.1%}")
    if abs(drift_z(history, actual_df.y.iloc[-1])) > cfg["monitoring"]["drift_z_alert"]:
        alerts.append("Revenue level shift – review for structural break (M&A, pricing, new product)")
    return acc, alerts      # send alerts to Slack / email; trigger retrain

15. Quarterly Runbook

  1. Quarter closes → finance publishes actuals to finance.revenue_quarterly.
  2. Airflow DAG fires (5th day) → ingest → validate (fails loudly on gaps / negatives).
  3. Monitor previous forecast vs. actuals → WAPE, bias, interval coverage logged.
  4. Retrain + backtest → leaderboard in MLflow → challenger registered.
  5. Review → analyst approves promotion to champion (or auto if metric improves).
  6. Forecast next 4 quarters with 80/95% intervals → written to table → dashboard refresh.
  7. Finance review → adjustments stored separately (never overwrite model output).

17. Interview Q&A – 50 Questions (Basic → Advanced)

Click a question to open the answer. Q1–14 basic · Q15–28 intermediate · Q29–38 advanced · Q39–45 scenarios · Q46–50 tricky.

Basic (1–14)

Q1. What is a time series?

Data points recorded in time order at regular intervals (for example quarterly revenue). Order matters, so you cannot treat the rows as independent.

Q2. What are the components of a time series?

Trend (long-term direction), seasonality (repeating pattern, such as a strong Q4), cycles (irregular long waves) and noise (random leftover).

Q3. What is stationarity and why does it matter?

A stationary series has constant mean, variance and autocorrelation over time. ARIMA-type models assume it. Check with ADF or KPSS tests and fix with differencing or a log transform.

Q4. Why can't we split train and test randomly?

A random split lets the model see the future while training (leakage), so the score looks better than reality. Always split by time: train on the past, test on the future.

Q5. What are Naive and Seasonal-Naive forecasts, and why use them?

Naive repeats the last value. Seasonal-Naive repeats the value from the same period last year. They are the benchmark: any complex model must beat them to be worth using.

Q6. Additive vs multiplicative seasonality?

Additive: the seasonal swing has constant size. Multiplicative: the swing grows with the level (a growing company has bigger Q4 spikes). A log transform turns multiplicative into additive.

Q7. MAE vs RMSE vs MAPE?

MAE is the average absolute error. RMSE squares errors, so it punishes big misses more. MAPE is a percentage, easy to explain, but it breaks when actuals are near zero and favours under-forecasting.

Q8. What are WAPE and MASE?

WAPE = total absolute error ÷ total actual (stable for revenue). MASE = your error ÷ the naive model's error; below 1 means you beat naive.

Q9. What are ACF and PACF?

ACF shows the correlation of the series with its own past at each lag. PACF shows the direct correlation at a lag after removing the shorter lags. They help choose ARIMA orders and spot seasonality.

Q10. What is differencing?

Subtracting the previous value (yt − yt−1) to remove trend. Seasonal differencing subtracts the value one season ago (lag 4 for quarters).

Q11. What is a lag feature?

A past value used as an input, such as last quarter's revenue or revenue four quarters ago. It converts a time series into a normal tabular problem.

Q12. What is a forecast horizon?

How many periods ahead you predict. Here it is 4 quarters. Accuracy usually drops as the horizon grows.

Q13. Point forecast vs interval forecast?

A point forecast is one number. An interval gives a range (for example 80% or 95%) that should contain the actual value that often. Finance plans on the range.

Q14. Why are 4 quarters of data a problem?

Too few points to learn trend and seasonality, so complex models overfit. Use simple models (Seasonal-Naive, Drift, ETS), widen intervals, and get more granular data (monthly, or by product and region).

Intermediate (15–28)

Q15. What do p, d, q mean in ARIMA?

p = number of autoregressive lags, d = number of differences to make the series stationary, q = number of past forecast errors (moving average terms).

Q16. SARIMA vs SARIMAX?

SARIMA adds seasonal terms (P, D, Q, m). SARIMAX also accepts external drivers (the X), such as bookings or pricing.

Q17. How does ETS / Holt-Winters work?

It keeps smoothed estimates of level, trend and seasonality, updating each with recent data using weights. Recent points count more. It is strong and stable on small data.

Q18. Rolling-origin CV vs k-fold CV?

Rolling-origin trains on an expanding window and always tests on the period right after it, so the future is never used. K-fold shuffles time and leaks information.

Q19. Give examples of data leakage in time series.

Scaling with statistics from the full dataset, rolling means that include the current row, using actual future drivers, and random splits. Fix: compute everything using only data before the forecast date.

Q20. Why do we shift before a rolling mean?

Without shift(1) the rolling window includes today's value, which is the target, so the model secretly sees the answer.

Q21. How do you handle missing periods?

First find out why (late data or truly zero). Reindex to a full calendar, then fill with interpolation or the seasonal value only if justified. Never fill with 0 blindly, and fail the pipeline if too much is missing.

Q22. How do you handle outliers?

Flag them, find the business cause (one-off deal, acquisition), and use an indicator variable or adjust the value with approval. Do not silently delete data.

Q23. Why can't tree models (LightGBM, Random Forest) extrapolate a trend?

They predict averages of values seen in training, so they cannot go beyond the training range. Fix: model growth or differences, or detrend first (linear or ETS) and let the tree model learn the residual.

Q24. What are the multi-step forecasting strategies?

Recursive (one model, feed predictions back in), direct (separate model per horizon step) and multi-output (one model predicts all steps together).

Q25. Recursive vs direct: trade-offs?

Recursive is simple but errors accumulate. Direct avoids error accumulation but needs more models and ignores links between steps. Direct is often better for longer horizons with enough data.

Q26. When is Prophet a good choice?

Daily or weekly data with multiple seasonalities, holidays and missing values. It is not suitable for 4 quarterly points and tends to overfit short series.

Q27. What is the rule for exogenous variables?

They must be known (or reliably forecast) at prediction time. Planned budget and price are fine; future actual sales of another product are not.

Q28. What is hierarchical forecasting?

Forecasting at several levels (total → region → product) and reconciling so the parts add up to the total. Methods: bottom-up, top-down, and MinT optimal reconciliation. It also gives you many series to learn from.

Advanced (29–38)

Q29. Global vs local models?

A local model is fitted to one series. A global model (for example LightGBM on all products) learns shared patterns across many series. Global models win with many short series, but need good identifiers and scaling.

Q30. How do you build prediction intervals?

Model-based (ARIMA/ETS variance), bootstrapping residuals, quantile regression (LightGBM with objective=quantile) or conformal prediction. Always check coverage against actuals.

Q31. What is conformal prediction?

A distribution-free method that uses past backtest errors to size the interval around any model's forecast, with a coverage guarantee under mild assumptions. Time series versions adapt to drift.

Q32. Data drift vs concept drift?

Data drift: input distribution changes (customer mix shifts). Concept drift: the relationship between inputs and revenue changes (a price change alters demand). Monitor both and retrain when error or drift alerts fire.

Q33. Why do forecast ensembles work?

Different models make different errors, and averaging cancels part of them. A simple average of ETS, ARIMA and a tree model often beats the best single model and is more robust.

Q34. What is interval calibration?

A 95% interval should contain about 95% of actuals. If it contains only 70%, intervals are too narrow and overconfident. Recalibrate using backtest errors.

Q35. How do you deal with a structural break?

Detect it (CUSUM, Chow test, residual monitoring), explain it (M&A, new pricing), then add an intervention dummy, train only on post-break data, or model the segments separately.

Q36. When are deep learning models (LSTM, N-BEATS, TFT) justified?

With long histories, thousands of related series, or rich covariates. For small quarterly company data they usually lose to ETS or a simple ensemble and are harder to explain.

Q37. What is point-in-time correctness in a feature store?

Each training row uses only feature values that were actually available on that date, including later restatements. It prevents leakage from revised data.

Q38. How do you deploy a new model safely?

Champion-challenger: run the new model in shadow mode, compare with the champion on live actuals, promote only if better, keep rollback by version alias.

Scenarios (39–45)

Q39. The CFO wants a forecast, but you have only 4 quarters. What do you do?

Deliver Seasonal-Naive or ETS with wide intervals and base/downside/upside cases. State the limits openly. Start collecting monthly and segment-level data, and add drivers such as pipeline bookings. Revisit once you have 8+ points.

Q40. Actual revenue came 25% below forecast. What next?

Check data first (was actual correct or late?). Then check whether it fell inside the interval, find the cause (lost customer, delayed deal, price change), compare against the naive model, and decide whether to retrain, add a driver or flag a structural break. Do not simply refit blindly.

Q41. One quarter has a huge one-time deal. How do you treat it?

Tag it as non-recurring. Forecast the base revenue without it, and add the one-off back as a separate line. Otherwise the model will assume the spike repeats.

Q42. The company acquired another firm last quarter, so revenue jumped. What do you do?

It is a level shift, not growth. Use an intervention dummy or restate history on a pro-forma (combined) basis, and avoid training on the old level alone.

Q43. Sales leadership wants to override the forecast. How do you handle it?

Allow overrides, but store them in a separate column with owner and reason, never overwrite the model output. Track model vs override error each quarter to see who is more accurate.

Q44. The backtest looked great but live performance is poor. Why?

Likely causes: leakage in features, tuning on the test period, too few folds, data revisions not reflected, or a regime change after training. Audit the features for point-in-time correctness and compare with the naive baseline.

Q45. Past revenue numbers get restated by finance. How does the pipeline cope?

Version the raw snapshots, keep a "as-of" date for each load, retrain on the latest restated data, and evaluate past forecasts against the actuals as first reported and as restated.

Tricky (46–50)

Q46. A model shows R² = 0.99 on a trending revenue series. Is it great?

Not necessarily. Any trending series gives a high R² even for a poor model. Compare MASE or WAPE with Seasonal-Naive on out-of-time folds instead.

Q47. Model A has lower RMSE than B. Is A always better?

No. Check bias (consistent over-forecasting hurts planning), interval coverage, performance versus naive, stability across folds, and the business cost of errors. RMSE is one number from limited folds.

Q48. After creating lag features, rows look independent. Can we shuffle for LightGBM CV?

No. Neighbouring rows share overlapping information and the shuffled training set contains future periods, so the score is inflated. Use time-ordered splits.

Q49. Does a stationary series have no seasonality?

Not exactly. Strict stationarity rules out predictable seasonal patterns in the mean, so seasonal series must be seasonally differenced or modelled. A series with a stable repeating pattern after differencing is handled by SARIMA.

Q50. Why can adding more features make a forecast worse?

With little data the model fits noise (overfitting). Also, extra drivers must themselves be forecast, which adds error, and some leak future information. Add features one at a time and keep only those that improve rolling-origin error.

18. Ways to Build the Forecast in Production

There are 5 main ways (plus a hybrid). Only the model step changes. The production workflow around it stays the same.

WayBest whenEffortControl
1. Spreadsheet / BI (Excel ETS, Power BI)Quick answer, tiny data, no engineersVery lowLow
2. Custom code (this pipeline)You need audit trail, overrides, your own driversHighFull
3. Forecast libraries (statsforecast, Darts, sktime)You want many models with little codeMediumHigh
4. Cloud AutoML (Vertex AI, Azure, Databricks)Many series, small ML team, managed hostingLow to mediumMedium
5. Foundation models (Chronos, TimesFM)Very little history, want a strong zero-shot baselineLowLow

Check each cloud service's current availability and pricing before committing, because these products change often.

Step-wise workflow (same for all five)

  1. Ingest and validate. Pull revenue from the source system and check gaps, negatives and duplicates.
  2. Train and backtest. Run the chosen approach(es), test on past quarters, compare each against Seasonal-Naive.
  3. Select the champion. Lowest error (MASE or WAPE), not the fanciest model.
  4. Register and serve. Save the model with a version, publish the 4-quarter forecast with a range to a table or API.
  5. Monitor. When the quarter closes, compare forecast with actuals; watch error, bias and drift.
  6. Retrain. Every quarter, or sooner if an alert fires, then loop back to step 1.
Recommendation for 4 quarters of data:
  • Now: way 1 or 3 (ETS or Seasonal-Naive) for a safe, simple forecast.
  • For production: keep way 2, because versions, overrides and monitoring are what finance needs.
  • As a challenger: add way 5 and let backtesting decide if it beats ETS.
  • At 24+ points or many series: add LightGBM, and consider way 4 for less maintenance.
Most companies end up with a hybrid: statistical model plus ML model, averaged, with the finance override stored separately.
