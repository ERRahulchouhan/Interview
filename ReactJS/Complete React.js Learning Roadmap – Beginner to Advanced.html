2. Beginner Topics

Tap any topic to open its full notes: what, why, when, how it works, syntax, mistakes, interview question and how to say it.

  • What is React.js?

    What: A JavaScript library by Meta for building user interfaces from reusable components.

    Why: You describe the UI for the current data (declarative) and React updates the page. No manual DOM work.

    When: Interactive apps where data changes often: dashboards, shops, chat, admin panels.

    How it works: Components return element descriptions, React renders them into one root node and updates only what changes.

    Mistake: Calling it a framework. It handles the view; routing and data fetching come from other libraries.

    Interview Q: Library vs framework? Say it: “A library does one job and I pick the rest; a framework like Angular gives the whole structure. React is a UI library.”

  • Why React instead of HTML, CSS and JavaScript?

    What: Comparing React with hand-written DOM code.

    Why: Plain JS: find element, change text, change class, for every update. This breaks as apps grow. React: change the data and the UI follows. Components are reusable and testable.

    When: Plain HTML/JS is fine for a static page or tiny script; use React when the UI has lots of state and many screens.

    // Plain JS
document.getElementById("count").textContent = count;
// React
<p>{count}</p>

    Mistake: Using React for a simple static site.

    Interview Q: Declarative vs imperative? Say it: “Imperative lists the steps; declarative says what the result should be. React is declarative.”

  • React architecture

    What: A tree of components rendered into one <div id="root">, with data flowing from parent to child.

    Why: One-way data flow makes bugs easy to trace.

    When: Always. It shapes how you split a page: App, then pages, then sections, then small components.

    How: createRoot(...).render(<App />) starts the tree. State lives in a component; children get it by props; children report back by calling handler props.

    Mistake: Putting all code in App.

    Say it: “React apps are component trees with one-way data flow; state lives in the nearest common parent.”

  • SPA vs MPA

    What: SPA loads one HTML page and JavaScript swaps views. MPA asks the server for a new page on every link.

    Why: SPA gives fast navigation and keeps state; MPA is simpler and better for SEO by default.

    When: SPA for dashboards and apps behind login; MPA or SSR for blogs, news and marketing sites.

    Mistake: Ignoring SEO and first-load size in an SPA.

    Interview Q: How do you fix SPA SEO? Say it: “Use SSR or SSG, for example with Next.js.”

  • Virtual DOM and Real DOM

    What: Real DOM is the browser’s page tree. Virtual DOM is a lightweight JavaScript copy of it.

    Why: Touching the real DOM is costly; React compares trees in memory and applies only the differences.

    When: Automatic on every state or props change.

    How: Change, then new virtual tree, then diff with old (reconciliation), then minimal real DOM updates, batched.

    Mistake: Saying the Virtual DOM is always faster than direct DOM code. Its value is predictable batched updates.

    Say it: “React diffs old and new virtual trees and patches only what changed.”

  • React installation using Vite

    What: Vite is a fast dev server and bundler for starting React projects. Create React App is deprecated.

    Why: Instant start, fast updates, simple config.

    When: Every new client-side React project (use Next.js for SSR).

    node -v                                              # need Node 18+
npm create vite@latest my-app -- --template react
cd my-app && npm install && npm run dev            # http://localhost:5173

    How: In dev, Vite serves native ES modules; npm run build bundles with Rollup into dist/.

    Mistake: Running commands outside the project folder; skipping npm install.

    Say it: “Vite starts instantly because it does not bundle in dev.”

  • Project structure

    What: The files Vite creates: index.html (has #root), src/main.jsx (entry), src/App.jsx (root component), public/ (static files), package.json (scripts, dependencies), vite.config.js.

    Why: Knowing the entry point tells you where the app starts and where to add code.

    When: As the app grows, add components/, pages/, hooks/, services/, grouped by feature.

    Mistake: JSX in .js files (use .jsx); committing node_modules.

    Say it: “main.jsx mounts App into the root div; I organise by feature as the project grows.”

  • JSX

    What: HTML-like syntax written inside JavaScript.

    Why: Markup and logic that belong together stay together.

    When: In every component’s return.

    How: Compiled to function calls that return plain objects describing elements. Rules: one root (or <></>), className, htmlFor, camelCase attributes, close every tag, expressions only inside {}.

    const el = <h1 className="t">Total: {price * 2}</h1>;

    Mistake: Using class; two root elements; if statements inside {}.

    Say it: “JSX is syntax sugar for createElement-style function calls.”

  • Components

    What: A reusable, independent piece of UI.

    Why: Build once, reuse everywhere, test and maintain in small parts.

    When: Any UI block that repeats or has its own logic: Navbar, Card, Modal, Table.

    How: React calls the component each render and uses the returned JSX as the new UI.

    Mistake: Lowercase names (treated as HTML tags); defining a component inside another component (state resets every render); one giant component.

    Say it: “I split the screen into small single-purpose components with clear props.”

  • Functional components

    What: A plain JavaScript function that returns JSX. They replaced class components.

    Why: Less code, hooks for state and effects, easier to read and test.

    When: Always in new code. Only error boundaries still need a class.

    function Greeting({ name }) {
  return <h1>Hello, {name}</h1>;
}

    Mistake: Calling hooks inside loops or conditions.

    Say it: “Functional components with hooks are the standard; classes are legacy.”

  • Class components vs functional components (with code)

    What: Two ways to write components. Class components extend React.Component and use this.state, this.setState and lifecycle methods. Function components are plain functions that use hooks (React 16.8+).

    Why it matters: New code uses functions; classes appear in old codebases and are still required for error boundaries.

    // CLASS component
import React from "react";
class Counter extends React.Component {
  constructor(props) {
    super(props);                         // must call super(props)
    this.state = { count: 0 };
    this.increment = this.increment.bind(this);   // bind, or use an arrow function property
  }
  componentDidMount() { document.title = "Counter"; }                 // after first render
  componentDidUpdate(prevProps, prevState) {                            // after every update
    if (prevState.count !== this.state.count) document.title = `Count ${this.state.count}`;
  }
  componentWillUnmount() { /* cleanup timers, listeners */ }          // before removal
  increment() { this.setState(prev => ({ count: prev.count + 1 })); }  // merges into state
  render() {
    return <button onClick={this.increment}>{this.props.label}: {this.state.count}</button>;
  }
}

// FUNCTION component (same behaviour)
function Counter({ label }) {
  const [count, setCount] = useState(0);
  useEffect(() => { document.title = `Count ${count}`; }, [count]);   // mount + update
  return <button onClick={() => setCount(c => c + 1)}>{label}: {count}</button>;
}

    Lifecycle mapping:

    componentDidMount          -> useEffect(() => {...}, [])
componentDidUpdate         -> useEffect(() => {...}, [dep])
componentWillUnmount       -> useEffect(() => () => {...cleanup}, [])
shouldComponentUpdate/PureComponent -> React.memo
this.state / setState      -> useState / useReducer
static contextType         -> useContext
createRef                  -> useRef
getDerivedStateFromError   -> (no hook yet; keep a class error boundary)

    Differences: classes have this and bind problems, logic is split across lifecycle methods, and logic reuse needs HOCs or render props. Functions are shorter, group related logic in effects, and reuse logic with custom hooks. Class setState merges objects; useState replaces the value, so spread objects yourself.

    Problems with classes and fixes:

    // 1) this is undefined in the handler
class A extends React.Component {
  state = { n: 0 };
  bad() { this.setState({ n: 1 }); }          // onClick={this.bad} -> TypeError
  good = () => this.setState({ n: 1 });       // arrow property keeps this
}
// 2) setState is async: this.state is old right after calling it
this.setState({ n: this.state.n + 1 });
this.setState({ n: this.state.n + 1 });        // still +1 only
this.setState(p => ({ n: p.n + 1 }));          // use the updater form, or the callback: setState(x, cb)
// 3) forgetting cleanup leaks memory
componentDidMount() { this.id = setInterval(this.tick, 1000); }
componentWillUnmount() { clearInterval(this.id); }
// 4) infinite loop in componentDidUpdate
componentDidUpdate() { this.setState({ x: 1 }); }                    // BAD: updates forever
componentDidUpdate(pp) { if (pp.id !== this.props.id) this.load(); }  // GOOD: guard with a condition

    Error boundary (only possible with a class): see the Error boundaries topic in Advanced.

    Say it: “I write function components with hooks. I can read and maintain class components and map their lifecycle methods to useEffect. The only thing I still need a class for is an error boundary.”

  • Props

    What: Read-only inputs a parent passes to a child, like HTML attributes.

    Why: Makes components configurable and reusable.

    When: To pass data (strings, objects, arrays) and handler functions down.

    function Button({ label, onClick }) {
  return <button onClick={onClick}>{label}</button>;
}
<Button label="Save" onClick={save} />

    How: All attributes are collected into one object, the first argument.

    Mistake: Mutating props; onClick={save()} (calls immediately) instead of onClick={save}.

    Say it: “Props are read-only; data flows parent to child.”

  • State

    What: Data a component owns and remembers between renders.

    Why: Normal variables reset each render and never update the screen; changing state does.

    When: For data that changes: input text, open/closed, counters, fetched data.

    Props vs state: props come from outside and are read-only; state is owned inside and changeable.

    Mistake: Mutating state directly; storing values that can be calculated from other state.

    Say it: “State changes trigger a re-render; derived values I compute instead of storing.”

  • useState

    What: Hook that adds state to a function component. Returns [value, setter].

    Why: The setter tells React to re-render with the new value.

    When: Simple independent values. Use useReducer for complex related state.

    const [count, setCount] = useState(0);
setCount(c => c + 1);                       // safe when based on old value
setUser(prev => ({ ...prev, name: "A" }));  // copy objects, never mutate

    How: React stores state per component in call order, so hooks must run in the same order every render. Updates are batched.

    Mistake: items.push(x); setItems(items) (same reference, no re-render); expecting the new value right after calling the setter.

    Say it: “I use the functional form when the new value depends on the old one.”

  • Event handling

    What: Responding to user actions: onClick, onChange, onSubmit.

    Why: It is how the user changes state.

    When: Any interaction. Handlers get a synthetic event e.

    <form onSubmit={(e) => { e.preventDefault(); save(); }}>
  <input onChange={(e) => setName(e.target.value)} />
</form>

    Mistake: Forgetting preventDefault() (page reloads); calling the handler during render.

    Say it: “I pass a function reference, and use an arrow function when I need arguments.”

  • Conditional rendering

    What: Showing different UI depending on a condition.

    Why: Handle loading, error, empty and logged-in states.

    When: Whenever the screen depends on data or user status.

    if (loading) return <p>Loading...</p>;           // early return
{isLoggedIn ? <Dashboard /> : <Login />}         // either/or
{error && <p>{error}</p>}                       // show or nothing

    Mistake: {count && <List />} prints 0 when count is 0; use count > 0 && ....

    Say it: “Early returns for states like loading, ternary for either/or, && for optional.”

  • Lists and keys

    What: Render arrays using map; each item gets a key.

    Why: Keys give each item a stable identity so React updates, reorders and keeps state correctly.

    When: Product grids, todo lists, tables, menus.

    <ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>

    Mistake: Index as key in a list that can change; no key at all; random keys (remount every render).

    Say it: “Stable unique IDs from the data, not array indexes.”

  • Forms and controlled components

    What: A controlled input has its value stored in React state.

    Why: One source of truth: easy validation, resetting and live feedback.

    When: Small and medium forms. For big forms use React Hook Form.

    const [form, setForm] = useState({ email: "", password: "" });
const handle = (e) => setForm({ ...form, [e.target.name]: e.target.value });
<input name="email" value={form.email} onChange={handle} />

    Mistake: value without onChange (input frozen); starting with undefined then a string (controlled/uncontrolled warning).

    Say it: “Controlled: React state drives the input. Uncontrolled: the DOM holds it and I read it with a ref.”

  • CSS styling

    What: Ways to style components: plain CSS, CSS Modules, Tailwind, CSS-in-JS, inline styles.

    Why: Plain global CSS clashes as apps grow; scoped styles stay maintainable.

    When: CSS Modules or Tailwind for most apps; inline style={{ color: "red" }} only for dynamic values.

    import s from "./Card.module.css";
<div className={s.card}>...</div>

    Mistake: class instead of className; inline style as a string instead of an object.

    Say it: “I scope styles with CSS Modules or Tailwind to avoid global clashes.”

  • Component composition

    What: Building complex UI by nesting components and passing JSX as children.

    Why: More flexible than inheritance and avoids long prop chains.

    When: Layouts, cards, modals, wrappers.

    function Card({ title, children }) {
  return <div className="card"><h3>{title}</h3>{children}</div>;
}
<Card title="Profile"><Avatar /><Bio /></Card>

    Mistake: Passing many config props when children would be simpler.

    Say it: “React prefers composition over inheritance.”

3. Intermediate Topics

Tap any topic to open its notes with code.

  • useEffect (all use cases)

    What: Hook that runs side effects after render.

    Why: Render must stay pure; fetching, timers, listeners and document title belong in effects.

    When / dependency array: no array = every render; [] = once on mount; [a] = when a changes. Return a function for cleanup.

    useEffect(() => { document.title = `Cart (${n})`; }, [n]);      // sync on change
useEffect(() => { loadUsers(); }, []);                           // once on mount
useEffect(() => {                                               // listener + cleanup
  const onResize = () => setW(window.innerWidth);
  window.addEventListener("resize", onResize);
  return () => window.removeEventListener("resize", onResize);
}, []);
useEffect(() => {                                               // fetch with abort
  const c = new AbortController();
  fetch(url, { signal: c.signal }).then(r => r.json()).then(setData).catch(() => {});
  return () => c.abort();
}, [url]);

    Mistake: Missing dependencies (stale values); no cleanup (leaks); using an effect to compute state that can be derived during render; passing an async function directly.

    Say it: “Effects sync my component with outside systems; the dependency array says when, and cleanup undoes the previous run.”

  • useRef

    What: A box { current } that persists across renders without causing one.

    Why / when: Access DOM nodes (focus, scroll), store timer IDs, keep the previous value.

    const inputRef = useRef(null);
<input ref={inputRef} />
<button onClick={() => inputRef.current.focus()}>Focus</button>

const prev = useRef();                       // previous value
useEffect(() => { prev.current = value; });

    Mistake: Expecting a re-render when ref.current changes; reading DOM refs during render (null on first render).

    Say it: “useRef is for values that must survive renders but should not trigger one.”

  • useContext

    What: Hook that reads the nearest Context value.

    Why / when: Read shared data (theme, user, language) anywhere without passing props.

    const ThemeContext = createContext("light");
function Button() {
  const theme = useContext(ThemeContext);
  return <button className={theme}>OK</button>;
}
<ThemeContext.Provider value="dark"><Button /></ThemeContext.Provider>

    Mistake: Calling it outside a Provider (gets the default value); one big context for everything.

    Say it: “Every consumer re-renders when the value changes, so I keep contexts small.”

  • useReducer

    What: State handled by a pure reducer (state, action) => newState.

    Why / when: Complex or related state with many transitions: cart, multi-step form, undo.

    function reducer(state, action) {
  switch (action.type) {
    case "add": return [...state, action.item];
    case "remove": return state.filter(i => i.id !== action.id);
    default: return state;
  }
}
const [cart, dispatch] = useReducer(reducer, []);
dispatch({ type: "add", item: { id: 1, name: "Pen" } });

    Mistake: Mutating state in the reducer; API calls inside it; missing default.

    Say it: “useState for simple values, useReducer when updates are related and I want testable logic.”

  • React Router DOM

    What: Library for client-side routing; the URL decides which component shows.

    Why / when: Any multi-page SPA needing real, shareable URLs without reloads.

    // npm i react-router-dom
import { BrowserRouter, Routes, Route, Link } from "react-router-dom";
<BrowserRouter>
  <nav><Link to="/">Home</Link> <Link to="/about">About</Link></nav>
  <Routes>
    <Route path="/" element={<Home />} />
    <Route path="/about" element={<About />} />
    <Route path="*" element={<NotFound />} />
  </Routes>
</BrowserRouter>

    Mistake: Using <a href> (full reload); server not rewriting unknown paths to index.html.

    Say it: “It listens to the History API and renders the matching route without reloading.”

  • Dynamic routing

    What: Routes with parameters such as /users/:id.

    Why / when: Detail pages (product, user, order) from one route.

    <Route path="/users/:id" element={<User />} />
function User() {
  const { id } = useParams();                    // "42" (always a string)
  const [sp] = useSearchParams();                // ?tab=info
  return <h2>User {id}, tab {sp.get("tab")}</h2>;
}
// link: <Link to={`/users/${u.id}`}>{u.name}</Link>

    Mistake: Treating id as a number; not refetching when id changes (put it in the effect dependency array).

    Say it: “Params come from useParams, query strings from useSearchParams.”

  • Nested routes

    What: Child routes rendered inside a parent layout through <Outlet />.

    Why / when: Shared layout (sidebar, header) around many pages.

    <Route path="/dashboard" element={<Layout />}>
  <Route index element={<Overview />} />
  <Route path="settings" element={<Settings />} />   {/* /dashboard/settings */}
</Route>
function Layout() {
  return <div><Sidebar /><Outlet /></div>;
}

    Mistake: Forgetting <Outlet /> (children never show); starting child paths with /.

    Say it: “The parent renders the layout and Outlet is where the matched child appears.”

  • Protected routes

    What: Routes that redirect unauthenticated users to login.

    Why / when: Dashboards, profile, admin pages.

    function ProtectedRoute({ allow = [] }) {
  const { user } = useAuth();
  if (!user) return <Navigate to="/login" replace />;
  if (allow.length && !allow.includes(user.role)) return <Navigate to="/403" replace />;
  return <Outlet />;
}
<Route element={<ProtectedRoute allow={["admin"]} />}>
  <Route path="/admin" element={<Admin />} />
</Route>

    Mistake: Treating this as real security. It is only UX, and the API must enforce access. Also redirecting before the auth check finishes loading.

    Say it: “A wrapper route checks auth and either renders Outlet or redirects.”

  • API integration using Fetch and Axios

    What: Calling a backend over HTTP.

    Why: Real apps use server data. Fetch is built in; Axios adds auto JSON, error throwing, interceptors and timeouts.

    // Fetch: does not throw on 404/500
const res = await fetch("/api/users");
if (!res.ok) throw new Error(res.status);
const users = await res.json();

// Axios (npm i axios)
const api = axios.create({ baseURL: import.meta.env.VITE_API_URL });
const { data } = await api.get("/users");

    When: Always call APIs from effects or event handlers, through a service file, never in the render body.

    Mistake: Not checking res.ok; hard-coding URLs; no cleanup, causing race conditions.

    Say it: “I centralise HTTP in an Axios instance with interceptors for tokens and errors.”

  • CRUD operations

    What: Create, Read, Update, Delete mapped to POST, GET, PUT/PATCH, DELETE.

    Why / when: Every admin or data-driven screen (Employee Management, products).

    const getAll = () => api.get("/employees");
const create = (e) => api.post("/employees", e);
const update = (id, e) => api.put(`/employees/${id}`, e);
const remove = (id) => api.delete(`/employees/${id}`);

// after delete, update local state
await remove(id);
setList(list.filter(e => e.id !== id));

    Mistake: Not updating the UI after the call; no confirmation before delete; no error handling.

    Say it: “After each mutation I update state or refetch so the UI matches the server.”

  • Loading and error handling

    What: Showing UI for the waiting and failed states of async work.

    Why / when: Every request can be slow or fail; users need feedback.

    const [data, setData] = useState(null);
const [loading, setLoading] = useState(true);
const [error, setError] = useState(null);

try { setData((await api.get("/users")).data); }
catch (e) { setError(e.message); }
finally { setLoading(false); }

if (loading) return <Spinner />;
if (error) return <p>Error: {error}</p>;
return <List items={data} />;

    Mistake: Forgetting finally (spinner never stops); showing raw error objects to users.

    Say it: “Every request has three states: loading, error and data.”

  • Form validation

    What: Checking user input before submitting.

    Why / when: Better UX and clean data. Always validate again on the server.

    const validate = (f) => {
  const e = {};
  if (!/^\S+@\S+\.\S+$/.test(f.email)) e.email = "Invalid email";
  if (f.password.length < 6) e.password = "Min 6 characters";
  return e;
};
const onSubmit = (ev) => {
  ev.preventDefault();
  const e = validate(form);
  setErrors(e);
  if (Object.keys(e).length === 0) save(form);
};

    Mistake: Client-only validation; unclear error messages; validating before the user touched the field.

    Say it: “Client validation is for UX, server validation is for safety.”

  • Custom hooks

    What: A function named useXxx that calls other hooks to reuse logic.

    Why / when: Same logic in several components: fetching, debounce, localStorage, window size.

    function useDebounce(value, delay = 500) {
  const [v, setV] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setV(value), delay);
    return () => clearTimeout(id);
  }, [value, delay]);
  return v;
}
const debouncedSearch = useDebounce(search);   // use in an effect to call the API

    Mistake: Expecting two components to share state through a hook (each call has its own); calling hooks conditionally.

    Say it: “Hooks share logic, not state.”

  • Prop drilling

    What: Passing props through many levels of components that do not use them.

    Why it matters: It makes code hard to change and read.

    Fixes: composition (pass JSX as children), Context for shared values, or a state library for large apps.

    // drilling: App -> Layout -> Sidebar -> Avatar(user)
<Layout user={user} />   // Layout only forwards it
// fix: Context
const { user } = useContext(AuthContext);   // read directly in Avatar

    Mistake: Jumping to Redux for one or two levels of passing; that is fine.

    Say it: “I lift state up first, then use composition or Context if drilling gets deep.”

  • Context API

    What: Built-in way to provide data to a whole subtree: createContext, Provider, useContext.

    Why / when: Theme, logged-in user, language. Not for fast-changing data.

    const AuthContext = createContext(null);
export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  const value = useMemo(() => ({ user, login: setUser, logout: () => setUser(null) }), [user]);
  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}
export const useAuth = () => useContext(AuthContext);

    Mistake: Passing a new object as value every render without memoising; putting everything in one context.

    Say it: “I wrap the provider in a small custom hook so consumers stay clean.”

  • State management

    What: Deciding where each piece of state lives.

    Why: Wrong placement causes drilling, bugs and re-renders.

    Guide: 1) local useState; 2) lift up to common parent; 3) Context for low-frequency globals; 4) Redux Toolkit or Zustand for large shared client state; 5) TanStack Query or RTK Query for server data; 6) URL for filters and pagination.

    Mistake: Putting everything in global state; duplicating server data in Redux.

    Say it: “I keep state as local as possible and separate server state from client state.”

  • Redux Toolkit

    What: Official, simplified way to use Redux for global state.

    Why / when: Large apps where many screens share state; DevTools and predictable updates.

    // npm i @reduxjs/toolkit react-redux
const cartSlice = createSlice({
  name: "cart", initialState: [],
  reducers: { add: (s, a) => { s.push(a.payload); } },   // Immer: safe to "mutate"
});
export const { add } = cartSlice.actions;
export const store = configureStore({ reducer: { cart: cartSlice.reducer } });

<Provider store={store}><App /></Provider>
const items = useSelector(s => s.cart);
const dispatch = useDispatch();  dispatch(add(product));

// async
export const fetchUsers = createAsyncThunk("users/fetch", async () => (await api.get("/users")).data);

    Mistake: Mutating state outside slices; selecting the whole store (extra re-renders); using Redux for tiny apps.

    Say it: “Action, reducer, new state, UI: one-way flow, easy to debug.”

  • React Hook Form

    What: Form library using uncontrolled inputs registered by refs.

    Why / when: Fewer re-renders, less code, easy validation. Use for medium and large forms.

    // npm i react-hook-form
const { register, handleSubmit, reset, formState: { errors, isSubmitting } } = useForm();
<form onSubmit={handleSubmit(async (d) => { await api.post("/login", d); reset(); })}>
  <input {...register("email", { required: "Required", pattern: { value: /^\S+@\S+$/, message: "Invalid" } })} />
  {errors.email && <p>{errors.email.message}</p>}
  <button disabled={isSubmitting}>Login</button>
</form>
// with schema: useForm({ resolver: zodResolver(schema) })

    Mistake: Mixing controlled value with register; trusting client validation only.

    Say it: “It avoids re-rendering on every keystroke and pairs well with Zod.”

  • Authentication and authorization

    What: Authentication = who you are (login). Authorization = what you may do (roles, permissions).

    Why / when: Any app with private data or different user types.

    // AuthContext flow

  const { data } = await api.post("/auth/login", creds);
  localStorage.setItem("token", data.token);
  setUser(data.user);               // { name, role: "admin" }
};
const canEdit = user?.role === "admin";   // UI only; server must enforce

    Mistake: Trusting the client for permissions; not clearing user state on logout; not handling 401 responses.

    Say it: “The UI hides what you cannot do; the backend refuses it.”

  • JWT authentication

    What: JSON Web Token: signed string header.payload.signature issued after login.

    Why: Stateless: the server verifies the signature and expiry without storing sessions.

    Flow: login, receive token, send Authorization: Bearer <token> on each request, server verifies. Best practice: short-lived access token plus a refresh token in an HttpOnly cookie.

    api.interceptors.request.use((cfg) => {
  const t = localStorage.getItem("token");
  if (t) cfg.headers.Authorization = `Bearer ${t}`;
  return cfg;
});
api.interceptors.response.use(r => r, (err) => {
  if (err.response?.status === 401) { localStorage.removeItem("token"); window.location = "/login"; }
  return Promise.reject(err);
});

    Mistake: Putting secrets in the payload (it is only encoded, not encrypted); localStorage is exposed to XSS; ignoring expiry.

    Say it: “JWT proves identity statelessly; I keep access tokens short-lived and refresh securely.”

4. Advanced Topics

Tap any topic to open its notes with code.

  • React Fiber architecture

    What: The rewritten React engine (v16+) that splits rendering into small units of work (fibers), one per component.

    Why: Work can be paused, resumed, prioritised or dropped, which keeps the UI responsive and enables concurrent features.

    How: Each fiber holds type, props, state and links to parent, child and sibling. React keeps a current tree and a work-in-progress tree and swaps them on commit.

    Mistake: Thinking you use Fiber directly; it is internal.

    Say it: “Fiber makes rendering incremental and interruptible.”

  • Reconciliation

    What: The diffing process that decides what changed between two trees.

    Why: Avoids rebuilding the DOM. Rules: different element type means rebuild the subtree; same type means update props; keys identify list items.

    // Changing key remounts the component and resets its state
<Profile key={userId} id={userId} />

    Mistake: Index keys on reordering lists; defining components inside components (new type each render, so full remount).

    Say it: “Same type and position keeps state; a different type or key resets it.”

  • React rendering lifecycle

    What: Trigger (state or props change), render phase (call components, pure, may be paused), commit phase (update DOM, then layout effects, then effects).

    Why: Tells you where side effects belong: never in the render body.

    useEffect(() => {            // mount / update
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);   // before next run and on unmount
}, []);

    Mistake: Side effects in render; confusing render with a DOM update (render can happen without one); forgetting StrictMode runs effects twice in development.

    Say it: “Render is pure calculation; effects run after commit.”

  • useMemo

    What: Caches a computed value until its dependencies change.

    When: Expensive calculations, or keeping an object or array reference stable for a memoised child.

    const visible = useMemo(
  () => products.filter(p => p.name.includes(q)),
  [products, q]
);

    Mistake: Memoising cheap work (the hook has its own cost); wrong dependencies.

    Say it: “useMemo caches a value; I profile before using it.”

  • useCallback

    What: Caches a function reference between renders.

    When: Passing a callback to a React.memo child or using it in an effect dependency.

    const onSelect = useCallback((id) => setSelected(id), []);
<Row onSelect={onSelect} />     // Row is wrapped in React.memo

    useMemo vs useCallback: useCallback(fn, deps) equals useMemo(() => fn, deps). One caches a value, the other a function.

    Mistake: Using it without a memoised child (no benefit).

  • React.memo

    What: Higher-order component that skips re-rendering when props are shallow-equal.

    When: Expensive components that re-render often with the same props (rows in a big list).

    const Row = React.memo(function Row({ item, onSelect }) {
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});

    Mistake: Passing new objects, arrays or inline functions each render, which defeats it; wrapping everything.

    Say it: “Shallow prop comparison, so I keep props stable.”

  • Performance optimization

    What: Reducing wasted work so the app stays fast.

    Order: 1) measure with React DevTools Profiler and Lighthouse; 2) colocate state; 3) memo, useMemo, useCallback where proven; 4) virtualise long lists (react-window); 5) code split; 6) debounce inputs; 7) useTransition for heavy updates; 8) optimise images and bundle size.

    const [isPending, startTransition] = useTransition();
startTransition(() => setFilter(value));   // non-urgent update

    Mistake: Optimising by guess; memoising everything.

    Say it: “Measure, find the bottleneck, then fix that one thing.”

  • Code splitting

    What: Breaking the bundle into chunks loaded on demand.

    Why: Smaller first load, faster start.

    How: Dynamic import(); the bundler creates separate chunks. Split by route first, then heavy components (charts, editors).

    const Chart = lazy(() => import("./Chart"));

    Mistake: Splitting tiny components; no fallback UI.

  • Lazy loading

    What: Loading code, images or data only when needed.

    const Dashboard = lazy(() => import("./pages/Dashboard"));   // component
<img src={url} loading="lazy" alt="product" />                // image

    When: Routes, modals, below-the-fold images.

    Mistake: Lazy-loading above-the-fold content (slows first paint); using lazy without Suspense.

  • Suspense

    What: Component that shows a fallback while children are loading (lazy code or Suspense-enabled data).

    <Suspense fallback={<Spinner />}>
  <Dashboard />
</Suspense>

    When: Around lazy routes; with frameworks and libraries that support Suspense for data (Next.js, TanStack Query).

    Mistake: Missing boundary (error); one boundary for the whole app (everything flashes).

  • Error boundaries

    What: Class component that catches errors in its child tree and shows a fallback.

    class ErrorBoundary extends React.Component {
  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; }
  componentDidCatch(error, info) { logToSentry(error, info); }
  render() { return this.state.hasError ? <h2>Something went wrong</h2> : this.props.children; }
}

    Mistake: Expecting it to catch event-handler, async or SSR errors (use try/catch); a single root-level boundary only. The react-error-boundary package is a common shortcut.

  • Concurrent rendering

    What: React can interrupt low-priority renders to handle urgent updates.

    Why: Typing and clicking stay responsive while heavy UI updates in the background.

    const deferred = useDeferredValue(query);               // lagging copy of a value
const [isPending, startTransition] = useTransition();   // mark updates as non-urgent

    Mistake: Using transitions for urgent updates such as controlled input value.

    Say it: “Urgent updates win; transitions can be paused or dropped.”

  • Server-side rendering

    What: Rendering components to HTML on the server for each request.

    Why: Fast first paint and SEO. Trade-offs: server cost and more complexity.

    When: Public, content or SEO pages. Alternatives: SSG (build time) and ISR (revalidate periodically). Use Next.js or Remix rather than building it yourself.

    Mistake: Using window or localStorage during render (undefined on the server).

  • Hydration

    What: The browser attaches event handlers and state to server-rendered HTML.

    hydrateRoot(document.getElementById("root"), <App />);

    Mistake: Hydration mismatch: server and client output differ (Date.now(), Math.random(), window checks). Fix by rendering the same first output and updating in an effect.

    Say it: “HTML arrives first; hydration makes it interactive.”

  • React Server Components

    What: Components that run only on the server and send no JavaScript to the browser.

    Why: Smaller bundles and direct database or file access.

    // Server Component (default in Next.js App Router)
async function Products() {
  const items = await db.product.findMany();
  return <ul>{items.map(i => <li key={i.id}>{i.name}</li>)}</ul>;
}
// Client Component
"use client";
export function AddButton() { const [n, setN] = useState(0); return <button onClick={() => setN(n + 1)}>{n}</button>; }

    Mistake: Using hooks or event handlers in a Server Component; marking everything "use client".

  • Next.js fundamentals

    What: React framework with routing, rendering strategies and API routes.

    Why: SEO, performance and full-stack features out of the box.

    app/
  layout.jsx          # shared layout
  page.jsx            # /
  products/[id]/page.jsx   # dynamic route /products/42
  api/users/route.js  # API endpoint

export default async function Page({ params }) {
  const { id } = await params;
  return <h1>Product {id}</h1>;
}

    Concepts: file-based routing, Server vs Client Components, SSR/SSG/ISR, next/image, metadata API. Mistake: Making everything a client component.

  • TypeScript with React

    What: Typed JavaScript for props, state and events.

    Why: Catches errors at compile time, gives autocomplete, documents components.

    type User = { id: number; name: string; email?: string };

    Mistake: Using any; not typing API responses; useState(null) without a union type.

  • Testing using Jest and React Testing Library

    What: Jest (or Vitest) runs tests; Testing Library renders components and queries them like a user.

    Why: Prevents regressions and documents behaviour.

    test("adds a todo", async () => {

  await userEvent.click(screen.getByRole("button", { name: /add/i }));

    Mistake: Testing implementation details (state values); querying by class or test ID when a role works; not mocking network calls (use MSW).

  • Accessibility

    What: Making the app usable with keyboard, screen readers and low vision.

    Why: Inclusion, legal requirements, better SEO and UX.

    <button aria-label="Close dialog" onClick={close}>X</button>
<label htmlFor="email">Email</label><input id="email" />
<img src={u} alt="Red running shoe" />

    Checklist: semantic HTML (button, nav, main), labels, alt text, visible focus, keyboard support, colour contrast, ARIA only when native HTML is not enough.

    Mistake: div onClick instead of button.

  • Security best practices

    What: Protecting users and data in a React app.

    Practices: React escapes output by default, so avoid dangerouslySetInnerHTML (or sanitise with DOMPurify); never put secrets in client env variables; avoid long-lived tokens in localStorage (use HttpOnly cookies); validate on the server; use HTTPS and CSP headers; audit dependencies (npm audit); validate URLs before redirecting or linking (javascript: links).

    Mistake: Trusting client checks; hiding admin buttons and thinking that is security.

12. Topics Explained Like an Interview

Each topic is a question an interviewer would ask, with a crisp answer you can say out loud, plus a follow-up trap to watch for.

Level 1: Beginner

Q. What is React and why use it instead of plain HTML, CSS and JavaScript?

React is a JavaScript library for building UIs from reusable components. With plain JS you manually find DOM nodes and update them; with React you describe what the UI should look like for a given state, and React updates the DOM for you. That gives less bug-prone code, reusable components and an easy-to-scale structure.

Trap: React is a library, not a framework. It handles the view layer; routing and data fetching come from other libraries.

Q. SPA vs MPA?

An SPA loads one HTML page and swaps content with JavaScript, so navigation feels instant but the first load and SEO need care. An MPA requests a new page from the server on every navigation, which is simpler for SEO but slower to navigate.

Q. Virtual DOM vs Real DOM?

The Real DOM is the browser’s tree, and updating it is expensive. The Virtual DOM is a lightweight JavaScript copy. On a state change React builds a new virtual tree, diffs it against the old one, and applies only the minimal changes to the real DOM.

Trap: the Virtual DOM is not “always faster”. Its value is predictable, batched updates.

Q. What is JSX?

JSX is a syntax extension that looks like HTML but compiles to React.createElement calls (or the modern JSX runtime). Rules: one root element (or a fragment), className instead of class, camelCase attributes, and JavaScript expressions inside {}.

Q. What are components? Functional vs class?

Components are reusable functions that return UI. Functional components with hooks are the standard today. Class components still exist (error boundaries still require one), but they are rarely written in new code.

Q. Props vs state?

Props are read-only inputs passed from parent to child. State is data owned and changed by the component itself, and changing it triggers a re-render. Never mutate props. Never mutate state directly; use the setter.

Q. How does useState work?

It returns [value, setter]. Calling the setter schedules a re-render with the new value. Updates are batched and asynchronous, so use the functional form setCount(c => c + 1) when the new value depends on the old one.

Trap: setCount(count + 1) three times in a row only adds 1, because every call sees the same stale count.

Q. Why do lists need keys?

Keys give React a stable identity for each item so reconciliation can match, reorder and preserve state correctly. Use a unique ID from your data. Using the array index breaks things when items are inserted, removed or reordered.

Q. What is a controlled component?

A form input whose value is held in React state (value plus onChange), so React is the single source of truth. An uncontrolled input keeps its own value in the DOM and you read it through a ref.

Q. Ways to style React apps? Event handling? Conditional rendering? Composition?

Styling: plain CSS, CSS Modules, Tailwind, styled-components, inline styles. Events use camelCase handlers (onClick={handler}), and you pass the function, not its call. Conditional rendering uses ternaries, &&, or early returns. Composition means building complex UI from small components and passing children, which is preferred over inheritance.

Trap: {count && <List />} renders a literal 0 when count is 0.

Level 2: Intermediate

Q. Explain useEffect and its dependency array.

useEffect runs side effects (fetching, subscriptions, timers, DOM work) after render. No array: runs after every render. []: runs once on mount. [a, b]: runs when a or b changes. The returned function is cleanup, which runs before the next effect and on unmount.

Trap: missing dependencies cause stale closures; an object created in the component body as a dependency causes an infinite loop.

Q. When do you use useRef?

For direct DOM access (focus, scroll) and for mutable values that must survive renders without causing a re-render (timer IDs, previous value). Changing ref.current does not re-render.

Q. What is prop drilling and how does Context solve it?

Prop drilling is passing props through many intermediate components that do not use them. Context lets a provider expose a value to any descendant through useContext. Caveat: every consumer re-renders when the value changes, so keep contexts small, and use Redux or Zustand for frequently changing global state.

Q. useState vs useReducer?

useState suits simple, independent values. useReducer suits complex state with several related fields or many transitions, since logic lives in one pure reducer (state, action) => newState that is easy to test.

Q. How does React Router work? Dynamic, nested and protected routes?

It matches the URL against route definitions and renders the matching element without a page reload. Dynamic routes use params (/users/:id with useParams). Nested routes render children through <Outlet />. Protected routes wrap pages in a component that redirects with <Navigate> if the user is not authenticated.

Trap: client-side route protection is only UX. The server must enforce authorization.

Q. Fetch vs Axios? How do you structure API calls?

Fetch is built in but needs manual JSON parsing and does not reject on HTTP errors like 404 or 500. Axios auto-parses JSON, throws on error statuses, and supports interceptors and timeouts. In production, keep calls in a service layer (services/api.js), not inside components, and track loading, error and data states for each request.

Q. What is a custom hook?

A function starting with use that calls other hooks to reuse stateful logic (for example useFetch, useDebounce, useLocalStorage). Each call gets its own state; hooks share logic, not state.

Q. Why Redux Toolkit? How does it work?

Redux Toolkit removes Redux boilerplate. createSlice defines state and reducers (Immer lets you write “mutating” code safely), configureStore builds the store, and useSelector and useDispatch connect components. RTK Query handles server data caching. Use Redux for large shared client state, not for everything.

Q. Form validation and React Hook Form?

React Hook Form registers inputs as uncontrolled and reads them via refs, so typing does not re-render the whole form, which is faster. It supports built-in rules or schema validation with Zod or Yup.

Q. How does JWT authentication work in a React app?

The user logs in, the server returns a signed token, and the client sends it as Authorization: Bearer ... on each request. The server verifies the signature and expiry. Better practice: short-lived access token plus a refresh token in an HttpOnly cookie. Storing JWTs in localStorage is exposed to XSS.

Authentication = who are you. Authorization = what are you allowed to do (roles and permissions).

Level 3: Advanced

Q. What is React Fiber and reconciliation?

Reconciliation is the diffing process: React compares the old and new element trees, assuming different types produce different trees and that keys identify items in lists. Fiber is the engine (since React 16) that breaks rendering into small units of work that can be paused, resumed and prioritised, which makes concurrent features possible.

Q. Explain the render lifecycle.

Render phase (pure, can be paused): call components and compute the new tree. Commit phase (synchronous): update the DOM, then run layout effects and then effects. In functional components this maps to mount, update and unmount through useEffect and its cleanup. In Strict Mode development, effects run twice to expose bugs.

Q. useMemo vs useCallback vs React.memo?

useMemo caches a computed value. useCallback caches a function reference. React.memo wraps a component and skips re-rendering if its props are shallow-equal. useCallback is mostly useful when passing a function to a memoized child. Do not use them everywhere: measure first, because they have their own cost.

Q. How do you optimise a slow React app?

Profile first (React DevTools Profiler). Then: avoid unnecessary re-renders (memo, state colocation), virtualise long lists, code-split routes, lazy-load images and components, debounce inputs, and keep expensive work out of render.

Q. Code splitting, lazy loading, Suspense?

React.lazy(() => import(...)) loads a component’s bundle only when it is first rendered. Suspense shows a fallback while it loads. Split by route first.

Q. What are error boundaries?

Class components using getDerivedStateFromError and componentDidCatch to catch errors in the render tree and show a fallback. They do not catch errors in event handlers, async code, or SSR.

Q. What is concurrent rendering?

React can interrupt low-priority work to keep urgent updates (typing) responsive. APIs: useTransition and useDeferredValue mark updates as non-urgent.

Q. CSR vs SSR, hydration, and Server Components?

CSR renders in the browser after JS loads. SSR renders HTML on the server for faster first paint and SEO, then hydration attaches event handlers to that HTML. React Server Components run only on the server, send no JS to the client, and can access databases directly; interactive parts are marked "use client".

Q. Why Next.js?

It adds file-based routing, SSR, SSG, ISR, API routes, image optimisation and the App Router with Server Components on top of React.

Q. Why TypeScript, how do you test, and what about accessibility and security?

TypeScript catches prop and state errors at compile time and documents components. For testing, Jest or Vitest plus React Testing Library: test behaviour the way a user sees it (roles, text), not implementation details. Accessibility: semantic HTML, labels, keyboard navigation, ARIA only when needed. Security: React escapes by default, so avoid dangerouslySetInnerHTML, sanitise any HTML, avoid tokens in localStorage, validate on the server, and keep dependencies updated.

Level 4: Production

Q. How do you structure a large React project?

Feature-based folders (features/auth, features/orders), each holding its components, hooks, services and tests, plus shared components, hooks and utils. Keep an API service layer, route configuration and a clear boundary between UI and data logic.

Q. How do you design reusable components and patterns?

Small, single-purpose components with a clear props API. Patterns: container/presentational, compound components, custom hooks, render props, and higher-order components. Prefer composition and hooks.

Q. Environment variables and role-based access?

In Vite use VITE_ prefixed variables via import.meta.env. They are bundled into the client, so never put secrets there. For RBAC, store the role from the verified token, hide UI by role, and always enforce permissions on the backend.

Q. Error handling, logging and monitoring?

Error boundaries for render errors, try/catch for async, a global handler for API errors, and a service like Sentry for logging. Use Web Vitals and Lighthouse to track performance.

Q. SEO and responsive UI in React?

Pure CSR hurts SEO, so use SSR or SSG (Next.js), proper meta tags, and semantic HTML. For responsiveness: mobile-first CSS, flexbox and grid, media queries.

Q. How do you deploy a React app?

npm run build produces static files. Docker: multi-stage build, then serve with Nginx. CI/CD (GitHub Actions): install, lint, test, build, then deploy to AWS (S3 + CloudFront, or ECS) or Azure (Static Web Apps). Use env-specific configs and cache-busted asset names.

Q. A production page is blank after deploy. How do you debug?

Open the console and network tab for JS errors and 404s; check the build output and base path; check environment variables; for routing issues, confirm the server rewrites all paths to index.html; check source maps and Sentry for the exact error; roll back if users are affected, then fix.

13. Topic Notes: What, Why, How, Syntax, Example, Mistakes

Full notes for the beginner topics and the core hooks, following your 8-point structure. Interview questions for each are in section 12, and larger examples in section 11.

React.js, and why not plain HTML/CSS/JS

What: A JavaScript library by Meta for building UIs from components.

Why: Plain JS needs manual DOM updates (getElementById, innerHTML), which gets messy as apps grow. React is declarative: you write UI = f(state), and React keeps the screen in sync. (Hinglish: aap batate ho “kya dikhna chahiye”, “kaise update karna hai” React khud dekhta hai.)

Internally: React builds a tree of elements, compares it with the previous one, and patches only what changed in the browser DOM.

Syntax: createRoot(document.getElementById("root")).render(<App />)

Real-world: Dashboards, e-commerce storefronts, chat UIs: anything with lots of changing state.

Mistakes: Thinking React is a full framework; manipulating the DOM directly alongside React.

React architecture, SPA vs MPA, Virtual DOM

What: A component tree rendered into one root element. SPA = one HTML page, JavaScript swaps views. MPA = new HTML page per navigation. Virtual DOM = an in-memory copy of the UI tree.

Why: SPAs feel fast after the first load and keep state between views. The Virtual DOM makes updates batched and predictable.

Internally: State change, then re-render (new virtual tree), then diff, then commit minimal DOM changes.

Real-world: Gmail is an SPA; a content-heavy blog often works better as an MPA or SSR.

Mistakes: Ignoring SEO and first-load size in an SPA; saying the Virtual DOM is always faster than the real DOM.

Installation with Vite and project structure

What: Vite is a fast dev server and bundler. Create React App is deprecated; Vite or Next.js is the standard now.

Syntax:

npm create vite@latest my-app -- --template react
cd my-app && npm install && npm run dev

Structure: index.html (entry page with #root), src/main.jsx (mounts the app), src/App.jsx (root component), public/ (static files), package.json (scripts and dependencies), vite.config.js.

Internally: In dev, Vite serves native ES modules and only transforms files the browser asks for, so startup is near-instant. For production it bundles with Rollup.

Mistakes: Using .js instead of .jsx for JSX files (Vite expects .jsx); forgetting npm install; committing node_modules.

JSX

What: HTML-like syntax inside JavaScript.

Why: UI and logic that belong together live together.

Internally: Compiled to function calls, so <h1 className="t">Hi</h1> becomes jsx("h1", { className: "t", children: "Hi" }), which returns a plain object describing the element.

Syntax:

const el = (
  <>
    <h1 className="title">Total: {price * 2}</h1>
    <img src={url} alt="product" />
  </>
);

Mistakes: Using class or for (use className, htmlFor); returning two root elements; putting statements like if inside {} (only expressions allowed); forgetting to close tags like <img />.

Components and functional components

What: A reusable function that returns JSX. The name must start with a capital letter.

Why: Build once, reuse everywhere; each piece is testable on its own.

Internally: React calls your function on every render and uses the returned elements as the new UI description. Local variables reset each call; state and refs persist.

Syntax: function Card() { return <div>...</div>; } then <Card />

Real-world: Navbar, ProductCard, Modal, DataTable.

Mistakes: Lowercase names (<card /> is treated as an HTML tag); defining components inside other components (state is lost on every render); one giant component.

Props

What: Inputs to a component, passed like HTML attributes.

Why: Make components configurable and reusable.

Internally: Collected into a single read-only object passed as the first argument.

Syntax:

function Button({ label, onClick, variant = "primary" }) {
  return <button className={variant} onClick={onClick}>{label}</button>;
}
<Button label="Save" onClick={save} />

Real-world: One Button used across 200 screens with different labels and handlers.

Mistakes: Mutating props; passing a call (onClick={save()}) instead of a function (onClick={save}); copying props into state without a reason.

State and useState

What: Data a component remembers between renders.

Why: Normal variables reset every render and do not trigger updates.

Internally: React stores state per component instance, in call order, which is why hooks must be called in the same order every time. The setter schedules a re-render, and updates in one event are batched.

Syntax: const [user, setUser] = useState(null); Use setUser(prev => ...) when based on the previous value; create new objects/arrays instead of mutating.

Real-world: Cart items, modal open/closed, form values.

Mistakes: items.push(x) then setItems(items) (same reference, no re-render); reading state right after setting it (you still see the old value this render); hooks inside if or loops.

Event handling

What: Reacting to clicks, typing, submits.

Internally: React uses a synthetic event wrapper and delegates events at the root.

Syntax:

<input onChange={(e) => setName(e.target.value)} />
<form onSubmit={(e) => { e.preventDefault(); save(); }}>

Mistakes: Forgetting preventDefault() on form submit (page reloads); calling the handler during render.

Conditional rendering, lists and keys

What: Show different UI by condition; render arrays with map.

Syntax:

{isLoggedIn ? <Dashboard /> : <Login />}
{error && <p>{error}</p>}
<ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>

Internally: Keys let reconciliation track each item across renders; the same key means the same component instance and its state.

Real-world: Loading, empty and error states; product grids.

Mistakes: Index as key in a changing list; {count && ...} rendering 0; missing key warnings.

Forms and controlled components

What: Inputs whose value comes from state.

Syntax:

const [form, setForm] = useState({ email: "", password: "" });
const handle = (e) => setForm({ ...form, [e.target.name]: e.target.value });
<input name="email" value={form.email} onChange={handle} />

Why: One source of truth makes validation and resets easy.

Mistakes: value without onChange (input becomes read-only); switching between undefined and a string (controlled/uncontrolled warning).

CSS styling and component composition

Options: Plain CSS files, CSS Modules (import s from "./a.module.css", scoped class names), Tailwind utilities, CSS-in-JS, inline style={{ color: "red" }} (camelCase object).

Composition: Pass JSX as children to build flexible layouts:

function Card({ title, children }) {
  return <div className="card"><h3>{title}</h3>{children}</div>;
}
<Card title="Profile"><Avatar /><Bio /></Card>

Mistakes: Global CSS class clashes; heavy inline styles; deep prop passing when composition would remove the need.

useEffect

What: Runs side effects after React updates the screen.

Why: Render must stay pure; fetching, subscriptions, timers and document title belong in effects.

Internally: After commit, React compares the dependency array with the last one and runs the effect only if something changed; cleanup runs before the next run and on unmount.

Syntax and use cases:

useEffect(() => { document.title = `Cart (${n})`; }, [n]);       // sync on change
useEffect(() => { fetchData(); }, []);                            // once on mount
useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);                                 // cleanup
}, []);

Mistakes: Missing dependencies; no cleanup (memory leaks); using an effect to derive state that can be computed during render; async function passed directly to useEffect (define it inside and call it).

useRef

What: A box { current } that persists across renders.

Why: Access DOM nodes or keep values (timer IDs, previous props) without re-rendering.

Syntax: const ref = useRef(null); <input ref={ref} />; ref.current.focus();

Mistakes: Expecting a re-render when ref.current changes; reading ref.current during render for DOM nodes (it is null on first render).

useContext and Context API

What: Shared data available to any descendant without passing props.

Why: Avoids prop drilling for theme, auth user, language.

Internally: The nearest Provider above supplies the value; when it changes, all components reading that context re-render.

Syntax: createContext(), then <Ctx.Provider value={...}>, then useContext(Ctx). See the full example in section 11.

Mistakes: One giant context for everything; creating a new object in value every render without memoising it; using Context as a replacement for server-state caching.

useReducer

What: State management through a pure reducer function plus dispatched actions.

Why: Cleaner than many useState calls when updates are related or complex (carts, multi-step forms).

Internally: dispatch(action) calls reducer(currentState, action), and the returned value becomes the new state.

Syntax: const [state, dispatch] = useReducer(reducer, initialState);

Mistakes: Mutating state inside the reducer; side effects (API calls) in the reducer; forgetting the default case.

Intermediate (continued)

React Router (dynamic, nested, protected routes)

What: Client-side routing: the URL decides which component renders, with no page reload.

Why: SPAs need multiple “pages” with shareable, bookmarkable URLs.

Internally: It listens to the History API, matches the path against route definitions, and renders the matching element; <Link> changes the URL without a request.

Syntax: <Route path="/users/:id" element={<User />} />, useParams(), useNavigate(), <Outlet /> for nested layouts, <Navigate to="/login" /> for redirects. Full example in section 11.

Real-world: Public pages, a protected dashboard, /products/:id detail pages.

Mistakes: Using <a href> (full reload); treating client-side guards as security; forgetting the server must serve index.html for every path.

API integration (Fetch, Axios), CRUD, loading and error handling

What: Talking to a backend over HTTP: GET (read), POST (create), PUT/PATCH (update), DELETE.

Why: Real apps show server data, not hard-coded arrays.

Syntax:

const res = await fetch("/api/employees", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(emp),
});
if (!res.ok) throw new Error("Failed");        // fetch does not throw on 404/500
const created = await res.json();
// Axios: const { data } = await api.post("/employees", emp);

Pattern: keep three states (data, loading, error), call APIs from a service layer, and update the list in state after create/update/delete. For larger apps use TanStack Query or RTK Query for caching.

Mistakes: No loading or error UI; not checking res.ok; fetching in render instead of an effect; no cleanup, causing race conditions.

Custom hooks and prop drilling

What: A custom hook is a function named useXxx that reuses stateful logic. Prop drilling is passing props through components that do not need them.

Why: Remove duplicated logic (useFetch, useDebounce, useLocalStorage) and keep components small.

Internally: Hooks are plain functions; each component calling the hook gets its own separate state.

Mistakes: Expecting two components to share state through a hook (use Context or a store); calling hooks conditionally; not prefixing with use.

State management and Redux Toolkit

What: Choosing where state lives. Local state (useState) first, lift state up when siblings need it, Context for low-frequency globals, Redux Toolkit or Zustand for large shared state, TanStack Query for server data.

Redux Toolkit: createSlice (state + reducers), configureStore, createAsyncThunk for API calls, useSelector/useDispatch. Data flows one way: dispatch action, reducer, new state, UI.

Real-world: Cart, auth user, filters shared across many pages.

Mistakes: Putting all state in Redux; mutating state outside slice reducers; storing derived data instead of computing it with selectors.

Form validation and React Hook Form

What: A library that manages form state with uncontrolled inputs.

Why: Fewer re-renders, less boilerplate, easy validation (built-in rules or Zod/Yup schemas via a resolver).

Syntax: const { register, handleSubmit, formState: { errors } } = useForm(); then <input {...register("email", { required: true })} />. Full example in section 11.

Mistakes: Validating only on the client (the server must validate too); not showing error messages; mixing controlled value with register.

Authentication, authorization and JWT

What: Authentication proves who you are; authorization decides what you can do. A JWT is a signed token (header.payload.signature) the server issues after login.

Flow: POST credentials, receive token, send Authorization: Bearer <token> on each request, server verifies the signature and expiry. Use a short-lived access token plus a refresh token in an HttpOnly cookie.

In React: an AuthContext holding the user, a login/logout function, a protected-route component, role checks to show or hide UI, and an Axios interceptor to attach the token and handle 401 responses.

Mistakes: Storing tokens in localStorage without understanding XSS risk; trusting the role from the client; putting secrets in the JWT payload (it is only encoded, not encrypted); not handling token expiry.

Advanced

Fiber, reconciliation and the rendering lifecycle

What: Reconciliation diffs the old and new element trees. Fiber is the engine that splits rendering into small, interruptible units with priorities.

Rules of diffing: different element type means rebuild the subtree; same type means update props; keys identify list items.

Lifecycle: render phase (pure, may be paused or repeated), commit phase (DOM updated, then layout effects, then effects). Mount, update and unmount map to useEffect setup and cleanup.

Mistakes: Side effects in render; changing a component’s key by accident (it remounts and loses state); assuming render means the DOM changed.

useMemo, useCallback, React.memo and performance

useMemo caches a calculated value; useCallback caches a function identity; React.memo skips re-rendering a component when props are shallow-equal. They work together: a memoised child only helps if the callbacks and objects passed to it are stable.

Other tools: list virtualisation (react-window), state colocation, debouncing, useTransition, Profiler to measure first.

Mistakes: Memoising everything (adds overhead); wrong dependency arrays; creating new objects or arrays inline as props to a memoised child.

Code splitting, lazy loading, Suspense, error boundaries

Why: Smaller first bundle, faster load, and resilience when one part crashes.

How: lazy(() => import("./Page")) inside <Suspense fallback={...}>; wrap sections in an error boundary class. Split per route first. See the code in section 11.

Mistakes: Expecting error boundaries to catch event-handler or async errors; one huge boundary at the root only; no Suspense fallback.

Concurrent rendering, SSR, hydration, Server Components, Next.js

Concurrent: React can pause low-priority renders; useTransition and useDeferredValue keep typing responsive while heavy lists update.

SSR and hydration: the server sends ready HTML (fast first paint, good SEO); the browser then hydrates it by attaching event handlers. Hydration mismatch errors happen when server and client output differ (for example Date.now() or window in render).

Server Components: run only on the server, ship no JS, and can read the database directly; add "use client" for interactivity.

Next.js: file-based routing, layouts, SSR/SSG/ISR, route handlers, image and font optimisation.

TypeScript, testing, accessibility, security

TypeScript: type props (type Props = {...}), state (useState<User | null>(null)) and events (React.ChangeEvent<HTMLInputElement>). Avoid any.

Testing: Jest or Vitest with React Testing Library; query by role and text, simulate users with userEvent, mock network with MSW. Test behaviour, not implementation.

Accessibility: semantic elements, alt text, labels for inputs, keyboard focus, colour contrast, ARIA only when native HTML is not enough.

Security: avoid dangerouslySetInnerHTML (or sanitise with DOMPurify), never put secrets in client env vars, validate on the server, set CSP headers, update dependencies, validate any URL you redirect to.

Production-level React

Architecture, patterns, services, config

Folders: feature-based (features/orders/{components,hooks,api,tests}) plus shared components, hooks, utils.

Patterns: container/presentational, compound components, custom hooks, render props, HOCs; prefer composition and hooks.

API layer: one configured Axios instance, typed service functions, centralised error handling.

Env variables: VITE_API_URL per environment (.env.development, .env.production); remember they are public in the bundle.

RBAC: role in the verified token, route guards and conditional UI, with real enforcement on the backend.

Errors, logging, monitoring, SEO, responsive UI

Error boundaries plus try/catch, a toast or error page for users, Sentry (or similar) for logs with source maps, Web Vitals and Lighthouse for performance monitoring. For SEO use SSR/SSG (Next.js), meta tags, semantic HTML and sitemaps. For responsive UI use mobile-first CSS, flexbox/grid and media queries.

Docker, CI/CD, AWS/Azure, production debugging

Docker: multi-stage build (Node builds, Nginx serves) as in section 11; add an Nginx rule sending all routes to index.html.

CI/CD: on every push run install, lint, test, build; on merge to main deploy. AWS: S3 + CloudFront for static apps, or ECS for containers. Azure: Static Web Apps or App Service.

Debugging: reproduce with the production build, check console and network, use source maps and Sentry stack traces, compare env variables, check recent deploys, and roll back first if users are affected.

14. How to Explain Each Topic to the Interviewer

Spoken scripts in first person. Formula for every answer: definition, why it exists, how it works, a quick example from a project, one trade-off or mistake you avoid. Say it in 30 to 60 seconds, then wait for follow-ups.

Beginner

React.js

“React is a JavaScript library for building user interfaces out of reusable components. Instead of manually updating the DOM, I describe the UI for a given state and React keeps the screen in sync. In my todo project, I just changed the todos array in state and the list updated itself.”

SPA vs MPA

“In an SPA the browser loads one HTML page and JavaScript swaps the views, so navigation is fast and state is preserved. An MPA asks the server for a new page each time. I’d choose an SPA for a dashboard, and SSR or an MPA when SEO and first load matter most, like a blog.”

Virtual DOM

“The Virtual DOM is a lightweight JavaScript representation of the UI. When state changes, React builds a new virtual tree, diffs it with the old one, and applies only the changes to the real DOM. The benefit is predictable, batched updates, not that it is magically faster than hand-written DOM code.”

JSX and components

“JSX is a syntax that lets me write markup inside JavaScript; it compiles to plain function calls that return element objects. A component is a function that returns JSX and starts with a capital letter. I split a page into small components like Navbar and ProductCard so they can be reused and tested separately.”

Props vs state

“Props are read-only inputs from the parent; state is data the component owns and can change. Changing state re-renders the component. I never mutate either. If two siblings need the same data, I lift the state up to their common parent.”

useState

“useState gives me a value and a setter. Calling the setter schedules a re-render. Updates are batched, so when the new value depends on the old one I use the functional form, like setCount(c => c + 1). For objects and arrays I create new copies instead of mutating.”

Events, conditional rendering, lists and keys

“I pass a function to handlers like onClick, not a function call. For conditions I use ternaries, && or early returns. For lists I use map and give each item a stable unique key, such as the database ID, so React can match items between renders. I avoid index keys when the list can change.”

Forms and controlled components

“In a controlled component the input’s value lives in React state, with value and onChange. That makes validation, resetting and conditional disabling simple. For big forms I switch to React Hook Form to avoid re-rendering on every keystroke.”

Styling and composition

“I use CSS Modules or Tailwind for scoped, maintainable styles. For layouts I rely on composition: components accept children, so a Card or Modal can wrap anything. This is more flexible than inheritance and avoids long prop chains.”

Intermediate

useEffect

“useEffect is for side effects: things that happen outside rendering, like fetching data, subscriptions or timers. The dependency array controls when it re-runs, and the returned function is cleanup. In my weather app I fetched in an effect keyed on the city and aborted the previous request in cleanup to prevent race conditions.”

useRef

“useRef returns a mutable object that survives renders without triggering one. I use it to focus an input, keep a timer ID, or store the previous value.”

Context and prop drilling

“Prop drilling is passing props through components that do not use them. Context lets me provide a value once and read it anywhere below with useContext. I use it for theme and the logged-in user. Because every consumer re-renders on change, I don’t use it for rapidly changing data; that goes to Redux Toolkit or Zustand.”

useReducer

“useReducer centralises state transitions in a pure reducer function. I prefer it over many useState calls when updates are related, like a cart with add, remove and update-quantity actions. It’s also easy to unit test.”

React Router

“React Router maps URLs to components on the client without reloading. I use dynamic params like /users/:id, nested routes with Outlet for shared layouts, and a wrapper route that redirects unauthenticated users. I mention that this guard is only UX, and the API enforces real permissions.”

API integration and CRUD

“I keep API calls in a service layer using an Axios instance, and in components I track data, loading and error states. After create, update or delete, I update local state or refetch. With fetch I check res.ok since it doesn’t throw on 404 or 500. For caching and retries in larger apps I use TanStack Query.”

Custom hooks

“A custom hook extracts reusable stateful logic into a function starting with use. For example useFetch(url) returns data, loading and error. Each component that calls it gets its own state; it shares logic, not data.”

Redux Toolkit and state management

“I start with local state, lift it up when needed, and use Context for light global values. For large shared state I use Redux Toolkit: slices define reducers (Immer lets me write simple update logic), thunks handle async calls, and selectors read data. Unidirectional data flow makes it easy to debug with Redux DevTools.”

React Hook Form

“It registers inputs as uncontrolled, so typing doesn’t re-render the whole form. I define rules inline or with a Zod schema, show errors from formState.errors, and always validate again on the server.”

Authentication, authorization, JWT

“Authentication verifies identity; authorization decides permissions. After login the server issues a signed JWT, I send it as a Bearer token with an Axios interceptor, and the server verifies it. I prefer short-lived access tokens with a refresh token in an HttpOnly cookie, because localStorage is exposed to XSS. UI role checks are convenience; the backend enforces access.”

Advanced

Fiber and reconciliation

“Reconciliation is how React diffs the old and new trees: different types rebuild the subtree, same type updates, and keys identify list items. Fiber is the engine that makes rendering incremental, so React can pause, resume and prioritise work, which enables concurrent features.”

Rendering lifecycle

“There are two phases. The render phase is pure and computes what the UI should be; it can be paused or repeated. The commit phase applies changes to the DOM and runs layout effects and effects. That’s why I never put side effects in the render body.”

useMemo, useCallback, React.memo

“useMemo caches a computed value, useCallback caches a function reference, and React.memo skips re-rendering when props are unchanged. They need to work together, because a memoised child still re-renders if I pass it a new function each time. I profile first and only add them where there’s a measurable problem.”

Performance optimisation

“I measure with the React Profiler, then fix the actual bottleneck: colocate state, memoise expensive children, virtualise long lists, code-split routes, lazy-load images, debounce search inputs, and use useTransition for heavy updates.”

Code splitting, lazy loading, Suspense

“I use React.lazy with dynamic import() so a route’s code loads only when needed, wrapped in Suspense with a fallback. This cuts the initial bundle and speeds up first load.”

Error boundaries

“An error boundary is a class component that catches rendering errors in its children and shows a fallback UI, and logs to a service like Sentry. It doesn’t catch event-handler or async errors, so I still use try/catch there.”

Concurrent rendering

“React can interrupt low-priority rendering to keep urgent updates responsive. I use useTransition or useDeferredValue so typing stays smooth while a large filtered list updates in the background.”

SSR, hydration, Server Components, Next.js

“With SSR the server sends rendered HTML for fast first paint and SEO, and hydration attaches event handlers in the browser. Server Components run only on the server, send no JavaScript for themselves and can access data directly; interactive parts are client components. Next.js provides routing, SSR/SSG/ISR and these features out of the box.”

TypeScript, testing, accessibility, security

“TypeScript catches prop and state errors early. For tests I use Jest or Vitest with Testing Library and query by role like a user would. For accessibility I use semantic HTML, labels and keyboard support. For security I avoid dangerouslySetInnerHTML, keep secrets off the client, validate on the server and keep dependencies updated.”

Production

Folder structure and reusable architecture

“I organise by feature, each with its own components, hooks, API calls and tests, plus shared UI components and utilities. That keeps changes local and lets multiple developers work without conflicts. Components have small, clear prop APIs, and logic lives in hooks.”

API layer, environment variables, role-based access

“All HTTP goes through one configured Axios instance with interceptors for tokens and error handling. Config comes from environment variables, remembering that anything in the client bundle is public. For role-based access I use route guards and conditional UI, with the backend as the real authority.”

Logging, monitoring, SEO, responsive UI

“I use error boundaries plus Sentry with source maps, and track Web Vitals. For SEO on public pages I use SSR or SSG with proper meta tags. The UI is mobile-first with flexbox and grid.”

Docker, CI/CD, cloud deployment

“I build with a multi-stage Dockerfile and serve static files through Nginx with a fallback to index.html. The CI pipeline runs lint, tests and build on every push, and deploys on merge to main, for example to S3 + CloudFront on AWS or Static Web Apps on Azure.”

Production debugging

“First I check whether users are affected and roll back if so. Then I reproduce with the production build, read the console and network tab, check Sentry stack traces with source maps, and compare environment variables and the last deploy. After the fix I add a test or monitoring so it can’t silently happen again.”

1. What is it? React is just JavaScript. If your JS basics are weak, React feels hard. These 7 things appear in almost every React file.

2. Why do we use it? React code uses arrow functions, destructuring, map and modules constantly. (Hinglish: JS strong hai to React aasaan lagta hai.)

3. How it works internally: Nothing special: React components are normal functions, and props are normal objects. Browsers run the JS; the bundler (Vite) joins your files.

4 and 5. Syntax and examples, line by line:

// 1) let / const
const city = "Bengaluru";      // const: cannot be reassigned (use by default)
let age = 20;                  // let: can be reassigned
age = 21;

// 2) Arrow functions + template strings
const greet = (name) => `Hello, ${name}!`;   // ${} puts a variable inside text
console.log(greet("Riya"));

// 3) Objects and destructuring
const user = { name: "Aman", age: 25 };
const { name, age: userAge } = user;           // pull values out by key
console.log(name, userAge);

// 4) Arrays and destructuring (useState uses this!)
const [first, second] = ["a", "b"];
console.log(first, second);

// 5) Spread operator: copy and update without changing the original
const updated = { ...user, age: 26 };
const more = [...[1, 2], 3];
console.log(updated, more, user.age);

// 6) map and filter (rendering lists in React)
const nums = [1, 2, 3, 4];
console.log(nums.map(n => n * 2));            // transform every item
console.log(nums.filter(n => n % 2 === 0));   // keep matching items

// 7) Modules: split code across files
// math.js:   export const add = (a, b) => a + b;   export default function sub(a, b) { return a - b; }
// app.js:    import sub, { add } from "./math.js";

Expected output: Hello, Riya!, then Aman 25, then a b, then { name: 'Aman', age: 26 } [ 1, 2, 3 ] 25, then [ 2, 4, 6, 8 ], then [ 2, 4 ].

Bonus: async/await (needed for API calls):

async function getUser() {
  const res = await fetch("https://jsonplaceholder.typicode.com/users/1");  // wait for response
  const data = await res.json();                                            // wait for JSON
  console.log(data.name);
}
getUser();

Expected output: Leanne Graham

6. Real-world example: Rendering a product list is products.map(...); updating a cart item is { ...item, qty: item.qty + 1 }; reading props is destructuring.

7. Common mistakes: Using var; mutating arrays/objects instead of copying with spread; forgetting await (you get a Promise, not data); confusing =, == and === (use ===).

8. Interview questions:

var vs let vs const? var is function-scoped and hoisted with undefined; let and const are block-scoped; const cannot be reassigned (but an object it holds can still be mutated).

What does the spread operator do? It expands an array or object into another, used to copy and update immutably.

Output? console.log([1,2,3].map(n => n * 2)) prints [2, 4, 6] and does not change the original array.

Topic 2: React introduction

1. What: A JavaScript library for building UIs using components.

2. Why: With plain JS you write “find element, change text, change class” for every update. In React you write what the screen should look like for the current data, and React updates the page.

// Plain JS: you manage the DOM yourself
document.getElementById("count").textContent = count;

// React: you manage data; the screen follows
<p>{count}</p>

3. Internally: Data changes, then React re-runs the component, builds a Virtual DOM tree, diffs it against the previous tree, and updates only the changed real DOM nodes.

6. Real-world: Facebook, Instagram, Netflix, Airbnb use React for dynamic parts of their UIs.

7. Mistakes: Calling it a framework; thinking you must learn Redux or Next.js first.

8. Interview: Library vs framework? A library does one job (UI) and you choose the rest; a framework (like Angular) provides routing, forms, HTTP and structure. Declarative vs imperative? Declarative says what the result should be; imperative lists the steps.

Topic 3: Installation with Vite

Requirements: Node.js 18 or newer (check with node -v) and a code editor like VS Code.

npm create vite@latest my-app -- --template react   # make the project
cd my-app                                            # go inside
npm install                                          # download dependencies
npm run dev                                          # start the dev server

Expected output: the terminal shows Local: http://localhost:5173/. Open it to see the Vite + React page with a counter button.

Project structure:

my-app/
  index.html        # the only HTML page, has <div id="root"></div>
  package.json      # project name, scripts, dependencies
  vite.config.js    # Vite settings
  public/           # static files served as-is
  src/
    main.jsx        # entry: connects React to #root
    App.jsx         # your root component
    App.css, index.css
    assets/         # images used inside components

Mistakes: Running commands outside the project folder; Node too old; editing node_modules; naming files with JSX as .js.

Interview: Why Vite over Create React App? Vite starts instantly using native ES modules and builds with Rollup; CRA is deprecated and slow. What does npm run build do? Creates an optimised production bundle in dist/.

Topic 4: Your first React application

Open src/main.jsx and read it:

import { StrictMode } from "react";            // helper that finds bugs in development
import { createRoot } from "react-dom/client"; // connects React to the browser DOM
import App from "./App.jsx";                   // your root component
import "./index.css";

createRoot(document.getElementById("root")).render(  // find <div id="root"> and render inside it
  <StrictMode>
    <App />
  </StrictMode>
);

Now replace everything in src/App.jsx with:

import { useState } from "react";

function Welcome({ name }) {                 // component: capital letter, receives props
  return <h2>Welcome, {name}!</h2>;        // {name} inserts the prop value
}

export default function App() {            // root component
  const [count, setCount] = useState(0);   // state: starts at 0

  return (
    <div>                                   {/* one parent element */}
      <h1>My First React App</h1>
      <Welcome name="Riya" />                {/* reuse with different props */}
      <Welcome name="Aman" />
      <p>You clicked {count} times</p>
      <button onClick={() => setCount(count + 1)}>Click me</button>
    </div>
  );
}

Expected output: a heading “My First React App”, “Welcome, Riya!”, “Welcome, Aman!”, the text “You clicked 0 times”, and a button. Each click raises the number by 1 without a page reload.

What happened when you clicked: setCount told React the state changed, then React called App() again with count = 1, built a new virtual tree, saw only the paragraph text differed, and updated just that text in the DOM.

Mistakes: Lowercase component name; two root elements without a wrapper or <></>; onClick={setCount(count + 1)} (runs immediately and loops); forgetting to import useState.

17. Common Problems and Fixes, With Code

Each item shows the bug, the fix and the reason. Tap to open. Class-component problems are in section 2, under “Class components vs functional components”.

  • Too many re-renders (infinite loop)
    // BAD: setState during render
function A() { const [n, setN] = useState(0); setN(n + 1); return n; }
// BAD: calling the handler instead of passing it
<button onClick={setN(n + 1)}>+</button>
// GOOD
<button onClick={() => setN(n + 1)}>+</button>

    Why: setting state in render triggers another render forever.

  • State not updating (mutation)
    // BAD: same reference, React sees no change
items.push(x); setItems(items);
user.name = "A"; setUser(user);
// GOOD
setItems([...items, x]);
setUser({ ...user, name: "A" });
  • New state not visible right after setState
    setCount(count + 1);
console.log(count);        // old value: state updates on the next render
// GOOD
useEffect(() => { console.log(count); }, [count]);
setCount(c => c + 1);      // when depending on the previous value
  • Stale closure (old value inside setInterval or handler)
    // BAD: count is always 0 inside the interval
useEffect(() => { const id = setInterval(() => setCount(count + 1), 1000); return () => clearInterval(id); }, []);
// GOOD: functional update, no dependency needed
useEffect(() => { const id = setInterval(() => setCount(c => c + 1), 1000); return () => clearInterval(id); }, []);
  • useEffect infinite loop or running too often
    // BAD: new object each render, effect runs every time
const opts = { page };
useEffect(() => { load(opts); }, [opts]);
// BAD: setting the same state the effect depends on, without a guard
useEffect(() => { setData(fetchData()); }, [data]);
// GOOD: depend on primitives, or memoise
useEffect(() => { load({ page }); }, [page]);
  • async function passed to useEffect
    // BAD: effect must return a cleanup function or nothing, not a Promise
useEffect(async () => { await load(); }, []);
// GOOD
useEffect(() => { const run = async () => { await load(); }; run(); }, []);
  • Race condition and memory leak in fetch
    // GOOD: abort the previous request on change or unmount
useEffect(() => {
  const c = new AbortController();
  fetch(`/api/items?q=${q}`, { signal: c.signal }).then(r => r.json()).then(setItems).catch(e => { if (e.name !== "AbortError") setError(e); });
  return () => c.abort();
}, [q]);
  • Hooks called conditionally
    // BAD: "Rendered fewer hooks than expected"
if (!user) return null;
const [open, setOpen] = useState(false);
// GOOD: hooks first, conditions after
const [open, setOpen] = useState(false);
if (!user) return null;
  • Missing key warning and wrong index keys
    // BAD: index keys break when items are removed or reordered (inputs keep wrong values)
items.map((it, i) => <Row key={i} item={it} />)
// GOOD
items.map(it => <Row key={it.id} item={it} />)
  • Controlled vs uncontrolled input warning
    // BAD: starts undefined, later a string
const [name, setName] = useState();
<input value={name} onChange={e => setName(e.target.value)} />
// BAD: value without onChange makes the input read-only
// GOOD
const [name, setName] = useState("");
  • Page reloads on form submit
    const submit = (e) => { e.preventDefault(); save(form); };
<form onSubmit={submit}>...</form>
  • 0 appears on screen with &&
    {items.length && <List items={items} />}        // BAD: renders 0
{items.length > 0 && <List items={items} />}    // GOOD
  • Component defined inside another component (state resets)
    // BAD: Inner is a new component type every render, so it remounts and loses state
function Outer() { const Inner = () => <input />; return <Inner />; }
// GOOD: define at module level
const Inner = () => <input />;
function Outer() { return <Inner />; }
  • React.memo not preventing re-renders
    // BAD: new object and function each render
<Child style={{ color: "red" }} onSave={() => save()} />
// GOOD
const style = useMemo(() => ({ color: "red" }), []);
const onSave = useCallback(() => save(), []);
<Child style={style} onSave={onSave} />
  • useRef change does not update the screen
    const r = useRef(0); r.current++;        // no re-render, UI stays the same
// If the UI must change, use state
const [n, setN] = useState(0);
  • Context makes everything re-render
    // BAD: new value object every render
<Ctx.Provider value={{ user, setUser }}>
// GOOD: memoise, and split rarely-changing and often-changing contexts
const value = useMemo(() => ({ user, setUser }), [user]);
  • Router: 404 on refresh, useNavigate in render
    // Nginx: send all routes to index.html
location / { try_files $uri /index.html; }
// BAD: navigating during render
if (!user) navigate("/login");
// GOOD
if (!user) return <Navigate to="/login" replace />;
// or inside useEffect / an event handler
  • CORS error when calling the API
    # FastAPI
app.add_middleware(CORSMiddleware, allow_origins=["http://localhost:5173"], allow_methods=["*"], allow_headers=["*"])
// Vite dev proxy (vite.config.js)
server: { proxy: { "/api": "http://localhost:8000" } }

    Why: CORS is enforced by the browser; fix it on the server or use a proxy in development.

  • Redux: mutating state or selecting too much
    // Inside createSlice, mutation is fine (Immer). Outside, it is not.
const state = store.getState(); state.cart.items.push(x);   // BAD
// BAD: re-renders on any store change
const all = useSelector(s => s);
// GOOD
const items = useSelector(s => s.cart.items);
  • JWT: 401 loop or expired token
    api.interceptors.response.use(r => r, async (err) => {
  const original = err.config;
  if (err.response?.status === 401 && !original._retry) {
    original._retry = true;                         // retry only once
    const { data } = await api.post("/auth/refresh");
    localStorage.setItem("token", data.token);
    original.headers.Authorization = `Bearer ${data.token}`;
    return api(original);
  }
  return Promise.reject(err);
});
  • Hydration mismatch (Next.js / SSR)
    // BAD: differs between server and client
return <p>{new Date().toLocaleTimeString()}</p>;
// GOOD: render the same first, then update on the client
const [time, setTime] = useState(null);
useEffect(() => setTime(new Date().toLocaleTimeString()), []);
return <p>{time ?? ""}</p>;
  • Env variable is undefined in Vite
    # must start with VITE_ and the dev server must be restarted
VITE_API_URL=http://localhost:8000
const url = import.meta.env.VITE_API_URL;   // not process.env in Vite
