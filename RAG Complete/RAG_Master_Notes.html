PART 1 — FOUNDATIONS

1.1 What is RAG?

📌 Definition Retrieval-Augmented Generation (RAG) is an AI architecture that makes a Large Language Model (LLM) smarter by giving it extra, relevant information at the exact moment it needs to answer a question — instead of relying only on what it memorized during training.

Simple analogy: Imagine a brilliant student who studied a huge amount of material years ago (the LLM's training). Now you ask them a question about something that happened yesterday, or about your company's private internal policy. The student doesn't know it — because they never studied it.

Now imagine you hand that same student a small, relevant note right before they answer — "here's the page from the policy document that talks about this." Suddenly they can answer correctly. That note is the retrieved context, and the whole process is RAG.

User Query │ ▼ Retrieve Relevant Documents ──► External Knowledge Base │ ▼ Combine Query + Retrieved Context │ ▼ Send to LLM │ ▼ Grounded, Accurate Answer

1.2 Why Do We Need RAG? (The Three Core Problems)

To understand RAG deeply, you must first understand why a plain LLM is not enough. There are three major problems with using an LLM "as-is."

Problem 1: Knowledge Cutoff

Every LLM is trained on data up to a certain date — called the knowledge cutoff. Anything that happened after that date is invisible to the model. Ask a raw open-source LLM "What's the biggest news today?" and it simply cannot know.

Problem 2: Private / Internal Data

LLMs are trained on public internet-scale data. They have never seen your company's internal wiki, your private course videos, your customer database, or your personal notes. No matter how well you phrase your prompt, the model cannot answer questions about data it never saw.

Problem 3: Hallucination

⚠️ What is Hallucination? Hallucination is when an LLM generates text that sounds confident and fluent but is factually wrong. This happens because LLMs are fundamentally probabilistic next-word predictors — they predict the most statistically likely next token, not necessarily the "true" one.

Example: An LLM might confidently state "Einstein played football for Germany," which is completely false — but it sounds plausible enough that the model generates it anyway.

1.3 The Traditional Alternative: Fine-Tuning (and Why It's Not Enough Alone)

Before RAG became popular, the standard way to inject new knowledge into a model was fine-tuning — taking a pre-trained LLM and training it further on a smaller, domain-specific dataset.

🎓 Real-World Analogy

Think of pre-training as getting an engineering degree (broad, general knowledge). Fine-tuning is like a company's 2–3 month onboarding program — it teaches job-specific skills on top of that general foundation.

🔧 Types of Fine-Tuning

  • Supervised Fine-Tuning (SFT) — trains on labeled prompt→answer pairs
  • Continued Pre-training — unsupervised, feeds raw domain text
  • RLHF — reinforcement learning from human feedback
  • LoRA / QLoRA — parameter-efficient fine-tuning

Why Fine-Tuning Alone Falls Short

LimitationExplanation
Computational CostTraining large models requires expensive GPU clusters
Technical ExpertiseRequires skilled ML engineers to design and run training
Frequent Updates ProblemEvery time data changes, you must retrain — slow and costly
Hard to "Forget"Removing outdated or wrong information from a fine-tuned model is very difficult
🧠 Key Insight Fine-tuning is great for teaching a model a new style, tone, or skill pattern. It is a poor fit for knowledge that changes often. RAG, on the other hand, updates instantly — you just add a new document to the index, no retraining required.

1.4 In-Context Learning: The Bridge to RAG

📖 Definition In-Context Learning (ICL) is the ability of large language models to learn how to perform a task simply by seeing examples or information inside the prompt itself — without updating any model weights.

This is an emergent property — a capability that wasn't explicitly programmed, but appeared naturally once models grew large enough (first clearly observed with GPT-3's 175 billion parameters, described in the landmark paper "Language Models are Few-Shot Learners").

Example: Few-Shot Sentiment Classification

"I love this phone. It's so smooth."     → Positive
"This app crashes a lot."                → Negative
"The camera is amazing."                 → Positive
"I hate the battery life."               → ?

The model sees the pattern from examples and correctly predicts Negative — without any training step. This is "Few-Shot Prompting," a practical implementation of in-context learning.

Now take this one step further: instead of giving a few labeled examples, what if you gave the model all the relevant information it needs, directly in the prompt? That is exactly the idea behind RAG — we retrieve relevant text and inject it as context so the model can use in-context learning to produce a grounded answer.

1.7 Semantic Search vs. Lexical Search

🔤 Lexical (Sparse) Search

Matches based on exact keywords. Classic algorithm: BM25 (an improvement over TF-IDF). Fast, interpretable, great for exact terms like product codes or names — but fails on synonyms ("car" vs "automobile").

🧠 Semantic (Dense) Search

Matches based on meaning, using embeddings. Understands that "I'm broke" and "I have no money" are similar. Requires an embedding model and a vector index. Can occasionally miss exact keyword matches.
💡 Best Practice In production, combine both using Hybrid Search (sparse + dense), merged using a technique like Reciprocal Rank Fusion (RRF). This is covered in depth in Part 4.

1.9 Similarity Search & Distance Metrics

Once everything is turned into vectors, how do we measure "closeness"? Three core metrics:

Cosine Similarity

Measures the angle between two vectors, ignoring their magnitude. Range: -1 to 1 (1 = identical direction/meaning). This is the most common metric for text embeddings.

cosine_similarity(A, B) = (A · B) / (||A|| × ||B||)

Euclidean Distance (L2)

Measures the straight-line distance between two points in vector space. Smaller = more similar. Sensitive to vector magnitude (not just direction).

euclidean(A, B) = sqrt(Σ(A_i - B_i)²)

Dot Product

Multiplies corresponding vector components and sums them. If vectors are normalized (unit length), dot product gives the same ranking as cosine similarity — and is computationally cheaper.

dot_product(A, B) = Σ(A_i × B_i)
MetricRangeWhen to Use
Cosine Similarity[-1, 1]Normalized embeddings — most common choice for text
Dot ProductUnboundedWhen vectors are already L2-normalized (≈ cosine, but faster)
Euclidean (L2)[0, ∞)Un-normalized vectors, sensitive to magnitude
❌ Common Mistake Mixing similarity metrics between indexing and querying — e.g., building your vector index with cosine similarity but querying with raw Euclidean distance. Always keep the metric consistent across your pipeline.

1.10 Embeddings — The Core Building Block

📌 What Are Embeddings? Embeddings are dense numeric vector representations of text that capture semantic meaning. Texts with similar meaning end up with vectors that are close together in vector space. 
"cat"    → [0.21, 0.85, 0.11, ...]
"kitten" → [0.30, 0.79, 0.18, ...]   ← very close to "cat"!
"car"    → [0.91, 0.10, 0.83, ...]   ← far away

Embeddings are generated by passing text through a transformer encoder. The output is typically a mean-pooled or [CLS]-token vector representing the entire input.

🧠 Memory Trick "Embeddings turn meaning into math." Once meaning becomes numbers, you can measure how close two pieces of text are using simple arithmetic (cosine similarity, dot product, etc.).

1.11 Chunking — Why We Split Documents

We never feed an entire huge document into a vector database as one giant blob. Instead, we split ("chunk") it into smaller, semantically meaningful pieces. Two reasons:

  1. LLM context length limits — you cannot fit a 500-page document into a single prompt.
  2. Semantic search quality — embedding an entire document blurs its meaning into one vague vector; embedding small, focused chunks gives much more precise retrieval.
💡 Rule of Thumb Start with chunk sizes of 256–512 tokens with ~10–15% overlap between chunks. We go deep into chunking strategies (fixed-size, recursive, semantic, parent-child, sliding window) in Part 2.

1.12 Metadata

Metadata is extra structured information attached to each chunk — such as source_url, page_number, document_title, author, date, and chunk_index. Metadata enables:

  • Filtered retrieval — e.g., "only search documents from the Legal department"
  • Citations — showing the user exactly where an answer came from
  • Freshness control — filtering out outdated documents

1.13 Indexing

Indexing is the offline process of preparing your external knowledge base so it can be searched efficiently at query time. It involves: loading documents → cleaning → chunking → embedding → storing in a vector database with an Approximate Nearest Neighbor (ANN) index (like HNSW) built on top for fast search.

1.14 Retriever & Generator

🔍 Retriever

The component responsible for taking a user query, embedding it, and searching the vector store to find the most relevant chunks. It can use simple similarity search or advanced techniques like hybrid search, MMR, or re-ranking.

✍️ Generator

The LLM itself. It receives the augmented prompt (query + retrieved context) and produces the final natural-language answer, combining its own parametric knowledge with the externally provided context.

1.15 Vector Store

A specialized database optimized for storing and searching high-dimensional vectors using ANN algorithms. Stores: the embedding vector, the original text chunk, and metadata. Popular options: FAISS, ChromaDB, Pinecone, Weaviate, Qdrant, Milvus (deep dive in Part 6).

1.16 Context Injection & Prompt Construction

This is the "Augmentation" step — combining the retrieved chunks with the user's query into a single, well-structured prompt that explicitly instructs the LLM how to behave.

System: You are a helpful assistant. Answer the user's question
based ONLY on the provided context. If the answer is not in the
context, say "I don't know." Do not fabricate information.

Context:
[CHUNK 1] (Source: policy.pdf, page 3)
{chunk_1_text}

[CHUNK 2] (Source: policy.pdf, page 7)
{chunk_2_text}

User Question: {user_query}

Answer (with source citations):
⚠️ Why This Instruction Matters Without an explicit grounding instruction, the LLM may blend the retrieved context with its own (possibly outdated or wrong) parametric knowledge, defeating the purpose of RAG.

Complete Code

"""
simple_rag.py
A minimal end-to-end RAG pipeline: load → chunk → embed → store → retrieve → generate
"""

import os
from langchain_community.document_loaders import TextLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_community.vectorstores import Chroma
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain.chains import RetrievalQA

# 1. Set your API key (use environment variables in production!)
os.environ["OPENAI_API_KEY"] = "your-api-key-here"

# 2. Load the document
loader = TextLoader("data/sample.txt")
documents = loader.load()

# 3. Split into chunks
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,      # ~500 characters per chunk
    chunk_overlap=50,    # 50 character overlap to avoid losing context at boundaries
)
chunks = text_splitter.split_documents(documents)
print(f"Created {len(chunks)} chunks")

# 4. Embed and store in a vector database (Chroma, local and free)
embedding_model = OpenAIEmbeddings(model="text-embedding-3-small")
vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=embedding_model,
    persist_directory="./chroma_db"
)

# 5. Build the RAG chain (retriever + LLM)
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    retriever=vectorstore.as_retriever(search_kwargs={"k": 3}),
    return_source_documents=True
)

# 6. Ask a question
query = "What is the main topic of this document?"
result = qa_chain.invoke({"query": query})

print("Answer:", result["result"])
print("\nSources used:")
for doc in result["source_documents"]:
    print("-", doc.metadata)

2.1 Document Loader

📌 What is it? A Document Loader reads raw source files (PDF, DOCX, HTML, CSV, Markdown, databases, APIs) and converts them into a standard in-memory format the rest of the pipeline can use — usually a list of Document objects, each holding page_content (text) and metadata (source, page number, etc.).

Why do we need it?

Your knowledge doesn't live in one clean format. Some of it is PDFs, some is HTML pages, some is rows in a database. A document loader normalizes all these into one consistent structure so chunking and embedding can work the same way regardless of source.

Python Implementation — Multi-Format Loader (Intermediate)

from langchain_community.document_loaders import (
    PyPDFLoader, Docx2txtLoader, WebBaseLoader, CSVLoader
)
from pathlib import Path

def load_any(file_path: str):
    """Route to the correct loader based on file extension."""
    ext = Path(file_path).suffix.lower()
    loaders = {
        ".pdf": PyPDFLoader,
        ".docx": Docx2txtLoader,
        ".csv": CSVLoader,
    }
    if ext in loaders:
        return loaders[ext](file_path).load()
    elif file_path.startswith("http"):
        return WebBaseLoader(file_path).load()
    else:
        raise ValueError(f"Unsupported file type: {ext}")

docs = load_any("data/handbook.pdf")
print(f"Loaded {len(docs)} documents")
❌ Common Mistakes
  • Forgetting that PDF loaders often split per page, not per logical section — leading to documents that arbitrarily cut off mid-sentence.
  • Not checking metadata after loading — losing the ability to cite sources later.
  • Ignoring encoding issues (especially with scanned PDFs — see OCR note below).
💡 Tip For scanned PDFs (images, no extractable text), use OCR tools like pytesseract or Unstructured.io with OCR mode enabled — a plain PDF loader will return empty text.

2.2 Data Cleaning

📌 What is it? Data cleaning removes noise from raw extracted text — boilerplate, navigation menus, headers/footers, broken whitespace, encoding artifacts — before chunking. Dirty input text directly degrades retrieval quality.

Common Cleaning Steps

  • Strip HTML tags and scripts
  • Normalize whitespace (multiple spaces/newlines → single)
  • Remove repeated headers/footers (common in PDFs)
  • Fix encoding issues (e.g., mojibake from bad UTF-8 handling)
  • Extract and preserve useful metadata (title, date, author) before discarding boilerplate

Python Implementation

import re

def clean_text(text: str) -> str:
    # Remove excessive whitespace and newlines
    text = re.sub(r"\s+", " ", text)
    # Remove common PDF page artifacts like "Page 3 of 20"
    text = re.sub(r"Page \d+ of \d+", "", text)
    # Strip leading/trailing whitespace
    return text.strip()

raw = "This   is\n\n\na messy   document.   Page 3 of 20"
print(clean_text(raw))
# Output: "This is a messy document."
⚠️ Best Practice Clean text before chunking, not after — cleaning after chunking can break sentence boundaries that chunking already respected.

Python Implementation — Parent-Child (Hierarchical) Chunking (Production-Level)

from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore
from langchain_community.vectorstores import Chroma
from langchain_openai import OpenAIEmbeddings
from langchain.text_splitter import RecursiveCharacterTextSplitter

# Small chunks used for precise retrieval
child_splitter = RecursiveCharacterTextSplitter(chunk_size=200, chunk_overlap=20)
# Large chunks returned to the LLM for full context
parent_splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=100)

vectorstore = Chroma(
    collection_name="parent_child",
    embedding_function=OpenAIEmbeddings(model="text-embedding-3-small")
)
docstore = InMemoryStore()   # stores the full parent documents

retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=docstore,
    child_splitter=child_splitter,
    parent_splitter=parent_splitter,
)

retriever.add_documents(documents)   # documents loaded earlier

results = retriever.invoke("What is the refund policy?")
print(results[0].page_content)   # returns the FULL parent chunk, not just the small matched piece

2.5 Embedding Models

Already introduced in Part 1 — here we go deeper into model choice.

How Embeddings Work Internally

A transformer encoder passes tokenized text through multiple attention layers, producing a contextual representation per token. These token vectors are then combined (mean-pooling, or using a special [CLS] token) into one sentence/chunk embedding.

Bi-Encoder

Encodes query and document separately. Fast — document embeddings can be pre-computed. Used for the initial retrieval step. Slightly less accurate than cross-encoders.

Cross-Encoder

Encodes query + document together, jointly attending over both. Much more accurate but cannot be pre-computed — O(k) cost at query time. Used for re-ranking (Part 4).

    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

💡 Choosing an Embedding Model Higher dimensions generally mean better accuracy but slower search and more storage. Match the domain (medical, legal, general). Always benchmark on your own data using metrics like nDCG@10 before committing — public leaderboards (MTEB) are a good starting filter, not a guarantee for your use case.

from langchain_community.document_loaders import PyPDFLoader, TextLoader
from pathlib import Path

def ingest_document(file_path: str):
    """Load a single document based on its extension."""
    ext = Path(file_path).suffix.lower()
    if ext == ".pdf":
        loader = PyPDFLoader(file_path)
    elif ext == ".txt":
        loader = TextLoader(file_path)
    else:
        raise ValueError(f"Unsupported file type: {ext}")
    return loader.load()

def ingest_folder(folder_path: str):
    """Load every supported file inside a folder."""
    all_docs = []
    for file in Path(folder_path).glob("*"):
        if file.suffix.lower() in (".pdf", ".txt"):
            all_docs.extend(ingest_document(str(file)))
    return all_docs

from src.chunking import chunk_documents

from src.vector_store import build_vector_store, load_vector_store

from src.generator import generate_answer
import os

class RAGPipeline:
    def __init__(self, data_folder="data/raw", persist_dir="./chroma_db"):
        self.data_folder = data_folder
        self.persist_dir = persist_dir
        self.embedding_model = get_embedding_model()
        self.vectorstore = None

    def build_index(self):
        """Run once (offline) to build the knowledge base."""
        raw_docs = ingest_folder(self.data_folder)
        cleaned = clean_documents(raw_docs)
        chunks = chunk_documents(cleaned)
        self.vectorstore = build_vector_store(chunks, self.embedding_model, self.persist_dir)
        print(f"Indexed {len(chunks)} chunks from {len(raw_docs)} pages.")

    def load_index(self):
        """Load an already-built index (skip re-indexing)."""
        self.vectorstore = load_vector_store(self.embedding_model, self.persist_dir)

    def ask(self, query: str, k_retrieve=10, k_final=3):
        """Run the full online inference pipeline."""
        retriever = get_retriever(self.vectorstore, k=k_retrieve)
        candidates = retriever.invoke(query)
        top_chunks = rerank(query, candidates, top_n=k_final)
        prompt = build_prompt(query, top_chunks)
        answer = generate_answer(prompt)
        return {
            "answer": answer,
            "sources": [c.metadata for c in top_chunks]
        }

Python Implementation — HyDE (Hypothetical Document Embeddings)

from langchain_openai import ChatOpenAI, OpenAIEmbeddings

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.3)
embedder = OpenAIEmbeddings(model="text-embedding-3-small")

def hyde_retrieve(query: str, vectorstore, k=5):
    # Step 1: generate a hypothetical answer
    hypothetical = llm.invoke(
        f"Write a short, plausible passage that could answer this question:\n{query}"
    ).content

    # Step 2: embed the hypothetical answer, not the raw query
    hyde_vector = embedder.embed_query(hypothetical)

    # Step 3: search using that vector
    return vectorstore.similarity_search_by_vector(hyde_vector, k=k)
💡 Why HyDE Works A hypothetical answer is often written in the same style/vocabulary as real documents in your corpus (since the LLM is mimicking expected document style), so it embeds closer to relevant chunks than a short, differently-phrased user question would.

4.2 Hybrid Search (Sparse + Dense)

📌 Why Hybrid? Dense (semantic) retrieval handles meaning and synonyms but can miss exact keyword/code/number matches. Sparse (BM25) retrieval is great at exact terms but misses paraphrases. Hybrid search combines both — this is the recommended production default.

BM25 — How It Works

BM25 (Best Match 25) scores documents using three factors: term frequency (TF), inverse document frequency (IDF), and document length normalization. Key parameters: k1 (term saturation, typically 1.2–2.0) and b (length normalization, typically 0.75).

Python Implementation — Hybrid Search with Reciprocal Rank Fusion (RRF)

def reciprocal_rank_fusion(ranked_lists: list[list[str]], k: int = 60) -> list[str]:
    """
    ranked_lists: a list of ranked document-id lists, one per retrieval method
    Returns a single fused ranking.
    """
    scores = {}
    for ranked_list in ranked_lists:
        for rank, doc_id in enumerate(ranked_list):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)
    return sorted(scores.keys(), key=lambda d: scores[d], reverse=True)

# Example: combine BM25 ranking and dense vector ranking
bm25_ranking = ["doc3", "doc1", "doc5", "doc2"]
dense_ranking  = ["doc1", "doc2", "doc4", "doc3"]

fused = reciprocal_rank_fusion([bm25_ranking, dense_ranking])
print(fused)
# doc1 ranks well in both lists -> rises to the top of the fused ranking
💡 Why RRF Over Weighted Score Combination BM25 scores and cosine similarity scores live on completely different, incompatible scales. RRF sidesteps this by using only rank position, not raw score values — no normalization or tuning of weight hyperparameters required, and it's empirically very competitive.

4.3 Maximum Marginal Relevance (MMR)

📌 What is it? MMR balances relevance with diversity. Plain top-K similarity search can return 5 chunks that are all near-duplicates of each other (all about the same sub-topic), wasting context window. MMR penalizes redundancy and rewards covering different angles of the query. 
MMR = λ × Similarity(query, doc) − (1 − λ) × max(Similarity(doc, already_selected))

4.6 Multi-Hop Retrieval

📌 What is it? For questions that require chaining facts from multiple different documents, a single retrieval pass isn't enough. Multi-hop retrieval iterates: retrieve → reason → retrieve again, using insights from the first pass to inform the next query.

Python Implementation — Simple Iterative Multi-Hop Loop

from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

def multi_hop_answer(query: str, vectorstore, max_hops=3):
    context_so_far = []
    current_query = query

    for hop in range(max_hops):
        docs = vectorstore.as_retriever(search_kwargs={"k": 3}).invoke(current_query)
        context_so_far.extend([d.page_content for d in docs])

        check_prompt = f"""Given this context:
{chr(10).join(context_so_far)}

Question: {query}

Can this question be fully answered with the context above? Reply YES or NO.
If NO, what follow-up search query would help find the missing piece?
Format: YES  OR  NO: """

        decision = llm.invoke(check_prompt).content.strip()
        if decision.startswith("YES"):
            break
        else:
            current_query = decision.split(":", 1)[1].strip()

    final_prompt = f"Context:\n{chr(10).join(context_so_far)}\n\nQuestion: {query}\n\nAnswer:"
    return llm.invoke(final_prompt).content

4.7 Retrieval Evaluation Metrics

MetricRangeMeasures
Precision@k[0,1]What fraction of the top-k retrieved docs are actually relevant?
Recall@k[0,1]What fraction of all relevant docs were found in the top-k?
MRR (Mean Reciprocal Rank)[0,1]How early does the first relevant result appear?
nDCG@k[0,1]Ranked quality, rewarding relevant docs appearing higher (standard benchmark)
Hit Rate@k[0,1]Does the retrieval find ANY useful result at all?

Python Implementation — Precision@k, Recall@k, MRR

def precision_at_k(retrieved_ids: list, relevant_ids: set, k: int) -> float:
    top_k = retrieved_ids[:k]
    hits = sum(1 for doc_id in top_k if doc_id in relevant_ids)
    return hits / k

def recall_at_k(retrieved_ids: list, relevant_ids: set, k: int) -> float:
    top_k = retrieved_ids[:k]
    hits = sum(1 for doc_id in top_k if doc_id in relevant_ids)
    return hits / len(relevant_ids) if relevant_ids else 0.0

def mean_reciprocal_rank(retrieved_ids: list, relevant_ids: set) -> float:
    for rank, doc_id in enumerate(retrieved_ids, start=1):
        if doc_id in relevant_ids:
            return 1 / rank
    return 0.0

# Example
retrieved = ["doc4", "doc1", "doc7", "doc2"]
relevant  = {"doc1", "doc2"}

print("Precision@4:", precision_at_k(retrieved, relevant, 4))   # 0.5
print("Recall@4:", recall_at_k(retrieved, relevant, 4))          # 1.0
print("MRR:", mean_reciprocal_rank(retrieved, relevant))         # 0.5 (doc1 found at rank 2)
⚠️ Common Mistake Evaluating only generation quality (does the final answer look good?) and skipping retrieval evaluation entirely. If retrieval silently fails, no amount of prompt engineering on the generation side will fix wrong or missing answers — always test retrieval in isolation first.

5.1 Simple RAG

Why introduced / Problem solved

The baseline pattern: solves knowledge cutoff, private data, and basic hallucination by grounding answers in retrieved context. Already fully covered in Parts 1–3.

Architecture

Query → Embed → Vector Search (top-K) → Prompt → LLM → Answer
AdvantagesLimitations

5.2 Hybrid RAG

Why introduced

Pure dense retrieval misses exact keyword matches (product codes, names, numbers); pure sparse retrieval misses paraphrases. Hybrid RAG combines both — covered in depth in Part 4.

Architecture

┌──► BM25 (Sparse) ──┐ Query ──────────┤ ├──► RRF Fusion ──► Re-rank ──► LLM ──► Answer └──► Dense (Vector) ─┘

Python Implementation (Production Pattern)

from langchain_community.retrievers import BM25Retriever
from langchain.retrievers import EnsembleRetriever
from src.reranker import rerank

class HybridRAG:
    def __init__(self, chunks, vectorstore):
        bm25 = BM25Retriever.from_documents(chunks)
        bm25.k = 10
        dense = vectorstore.as_retriever(search_kwargs={"k": 10})
        self.retriever = EnsembleRetriever(retrievers=[bm25, dense], weights=[0.4, 0.6])

    def ask(self, query, llm, top_n=3):
        candidates = self.retriever.invoke(query)
        top_chunks = rerank(query, candidates, top_n=top_n)
        context = "\n\n".join(c.page_content for c in top_chunks)
        prompt = f"Context:\n{context}\n\nQuestion: {query}\n\nAnswer:"
        return llm.invoke(prompt).content
💡 Best Practice Hybrid Search + Re-ranking is the recommended production default for most general-purpose RAG systems in 2025–26.

5.3 Corrective RAG (CRAG)

Why introduced / Problem solved

Simple RAG blindly trusts whatever the retriever returns. If retrieval quality is poor, the LLM generates a bad answer with full confidence. CRAG adds a self-correcting evaluation step before generation.

Architecture & Internal Workflow

Query → Retrieve → Retrieval Evaluator │ ┌─────────────────┼─────────────────┐ CORRECT AMBIGUOUS INCORRECT │ │ │ Use chunks Decompose query Trigger Web Search as-is & re-retrieve for fresh context │ │ │ └──────────────────┴──────────────────┘ │ ▼ Generate Answer

Components

  • Retrieval Evaluator — scores retrieved chunks as Correct / Ambiguous / Incorrect (often a lightweight classifier or LLM-as-judge)
  • Knowledge Refinement — strips out irrelevant strips of text from "correct" chunks
  • Web Search Fallback — triggers external search when local retrieval is judged Incorrect

Python Implementation

from langchain_openai import ChatOpenAI
from langchain_community.tools import DuckDuckGoSearchRun

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
web_search = DuckDuckGoSearchRun()

def evaluate_retrieval(query: str, chunks: list) -> str:
    """Returns 'CORRECT', 'AMBIGUOUS', or 'INCORRECT'."""
    context = "\n".join(c.page_content for c in chunks)
    prompt = f"""Question: {query}
Retrieved context: {context}

Judge the retrieved context's relevance to the question.
Reply with exactly one word: CORRECT, AMBIGUOUS, or INCORRECT."""
    return llm.invoke(prompt).content.strip().upper()

def corrective_rag(query: str, vectorstore):
    chunks = vectorstore.as_retriever(search_kwargs={"k": 5}).invoke(query)
    verdict = evaluate_retrieval(query, chunks)

    if verdict == "CORRECT":
        context = "\n\n".join(c.page_content for c in chunks)

    elif verdict == "AMBIGUOUS":
        # Decompose and re-retrieve with sub-queries
        sub_q = llm.invoke(f"Break this into a clearer, simpler search query: {query}").content
        chunks = vectorstore.as_retriever(search_kwargs={"k": 5}).invoke(sub_q)
        context = "\n\n".join(c.page_content for c in chunks)

    else:  # INCORRECT
        context = web_search.run(query)

    prompt = f"Context:\n{context}\n\nQuestion: {query}\n\nAnswer:"
    return llm.invoke(prompt).content
AdvantagesLimitations
Adds robustness against poor retrievalExtra LLM call adds latency and cost
Falls back to live web search when local KB is insufficientEvaluator itself can make mistakes

5.4 Self-RAG

Why introduced / Problem solved

Self-RAG teaches the LLM itself to decide: should I retrieve at all? What should I retrieve? Is the retrieved passage actually useful? This avoids unnecessary retrieval (saving latency) and lets the model critique its own output.

Architecture

The original Self-RAG paper trains a model with special reflection tokens:

TokenMeaning
[Retrieve] / [No Retrieve]Decides whether retrieval is even needed for this query
[Relevant] / [Irrelevant]Judges whether a retrieved passage is useful
[Supported] / [Contradicts]Checks whether the generated answer is actually backed by the passage

Simplified Production Implementation (without custom training)

Most teams approximate Self-RAG behavior with prompting rather than training a custom reflection-token model:

from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

def needs_retrieval(query: str) -> bool:
    verdict = llm.invoke(
        f"Does answering this question require looking up external documents, "
        f"or can it be answered from general knowledge/conversation alone? "
        f"Reply only YES or NO.\nQuestion: {query}"
    ).content.strip().upper()
    return verdict.startswith("YES")

def self_rag_answer(query: str, vectorstore):
    if not needs_retrieval(query):
        return llm.invoke(query).content   # skip retrieval entirely

    chunks = vectorstore.as_retriever(search_kwargs={"k": 5}).invoke(query)

    # Critique each chunk for relevance
    relevant_chunks = []
    for c in chunks:
        verdict = llm.invoke(
            f"Question: {query}\nPassage: {c.page_content}\n"
            f"Is this passage relevant to answering the question? Reply YES or NO."
        ).content.strip().upper()
        if verdict.startswith("YES"):
            relevant_chunks.append(c)

    context = "\n\n".join(c.page_content for c in relevant_chunks) or "No relevant context found."
    answer = llm.invoke(f"Context:\n{context}\n\nQuestion: {query}\n\nAnswer:").content

    # Self-critique: is the answer actually supported by context?
    support_check = llm.invoke(
        f"Context:\n{context}\n\nAnswer: {answer}\n\n"
        f"Is this answer fully supported by the context? Reply YES or NO."
    ).content.strip().upper()

    if not support_check.startswith("YES"):
        answer += "\n\n(Note: this answer could not be fully verified against the source material.)"

    return answer
AdvantagesLimitations
Avoids unnecessary retrieval → lower latency for simple queriesTrue Self-RAG requires custom model training with reflection tokens
Built-in self-critique improves faithfulnessPrompted approximation adds multiple extra LLM calls

5.5 Graph RAG

Why introduced / Problem solved

Vector search treats each chunk independently — it struggles with questions about relationships between entities spread across many documents ("How is Company A connected to Company B through their executives?"). Graph RAG builds a knowledge graph of entities and relationships, then retrieves by graph traversal instead of (or alongside) vector search.

Architecture

Documents → Entity & Relationship Extraction (LLM) → Knowledge Graph │ Query → Entity Recognition → Graph Traversal / Community Detection │ ▼ Subgraph + Text → LLM → Answer

Microsoft's GraphRAG approach additionally clusters the graph into "communities" and pre-generates hierarchical summaries — useful for high-level, holistic questions about an entire corpus rather than a single fact.

Python Implementation — Building a Simple Knowledge Graph

import networkx as nx
from langchain_openai import ChatOpenAI
import json

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

def extract_triples(text: str) -> list[tuple]:
    """Extract (entity1, relationship, entity2) triples from text using an LLM."""
    prompt = f"""Extract entity relationships from this text as a JSON list of
[subject, relationship, object] triples.

Text: {text}

JSON:"""
    response = llm.invoke(prompt).content
    return json.loads(response)

def build_graph(documents: list[str]) -> nx.DiGraph:
    graph = nx.DiGraph()
    for doc in documents:
        triples = extract_triples(doc)
        for subj, rel, obj in triples:
            graph.add_edge(subj, obj, relationship=rel)
    return graph

def graph_retrieve(graph: nx.DiGraph, entity: str, hops: int = 2) -> list:
    """Retrieve all relationships within N hops of a given entity."""
    if entity not in graph:
        return []
    subgraph_nodes = nx.single_source_shortest_path_length(graph, entity, cutoff=hops)
    facts = []
    for node in subgraph_nodes:
        for _, target, data in graph.out_edges(node, data=True):
            facts.append(f"{node} {data['relationship']} {target}")
    return facts

# Example usage
docs = ["Acme Corp acquired BetaTech in 2022. BetaTech's CEO later joined Acme's board."]
kg = build_graph(docs)
print(graph_retrieve(kg, "Acme Corp"))
AdvantagesLimitations
Excellent for relationship/entity-heavy questionsGraph construction is expensive (LLM extraction per document)
Supports holistic, corpus-wide summarizationRequires ongoing graph maintenance as data changes
💡 Real-World Use Cases Investigative journalism, fraud detection, legal case research, organizational/compliance mapping.

5.6 Agentic RAG

Why introduced / Problem solved

All previous architectures follow a fairly fixed pipeline. Agentic RAG turns the LLM into an autonomous agent that plans, decides which tools to use (vector search, SQL, web search, calculator), executes them, observes results, and iterates until it's satisfied with the answer — enabling true multi-hop reasoning and tool use.

Architecture — ReAct Pattern

Thought: "I need to find the Q3 revenue figure" │ ▼ Action: search_vector_db("Q3 revenue") │ ▼ Observation: "Q3 revenue was $4.2M" │ ▼ Thought: "Now I need the Q2 figure to compare" │ ▼ Action: search_vector_db("Q2 revenue") │ ▼ Observation: "Q2 revenue was $3.8M" │ ▼ Thought: "I have enough information now" │ ▼ Final Answer: "Revenue grew from $3.8M to $4.2M (+10.5%) from Q2 to Q3"

Tools Available to Agentic RAG

Vector search (semantic retrieval)
Web search (Tavily, Serper, Bing)
SQL query (structured data)
API calls (CRM, weather, stock data)
Calculator / code interpreter
Document reader (specific file formats)
Memory store (persist across turns)
Knowledge graph traversal

Python Implementation — Production-Ready Agentic RAG (LangChain Agent)

from langchain.agents import create_tool_calling_agent, AgentExecutor
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

@tool
def search_knowledge_base(query: str) -> str:
    """Search the internal vector database for relevant company documents."""
    docs = vectorstore.as_retriever(search_kwargs={"k": 5}).invoke(query)
    return "\n\n".join(d.page_content for d in docs)

@tool
def search_web(query: str) -> str:
    """Search the live web for recent or external information."""
    from langchain_community.tools import DuckDuckGoSearchRun
    return DuckDuckGoSearchRun().run(query)

@tool
def calculate(expression: str) -> str:
    """Evaluate a mathematical expression, e.g. '4.2 - 3.8'."""
    try:
        return str(eval(expression, {"__builtins__": {}}))
    except Exception as e:
        return f"Error: {e}"

tools = [search_knowledge_base, search_web, calculate]

prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a research assistant. Use tools as needed, "
               "reasoning step by step, before giving a final answer."),
    ("human", "{input}"),
    ("placeholder", "{agent_scratchpad}"),
])

agent = create_tool_calling_agent(llm, tools, prompt)
executor = AgentExecutor(agent=agent, tools=tools, verbose=True, max_iterations=6)

result = executor.invoke({
    "input": "Compare our Q2 and Q3 revenue and tell me the percentage growth."
})
print(result["output"])

6.1 FAISS (Facebook AI Similarity Search)

📌 What is FAISS? FAISS is a library (not a server) from Meta AI for fast nearest-neighbour search over dense vectors. It lives entirely in-memory/on-disk as a Python object — no server, no network calls. The fastest option for batch offline search.

Architecture

  • Stores vectors in one of several index types: IndexFlatL2 (brute force, exact), IndexIVFFlat (approximate), IndexIVFPQ (compressed + approximate)
  • No metadata storage — you manage a parallel list of texts/metadata yourself
  • No built-in CRUD — best for static or infrequently updated indexes

7.1 LangChain

📌 What is LangChain? LangChain is the most widely used LLM framework. It provides abstractions for every RAG component (document loaders, text splitters, embedding models, vector stores, retrievers, prompt templates, LLMs, output parsers) and lets you chain them together using the LCEL (LangChain Expression Language) pipe syntax. It also has a rich ecosystem of 300+ integrations and built-in support for agents, memory, and tools.

Core Architecture

LangChain Core Concepts: Runnable Interface ──► everything is composable with the | pipe operator chain = prompt | llm | output_parser rag = retriever | prompt_builder | llm | parser Key Modules: ├── langchain-core (base interfaces, LCEL) ├── langchain-community (300+ 3rd-party integrations) ├── langchain-openai (OpenAI-specific wrappers) └── langgraph (stateful agent graphs)

Installation

Python Implementation — Basic RAG Chain with LCEL

from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_community.vectorstores import Chroma
from langchain_community.document_loaders import PyPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

# ── 1. INDEXING ──
loader = PyPDFLoader("data/company_policy.pdf")
docs = loader.load()

splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = splitter.split_documents(docs)

embedder = OpenAIEmbeddings(model="text-embedding-3-small")
vectorstore = Chroma.from_documents(chunks, embedder)
retriever = vectorstore.as_retriever(search_kwargs={"k": 4})

# ── 2. PROMPT ──
prompt = ChatPromptTemplate.from_template("""
Answer the question based ONLY on the context below.
If the answer is not found, say "I don't know."

Context:
{context}

Question: {question}
""")

# ── 3. LLM ──
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# ── 4. LCEL CHAIN (pipe syntax) ──
def format_docs(docs):
    return "\n\n".join(d.page_content for d in docs)

rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)

answer = rag_chain.invoke("What is the refund window?")
print(answer)

7.3 Haystack

📌 What is Haystack? Haystack (by deepset) is a production-grade, pipeline-based NLP framework. from haystack.document_stores.in_memory import InMemoryDocumentStore
from haystack.components.embedders import (
    SentenceTransformersDocumentEmbedder,
    SentenceTransformersTextEmbedder

from haystack.components.retrievers.in_memory import InMemoryEmbeddingRetriever
from haystack.components.builders import PromptBuilder
from haystack.components.generators import OpenAIGenerator

# ── DOCUMENT STORE ──
doc_store = InMemoryDocumentStore()

docs = [
    Document(content="RAG grounds LLM answers in retrieved evidence.", meta={"source": "guide.pdf"}),
    Document(content="Refunds are accepted within 30 days of purchase.", meta={"source": "policy.pdf"}),

doc_store.write_documents(embedded_docs)

rag_pipeline = Pipeline()

rag_pipeline.add_component(
    "query_embedder",
    SentenceTransformersTextEmbedder(model="all-MiniLM-L6-v2")
)
rag_pipeline.add_component(
    "retriever",
    InMemoryEmbeddingRetriever(document_store=doc_store, top_k=3)
)
rag_pipeline.add_component(
    "prompt_builder",
    PromptBuilder(template="""
Answer the question based only on the context below.
Context:
{% for doc in documents %}
  {{ doc.content }}
{% endfor %}
Question: {{question}}
Answer:""")
)
rag_pipeline.add_component(
    "llm",

)

rag_pipeline.connect("query_embedder.embedding", "retriever.query_embedding")
rag_pipeline.connect("retriever.documents",       "prompt_builder.documents")
rag_pipeline.connect("prompt_builder.prompt",     "llm.prompt")

# ── RUN ──
result = rag_pipeline.run({
    "query_embedder": {"text": "What is the refund window?"},

print(result["llm"]["replies"][0])

8.3 Semantic Caching

📌 What is Semantic Caching? Instead of exact key-value caching, semantic caching stores previous query embeddings alongside their answers. When a new query arrives, if its embedding is close enough to a cached query (similarity > threshold), the cached answer is returned immediately — skipping retrieval and LLM generation entirely. Typically saves 30–60% of LLM cost in production. 
import numpy as np
import json, time
from langchain_openai import OpenAIEmbeddings

class SemanticCache:
    """
    A lightweight in-memory semantic cache.
    In production, store cache_store in Redis with TTL.
    """
    def __init__(self, embedder, threshold=0.92, ttl_seconds=3600):
        self.embedder = embedder
        self.threshold = threshold
        self.ttl = ttl_seconds
        self.cache_store: list[dict] = []   # [{embedding, answer, sources, timestamp}]

    def _cosine(self, a, b):
        return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

    def get(self, query: str):
        q_vec = np.array(self.embedder.embed_query(query))
        now = time.time()
        for entry in self.cache_store:
            if now - entry["timestamp"] > self.ttl:
                continue   # expired
            sim = self._cosine(q_vec, entry["embedding"])
            if sim >= self.threshold:
                return entry["answer"], entry["sources"], sim
        return None, None, 0.0

    def set(self, query: str, answer: str, sources: list):
        q_vec = np.array(self.embedder.embed_query(query))
        self.cache_store.append({
            "embedding": q_vec,
            "answer": answer,
            "sources": sources,
            "timestamp": time.time()
        })

# Usage inside the RAG pipeline
embedder = OpenAIEmbeddings(model="text-embedding-3-small")
cache = SemanticCache(embedder, threshold=0.92)

def cached_ask(query: str, pipeline):
    cached_answer, cached_sources, sim = cache.get(query)
    if cached_answer:
        print(f"Cache HIT (similarity={sim:.3f})")
        return {"answer": cached_answer, "sources": cached_sources, "cached": True}
    result = pipeline.ask(query)
    cache.set(query, result["answer"], result["sources"])
    return result

from langchain_openai import ChatOpenAI

cheap_llm  = ChatOpenAI(model="gpt-4o-mini", temperature=0)   # ~$0.15/1M tokens

def route_query(query: str) -> str:
    """Classify query complexity and route to appropriate LLM."""
    verdict = cheap_llm.invoke(
        f"Is this question simple (single fact) or complex (multi-step reasoning)? "
        f"Reply only SIMPLE or COMPLEX.\nQuestion: {query}"
    ).content.strip().upper()
    return "cheap" if verdict == "SIMPLE" else "strong"

def smart_generate(query: str, context: str) -> str:
    prompt = f"Context:\n{context}\n\nQuestion: {query}\n\nAnswer:"
    tier = route_query(query)
    llm = cheap_llm if tier == "cheap" else strong_llm
    return llm.invoke(prompt).content

Async Batched Embedding for Indexing

import asyncio
from langchain_openai import OpenAIEmbeddings

async def embed_batch_async(texts: list[str], batch_size=100) -> list[list[float]]:
    embedder = OpenAIEmbeddings(model="text-embedding-3-small")
    batches = [texts[i:i+batch_size] for i in range(0, len(texts), batch_size)]
    tasks = [asyncio.to_thread(embedder.embed_documents, batch) for batch in batches]
    results = await asyncio.gather(*tasks)
    return [vec for batch_result in results for vec in batch_result]

8.11 Input & Output Guardrails

def check_input_guardrails(query: str) -> tuple[bool, str]:
    """Block harmful or off-topic queries before hitting the RAG pipeline."""
    blocked_patterns = ["ignore previous instructions", "jailbreak", "act as DAN"]
    for p in blocked_patterns:
        if p.lower() in query.lower():
            return False, "Query blocked by content policy."
    if len(query.strip()) < 3:
        return False, "Query too short."
    return True, ""

def check_output_guardrails(answer: str, context: str, llm) -> str:
    """NLI-style faithfulness check: flag if answer isn't grounded in context."""
    verdict = llm.invoke(
        f"Context: {context}\nAnswer: {answer}\n\n"
        f"Is this answer fully supported by the context? Reply YES or NO."
    ).content.strip().upper()
    if verdict != "YES":
        return answer + "\n\n⚠️ Warning: this answer could not be fully verified against source documents."
    return answer

"""
ingestion.py — Loads raw documents from the data directory.
Supports PDF, TXT, and DOCX. Returns list[Document].
"""
import logging
from pathlib import Path
from langchain_community.document_loaders import PyPDFLoader, TextLoader, Docx2txtLoader
from config.config import cfg

logger = logging.getLogger(__name__)

LOADER_MAP = {
    ".pdf":  PyPDFLoader,
    ".txt":  TextLoader,
    ".docx": Docx2txtLoader,
}

def load_documents(data_dir: str = cfg.DATA_DIR) -> list:
    """Load all supported files from data_dir recursively."""
    all_docs = []
    for path in Path(data_dir).rglob("*"):
        ext = path.suffix.lower()
        if ext in LOADER_MAP:
            try:
                docs = LOADER_MAP[ext](str(path)).load()
                # Attach the original file path as metadata
                for doc in docs:
                    doc.metadata.setdefault("source", str(path))
                all_docs.extend(docs)
                logger.info(f"Loaded {len(docs)} page(s) from {path.name}")
            except Exception as e:
                logger.error(f"Failed to load {path}: {e}")
    logger.info(f"Total documents loaded: {len(all_docs)}")
    return all_docs

"""
preprocessing.py — Text cleaning and chunking.
Always clean BEFORE chunking.
"""
import re
import logging
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_core.documents import Document
from config.config import cfg

logger = logging.getLogger(__name__)

def clean_text(text: str) -> str:
    """Remove common PDF artifacts and normalise whitespace."""
    text = re.sub(r"Page \d+ of \d+", "", text)       # page numbers
    text = re.sub(r"\f", " ", text)                     # form-feed characters
    text = re.sub(r"[ \t]+", " ", text)                 # multiple spaces/tabs
    text = re.sub(r"\n{3,}", "\n\n", text)              # excessive newlines
    return text.strip()

def clean_documents(documents: list[Document]) -> list[Document]:
    cleaned = []
    for doc in documents:
        text = clean_text(doc.page_content)
        if len(text) > 30:   # discard near-empty pages
            cleaned.append(Document(page_content=text, metadata=doc.metadata))
    logger.info(f"Cleaned {len(cleaned)} / {len(documents)} documents")
    return cleaned

def chunk_documents(documents: list[Document]) -> list[Document]:
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=cfg.CHUNK_SIZE,
        chunk_overlap=cfg.CHUNK_OVERLAP,
        separators=["\n\n", "\n", ". ", " ", ""]
    )
    chunks = splitter.split_documents(documents)
    # Add stable chunk index for traceability
    for i, chunk in enumerate(chunks):
        chunk.metadata["chunk_index"] = i
    logger.info(f"Created {len(chunks)} chunks from {len(documents)} documents")
    return chunks

9.11 src/reranker.py

"""
reranker.py — Cross-encoder re-ranking to refine retrieval results.
"""
import logging
from sentence_transformers import CrossEncoder
from langchain_core.documents import Document

logger = logging.getLogger(__name__)

_model = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def rerank(query: str, documents: list[Document], top_n: int) -> list[Document]:
    if not documents:
        return []
    pairs = [(query, doc.page_content) for doc in documents]
    scores = _model.predict(pairs)
    ranked = sorted(zip(documents, scores), key=lambda x: x[1], reverse=True)
    top = [doc for doc, _ in ranked[:top_n]]
    logger.info(f"Re-ranked {len(documents)} candidates → top {len(top)}")
    return top

        label  = f"[{i}] {source}" + (f", p.{page}" if page != "" else "")
        parts.append(f"{label}\n{doc.page_content}")
    return "\n\n".join(parts)

"""
cache.py — Semantic cache backed by in-memory store.
Replace cache_store list with Redis in production for persistence + TTL.
"""
import time, numpy as np, logging
from src.embedding import get_embedder
from config.config import cfg

logger = logging.getLogger(__name__)

class SemanticCache:
    def __init__(self):
        self.store: list[dict] = []
        self.threshold = cfg.CACHE_THRESHOLD
        self.embedder  = get_embedder()

    def _cosine(self, a, b) -> float:
        return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b) + 1e-10))

    def get(self, query: str):
        q_vec = np.array(self.embedder.embed_query(query))
        for entry in self.store:
            sim = self._cosine(q_vec, entry["vec"])
            if sim >= self.threshold:
                logger.info(f"Cache HIT (sim={sim:.3f})")
                return entry["answer"], entry["sources"]
        return None, None

    def set(self, query: str, answer: str, sources: list):
        q_vec = np.array(self.embedder.embed_query(query))
        self.store.append({"vec": q_vec, "answer": answer, "sources": sources})
        logger.info("Cached new answer.")

_cache = SemanticCache()
def get_cache() -> SemanticCache:
    return _cache

"""
rag_pipeline.py — Main orchestrator. Wires all components together.
"""
import logging, os
from langchain_core.output_parsers import StrOutputParser
from src.ingestion     import load_documents
from src.preprocessing import clean_documents, chunk_documents
from src.vector_store  import build_vector_store, load_vector_store
from src.retriever     import build_retriever
from src.reranker      import rerank
from src.prompt        import get_rag_prompt, build_context_string
from src.llm           import get_llm
from src.cache         import get_cache
from config.config     import cfg

logger = logging.getLogger(__name__)

class RAGPipeline:
    def __init__(self):
        self.vectorstore = None
        self.retriever   = None
        self._chunks     = []

    # ── OFFLINE ──────────────────────────────────────────────────────────────
    def build_index(self):
        """Run once to build the knowledge base from raw documents."""
        raw   = load_documents()
        clean = clean_documents(raw)
        self._chunks = chunk_documents(clean)
        self.vectorstore = build_vector_store(self._chunks)
        self.retriever   = build_retriever(self.vectorstore, self._chunks)
        logger.info("Index built successfully.")

    def load_index(self):
        """Load an already-built index."""
        self.vectorstore = load_vector_store()
        # BM25 needs the raw chunks — we reconstruct from Chroma for simplicity
        self._chunks = list(self.vectorstore.get()["documents"] or [])
        self.retriever = build_retriever(self.vectorstore, self.vectorstore.get_all_documents() if hasattr(self.vectorstore, "get_all_documents") else [])
        logger.info("Index loaded.")

    # ── ONLINE ───────────────────────────────────────────────────────────────
    def ask(self, query: str) -> dict:
        """Full online inference pipeline with caching."""
        cache = get_cache()

        # 1. Semantic cache check
        cached_answer, cached_sources = cache.get(query)
        if cached_answer:
            return {"answer": cached_answer, "sources": cached_sources, "cached": True}

        # 2. Retrieve
        candidates = self.retriever.invoke(query)

        # 3. Re-rank
        top_docs = rerank(query, candidates, top_n=cfg.RERANK_TOP_N)

        # 4. Build prompt
        context = build_context_string(top_docs)
        prompt  = get_rag_prompt()
        llm     = get_llm()
        chain   = prompt | llm | StrOutputParser()
        answer  = chain.invoke({"context": context, "question": query})

        # 5. Extract source metadata
        sources = [
            {"source": d.metadata.get("source", ""), "page": d.metadata.get("page", "")}
            for d in top_docs
        ]

        # 6. Cache the result
        cache.set(query, answer, sources)

        return {"answer": answer, "sources": sources, "cached": False}

    def stream(self, query: str):
        """Streaming version — yields tokens."""
        candidates = self.retriever.invoke(query)
        top_docs   = rerank(query, candidates, top_n=cfg.RERANK_TOP_N)
        context    = build_context_string(top_docs)
        prompt     = get_rag_prompt()
        llm        = get_llm(streaming=True)
        chain      = prompt | llm | StrOutputParser()
        for token in chain.stream({"context": context, "question": query}):
            yield token

10.1 Beginner Questions

QModel Answer
What is RAG? RAG stands for Retrieval-Augmented Generation. It enhances a Large Language Model by retrieving relevant documents from an external knowledge base at query time and injecting them into the prompt as context. This grounds the LLM's answer in real evidence rather than its training data alone, solving knowledge cutoff, private data access, and hallucination problems.
What are the three main problems RAG solves? (1) Knowledge cutoff — LLMs can't answer about events after their training date; RAG retrieves live documents. (2) Private data — LLMs never saw your internal docs; RAG indexes them. (3) Hallucination — LLMs confabulate; RAG grounds answers in retrieved evidence.
What is an embedding? A dense numeric vector that represents the meaning of a piece of text. Semantically similar texts have vectors that are close together in vector space. Generated by passing text through a transformer encoder model (e.g., OpenAI text-embedding-3-small outputs a 1536-dimension vector).
What is a vector database? A database specialised for storing high-dimensional embedding vectors and searching them efficiently using Approximate Nearest Neighbour (ANN) algorithms like HNSW. Examples: ChromaDB, Pinecone, Qdrant, Weaviate, Milvus, FAISS.
What is chunking and why is it needed? Chunking splits large documents into smaller, semantically coherent pieces before embedding. Needed for two reasons: (1) LLMs have a maximum context length and can't receive an entire knowledge base in one prompt, and (2) smaller, focused chunks give better semantic search precision than one giant blob.
What is cosine similarity? A metric that measures the angle between two vectors, ignoring their magnitudes. Range [-1, 1], where 1 = identical direction (most similar), 0 = orthogonal, -1 = opposite. Most common similarity metric for text embeddings because meaning doesn't depend on text length (magnitude).

10.2 Intermediate Questions

QModel Answer
Explain the difference between sparse and dense retrieval. Sparse (BM25/TF-IDF): represents text as high-dimensional, mostly-zero vectors based on term frequency. Fast, interpretable, excellent for exact keyword and number matching. Fails on synonyms and paraphrases. Dense (bi-encoder embeddings): represents text as low-dimensional, fully-populated vectors capturing semantic meaning. Handles synonyms and paraphrases but may miss exact keyword matches. Production best practice: combine both with Reciprocal Rank Fusion (hybrid search).
What is the difference between a bi-encoder and a cross-encoder? Bi-encoder: encodes query and document independently into separate embeddings; similarity = dot product. Can pre-compute document embeddings offline — O(1) at query time. Used for initial retrieval. Cross-encoder: encodes the query-document pair jointly; full attention between both. More accurate (captures fine-grained interaction) but O(k) full forward passes at query time — can't pre-compute. Used for re-ranking the top-k candidates from bi-encoder retrieval.
What is Reciprocal Rank Fusion? A method to merge ranked lists from multiple retrieval systems without needing score normalisation. Formula: RRF_score(doc) = Σ 1/(k + rank_i(doc)) where k=60 is a smoothing constant. Documents that rank well in multiple retrieval lists get higher combined scores. Preferred over weighted score combination because BM25 and cosine scores are on incompatible scales.
What is HNSW and why do vector databases use it? Hierarchical Navigable Small World — an Approximate Nearest Neighbour algorithm that builds a multi-layer graph. Upper layers have long-range connections for fast navigation; lower layers have local connections for precision. Query complexity: O(log n). Best recall/speed trade-off of any ANN algorithm. Memory cost: ~1GB RAM per million 1536-dimension float32 vectors. Default index in Pinecone, Qdrant, Weaviate, Chroma.
What is HyDE? Hypothetical Document Embeddings. Instead of embedding the user's raw query, the LLM first generates a plausible hypothetical answer to the query, and that hypothetical answer is embedded for retrieval. Since the hypothesis is written in the same style and vocabulary as real corpus documents, it often retrieves better results — especially when the query is phrased very differently from the documents.
What is the "lost in the middle" problem? LLMs attend better to information placed at the beginning or end of their context window than in the middle (Liu et al. 2023). In RAG, if the most relevant chunk is in the middle of a long context block, the model may effectively ignore it. Mitigations: place most relevant chunks first and last, use context compression to reduce total context, limit the number of retrieved chunks.
What is semantic caching? A caching strategy where previous query embeddings and their answers are stored. When a new query arrives, its embedding is compared to cached embeddings; if cosine similarity exceeds a threshold (e.g. 0.92), the cached answer is returned without hitting the retriever or LLM. Typically saves 30–60% of LLM cost in production for systems with overlapping user queries.

10.3 Advanced Questions

QModel Answer
How would you improve a RAG system that frequently returns wrong answers? Systematic debugging approach: (1) Isolate whether the failure is in retrieval or generation — run RAGAS metrics separately. (2) If retrieval: check hit rate and context relevance; switch to hybrid search; try HyDE or multi-query; increase chunk overlap; check if relevant content is even indexed. (3) If generation: strengthen grounding instruction; lower temperature; add citation requirement; check for "lost in the middle" — compress context. (4) Cross-cutting: add re-ranking; fine-tune embedding model on domain data; evaluate with real user queries.
When would you use RAG vs fine-tuning vs both? Use RAG when: knowledge changes frequently, you need source citations, data is private/sensitive, you need facts beyond the training cutoff, or budget is limited. Use fine-tuning when: you need a specific response style or tone, a specialised skill/reasoning pattern not in the base model, or very low latency (no retrieval step). Use both when: you need domain-specific reasoning AND up-to-date knowledge (e.g. a medical AI assistant that understands clinical terminology AND has current guidelines).
How do you handle multi-hop questions? Three main approaches: (1) Query decomposition — LLM breaks the question into sub-questions, each answered via separate retrieval, then synthesised. (2) Iterative RAG (IRCoT) — interleave chain-of-thought reasoning with retrieval; each reasoning step triggers a new retrieval query when more information is needed. (3) Graph RAG — build a knowledge graph from entities and relationships; traversal naturally supports multi-hop entity chains. Choice depends on scale and latency budget.
Walk me through CRAG and Self-RAG and how they differ. CRAG adds a retrieval evaluator that scores retrieved documents as Correct/Ambiguous/Incorrect after retrieval. If Incorrect, it falls back to web search. The evaluator and fallback are external to the LLM. Self-RAG trains the LLM itself with special reflection tokens — [Retrieve]/[No Retrieve] decides whether to retrieve at all; [Relevant]/[Irrelevant] judges each passage; [Supported]/[Contradicts] checks the generated answer. Key difference: CRAG is a wrapper around a standard LLM; Self-RAG requires custom model training.
How do you evaluate a RAG pipeline end-to-end? Two independent evaluation targets: Retrieval (Precision@k, Recall@k, nDCG@k, Hit Rate@k, MRR — requires annotated query-document relevance pairs) and Generation (Faithfulness, Answer Relevance, Context Precision, Context Recall — via RAGAS using LLM-as-judge). In production: sample 5–10% of queries and run RAGAS on them continuously; track reranker score distributions; capture user thumbs up/down feedback; monitor empty-retrieval rate and LLM refusal rate.

def rrf(ranked_lists, k=60):
    scores = {}
    for lst in ranked_lists:
        for rank, doc_id in enumerate(lst):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)
    return sorted(scores, key=scores.get, reverse=True)

Move from ChromaDB to Milvus or Qdrant distributed cluster; use IVF-PQ or HNSW with int8 quantization to reduce memory 4–8x; shard index by document domain/date for parallelism; async batched embedding pipeline with Celery + Redis; multiple read replicas of the vector DB; semantic caching at the gateway (30–60% query deflection); smaller local re-ranker (Flashrank) to avoid GPU bottleneck.
A user asks a question in Spanish but your documents are in English. How do you handle this? Option 1: Use a multilingual embedding model (bge-m3, multilingual-e5) that places Spanish queries and English documents in the same embedding space. Option 2: Translate the query to English first (LLM or translation API), retrieve in English, then answer in Spanish using a multilingual LLM. Store language as metadata to enable language-filtered retrieval when a mono-lingual index is preferred.
How do you prevent private data from leaking between tenants? Strict namespace/collection isolation in the vector DB (Pinecone namespaces, Qdrant collections, Weaviate multi-tenancy). API key bound to a specific namespace — all retrieval queries automatically scoped to that namespace. No cross-namespace queries allowed. PII redacted before indexing using Presidio. Audit logging of all queries per tenant. RBAC enforced at the API gateway layer before any request reaches the RAG pipeline.

11.6 Memory Tricks

🧠 Mnemonics to Remember
  • RAG = Retrieve → Augment → Generate (in that order every time)
  • Bi = Big speed; Cross = Cross my heart it's accurate (bi-encoder is fast; cross-encoder is accurate)
  • HNSW = Highways Navigate Small Worlds — upper layers are highways (long jumps), lower layers are local streets (fine detail)
  • RRF's k=60 — remember it as "60 seconds, always smooth" — the constant k=60 acts as a smoothing damper
  • Chunk overlap = safety net — catches ideas that fall through the gap between two chunks
  • Temperature 0 = robot (precise), Temperature 1 = poet (creative) — for RAG facts, be a robot
  • RAGAS = 4 metrics: Faithfulness, Answer Relevance, Context Precision, Context Recall
  • Lost in the Middle = sandwiches have the filling in the middle — but LLMs eat the bread (start and end) first

13.7 Speculative RAG

📌 What is Speculative RAG? Speculative RAG uses a small specialist LM to generate a draft answer and rationale using the retrieved documents first — then a larger LM reads both the draft and the original context to verify and refine. This reduces expensive large-LM calls while maintaining quality: the small model handles the heavy lifting, the large model only corrects.

Architecture

Query → Retrieve top-K chunks │ ▼ Small LM (e.g. Llama 3.2-3B) → Generate draft answer + rationale │ ▼ Large LM (e.g. GPT-4o or Llama 3.1-70B) → Verify draft against context → Correct or confirm │ ▼ Final Answer

Python Implementation

from langchain_ollama import OllamaLLM
from langchain_openai import ChatOpenAI

# Small fast model for drafting
drafter  = OllamaLLM(model="llama3.2", temperature=0.1)   # local, free
# Large accurate model for verification
verifier = ChatOpenAI(model="gpt-4o-mini", temperature=0)  # API, costs money

def speculative_rag(query: str, vectorstore) -> str:
    # 1. Retrieve
    docs    = vectorstore.as_retriever(search_kwargs={"k": 5}).invoke(query)
    context = "\n\n".join(d.page_content for d in docs)

    # 2. Small model drafts an answer
    draft_prompt = f"""Context:\n{context}\n\nQuestion: {query}\n
Draft a concise answer and brief reasoning. Format:
ANSWER: 
REASONING: """
    draft = drafter.invoke(draft_prompt)

    # 3. Large model verifies and refines
    verify_prompt = f"""Context:\n{context}\n\nQuestion: {query}\n
A draft answer was proposed:
{draft}

Review this draft against the context. If it is accurate and complete, confirm it.
If it contains errors or omissions, correct them.
Provide the final, verified answer:"""
    final = verifier.invoke(verify_prompt).content

    return final

print(speculative_rag("What is the refund policy for digital products?", vectorstore))

13.8 Modular RAG

📌 What is Modular RAG? Modular RAG decomposes the RAG pipeline into independent, swappable modules — Search, Memory, Fusion, Routing, Predict, Rerank — each with a well-defined interface. You can mix, remove, or replace modules without touching the rest. It also adds a Router that selects which retrieval strategy to use based on query type (e.g. vector search vs SQL vs web search vs graph traversal).

Architecture

Modular RAG Components: ┌─────────────────────────────────────────────────────────────┐ │ QUERY ROUTER │ │ Classifies query type → routes to appropriate module │ └──────────────────────────────────────────────────────────────┘ │ │ │ │ ▼ ▼ ▼ ▼ Vector Search SQL Query Web Search Graph Traversal (semantic QA) (structured) (real-time) (relationship Q) │ │ │ │ └───────────────┴──────────────┴──────────────┘ │ ▼ Fusion Module (RRF) │ ▼ Memory Module (conversation history) │ ▼ Re-rank Module │ ▼ Predict Module (LLM generate)

Python Implementation — Query Router (Core of Modular RAG)

from langchain_openai import ChatOpenAI
from langchain_community.utilities import SQLDatabase
from langchain_community.tools import DuckDuckGoSearchRun
import json

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

def classify_query(query: str) -> str:
    """Classify query to route to the right retrieval module."""
    prompt = f"""Classify this question into exactly ONE category:
- KNOWLEDGE_BASE: general questions answerable from company documents
- STRUCTURED_DATA: questions needing exact numbers, dates, tables from a database
- REAL_TIME: questions needing current/live information (news, prices, today's data)
- RELATIONSHIP: questions about connections between multiple entities

Question: {query}
Category (ONE WORD ONLY):"""
    return llm.invoke(prompt).content.strip().upper()

def modular_rag(query: str, vectorstore, db=None) -> str:
    query_type = classify_query(query)
    print(f"[Router] Query type: {query_type}")

    if query_type == "KNOWLEDGE_BASE":
        # Module: Vector Search
        docs    = vectorstore.as_retriever(search_kwargs={"k": 5}).invoke(query)
        context = "\n\n".join(d.page_content for d in docs)

    elif query_type == "STRUCTURED_DATA" and db:
        # Module: SQL Query
        from langchain.chains import create_sql_query_chain
        sql_chain = create_sql_query_chain(llm, db)
        sql_query = sql_chain.invoke({"question": query})
        context   = db.run(sql_query)

    elif query_type == "REAL_TIME":
        # Module: Web Search
        context = DuckDuckGoSearchRun().run(query)

    else:
        # Default fallback: vector search
        docs    = vectorstore.as_retriever(search_kwargs={"k": 5}).invoke(query)
        context = "\n\n".join(d.page_content for d in docs)

    # Predict Module (shared across all routes)
    answer = llm.invoke(
        f"Context:\n{context}\n\nQuestion: {query}\n\nAnswer:"
    ).content
    return answer

13.9 Fusion RAG / RAG-Fusion

📌 What is RAG-Fusion? RAG-Fusion generates multiple reformulated versions of the user's query, retrieves documents for each variant independently, then uses Reciprocal Rank Fusion to merge all result lists into one superior ranked set, and finally synthesises a single answer from the fused context. It addresses query ambiguity and improves recall — especially for vague or multi-faceted questions.

Architecture

User Query: "Tell me about the refund process" │ ▼ LLM generates N query variants: ├── "What are the steps to request a refund?" ├── "How long does the refund process take?" └── "What documents are needed for a refund?" │ ▼ Retrieve top-K for EACH variant separately ├── Results_1: [doc3, doc7, doc1, ...] ├── Results_2: [doc1, doc5, doc3, ...] └── Results_3: [doc7, doc2, doc1, ...] │ ▼ RRF Fusion → unified ranked list [doc1, doc3, doc7, ...] │ ▼ LLM synthesises final answer from fused context

Python Implementation

from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_community.vectorstores import Chroma
import json

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.3)

def generate_query_variants(query: str, n: int = 4) -> list[str]:
    """Generate N rephrased versions of the original query."""
    prompt = f"""Generate {n} different search query reformulations of the following question.
Return a JSON list of strings only, no explanation.

Original question: {query}

JSON:"""
    response = llm.invoke(prompt).content.strip()
    try:
        variants = json.loads(response)
        return [query] + variants[:n]   # include original too
    except Exception:
        return [query]

def reciprocal_rank_fusion(results_per_query: list[list], k: int = 60) -> list:
    """Merge multiple ranked result lists using RRF."""
    doc_scores = {}
    doc_map    = {}

    for results in results_per_query:
        for rank, doc in enumerate(results):
            doc_id = doc.page_content[:100]  # use content prefix as ID
            doc_scores[doc_id] = doc_scores.get(doc_id, 0) + 1 / (k + rank + 1)
            doc_map[doc_id]    = doc

    sorted_ids = sorted(doc_scores, key=doc_scores.get, reverse=True)
    return [doc_map[doc_id] for doc_id in sorted_ids]

def fusion_rag(query: str, vectorstore, top_n: int = 5) -> str:
    # 1. Generate query variants
    variants = generate_query_variants(query, n=3)
    print(f"[Fusion RAG] Generated {len(variants)} query variants")

    # 2. Retrieve for each variant independently
    retriever = vectorstore.as_retriever(search_kwargs={"k": 8})
    all_results = [retriever.invoke(v) for v in variants]

    # 3. Fuse results with RRF
    fused_docs = reciprocal_rank_fusion(all_results)[:top_n]

    # 4. Synthesise answer
    context = "\n\n".join(d.page_content for d in fused_docs)
    answer  = llm.invoke(
        f"Context (from multiple query perspectives):\n{context}\n\nQuestion: {query}\n\nAnswer:"
    ).content

    return answer

print(fusion_rag("Tell me about the refund process", vectorstore))

12.1 DSPy — Programming LLMs, Not Prompting Them

📌 What is DSPy? DSPy (Declarative Self-improving Python) by Stanford is a framework that replaces hand-written prompts with learnable modules. Instead of manually engineering a prompt and hoping it works, you define what you want the LLM to do (a signature), write a small set of examples, and DSPy automatically compiles and optimises the best prompt + few-shot examples through a teleprompter (optimizer). Think of it as "PyTorch for LLM pipelines" — you define the computation graph, DSPy finds the best parameters.

Why DSPy for RAG?

  • Your RAG prompt was hand-written and fragile — DSPy optimises it automatically
  • Changing LLMs no longer requires rewriting prompts manually
  • Built-in retrieval modules that plug directly into your vector store
  • Composable, testable pipeline — swap any module without breaking others

Core Concepts

ConceptWhat It Is
SignatureDeclares the task interface: input fields → output fields (like a typed function signature)
ModuleA building block (Predict, ChainOfThought, Retrieve, ReAct) that implements a signature
ProgramA composition of modules — your complete RAG pipeline
Optimizer (Teleprompter)Automatically finds the best prompts and few-shot examples for your program given training examples

Installation

pip install dspy-ai

class RAGSignature(dspy.Signature):
    """Answer questions based on the provided context. Be concise and cite sources."""
    context  = dspy.InputField(desc="Retrieved passages from the knowledge base")
    question = dspy.InputField(desc="Employee's question")
    answer   = dspy.OutputField(desc="Factual answer grounded in the context")

class SimpleRAG(dspy.Module):

        super().__init__()
        self.retrieve  = dspy.Retrieve(k=num_passages)    # built-in retriever
        self.generate  = dspy.ChainOfThought(RAGSignature) # CoT reasoning

    def forward(self, question):
        context = self.retrieve(question).passages        # retrieve top-k passages
        answer  = self.generate(context=context, question=question)
        return answer

class MultiHopRAG(dspy.Module):
    """Multi-hop RAG: iteratively retrieves and reasons before answering."""
    def __init__(self, num_passages=3, num_hops=2):
        super().__init__()
        self.retrieve       = dspy.Retrieve(k=num_passages)
        self.reason_to_search = dspy.ChainOfThought("context, question -> search_query")
        self.generate_answer  = dspy.ChainOfThought(RAGSignature)
        self.num_hops = num_hops

    def forward(self, question):
        context = []
        for _ in range(self.num_hops):
            passages = self.retrieve(question if not context else
                       self.reason_to_search(context="\n".join(context),
                                             question=question).search_query).passages
            context += passages
        return self.generate_answer(context="\n".join(context), question=question)

multi_hop = MultiHopRAG(num_hops=2)
result = multi_hop("How did the company's revenue in 2023 compare to R&D spending growth?")

12.3 LangGraph — Stateful Agentic RAG

📌 What is LangGraph? LangGraph is LangChain's framework for building stateful, multi-step, cyclical agentic workflows. Unlike LCEL chains (which are linear and acyclic), LangGraph lets you define a graph of nodes and edges where the agent can loop, branch, and maintain persistent state across turns. It is the modern production standard for Agentic RAG in 2025–26.

Why LangGraph over plain LangChain Agents?

  • Stateful — maintains conversation state, retrieved docs, and intermediate results across steps
  • Cyclical — can loop back to retrieve more info if the first pass was insufficient
  • Controllable — explicit graph structure makes debugging much easier than opaque agent loops
  • Streaming — streams intermediate steps, not just the final answer
  • Human-in-the-loop — can pause for human approval at any node

Installation

pip install langgraph langchain-openai

Core Concepts

LangGraph Building Blocks: StateGraph ─── defines the graph + shared state schema Node ─── a Python function that reads/writes state Edge ─── connects nodes (can be conditional) State ─── TypedDict passed between all nodes Flow: START → node_A → conditional_edge → node_B or node_C → END (can loop back to node_A)

Python Implementation — Adaptive RAG with LangGraph (Production Pattern)

from typing import TypedDict, Annotated, List
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_community.vectorstores import Chroma
from langchain_core.documents import Document

# ── 1. Define the shared State ──
class RAGState(TypedDict):
    question:    str
    documents:   List[Document]   # retrieved chunks
    generation:  str              # LLM answer
    hop_count:   int              # how many retrieval hops done
    sufficient:  bool             # did we find enough context?

# ── 2. Define Nodes (each is a pure function on State) ──
llm       = ChatOpenAI(model="gpt-4o-mini", temperature=0)
embedder  = OpenAIEmbeddings(model="text-embedding-3-small")
vectorstore = Chroma(persist_directory="./chroma_db", embedding_function=embedder)
retriever   = vectorstore.as_retriever(search_kwargs={"k": 5})

def retrieve(state: RAGState) -> RAGState:
    """Node: retrieve documents based on current question."""
    print(f"[retrieve] hop {state.get('hop_count', 0) + 1}")
    docs = retriever.invoke(state["question"])
    return {"documents": docs, "hop_count": state.get("hop_count", 0) + 1}

def grade_documents(state: RAGState) -> RAGState:
    """Node: grade whether retrieved documents are relevant."""
    context = "\n".join(d.page_content for d in state["documents"])
    verdict = llm.invoke(
        f"Question: {state['question']}\nContext: {context}\n"
        f"Are these documents sufficient to answer the question? Reply YES or NO."
    ).content.strip().upper()
    return {"sufficient": verdict.startswith("YES")}

def rewrite_query(state: RAGState) -> RAGState:
    """Node: rewrite the question to retrieve better documents."""
    new_q = llm.invoke(
        f"The retrieved documents were insufficient for: '{state['question']}'. "
        f"Rewrite as a clearer, more specific search query."
    ).content.strip()
    print(f"[rewrite] new query: {new_q}")
    return {"question": new_q}

def generate(state: RAGState) -> RAGState:
    """Node: generate the final answer from retrieved documents."""
    context = "\n\n".join(d.page_content for d in state["documents"])
    answer  = llm.invoke(
        f"Context:\n{context}\n\nQuestion: {state['question']}\n\nAnswer:"
    ).content
    return {"generation": answer}

# ── 3. Conditional edge logic ──
def decide_next(state: RAGState) -> str:
    if state["sufficient"]:
        return "generate"
    elif state.get("hop_count", 0) >= 3:   # max hops guard
        return "generate"
    else:
        return "rewrite_query"

# ── 4. Build the Graph ──
graph = StateGraph(RAGState)

graph.add_node("retrieve",        retrieve)
graph.add_node("grade_documents", grade_documents)
graph.add_node("rewrite_query",   rewrite_query)
graph.add_node("generate",        generate)

graph.add_edge(START,              "retrieve")
graph.add_edge("retrieve",         "grade_documents")
graph.add_conditional_edges("grade_documents", decide_next,
                             {"generate": "generate", "rewrite_query": "rewrite_query"})
graph.add_edge("rewrite_query",    "retrieve")   # loop back to retrieve
graph.add_edge("generate",         END)

app = graph.compile()

# ── 5. Run ──
result = app.invoke({"question": "What is the refund policy for digital products?",
                     "hop_count": 0, "sufficient": False})
print("ANSWER:", result["generation"])
print(f"Hops used: {result['hop_count']}")

12.4 TruLens — RAG Evaluation & Monitoring

📌 What is TruLens? TruLens is an open-source evaluation and monitoring framework for LLM applications. For RAG specifically, it implements the RAG Triad — three feedback functions that together measure whether your pipeline is working: Context Relevance, Groundedness, and Answer Relevance. It also records every LLM call with its inputs/outputs for debugging.

RAG Triad

User Question │ ▼ ┌─────────────┐ │ Retrieved │◄── Context Relevance: Is retrieved context relevant to the question? │ Context │ └─────────────┘ │ ▼ ┌─────────────┐ │ Answer │◄── Groundedness: Is the answer supported by the context? └─────────────┘ │ ▼ ┌─────────────┐ │ Answer │◄── Answer Relevance: Does the answer actually address the question? │ Relevance │ └─────────────┘

12.6 Embedding Fine-Tuning

📌 Why Fine-Tune Embeddings? General-purpose embedding models (e.g., all-MiniLM, bge-large) are trained on broad internet text. If your documents use specialised jargon (medical, legal, financial, engineering), the embedding space may not capture domain-specific similarities accurately. Fine-tuning adapts the model to your vocabulary, improving retrieval quality — often by 10–20% nDCG@10 on domain benchmarks.

Fine-Tuning Strategy

1. Collect positive query-document pairs (query, relevant_chunk) → label = 1 2. Mine hard negatives (query, similar-but-wrong_chunk) → label = 0 3. Train with contrastive loss (MultipleNegativesRankingLoss) → pushes query vector closer to positive, away from negatives 4. Evaluate on a held-out retrieval set (nDCG@10) 5. Deploy fine-tuned model as your new embedding model

Python Implementation — Generating Training Data from your Corpus

from langchain_openai import ChatOpenAI
import json, random

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.5)

def generate_qa_pairs(chunks: list, n_per_chunk: int = 2) -> list[dict]:
    """Generate synthetic query-document training pairs from your own chunks."""
    pairs = []
    for chunk in random.sample(chunks, min(200, len(chunks))):   # sample 200 chunks
        prompt = f"""Given this passage, generate {n_per_chunk} realistic search queries
a user might ask whose answer is in this passage. Return as JSON list of strings.

Passage: {chunk.page_content}

JSON:"""
        try:
            queries = json.loads(llm.invoke(prompt).content)
            for q in queries:
                pairs.append({"query": q, "positive": chunk.page_content})
        except Exception:
            continue
    return pairs

# Generate pairs from your indexed chunks
training_pairs = generate_qa_pairs(chunks, n_per_chunk=2)
print(f"Generated {len(training_pairs)} training pairs")

Python Implementation — Fine-Tuning with sentence-transformers

from sentence_transformers import SentenceTransformer, InputExample, losses
from sentence_transformers.evaluation import InformationRetrievalEvaluator
from torch.utils.data import DataLoader
import random

# ── 1. Load base model ──
model = SentenceTransformer("BAAI/bge-large-en-v1.5")

# ── 2. Prepare training examples ──
train_examples = []
for pair in training_pairs:
    train_examples.append(InputExample(texts=[pair["query"], pair["positive"]]))

# ── 3. Create DataLoader ──
train_dataloader = DataLoader(train_examples, shuffle=True, batch_size=32)

# ── 4. Loss function — MultipleNegativesRankingLoss ──
# Uses other items in the batch as hard negatives automatically
train_loss = losses.MultipleNegativesRankingLoss(model=model)

# ── 5. Evaluator (optional but recommended) ──
# queries: {id: query_text}, corpus: {id: doc_text}, relevant_docs: {query_id: set(doc_ids)}
queries      = {str(i): p["query"]    for i, p in enumerate(training_pairs[:50])}
corpus       = {str(i): p["positive"] for i, p in enumerate(training_pairs[:50])}
relevant     = {str(i): {str(i)}      for i in range(50)}

evaluator = InformationRetrievalEvaluator(
    queries=queries, corpus=corpus, relevant_docs=relevant,
    name="domain-eval", score_functions={"cos_sim": lambda a, b: (a @ b.T).diagonal()}
)

# ── 6. Train ──
model.fit(
    train_objectives=[(train_dataloader, train_loss)],
    epochs=3,
    warmup_steps=100,
    evaluator=evaluator,
    evaluation_steps=200,
    output_path="./fine_tuned_embedder",
    save_best_model=True,
    show_progress_bar=True
)

# ── 7. Use the fine-tuned model ──
fine_tuned = SentenceTransformer("./fine_tuned_embedder")
vec = fine_tuned.encode("What is the refund policy?")
print(f"Fine-tuned vector shape: {vec.shape}")
