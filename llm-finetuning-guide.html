Section 01

Introduction to LLM fine-tuning

What is fine-tuning?

A base LLM has already been trained on a very large corpus of text and has learned grammar, reasoning patterns, and a broad map of world knowledge. Fine-tuning takes that finished model and continues training it on a much smaller, carefully chosen dataset so the weights shift toward one behaviour, format, tone, or domain.

The mechanics are identical to pre-training: feed in tokens, predict the next token, compute cross-entropy loss, backpropagate, update weights. What changes is the scale and the intent. Pre-training uses trillions of tokens to build general capability; fine-tuning uses thousands to millions of tokens to specialise it.

The mental model interviewers want to hear

Fine-tuning changes behaviour — how the model responds. Retrieval changes context — what the model can see. If your problem is "it doesn't know our October pricing", that is a context problem. If your problem is "it won't stop writing five-paragraph essays when I need a JSON object", that is a behaviour problem.

Why is fine-tuning needed?

  • Consistent output format. A prompt asking for JSON works 95% of the time; a fine-tuned model can push that to 99.9%, which matters when a parser sits downstream.
  • Domain vocabulary and reasoning style. Medical coding, legal drafting, and chip-design notation all have conventions that generic instruction models approximate badly.
  • Shorter prompts, lower cost. Behaviour baked into weights doesn't need 2,000 tokens of instructions and few-shot examples on every single call.
  • Latency and model size. A fine-tuned 7B model often beats a general 70B model on one narrow task, at a fraction of the serving cost.
  • Privacy and control. An open-weights model fine-tuned in your VPC never sends customer data to a third party.
  • Alignment to preferences. RLHF and DPO teach the model which of two plausible answers humans actually prefer.

  • Pre-training produces a base model. It completes text; it does not follow instructions. Ask meta-llama/Llama-3.1-8B a question and it may well continue with more questions.
  • Instruction tuning is a specific flavour of supervised fine-tuning where the dataset is broad and varied — thousands of different task types — so the model learns the general habit of doing what it is told. Its output is an Instruct model.
  • Task fine-tuning is narrow SFT on one job: classify this ticket, extract these fields, answer in this voice.

In practice you almost always start from an -Instruct checkpoint, because it already has the instruction-following habit and you only need to add your specialisation.

When fine-tuning is the right call

  • You need a rigid output schema or a distinctive voice that prompting can't hold reliably.
  • You have 500+ high-quality examples of the exact behaviour you want.
  • The task is stable — the definition of "a good answer" is not changing weekly.
  • You want to distil a large expensive model's behaviour into a small cheap one.
  • Prompting genuinely plateaued: you measured it, and quality stalled below target.
  • Domain language is far from the pre-training distribution (clinical notes, proprietary DSLs, non-English dialects).

When fine-tuning is the wrong call

Don't fine-tune when
  • You want to inject facts. Weights are a lossy, unverifiable store. The model will confidently blend facts together. Use RAG.
  • The knowledge changes often. Retraining nightly to track a price list is absurd when re-indexing takes 90 seconds.
  • You have under ~100 examples. You'll mostly teach the model to memorise them.
  • You haven't tried prompting properly. Most "fine-tuning problems" are actually unclear-prompt problems. Establish a prompted baseline with real numbers first.
  • You need citations or auditability. Fine-tuned knowledge can't be traced to a source.
  • You have no evaluation set. Without one you can't tell improvement from regression, and you will ship the latter.

Real-world use cases

  • Customer support: a model that answers in company tone, escalates correctly, and always emits a structured ticket object.
  • Structured extraction: invoices, lab reports, contracts to strict JSON with reliably-named keys.
  • Code assistants for internal frameworks: trained on a monorepo so it uses your ORM, not the public one.
  • Classification and routing: intent, sentiment, PII detection, content moderation at scale.
  • Distillation: a 70B teacher generates data; a 7B student learns it and serves 20× cheaper.
  • Language and dialect adaptation: improving low-resource language performance.
  • Medical/legal scribes: clinical note summarisation in SOAP format, contract clause classification.
Section 02

Types of fine-tuning

Memory figures below assume a 7B-parameter model and are the numbers people expect you to know roughly, not to the gigabyte. The rule of thumb: full fine-tuning in mixed precision costs about 16–20 bytes per parameter once you count weights, gradients, and the Adam optimiser's two moment estimates.

Full fine-tuning

How it works. Every weight in the network is trainable. Forward pass, loss, backward pass, optimiser step over all 7 billion parameters.

7B params, bf16 mixed precision, AdamW weights (bf16) 7B × 2 bytes = 14 GB gradients (bf16) 7B × 2 bytes = 14 GB Adam m + v (fp32) 7B × 8 bytes = 56 GB fp32 master weights 7B × 4 bytes = 28 GB activations batch-dependent, 5-30 GB ------------------------------------------------ total ≈ 112 GB+ → 2× A100 80GB minimum
  • Advantages: maximum capacity to change behaviour; best possible ceiling on quality; can genuinely shift the model into a new domain.
  • Disadvantages: very expensive; high catastrophic-forgetting risk; every task needs a full model copy (14 GB each just to store); slow iteration.
  • Use when: you are a lab with a cluster, the domain is far from pre-training data, and you have millions of tokens of quality data.

Supervised fine-tuning (SFT)

How it works. This describes the objective, not the parameter strategy — you can do SFT fully or with LoRA. You provide labelled (prompt, ideal response) pairs and minimise cross-entropy on the response tokens. Crucially, you normally mask the prompt tokens from the loss so the model is graded only on what it should generate, not on reproducing the user's question.

tokens : [ <|user|> How do I reset my password? <|assistant|> Go to Settings → Security … ] labels : [ -100 -100 -100 ... -100 -100 Go to Settings → Security … ] ↑ masked, no gradient ↑ this is what we actually train on
  • Advantages: simple, stable, well-understood; the workhorse of practically every production fine-tune.
  • Disadvantages: only as good as your labels; teaches the model one "correct" answer rather than a ranking over answers.
  • Memory: whatever the parameter strategy costs — full (~112 GB) or LoRA (~16 GB).
  • Use when: you can write or collect examples of the exact output you want. This is the default starting point.

Instruction fine-tuning

How it works. SFT on a deliberately diverse mixture — summarise, translate, classify, rewrite, reason, refuse — often tens of thousands of tasks (FLAN, Alpaca, Dolly, OpenOrca lineage). The point is generalisation to unseen instructions, not mastery of one.

  • Advantages: turns a base model into a usable assistant; improves zero-shot behaviour broadly.
  • Disadvantages: needs large, diverse, high-quality data; expensive to curate; you're mostly redoing work Meta or Mistral already did well.
  • Use when: you have a raw base model — for example after domain-adaptive pre-training on your own corpus — and need it to follow instructions.

Parameter-efficient fine-tuning (PEFT)

How it works. Freeze the pre-trained weights. Introduce a small number of new trainable parameters — or select a small subset of existing ones — and train only those. The family includes LoRA, QLoRA, adapters, prefix tuning, prompt tuning, IA³, and BitFit.

The insight that justifies it: the weight update needed to adapt a model to one task has low intrinsic rank. You don't need 7 billion degrees of freedom to teach a support tone; a few million will do.

  • Advantages: 10–100× less memory; adapters are 10–200 MB, so you can store hundreds; base model stays intact, which sharply limits catastrophic forgetting; you can hot-swap adapters at serving time.
  • Disadvantages: slightly lower ceiling than full fine-tuning on very large domain shifts; adds an extra hyperparameter surface (rank, alpha, target modules).
  • Use when: almost always, in industry.

LoRA — Low-Rank Adaptation

How it works. For a frozen weight matrix W ∈ ℝ^(d×k), learn two small matrices A ∈ ℝ^(r×k) and B ∈ ℝ^(d×r) with r ≪ min(d,k), and compute h = Wx + (α/r)·BAx. Only A and B receive gradients. Full derivation in Section 7.

  • Advantages: typically 0.1–1% of parameters trainable; no added inference latency once merged; adapters compose and swap.
  • Disadvantages: rank must be tuned; a too-small rank underfits complex tasks; unmerged adapters add a small latency cost.
  • Memory (7B, bf16): weights 14 GB + activations + tiny optimiser state ≈ 16–20 GB. Fits an A100 40GB, or a 24GB card with short sequences.
  • Use when: you have a single 24–80 GB GPU and a behaviour/format/style task. The default choice.

QLoRA — Quantised LoRA

How it works. Quantise the frozen base model to 4-bit NF4, then train fp16/bf16 LoRA adapters on top. Gradients flow through the dequantised weights; the frozen 4-bit weights are never updated. Full detail in Section 8.

  • Advantages: ~4× memory reduction on the base weights; 7B fine-tunes comfortably on a 16 GB card, 70B on a single 80 GB A100.
  • Disadvantages: roughly 20–40% slower per step because of dequantisation; small quality cost versus bf16 LoRA; merging back to fp16 needs care.
  • Memory (7B): ~6–10 GB total. Runs on a free Colab T4 at short sequence lengths.
  • Use when: GPU memory is the binding constraint, or the model is very large.

Adapter-based fine-tuning (Houlsby-style)

How it works. Insert small bottleneck feed-forward blocks — down-project, non-linearity, up-project, residual — between transformer sub-layers. Train only those blocks.

  • Advantages: strong modularity; predates LoRA and generalises well; good for multi-task stacking.
  • Disadvantages: they add depth, so they add permanent inference latency — unlike LoRA they cannot be merged into the base weights. This is the main reason LoRA won in practice.
  • Memory: comparable to LoRA.
  • Use when: you need explicitly modular task components and can absorb the latency.

Preference optimisation — the general idea

SFT teaches "here is a good answer." Preference optimisation teaches "answer A is better than answer B." That second signal is what produces helpfulness, safety, concision, and tone that feels deliberate rather than merely correct. It runs after SFT, never instead of it.

RLHF — Reinforcement Learning from Human Feedback

1. SFT model ─────────────────────────────┐ 2. sample 2-4 responses per prompt │ 3. humans rank them │ 4. train reward model RM(prompt, resp) → scalar 5. PPO: optimise policy to maximise RM │ while a KL penalty keeps it near ───────┘ the SFT reference model
  • Advantages: learns from comparisons, which humans give far more reliably than absolute scores; historically the strongest alignment results.
  • Disadvantages: four models in memory at once (policy, reference, reward, value); notoriously unstable; reward hacking is real; expensive and slow.
  • Memory: very high — for 7B, plan on multiple 80 GB GPUs even with LoRA policies.
  • Use when: you're a well-resourced lab tuning a flagship model.

DPO — Direct Preference Optimization

How it works. DPO's insight is that the RLHF objective has a closed-form optimum, so you can skip the reward model and the RL loop entirely and optimise a simple classification-style loss directly on preference pairs:

L_DPO = -log σ( β · [ log π_θ(y_w|x)/π_ref(y_w|x) − log π_θ(y_l|x)/π_ref(y_l|x) ] ) y_w = chosen (winning) response π_θ = model being trained y_l = rejected (losing) response π_ref = frozen SFT reference β = 0.1-0.5, how hard to stay near the reference

In words: raise the log-probability of the chosen response and lower the rejected one, relative to what the frozen reference model already assigned. That relative framing is what stops the model from collapsing.

  • Advantages: two models instead of four; stable; a normal supervised training loop; works fine with LoRA; usually matches PPO quality.
  • Disadvantages: needs paired preference data; no online exploration, so it can't discover behaviours absent from the data; sensitive to β.
  • Memory (7B, LoRA): ~24–40 GB — the reference model is the extra cost, and with LoRA you can even get it free by disabling the adapter.
  • Use when: you have preference pairs and want alignment without an RL team. The pragmatic modern default. Variants worth naming: ORPO (merges SFT and preference into one stage, no reference model), KTO (works with thumbs-up/down instead of pairs), and SimPO (reference-free).

1 · Data collection

Source from production logs, human-written examples, existing documentation, or synthetic generation by a stronger model. Record provenance for every example — you will need it when you find a systematic error. Check licences if you plan to ship.

2 · Cleaning

Deduplicate (exact and near-duplicate), strip PII, drop truncated or empty responses, remove examples where the assistant says "as an AI language model" unless you want that, filter by length, and inspect a random sample of 50 by hand. That manual read is the single highest-ROI hour in the whole pipeline.

3 · Formatting and tokenization

Apply the base model's exact chat template — a Llama template on a Mistral model quietly costs you several points of accuracy. Convert text to token IDs, build attention masks, and mask prompt tokens with -100 in the labels.

4 · Splitting

Train / validation / test, typically 80/10/10 or 90/5/5 for larger sets. Split by entity (customer, document, conversation) rather than by row, or near-duplicates will straddle the boundary and inflate your numbers.

5 · Base model selection and training

Pick by licence, size, and how close the instruct-tuning already is to your task. Load in bf16 or 4-bit, attach LoRA adapters, run the training loop with gradient accumulation and checkpointing. Watch train and validation loss on every eval step.

6 · Evaluation

Validation loss tells you about fit; it does not tell you whether the model is good. Add a task metric — exact-match on JSON keys, ROUGE on summaries, an LLM judge on tone — and a small human-reviewed golden set.

7 · Saving

Save the adapter (small, composable) and optionally a merged full model (simple to serve). Version everything: base model revision hash, dataset hash, config, metrics, and seed.

8 · Deployment

Serve through vLLM, TGI, or TensorRT-LLM. Ramp with a canary, watch latency and throughput, log inputs and outputs, and sample a slice for offline human review.

9 · Feedback loop

Production failures are your next training set. The teams that win at fine-tuning are the ones that close this loop quickly, not the ones with the cleverest hyperparameters.

Section 04

Dataset preparation

The rule everything else follows from

1,000 excellent examples beat 100,000 mediocre ones. The LIMA paper made this concrete: 1,000 carefully curated examples produced a competitive assistant. Model quality is bounded above by data quality — no learning rate will rescue inconsistent labels.

What makes a good dataset

  • Consistent. If half your examples end with a summary line and half don't, the model learns to do it randomly. Pick a convention and enforce it.
  • Representative. The distribution of inputs should match production — including the short, rude, typo-ridden ones.
  • Diverse. Cover the edge cases: refusals, ambiguous questions, out-of-scope requests, multi-turn corrections.
  • Correct. Every response is one you'd be happy to ship verbatim. The model copies your mistakes faithfully.
  • Appropriately sized. Rough guide: 100–500 for format/style, 1k–10k for a solid task model, 10k–100k+ for domain expertise.
  • Balanced. For classification, avoid a 95/5 class split unless production really is 95/5.

Dataset formats

Instruction / input / output (Alpaca style)

Simple, readable, good for single-turn tasks. The input field is optional and often empty.

Chat / messages format (recommended)

This is the format to prefer. It maps directly onto tokenizer.apply_chat_template(), handles multi-turn naturally, and matches how the model will actually be called in production.

JSONL — one JSON object per line

JSONL streams line by line, so you never load a 40 GB file into RAM, and a corrupted line costs you one example rather than the whole dataset. Note the third line: an explicit out-of-scope refusal, which is exactly the kind of example people forget to include.

Data cleaning in practice

Data leakage

Leakage is when information from validation or test reaches training, making your metrics lie. The three forms that bite in LLM work:

  • Near-duplicate leakage. The same question phrased two ways lands on both sides of the split. Fix with normalised hashing or MinHash/embedding similarity before splitting.
  • Entity leakage. Ten tickets from the same customer, split across train and test. Group-split by customer ID.
  • Temporal leakage. Training on October data, testing on September. If production means "predict the future", split by time.

Realistic example training data

Look at what these examples teach beyond the answers: a fixed system prompt, a consistent trailing tag, a refusal for out-of-scope requests, an empathetic-but-brief tone for an angry customer, and numbered lists only when there genuinely are multiple causes. Every one of those is a behaviour you are deliberately installing.

Section 05

Tokenization

Models do not read text. They read integers. Tokenization is the reversible mapping between the two, and almost every subtle fine-tuning bug lives here.

The vocabulary

Modern LLMs use subword tokenizers — Byte-Pair Encoding, WordPiece, or SentencePiece/Unigram. Training on a corpus merges frequently co-occurring character pairs until the vocabulary reaches a target size (32k for Llama 2, 128k for Llama 3, ~100k for GPT-4-class models). Common words get one token; rare words split into pieces; any byte sequence is representable, so nothing is ever out-of-vocabulary.

"unbelievable" → ["un", "bel", "iev", "able"] 4 tokens "the" → ["the"] 1 token "Bengaluru" → ["Beng", "al", "uru"] 3 tokens "संस्करण" → ["स", "ंस", "्क", "रण"] ~6 tokens (non-Latin costs more) "def calc(x):" → ["def", " calc", "(", "x", "):"] 5 tokens Rule of thumb for English: 1 token ≈ 0.75 words ≈ 4 characters

The pieces you must know

  • Token — a subword unit. Token ID — its integer index in the vocabulary. Vocabulary — the full ID↔string table plus special tokens.
  • Special tokens — <s>/BOS, </s>/EOS, <pad>, and chat-role markers like <|im_start|>. If your training data lacks EOS at the end of each response, the model will never learn to stop generating.
  • Context window — the maximum number of tokens the model can attend over (4k, 8k, 128k…). Prompt plus generation must fit inside it.
  • Padding — filler tokens that make every sequence in a batch the same length so they stack into a tensor. For causal LMs, pad left for batched generation and right for training.
  • Truncation — cutting sequences that exceed max_length. Silent data loss; always check how many examples it hits.
  • Attention mask — a 0/1 vector marking real tokens vs padding, so attention ignores the filler.
  • Labels — the targets for the loss. Set to -100 where you want no gradient: padding and (usually) prompt tokens.

Chat templates — the step people skip

Each instruct model was trained with a specific control-token layout. Reproducing it exactly is not optional; using the wrong one degrades quality in ways that look like "the fine-tune didn't work".

Masking the prompt out of the loss

Why masking matters

Without it, the model spends capacity learning to generate user questions — a skill you will never use — and your loss curve becomes a poor proxy for answer quality. With long prompts and short answers, unmasked loss can be dominated almost entirely by the prompt.

Section 07

LoRA deep dive

Why LoRA exists

Full fine-tuning stores a full-rank update ΔW for every weight matrix — 7 billion numbers of gradient plus 7 billion×2 of optimiser state. But Aghajanyan et al. showed that fine-tuning updates have low intrinsic dimensionality: the useful part of the change lives in a small subspace. LoRA (Hu et al., 2021) makes that explicit by constraining ΔW to be low-rank.

The mathematics

Standard layer: h = W₀x W₀ ∈ ℝ^(d×k) Fine-tuned layer: h = (W₀ + ΔW)x LoRA constraint: ΔW = B·A B ∈ ℝ^(d×r), A ∈ ℝ^(r×k) Final LoRA layer: h = W₀x + (α/r)·B·A·x Parameter count full ΔW : d × k e.g. 4096 × 4096 = 16,777,216 LoRA B,A : r(d + k) r=16 → 16 × 8192 = 131,072 ratio : 2r/d ≈ 0.78% 128× fewer trainable numbers Initialisation (this detail matters) A ~ N(0, σ²) random normal B = 0 zeros ⇒ at step 0, BA = 0, so the model is bit-identical to the base model. Training starts from the pre-trained behaviour, never from noise.

Rank r caps how much information ΔW can carry: a rank-16 matrix can express at most 16 independent directions of change. That is the whole trade-off. Small r = fewer parameters, less capacity, more regularisation. Large r = more capacity, more memory, more overfitting risk.

The alpha convention

Because the scale is α/r, setting α = 2r keeps the effective scale at 2.0 as you change rank, so you can tune rank without re-tuning learning rate. r=16/α=32 and r=64/α=128 behave comparably in scale. Note that use_rslora=True switches to α/√r, which is more stable at high ranks.

Why merging is free

Because the LoRA path is linear and parallel to the frozen path, W₀x + (α/r)BAx = (W₀ + (α/r)BA)x. You can precompute that sum once and serve an ordinary dense model with zero added FLOPs. Houlsby adapters sit in series and cannot be collapsed this way, which is the practical reason LoRA displaced them.

Section 08

QLoRA

QLoRA (Dettmers et al., 2023) is LoRA plus aggressive quantisation of the frozen base. It made fine-tuning a 65B model on a single 48 GB GPU possible, and it is why a student with a Colab T4 can fine-tune a 7B model today.

Quantisation in one paragraph

A bf16 weight uses 16 bits. Quantisation maps a block of weights onto a smaller set of levels — 8-bit (256 levels) or 4-bit (16 levels) — storing a scale factor per block so values can be approximately reconstructed. It is lossy compression for tensors. The art is choosing levels that match the distribution of the data, and keeping blocks small enough that a single outlier can't wreck the scale for everything around it.

NF4 — 4-bit NormalFloat

Neural network weights are roughly zero-centred and normally distributed. Uniform int4 spaces its 16 levels evenly, wasting resolution in the sparse tails. NF4 places its 16 levels at the quantiles of a standard normal, so each level holds an equal share of the weight mass. It is information-theoretically optimal for normally-distributed data and measurably better than int4 at the same bit width.

weight distribution (roughly normal) ▁▂▄▆███▆▄▂▁ ────┴┴┴┴┴┴┴┴┴┴┴──── int4 | | | | | | evenly spaced → most levels sit where few weights live nf4 ||| | | | | ||| quantile spaced → dense where the weights are

Double quantisation

Each 64-weight block needs its own fp32 scale constant. That costs 32/64 = 0.5 bits per parameter — on a 7B model, about 0.4 GB of pure overhead. Double quantisation quantises those constants too (to 8-bit, in blocks of 256), cutting the overhead to roughly 0.127 bits per parameter and saving ~0.3 GB on a 7B model. Small, free, and switched on with one flag.

Paged optimizers

The third QLoRA trick: optimiser state lives in unified memory and pages to CPU RAM when a long sequence causes a memory spike, instead of crashing the run. That's what optim="paged_adamw_8bit" buys you.

Why the gradients still work

This is the question interviewers use to separate people who ran a notebook from people who understand it. The 4-bit weights are never updated — they're frozen. The backward pass computes gradients with respect to the LoRA parameters A and B only, which are stored in bf16 at full precision. Gradients flow through the quantised layer, not into it.

Section 10

Evaluation

The trap

Loss is a proxy for the thing you care about, not the thing itself. A model can improve validation loss while getting worse at the actual job — for instance by learning your dataset's formatting quirks. Always pair loss with a task metric.

Loss-based signals

  • Training loss — cross-entropy on training batches. Should fall smoothly. Flat means the learning rate is too low or the data is broken; spiky means the LR is too high.
  • Validation loss — the same measure on held-out data. This is your overfitting detector.
  • Perplexity = exp(cross_entropy_loss). Interpretable as "on average the model is choosing between this many equally likely next tokens." Loss 1.0 → perplexity 2.7; loss 2.3 → perplexity 10. Only comparable across models with the same tokenizer and the same evaluation text.

Classification metrics

When the fine-tuned model produces a label — ticket category, intent, sentiment — evaluate it like a classifier.

  • Accuracy — fraction correct. Misleading on imbalanced data: 95% accuracy is worthless if 95% of tickets are one class.
  • Precision = TP/(TP+FP) — of the ones you flagged, how many were right. Optimise when false positives are costly (auto-refunds, content takedowns).
  • Recall = TP/(TP+FN) — of the ones that existed, how many you caught. Optimise when misses are costly (fraud, safety, medical triage).
  • F1 = harmonic mean of the two. Use macro-F1 when small classes matter equally, weighted when they don't.

Generation metrics: BLEU and ROUGE

These compare generated text to a reference by n-gram overlap. BLEU is precision-oriented (how much of what you produced appears in the reference) and comes from machine translation. ROUGE is recall-oriented (how much of the reference you covered) and comes from summarisation; ROUGE-L uses longest common subsequence, so it tolerates reordering.

Use them with scepticism

Both punish valid paraphrases and reward copying. "Refunds post in 3–5 business days" and "You'll see the refund within 3 to 5 working days" score poorly against each other despite being equally correct. Use BLEU/ROUGE for translation and extractive summarisation; use an LLM judge or humans for open-ended assistant output. BERTScore sits between the two by comparing embeddings rather than exact n-grams.

LLM-as-a-judge

A strong model scores outputs against a rubric. Cheap, fast, and correlates reasonably with human judgment when done carefully.

Human and task-specific evaluation

Keep a golden set: 50–200 examples, human-written ideal answers, reviewed by a domain expert, never used in training. Before every release, generate on it and have a human rate pass/fail. It is slow and it is the only evaluation that reliably catches the failure modes you didn't anticipate.

Also measure what the business actually cares about: JSON parse rate, schema-valid key rate, escalation precision, deflection rate, average handle time. A model with worse ROUGE and a higher deflection rate is the better model.

Section 11

Common problems and how to fix them

CUDA out of memory

The single most common issue. Work down this list; each step costs some speed or quality, so stop as soon as it fits.

  1. Reduce per_device_train_batch_size to 1 and raise gradient_accumulation_steps to compensate — identical math, far less memory.
  2. Enable gradient_checkpointing=True.
  3. Reduce max_seq_length. Attention memory grows with sequence length; halving 2048→1024 is a large win. Check first how many examples this truncates.
  4. Switch to 4-bit QLoRA.
  5. Use optim="paged_adamw_8bit" or adafactor.
  6. Install Flash Attention 2 — it avoids materialising the full attention matrix.
  7. Reduce LoRA rank or the number of target modules.
  8. Set PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True to reduce fragmentation.
  9. Last resort: a smaller base model, or DeepSpeed ZeRO-3 / FSDP across GPUs.

Training loss isn't decreasing

Diagnose in this order: (1) print one fully rendered training example and confirm the chat template and label masking are right — this is the cause about half the time; (2) check that model.print_trainable_parameters() is non-zero, since a mis-specified target_modules silently trains nothing; (3) raise the learning rate by 5–10×; (4) overfit a single batch deliberately — if loss won't reach near zero on 8 examples, the pipeline is broken, not the hyperparameters; (5) confirm labels aren't all -100.

Validation loss increasing while training loss falls

Textbook overfitting. Enable load_best_model_at_end with an early-stopping callback, cut epochs, add data, increase dropout, or lower the rank.

Underfitting

Loss plateaus high and the model ignores your format. Raise the learning rate, raise the rank, add target modules, train more epochs, and check that your examples are actually consistent — a model cannot learn a rule that your data contradicts.

Catastrophic forgetting

The model nails your task and forgets how to do arithmetic, follow unrelated instructions, or speak another language. Causes: learning rate too high, too many epochs, or a dataset with no diversity.

Fixes

Use LoRA instead of full fine-tuning (the base weights are untouched by construction); mix 5–15% general instruction data into your set; lower the LR; fewer epochs; keep rank modest. And measure it — run a small general benchmark before and after, not just your task metric.

Repetitive outputs

The model loops phrases or never stops. Check that every training response ends with the EOS token — this is the usual cause. Then: repetition_penalty=1.05–1.15, no_repeat_ngram_size=4, raise temperature slightly, and remove repetitive examples from the data. If the model won't stop generating at all, verify eos_token_id is passed to generate().

Hallucinations

Often caused by fine-tuning: if you train on facts the base model doesn't know, you teach it the style of confident factual assertion without the underlying knowledge — so it invents facts in that style. Fix by moving factual content to RAG and keeping fine-tuning for behaviour; include explicit "I don't know" and out-of-scope examples in training; lower temperature at inference; and ground answers in retrieved text.

Bad dataset quality

Symptoms: inconsistent output format, contradictory answers, weird artefacts like stray HTML or "As an AI language model". Read 50 random examples by hand. Run a dedupe pass. Compute length distributions and look at the tails. Validate every example against a schema. Have a second person label 100 examples and measure agreement — if humans agree only 70% of the time, your model's ceiling is 70%.

Training quantisation (NF4) and serving quantisation are different jobs. For inference, use a calibrated method:

Versioning and release

Pin and record: base model revision hash, adapter hash, dataset hash, full training config, library versions, random seed, and the evaluation report. A model you cannot reproduce is a model you cannot debug.

Release with a shadow deployment first (run the new model on live traffic without serving it, compare offline), then a 5% canary with automatic rollback on metric regression, then full rollout. Keep the previous adapter one command away.

Offline evaluation predicts; production measures. Beginner
What is fine-tuning, in one sentence?

Continuing to train a pre-trained model on a smaller, task-specific dataset so its weights shift toward a particular behaviour, format, or domain.

The training objective is unchanged from pre-training — next-token prediction with cross-entropy loss. What changes is scale and intent: trillions of general tokens become thousands of curated examples. You're not teaching the model language; you're teaching it your job.

How is that different from pre-training?

Why fine-tune instead of just writing a better prompt?

When you need reliability that prompting can't reach, shorter prompts to cut cost and latency, or behaviour too subtle to describe in instructions.

Prompting gets a format right maybe 90–95% of the time; fine-tuning pushes that past 99%, which matters when a parser consumes the output. It also lets you delete 2,000 tokens of few-shot examples from every request — real money at scale. And some things are far easier to demonstrate than describe: house tone, a domain's reasoning style, when to escalate. That said, always establish a prompted baseline with numbers first.

What would make you decide prompting is enough?

What's the difference between a base model and an instruct model?

A base model just continues text. An instruct model has been fine-tuned on instruction-response data, so it follows commands and uses a chat template.

Give a base model "What is Python?" and you may get more questions, because that's a plausible continuation of a FAQ page. Instruct variants add the habit of answering. For most task fine-tuning you start from the instruct checkpoint, since you get instruction-following for free and only need to add specialisation. You'd start from base if you're doing large-scale domain-adaptive pre-training or want full control over the chat format.

When would you deliberately start from a base model?

What is supervised fine-tuning (SFT)?

Training on labelled prompt-response pairs, computing cross-entropy loss on the response tokens only, with the prompt masked out of the loss.

SFT describes the objective, not the parameter strategy — you can do SFT fully or with LoRA. The prompt masking (labels set to -100) is the detail people forget: without it the model wastes capacity learning to generate user questions, and with long prompts your loss becomes a poor proxy for answer quality.

What value do you set masked labels to, and why that value?

What is LoRA?

A parameter-efficient method that freezes the pre-trained weights and learns a low-rank update — two small matrices B and A whose product approximates the weight change — so you train under 1% of the parameters.

For a frozen W, the layer computes h = Wx + (α/r)·BAx, where B is d×r and A is r×k with r much smaller than d. Only B and A get gradients. Because the LoRA path is linear and parallel, you can merge it into W at the end and serve a normal model with no added latency.

Why is B initialised to zero?

What is QLoRA and why does it save so much memory?

LoRA on top of a base model quantised to 4-bit NF4. The base weights drop from 2 bytes per parameter to about 0.5, so a 7B model's weights go from ~14 GB to ~3.5 GB.

Three ingredients: NF4, a 4-bit data type whose levels sit at the quantiles of a normal distribution so they match how weights are actually spread; double quantisation, which quantises the per-block scale constants to save another ~0.3 GB; and paged optimizers, which offload optimiser state to CPU RAM during memory spikes instead of crashing. The quantised weights are frozen — gradients flow through them to the bf16 adapters, never into them.

What is tokenization and why does it matter for fine-tuning?

Converting text into integer IDs from a subword vocabulary. It matters because a mismatch between training and inference — wrong chat template, missing EOS, wrong padding side — silently destroys quality.

Modern models use BPE or SentencePiece with 32k–128k vocabularies. Roughly one token per 0.75 English words, more for code and non-Latin scripts. The practical failure modes are all pipeline bugs rather than algorithm problems: applying Llama's template to a Mistral model, forgetting to append EOS so the model never learns to stop, or padding right at generation time when it should be left.

How much data do you need to fine-tune?

Roughly 100–500 examples for format or tone, 1,000–10,000 for a solid task model, and tens of thousands for genuine domain expertise — but quality dominates quantity.

The LIMA result is the one to cite: 1,000 carefully curated examples produced a competitive assistant. Training loss keeps falling while validation loss flattens and then climbs. The model is memorising examples rather than learning the behaviour.

Behavioural symptoms are just as telling: the model reproduces training answers verbatim for slightly different questions, performs well on phrasings it saw and collapses on paraphrases, and loses general capability. The fixes in order are more diverse data, fewer epochs with early stopping and best-checkpoint loading, higher LoRA dropout, lower rank, lower learning rate.

Fine-tuning or RAG — how do you choose?

Fine-tuning changes behaviour; RAG changes knowledge. If the answer depends on facts that change or must be cited, use RAG. If you need a format, tone, or skill, fine-tune. Most production systems use both.

The failure mode worth naming is fine-tuning to inject facts: you teach the model the confident style of factual assertion without the underlying knowledge, so hallucinations get worse, not better. Retrieval also gives you per-user access control and citations, which weights can never provide.

Intermediate
Walk me through the memory footprint of fine-tuning a 7B model.

Full fine-tuning in bf16 with AdamW costs roughly 16–20 bytes per parameter — about 112 GB plus activations. LoRA cuts that to ~18 GB, QLoRA to ~7 GB.

The breakdown: weights 14 GB (2 bytes), gradients 14 GB, Adam's two moments in fp32 56 GB, fp32 master weights 28 GB, plus activations that scale with batch size and sequence length. LoRA removes almost all of the gradient and optimiser cost because only ~0.5% of parameters are trainable, leaving the frozen weights as the dominant term. QLoRA then attacks that term with 4-bit quantisation.

You OOM at batch size 4. List your options in order.

How do rank and alpha interact in LoRA?

Rank sets capacity; alpha sets the scale of the update, applied as α/r. Keeping α = 2r holds the effective scale constant so you can change rank without re-tuning the learning rate.

Rank r caps the number of independent directions the update can express. Alpha is a multiplier on the adapter output — too small and the adapter barely influences the model, too large and training destabilises. Because the scale is a ratio, r=16/α=32 and r=64/α=128 have the same scale but very different capacity. With use_rslora=True the scale becomes α/√r, which behaves better at high ranks.

If quality is poor, do you raise rank or the learning rate first?

Which modules should LoRA target, and why?

All seven linear projections — q, k, v, o in attention and gate, up, down in the MLP. The QLoRA paper showed this consistently beats the original attention-only setting.

The original LoRA paper targeted q_proj and v_proj only, which was a memory-driven compromise. The MLP holds roughly two-thirds of a transformer's parameters and much of its stored knowledge, so excluding it limits how much you can change. If memory is very tight, falling back to q and v and raising rank slightly is the sensible trade.

Why not include the embedding and LM head?

Explain gradient accumulation and when you'd use it.

Run several micro-batches, sum their gradients, then take one optimiser step. It gives you a large effective batch with the memory of a small one.

Effective batch = per-device batch × accumulation steps × number of GPUs. Memory scales only with per-device batch; gradient quality scales with effective batch. So when you OOM, halving the micro-batch and doubling accumulation keeps the optimisation mathematics essentially identical. The cost is wall-clock time, since you do more forward-backward passes per update.

Is it mathematically identical to a true large batch? Where does it differ?

What is catastrophic forgetting and how do you prevent it?

The model learns your task and loses unrelated general capability. Prevent it with LoRA rather than full fine-tuning, a lower learning rate, fewer epochs, and 5–15% general instruction data mixed into the set.

LoRA helps structurally: the base weights are frozen, so general knowledge sits intact underneath, and you can even disable the adapter to recover the original model exactly. Full fine-tuning at a high learning rate on narrow data is the classic recipe for producing a model that writes perfect support tickets and can no longer add two numbers. The key practice is measuring it — run a small general benchmark before and after, not just your task metric.

Explain DPO and why it displaced RLHF in most shops.

DPO optimises preference data directly with a classification-style loss, skipping the reward model and the RL loop. Two models instead of four, a normal supervised loop, comparable quality.

RLHF trains a reward model on human rankings then optimises the policy with PPO under a KL penalty — four models in memory, notorious instability, and reward hacking. DPO's derivation shows the optimal RLHF policy has a closed form, so you can reparameterise the reward in terms of the policy and reference log-probabilities and train directly on chosen/rejected pairs. The trade-off is no online exploration: DPO can only learn from behaviours present in the data.

What does β control in DPO, and what happens if it's too small?

How do you prevent data leakage in an LLM fine-tuning dataset?

Deduplicate near-duplicates before splitting, split by entity rather than by row, and split by time when the task is predictive.

Three failure modes. Near-duplicate leakage: the same question phrased two ways lands on both sides — fix with normalised hashing or MinHash/embedding similarity. Entity leakage: ten tickets from one customer split across train and test — use GroupShuffleSplit on customer ID. Temporal leakage: training on October and testing on September inflates results if production means predicting the future. Any of these makes your metrics lie in the optimistic direction.

How do you evaluate a fine-tuned LLM properly?

Validation loss and perplexity for fit, a task metric for capability, an LLM judge for open-ended quality, and a human-reviewed golden set before release — all compared against a prompted baseline.

Loss alone misleads: a model can improve loss while getting worse at the job by learning formatting quirks. For structured output measure schema validity and field accuracy; for classification use macro-F1; for summarisation ROUGE plus a judge; for assistants a judge on a rubric plus human review. The baseline comparison is what turns "it works" into "it's worth the cost".

What is perplexity and what are its limits?

The exponential of cross-entropy loss — roughly, how many equally likely options the model is choosing between per token. Only comparable across models with the same tokenizer and the same evaluation text.

Loss 1.0 gives perplexity 2.7; loss 2.3 gives 10. It's a good progress signal within one training run, but it rewards predicting your dataset's surface statistics, which is not the same as being useful. A model that has memorised your training distribution will show excellent perplexity and may still fail on paraphrased questions.

Why does LoRA work at all? Justify the low-rank assumption.

Fine-tuning updates have low intrinsic dimensionality — the useful change lives in a small subspace — so constraining ΔW to rank r loses little while removing most parameters.

Aghajanyan et al. showed pre-trained models can be fine-tuned effectively in a randomly projected low-dimensional subspace, with the required dimension falling as models get larger. Intuitively, adaptation is re-weighting and recombining features the model already has rather than learning new ones. The caveat: the assumption holds for behaviour and style adaptation, and weakens for genuinely new capability or large domain shifts, where higher ranks or continued pre-training do better.

Walk through gradient flow in QLoRA. If weights are 4-bit, how does backprop work?

The 4-bit weights are frozen and never receive gradients. During the forward pass each block is dequantised to bf16, used in the matmul, and discarded. Backprop computes gradients only with respect to the bf16 LoRA parameters.

Gradients pass through the quantised layer as part of the chain rule — you need ∂L/∂x at each layer to keep propagating — but nothing is ever accumulated into the frozen weights, so their precision only affects the forward values and the backward pass through them, never an update. prepare_model_for_kbit_training upcasts layer norms and the LM head to fp32 for stability and makes input embeddings require grad so the chain isn't broken at the bottom.

You fine-tuned for a new domain and hallucinations got worse. Why?

You trained the model to assert facts it doesn't actually know. It learned the confident style of expert answers without the underlying knowledge, so it generates fluent fabrications in that style.

This is the central argument for keeping facts in retrieval. If the training data contains facts absent from pre-training, SFT teaches the surface form of knowing rather than the knowledge — the model's next-token distribution shifts toward confident assertion regardless of whether it has support. Fixes: move factual content into RAG, include explicit "I don't know" and out-of-scope examples so uncertainty is a learned behaviour, lower temperature, and evaluate specifically for fabrication on questions with no valid answer.

Compare LoRA, adapters, prefix tuning and full fine-tuning on a production axis.

LoRA wins in practice because it's the only one that merges into the base weights, so it costs nothing at inference. Adapters add permanent latency, prefix tuning eats context budget, and full fine-tuning costs a model copy per task.

Houlsby adapters sit in series between sub-layers, so their compute can't be folded away. Prefix and prompt tuning prepend learned vectors, consuming context window and generally topping out lower in quality. Full fine-tuning has the highest ceiling for large domain shifts but demands a cluster, 14 GB of storage per variant, and carries real forgetting risk. LoRA gives roughly full-FT quality on behaviour tasks at 1% of trainable parameters with zero merged inference cost — which is why it's the default.

How would you choose between DPO, ORPO, KTO and PPO?

DPO if you have paired preferences and an SFT model. ORPO if you want one stage and no reference model. KTO if your feedback is thumbs-up/down rather than pairs. PPO only if you have the team, the compute, and a need for online exploration.

ORPO folds preference learning into SFT with an odds-ratio penalty, cutting a stage and the reference model — attractive when compute is tight. KTO uses prospect-theory-style utilities on unpaired binary signals, which matters because production feedback is overwhelmingly thumbs-up/down, not rankings. SimPO removes the reference model with length normalisation. PPO's remaining advantage is that it can discover behaviours absent from the preference dataset, which offline methods structurally cannot.

What does an offline method structurally fail to learn?

Your model scores well offline and users complain after launch. Diagnose it.

Usually distribution shift between the eval set and real traffic, or a serving-layer mismatch — a different chat template, a truncated system prompt, or quantisation applied after evaluation.

Checklist: compare the exact prompt string the server builds against the training format, character for character; confirm sampling parameters match what you evaluated with; re-run the eval set against the deployed endpoint rather than the local model, which isolates infrastructure regressions; re-evaluate after quantisation, since 4-bit AWQ typically costs 1–2%; and embed real prompts to compare their distribution against training data. Then sample 100 real failures and read them — the pattern is usually obvious and absent from your eval set.

Explain the KV cache and why it dominates serving memory.

It stores key and value tensors for every past token so each new token doesn't recompute attention over the whole sequence. Its size grows linearly with context length and with concurrency, and at high batch sizes it typically exceeds the weights.

Per token, roughly 2 × layers × kv_heads × head_dim × bytes. For a 7B model at 4k context with 32 concurrent requests that's several gigabytes on top of 14 GB of weights. Grouped-query attention shrinks it by sharing KV heads across query heads; vLLM's PagedAttention removes fragmentation by allocating in blocks; quantising the cache to fp8 halves it again. It is usually the thing that caps your batch size, and therefore your throughput.

How do you decide whether a fine-tune is worth shipping?

It must beat the prompted baseline on the business metric by a margin larger than your evaluation noise, hold up on a human-reviewed golden set, and survive quantisation — with total cost of ownership accounted for.

Concretely: bootstrap a confidence interval on the test metric so you're not shipping a 1.5-point difference that's noise; check for regression on general capability, not just improvement on your task; re-run everything after merging and quantising; and price the ongoing cost — retraining cadence, GPU serving, adapter versioning, monitoring — against the prompting alternative. A fine-tune that wins by two points and adds a permanent maintenance burden is often the wrong call.

Coding interview questions

Q1 · Implement a LoRA layer and inject it into a model

Problem. Without using PEFT, write a LoRALinear wrapper and a function that replaces every nn.Linear whose name matches a target list. Report the trainable-parameter percentage and support merging.

Approach. Wrap the frozen linear, add A (random init) and B (zeros), scale by α/r. Walk the module tree with named_modules(), and use setattr on the parent to swap children in place — you can't mutate a dict while iterating it, so collect targets first.

Explanation. B = 0 means the model is bit-identical to the base at step 0, so training starts from pre-trained behaviour rather than perturbed noise. Merging works only because the LoRA branch is linear and parallel: W₀x + sBAx = (W₀ + sBA)x.

Complexity. Injection is O(M) over modules. Forward adds O(r(d+k)) per layer versus O(dk) for the base — about 0.4% extra FLOPs at r=8, d=k=4096, and zero after merging. Extra parameter space is O(r(d+k)) per adapted layer.

Follow-up. Add unmerge(), and make the wrapper work for nn.Conv1D as used in GPT-2.

Q2 · Build a collator that masks prompt tokens from the loss

Problem. Given chat-format examples, produce padded batches of input_ids, attention_mask and labels, where prompt tokens and padding are set to -100.

Approach. Render the prompt and the full conversation separately, tokenize both, and mask the first len(prompt_ids) label positions. Pad dynamically to the longest sequence in the batch rather than to a global maximum.

Explanation. PyTorch's cross-entropy skips index -100 entirely, so masked positions contribute neither loss nor gradient. Sorting examples by length before batching (a length-grouped sampler) reduces padding further and can cut training time meaningfully.

Complexity. Time O(B·L) for a batch of B sequences of max length L. Space O(B·L) for the three tensors.

Follow-up. Extend it to multi-turn conversations where every assistant turn should be trained on, not just the last.

Q3 · Estimate training memory before you launch the run

Problem. Write a function that estimates peak GPU memory for a given model size, precision, optimiser, and training strategy, so you can pick a configuration without trial-and-error OOMs.

Approach. Sum four terms — weights, gradients, optimiser state, activations — with bytes-per-parameter factors that depend on the strategy.

Explanation. The insight worth stating aloud: for full fine-tuning the optimiser state dominates (12 bytes per parameter versus 2 for the weights). PEFT shrinks the trainable count, which collapses both the gradient and optimiser terms, leaving the frozen weights as the main cost — which is exactly what quantisation then attacks.

Complexity. O(1) time and space — it's arithmetic, which is the point. Treat the result as ±20%; real runs vary with attention implementation and fragmentation.

Follow-up. Extend it to multi-GPU with ZeRO stages 1, 2 and 3, where optimiser state, gradients, and parameters are sharded in turn.

Q4 · Implement the DPO loss

Problem. Given policy and reference log-probabilities for chosen and rejected responses, implement the DPO loss and the implicit reward margin.

Approach. Compute the log-ratio for each response relative to the reference, take the difference, scale by β, and apply -logsigmoid. Use F.logsigmoid rather than log(sigmoid(x)) for numerical stability.

Explanation. The reference log-probabilities are what keep this stable. Without them the model could raise the chosen response's probability by simply collapsing its output distribution; measuring the change relative to the frozen reference means it must specifically prefer the chosen answer. β controls how far the policy may drift: small β allows large drift and risks degeneration, large β keeps it close to the SFT model and learns little. Watch reward_accuracy — if it doesn't climb above ~0.6, your preference data is probably noise.

Complexity. One forward pass through the policy and one through the reference for each of chosen and rejected — four sequence forwards per pair, O(B·L·V) time dominated by the vocabulary projection, O(B·L·V) space for the logits, which is why DPO batches are small.

Follow-up. With a LoRA policy you can eliminate the reference model entirely. How, and why does that work?

Q5 · Deduplicate a 40 GB JSONL dataset that won't fit in memory

Problem. Remove exact and near-duplicate examples from a dataset too large for RAM, preserving order, and report statistics.

Approach. Stream line by line. Store only fixed-size hashes, not text. For exact duplicates, a normalised MD5 in a set. For near-duplicates, MinHash over shingles with LSH banding.

Explanation. The naive approach compares every pair — O(n²), which is 10¹² comparisons on a million examples. MinHash reduces each document to a fixed-size sketch whose collision probability approximates Jaccard similarity; LSH banding then only compares documents that already agree on a whole band, making the expected work near-linear. Tune the threshold with the banding relation: similarity ≈ (1/bands)^(1/rows).

Complexity. Time O(n·s·p) where s is shingles per document and p is permutations — linear in dataset size. Space O(n·p) for the sketches, which is orders of magnitude smaller than the text and the reason this fits in RAM when the data doesn't.

Follow-up. How would you shard this across machines, and how do you keep the best copy of a duplicate group rather than the first one you happened to see?

Section 17

Cheat sheet

Fine-tuning

Continue training a pre-trained model on task-specific data. Changes behaviour, not knowledge. Same next-token objective, tiny fraction of the data.

SFT

Supervised fine-tuning on (prompt, response) pairs. Mask prompt tokens with -100 so loss is computed only on the answer.

PEFT

Freeze the base, train a small number of new parameters. Family: LoRA, QLoRA, adapters, prefix/prompt tuning, IA³, BitFit.

LoRA

h = Wx + (α/r)·BAx. B zero-init, A random. Train ~0.1–1% of parameters. Merges into W for free inference.

QLoRA

4-bit NF4 base + double quantisation + paged optimizers + bf16 LoRA adapters. 7B fine-tunes in ~7 GB. ~25% slower.

RLHF

SFT → reward model from human rankings → PPO with KL penalty. Four models, unstable, expensive, powerful.

DPO

Preference optimisation without a reward model or RL. Loss on chosen/rejected log-ratios vs a frozen reference. β = 0.1–0.5.

Tokenization

Text → subword IDs. ~0.75 words per token. Use the model's own chat template. Always append EOS. Pad right to train, left to generate.

Quantization

Training: NF4 via bitsandbytes. Serving: AWQ, GPTQ, FP8, GGUF. Expect 4× memory cut, 1–2% quality cost. Re-evaluate after.

Memory (7B)

Full ≈ 112 GB · LoRA ≈ 18 GB · QLoRA ≈ 7 GB. Full FT ≈ 16–20 bytes/param. Effective batch = micro × accum × GPUs.

Key hyperparameters

lr 2e-4 (LoRA) / 2e-5 (full) · r=16, α=32, dropout 0.05 · 3 epochs · cosine + 3% warmup · bf16 · grad checkpointing on.

Evaluation

Train/val loss · perplexity = exp(loss) · macro-F1 for labels · ROUGE/BLEU for generation (weak) · LLM judge · human golden set.

Overfitting

Val loss rises while train falls. Fix: more/diverse data → early stopping → dropout → lower rank → lower lr.

Fine-tuning vs RAG

Behaviour vs knowledge. Weights vs context. Retrain vs re-index. No citations vs citations. Use both in production.

Deployment

Merge or hot-swap adapters · AWQ quantise · vLLM/TGI · watch TTFT, TPOT, KV cache · canary + rollback · version every hash.

Debug order

Print a rendered example → check trainable params ≠ 0 → overfit one batch → raise lr → check labels aren't all -100.

Say this in an interview

"Fine-tuning teaches behaviour; RAG supplies knowledge." · "B is zero-init so step 0 is identical to the base." · "Quantised weights are frozen — gradients flow through, not into."

Red flags to avoid

Fine-tuning to add facts · no prompted baseline · no held-out set · row-wise splitting with duplicates · shipping without re-evaluating after quantisation.
