Q1. What is RAG (Retrieval-Augmented Generation)?

▶ Answer RAG is a technique that combines a retrieval system (finding relevant documents) with a generation system (an LLM) to answer questions. Instead of relying only on the LLM's trained knowledge (which can be outdated or hallucinated), RAG fetches relevant, real-time context from a knowledge base and passes it to the LLM.

Real-world analogy: Imagine an open-book exam. Without RAG, the student relies on memory (LLM only). With RAG, the student can look up the textbook (retrieval) before writing the answer (generation).

Q2. Why do we need RAG? What problems does it solve?

▶ Answer RAG solves 4 key problems with vanilla LLMs:

Problem Without RAG With RAG
Knowledge cutoff LLM only knows up to training date Retrieves real-time documents
Hallucination LLM makes up facts Grounded in retrieved evidence
Private data LLM never saw your company docs Retrieves from your private KB
Cost of fine-tuning Expensive to retrain for new data Just index new docs, no retraining

Q3. Explain the two main components of a RAG system.

▶ Answer

1. Indexing Pipeline (Offline / One-time)

Documents → Parse → Chunk → Embed → Store in Vector DB

2. Query Pipeline (Online / Real-time)

Query → Embed Query → Retrieve Top-K Chunks → Build Prompt → LLM → Answer

Q4. What is the difference between a parametric and non-parametric memory in LLMs?

▶ Answer - Parametric memory: Knowledge stored in the LLM's weights during training. Fixed, can't be updated without retraining. - Non-parametric memory: External storage (vector databases, document stores) that can be updated anytime. RAG uses non-parametric memory.

🎯 Interviewer's intent: Tests if you understand why RAG is architecturally significant — it externalizes memory.

▶ Answer

Q7. What is a vector embedding?

▶ Answer A vector embedding is a numerical representation of text (or images, audio) as a list of numbers (a vector in high-dimensional space). Similar meanings → similar vectors → close in space.

"dog"  →  [0.2, 0.8, 0.1, ..., 0.4]  (384 or 1536 dimensions)
"puppy"→  [0.21, 0.79, 0.12, ..., 0.39]  ← very similar!
"car"  →  [0.9, 0.1, 0.7, ..., 0.2]  ← very different

💡 Memory Trick: Embeddings are like GPS coordinates for meaning. Similar meaning = close GPS location.

Q9. What is cosine similarity and why is it used in RAG?

▶ Answer Cosine similarity measures the angle between two vectors (not the distance). It ranges from -1 to 1 where 1 = identical direction (most similar).

Formula:  cos(θ) = (A · B) / (|A| × |B|)

Vector A: [1, 0, 1]   → "dog food"
Vector B: [0.9, 0, 1] → "pet nutrition"
cos(θ) = 0.95 → highly similar ✅

Vector C: [0, 1, 0]   → "car engine"
cos(θ with A) = 0.1 → very different ❌

Why cosine over Euclidean? Cosine is length-invariant — a short and long document about the same topic get same similarity. Euclidean would penalize the longer doc.

Q11. What is "grounding" in the context of RAG?

▶ Answer Grounding means the LLM's answer is anchored to real retrieved documents, not made up. A grounded answer can be traced back to a specific source chunk. Grounding reduces hallucination.

Grounded answer example:

"Based on document HR-Policy-2024.pdf (page 3): Employees receive 15 days of paid vacation annually."

Ungrounded (hallucinated) answer:

"Employees get 20 days of vacation." (made up)

Q12. What is the "knowledge cutoff" problem and how does RAG solve it?

▶ Answer LLMs are trained on data up to a specific date (e.g., GPT-4's cutoff is early 2024). Events after that date are unknown to the model. RAG solves this by: 1. Indexing new documents (news, updated policies, product releases) into the vector DB 2. Retrieving that fresh content at query time 3. The LLM uses that retrieved context — no retraining needed

▶ Answer

Retrieval Failure Wrong/irrelevant docs retrieved Asked about "Python" (programming) but got "Python" (snake) docs

Q15. What is the "Lost in the Middle" problem?

▶ Answer Research shows LLMs perform best when relevant information is at the beginning or end of the context window, and worst when it's in the middle. This is a critical production concern.

Context Window:
┌─────────────────────────────────────────────┐
│ [Chunk A] ← LLM pays HIGH attention         │
│ [Chunk B]                                   │
│ [Chunk C] ← LLM pays LOW attention ⚠️       │
│ [Chunk D]                                   │
│ [Chunk E] ← LLM pays HIGH attention         │
└─────────────────────────────────────────────┘

Solutions: 1. Put most relevant chunks at beginning/end of context 2. Reduce number of retrieved chunks (top-3 instead of top-10) 3. Use reranker to select only the most critical chunks

Q17. What is the Unstructured library and why is it popular?

▶ Answer Unstructured is a Python library that handles 40+ document types with a single API. It automatically detects document type and extracts structured elements (titles, narratives, tables, lists).

Q19. What is OCR and when do you need it in RAG?

▶ Answer OCR (Optical Character Recognition) converts images of text into machine-readable text. You need it when: 1. PDFs are scanned (no text layer) 2. Documents are photographed images 3. Handwritten notes need digitization

Tools: - Tesseract — free, open-source, good for clear scans - AWS Textract — production-grade, handles forms/tables - Google Document AI — enterprise, complex layouts - Azure Form Recognizer — structured forms

⚠️ Common mistake: Not checking if a PDF is text-native vs. scanned. Use pdfplumber — if text extraction returns empty strings, you need OCR.

Q21. How do you handle tables in RAG systems?

▶ Answer Tables are one of the hardest challenges. Three strategies:

Strategy 1: Serialize as text

| Revenue | Q1  | Q2  |
|---------|-----|-----|
| Product | $1M | $2M |

→ "Revenue: Q1=$1M, Q2=$2M for Product"

Strategy 2: Keep as markdown table (works well with modern LLMs)

Strategy 3: Multi-vector approach — Store original table + generate a text summary, embed the summary, return both.

Strategy 4: Use specialized table extractors — Camelot, pdfplumber for PDFs; pandas for CSV/Excel.

⚠️ Production tip: Never flatten a table into plain text without structure — LLMs can't understand "Revenue Q1 $1M Q2 $2M" as table data.

🟢 Beginner

Q24. What is chunking and why is it necessary in RAG?

▶ Answer Chunking is splitting a large document into smaller pieces (chunks) that can be: 1. Embedded (embedding models have token limits, typically 512-8192 tokens) 2. Retrieved (specific relevant pieces, not entire documents) 3. Fit into context (LLM context windows have limits)

Without chunking, a 500-page PDF can't be embedded or retrieved meaningfully.

Q25. What are the main chunking strategies?

▶ Answer

CHUNKING STRATEGIES COMPARISON:
════════════════════════════════════════════════════════════════

1. FIXED-SIZE CHUNKING
───────────────────────
"The cat sat on the mat. The dog ran away. The bird flew high."
                    ↓ chunk_size=20 chars, overlap=5
[The cat sat on the] [on the mat. The dog] [The dog ran away.] ...

✅ Simple, predictable
❌ Breaks sentences mid-thought

2. RECURSIVE CHARACTER SPLITTING
──────────────────────────────────
Tries separators in order: \n\n → \n → . → " " → char
Respects paragraph/sentence boundaries first.

✅ Smarter than fixed-size
✅ Language-aware
❌ Can still break semantic units

3. SENTENCE-BASED CHUNKING
────────────────────────────
Split on sentence boundaries (NLTK, spaCy)

✅ Semantically clean units
❌ Sentences can be too short for good embeddings

4. SEMANTIC CHUNKING
─────────────────────
Split where embedding similarity drops between sentences

Sentences: [s1][s2][s3] --- big drop here --- [s4][s5]
→ Chunk1: [s1,s2,s3]  Chunk2: [s4,s5]

✅ Semantically coherent chunks
❌ Expensive (requires embedding every sentence)

5. DOCUMENT-STRUCTURE AWARE
────────────────────────────
Split on headers/sections (Markdown, HTML h1/h2)

# Introduction → chunk1
## Background → chunk2

✅ Preserves document intent
❌ Sections can be very uneven in size

6. AGENTIC / PROPOSITION CHUNKING
───────────────────────────────────
LLM extracts atomic propositions/facts from text

"Apple Inc., founded in 1976, makes iPhones."
→ ["Apple Inc. was founded in 1976",
   "Apple Inc. makes iPhones"]

✅ Most semantically precise
❌ Very expensive (LLM call per chunk)

Q26. What is chunk overlap and why is it important?

▶ Answer Chunk overlap means consecutive chunks share some text. This prevents information at chunk boundaries from being "lost."

Without Overlap (chunk_size=100):
[...the revenue for Q3 was] [12M dollars, exceeding...]
                            ↑ "12M" context lost if only 1st chunk retrieved

With Overlap (chunk_size=100, overlap=20):
[...the revenue for Q3 was] [Q3 was 12M dollars, exceeding...]
                            ↑ "12M" is captured with context ✅

Typical overlap values: 10-20% of chunk size. Too much overlap = redundancy and higher storage cost.

Q27. What chunk size should you use? What factors influence the decision?

▶ Answer

Factor Smaller Chunks (128-256 tokens) Larger Chunks (512-1024 tokens)
Precision Higher — specific retrieval Lower — may include noise
Context Lower — lacks surrounding info Higher — more context per chunk
Cost More chunks = more embeddings Fewer embeddings
Use case Factual QA, specific lookup Summarization, complex reasoning

Golden Rule: Match chunk size to the query type and embedding model's sweet spot.

Typical Recommendations:
- Short factual queries:    128–256 tokens
- General knowledge base:  512 tokens (sweet spot)
- Long-form documents:     1024 tokens
- Code files:              Function-level (semantic)

Q28. What is the Small-to-Big (Parent-Child) chunking strategy?

▶ Answer Index small chunks for precise retrieval, but return the parent (larger) chunk for better context to the LLM.

SMALL-TO-BIG CHUNKING:
═══════════════════════════════════════════════════════

Document (full)
├── Parent Chunk A (512 tokens) — stored but NOT embedded for search
│   ├── Child Chunk A1 (128 tokens) ← embedded & searchable
│   ├── Child Chunk A2 (128 tokens) ← embedded & searchable
│   └── Child Chunk A3 (128 tokens) ← embedded & searchable
└── Parent Chunk B (512 tokens)
    ├── Child Chunk B1 (128 tokens) ← embedded & searchable
    └── Child Chunk B2 (128 tokens) ← embedded & searchable

Query → matches Child A2 → return Parent Chunk A (full context)
                                   ↑ Much better context for LLM!

Why it works: Small chunks = precise matching. Large parent chunks = rich context for generation.

Q29. What is the Sliding Window approach and when does it help?

▶ Answer Sliding window creates chunks that overlap significantly, like a window sliding over the text:

Text: [W1][W2][W3][W4][W5][W6][W7][W8][W9][W10]

Chunk 1: [W1 W2 W3 W4 W5]
Chunk 2:    [W2 W3 W4 W5 W6]  ← slides by 1 word
Chunk 3:       [W3 W4 W5 W6 W7]
...

When it helps: Medical/legal documents where missing a phrase at a boundary could mean missing a critical condition or clause.

Q30. What is semantic chunking and how does it work technically?

▶ Answer

# Semantic Chunking Algorithm:

Step 1: Split text into sentences
sentences = ["Apple makes iPhones.", "Tim Cook is CEO.", "Samsung makes Galaxy."]

Step 2: Embed each sentence
embeddings = [embed(s) for s in sentences]

Step 3: Compute consecutive similarity
sim_1_2 = cosine_similarity(embed(s1), embed(s2))  # 0.85 (same topic)
sim_2_3 = cosine_similarity(embed(s2), embed(s3))  # 0.30 (topic shift!)

Step 4: Find breakpoints where similarity drops below threshold (e.g., 0.5)
breakpoints = [index where sim < threshold]

Step 5: Group sentences between breakpoints into chunks
Chunk 1: ["Apple makes iPhones.", "Tim Cook is CEO."]
Chunk 2: ["Samsung makes Galaxy."]

✅ Produces semantically coherent chunks ❌ 2x expensive (embed all sentences first)

Q31. Scenario: You're building a RAG system for a 10,000-page legal document repository. A lawyer complains that retrieved chunks often lack context (e.g., "as defined in Section 3" without the actual definition). How do you fix this?

▶ Answer This is a chunk boundary context loss problem. Multi-layered fix:

SOLUTION: HIERARCHICAL CHUNKING + METADATA ENRICHMENT

Step 1: Structure-aware parsing
  - Parse legal docs preserving: Section #, subsection, cross-references

Step 2: Hierarchical chunking
  - Small chunks (128 tokens) for retrieval precision
  - Parent sections (full legal section) for context delivery

Step 3: Metadata enrichment
  - Each chunk stores: section_number, references_sections: ["Section 3", "Appendix A"]

Step 4: Cross-reference resolution at query time
  - If retrieved chunk mentions "Section 3", also retrieve Section 3 chunk
  - Add it to context automatically

Step 5: Contextual chunk prefix (LLM-powered)
  - For each small chunk, use LLM to generate:
    "Context: This chunk is from Section 5.2 about Contract Termination..."
  - Prepend to the chunk text before embedding

Q32. What is a text embedding model and how does it work?

▶ Answer An embedding model (usually a Transformer-based model like BERT or similar) converts text into dense vectors. The model is trained via contrastive learning — pushing similar texts close together and dissimilar texts far apart.

Training (contrastive):
("cat", "feline") → similar → vectors pulled TOGETHER
("cat", "car")   → different → vectors pushed APART

Inference:
"What is machine learning?" → [0.12, -0.34, 0.89, ...]  (1536-dim vector)

Q34. What is the difference between a bi-encoder and cross-encoder?

▶ Answer

BI-ENCODER (used for retrieval/embedding):
════════════════════════════════════════
Query  → [Encoder] → vector_q
Document → [Encoder] → vector_d
Similarity = cosine(vector_q, vector_d)

✅ Fast: embed once, compare instantly
✅ Scalable: precompute all doc embeddings
❌ Less accurate (query and doc encoded independently)
Use: First-stage retrieval from millions of docs

CROSS-ENCODER (used for reranking):
════════════════════════════════════
[Query + Document] → [Encoder] → Relevance Score (0-1)

✅ Very accurate (sees both together, full attention)
❌ Slow: must score every query-doc pair fresh
❌ Not scalable for large corpora
Use: Second-stage reranking of top-20 retrieved docs

Q36. Why must you use the SAME embedding model for indexing and querying?

▶ Answer Different embedding models create vectors in different spaces (different coordinate systems). Querying with Model B's vector in a database indexed with Model A's vectors would return completely wrong results — like searching GPS coordinates from one map in a different coordinate system.

❌ WRONG:
Index time:  "dog" → Model-A → [0.2, 0.8, ...]
Query time:  "dog" → Model-B → [0.9, 0.1, ...]  ← Different space!
Result: Garbage retrieval

✅ CORRECT:
Index time:  "dog" → Model-A → [0.2, 0.8, ...]
Query time:  "dog" → Model-A → [0.2, 0.8, ...]  ← Same space!
Result: Correct retrieval

⚠️ Production trap: If you switch embedding models, you MUST re-index all documents.

Q43. What is Approximate Nearest Neighbor (ANN) search? Why "approximate"?

▶ Answer Finding the exact nearest neighbor in high-dimensional space requires comparing the query against every stored vector — O(n) time. For millions of vectors, this is too slow.

ANN trades a tiny bit of accuracy for massive speed gains using index structures:

Exact NN: Compare to ALL 10M vectors → 100% accurate, 10 seconds
ANN:      Compare to ~1000 vectors → 99.9% accurate, 10 milliseconds ✅

Common ANN algorithms: - HNSW (Hierarchical Navigable Small World) — fastest, most popular - IVF (Inverted File Index) — good for large-scale datasets - LSH (Locality-Sensitive Hashing) — older, less used - ScaNN (Google) — highly optimized for production

Q44. What is HNSW and why is it the most popular ANN index?

▶ Answer HNSW builds a multi-layer graph where nodes are vectors and edges connect nearby vectors. Search starts at the top layer (fewer, long-range connections) and drills down.

HNSW STRUCTURE:
═══════════════════════════════════════════
Layer 2 (sparse): A ────────── E
                  (long-range connections)
Layer 1:          A ─── B ─── C ─── E
                  (medium-range)
Layer 0 (dense):  A─B─C─D─E─F─G─H
                  (all nodes, short connections)

Search for query Q:
1. Start at Layer 2: find nearest → E
2. Descend to Layer 1: greedy search near E → C
3. Descend to Layer 0: fine-grained search → D (answer)

HNSW parameters: - M — connections per node (higher = more accurate, more RAM) - ef_construction — search depth during indexing (higher = better index quality) - ef_search — search depth at query time (higher = better recall, slower)

Q45. What is IVF (Inverted File Index) and when do you choose it over HNSW?

▶ Answer

IVF STRUCTURE:
═══════════════════════════════════════════
Training: Cluster all vectors into K clusters (K-means)

         Cluster 1        Cluster 2        Cluster 3
         ┌───────┐        ┌───────┐        ┌───────┐
         │v1,v3  │        │v2,v5  │        │v4,v6  │
         │v7,v8  │        │v9     │        │v10    │
         └───────┘        └───────┘        └───────┘

Query: 
1. Find nearest cluster centers (1-10 clusters)
2. Only search vectors in those clusters
3. Return best matches
HNSW IVF
Speed Very fast Fast
RAM High Lower
Disk Limited Good (IVFPQ)
Billion-scale Challenging Better with IVF+PQ
Update-friendly Yes Needs re-clustering

Choose IVF when: Billions of vectors, RAM-constrained, or using product quantization (IVF+PQ) for compression.

Q46. What is Product Quantization (PQ) and why does it matter?

▶ Answer PQ compresses high-dimensional vectors to save memory, enabling billion-scale vector search.

WITHOUT PQ:
1 vector = 1536 floats × 4 bytes = 6,144 bytes ≈ 6KB
1M vectors = 6 GB RAM!

WITH PQ:
Split 1536-dim vector into 96 sub-vectors of 16-dims each
Each sub-vector → nearest centroid code (1 byte)
1 vector = 96 bytes (64x compression!)
1M vectors = 96 MB ✅

Trade-off: ~5-10% accuracy loss for 64x memory savings

Q49. What is the difference between index types: Flat, IVF, HNSW, and ScaNN?

▶ Answer

FLAT (Brute-force):
- Compares query to EVERY vector
- 100% accurate, very slow for large datasets
- Use: <100K vectors, development/testing

IVF (Inverted File):
- Clusters vectors, searches relevant clusters only
- Good accuracy, scalable with IVF+PQ
- Use: 1M–1B vectors, RAM-constrained

HNSW (Hierarchical Navigable Small World):
- Graph-based navigation
- Fastest query speed, high recall
- High RAM usage
- Use: 100K–100M vectors, speed-critical

ScaNN (Google Scalable Nearest Neighbors):
- Asymmetric quantization, highly optimized
- Best speed+accuracy trade-off
- Use: Google-scale production

Q50. How do you handle vector database updates when documents change?

Q56. What is the difference between dense retrieval and sparse retrieval?

▶ Answer

DENSE RETRIEVAL (Semantic Search):
════════════════════════════════════
- Uses neural embedding vectors
- Captures MEANING, semantics, synonyms
- "dog" ↔ "canine" ↔ "puppy" (all similar)
- Uses: cosine similarity, dot product
- Index: HNSW, IVF
- Miss: exact rare keywords ("Product SKU #XH-2341")

SPARSE RETRIEVAL (Keyword/Lexical Search):
══════════════════════════════════════════
- Uses term frequency (TF-IDF, BM25)
- Captures EXACT keyword matches
- "dog" ≠ "canine" (different tokens)
- Uses: inverted index
- Index: Elasticsearch, Lucene
- Miss: semantic variations, paraphrases

TF-IDF Formula: TF × log(N/df)
  TF  = frequency of term in doc
  N   = total documents
  df  = docs containing the term

BM25 (Better than TF-IDF): Adds length normalization
Score(q,d) = Σ IDF(qi) × (f(qi,d) × (k1+1)) / (f(qi,d) + k1×(1-b+b×|d|/avgdl))
  k1 = term saturation (1.2-2.0)
  b  = length normalization (0.75)

Q58. What is Reciprocal Rank Fusion (RRF) and how does it work?

▶ Answer RRF is a fusion algorithm that merges ranked lists from multiple retrievers without needing score normalization.

RRF FORMULA:
RRF_score(d) = Σ 1 / (k + rank_i(d))
  k = 60 (constant, prevents over-weighting top ranks)
  rank_i(d) = rank of document d in list i

EXAMPLE:
Doc "Metformin dosage" appears in:
  - Dense retrieval: rank 3
  - Sparse retrieval: rank 1

RRF = 1/(60+3) + 1/(60+1) = 0.0159 + 0.0164 = 0.0323

Doc "Diabetes meds overview":
  - Dense retrieval: rank 1
  - Sparse retrieval: rank 15

RRF = 1/(60+1) + 1/(60+15) = 0.0164 + 0.0133 = 0.0297

Winner: "Metformin dosage" (0.0323 > 0.0297) ✅
Even though it wasn't #1 in either list, it was consistently relevant

Q59. What is Maximal Marginal Relevance (MMR) and when do you use it?

▶ Answer MMR selects documents that are relevant to the query AND diverse from already-selected documents. Prevents retrieving 5 chunks that all say the same thing.

MMR ALGORITHM:
════════════════════════════════════════════

Initial candidates (top-20 from vector search):
[A=0.9, B=0.88, C=0.87, D=0.85, E=0.84, ...]
where score = cosine similarity to query

MMR selection (λ=0.5, selecting top-3):
Step 1: Select A (highest relevance: 0.9) ✅
Step 2: Score remaining by: λ×sim(q,d) - (1-λ)×max_sim(d, selected)
        B: 0.5×0.88 - 0.5×0.95 = 0.44 - 0.47 = -0.03 (B is too similar to A)
        C: 0.5×0.87 - 0.5×0.20 = 0.43 - 0.10 = 0.33 (C is different from A!)
        Select C ✅
Step 3: Score remaining with A and C considered...
        Select E (most relevant AND different from A,C) ✅

Result: [A, C, E] — relevant AND diverse
vs naive top-3: [A, B, C] — relevant but redundant

Q75. What is hallucination in LLMs and what types exist in RAG systems?

▶ Answer

TYPES OF HALLUCINATION IN RAG:

1. INTRINSIC HALLUCINATION (Context contradiction)
   LLM contradicts information in the retrieved context
   Context: "Product A costs $100"
   Answer:  "Product A costs $150" ← made up ❌

2. EXTRINSIC HALLUCINATION (Context extension)
   LLM adds information NOT in the context
   Context: "Aspirin relieves headaches"
   Answer:  "Aspirin relieves headaches and prevents cancer" ← invented ❌

3. RETRIEVAL-INDUCED HALLUCINATION
   Wrong context retrieved → LLM gives confident wrong answer
   Query: "CEO of Acme Corp"
   Retrieved: "CEO of Globex Corp is John Smith"
   Answer: "CEO of Acme Corp is John Smith" ← wrong retrieval ❌

4. FAITHFULNESS FAILURE
   LLM changes numbers, dates, names even when context is correct
   Context: "Founded in 1984"
   Answer:  "Founded in 1948" ← number transposition ❌

Q76. How do you reduce hallucinations in RAG systems?

▶ Answer

ANTI-HALLUCINATION STRATEGIES:
════════════════════════════════════════════════════════

1. STRONG SYSTEM PROMPT GROUNDING
   "Answer ONLY from provided context. If unsure, say 'I don't know.'"
   "Never add information not explicitly stated in the documents."

2. RETRIEVAL QUALITY (Fix at source)
   - Better chunking → more relevant context
   - Reranking → most relevant chunks at top
   - Higher top-K → less chance of missing answer

3. TEMPERATURE = 0 (or very low)
   Low temperature → LLM sticks to context, less creative invention
   temperature=0 → Deterministic, closest to context

4. CITATION FORCING
   "Quote the exact sentence from context that supports your answer."
   LLM must find the sentence → can't invent what doesn't exist

5. FAITHFULNESS CHECKING (Post-generation)
   Use another LLM call or NLI model to verify:
   "Does this answer contradict the retrieved context?" → flag if yes

6. ABSTAIN WHEN UNCERTAIN
   Teach model to say "I don't have this information" instead of guessing
   Use confidence calibration or special tokens

7. SELF-CONSISTENCY
   Generate 3 answers → check if they agree → if not, flag low confidence

Q77. What is groundedness checking and how do you implement it?

# Groundedness Check Implementation

from transformers import pipeline
nli = pipeline("text-classification", model="cross-encoder/nli-deberta-v3-base")

def check_groundedness(answer_sentence, context):

    # result: {"label": "ENTAILMENT", "score": 0.95}
    return result["label"] == "ENTAILMENT" and result["score"] > 0.8

prompt = """

Answer: {answer}

For each statement in the answer, determine if it is:
1. Supported by the context (GROUNDED)

List each statement and its status:
"""

APPROACH 3: Sentence-level decomposition
1. Split answer into individual claims
2. Check each claim against context
3. Flag any claim not supported
4. Return groundedness score = grounded_claims / total_claims

Q80. What is Context Precision and how is it calculated?

▶ Answer Context Precision measures what fraction of the retrieved chunks are actually relevant to the question. Precision = signal / noise in retrieved context.

CONTEXT PRECISION:
═══════════════════════════════════════════

Question: "What is the vacation policy?"
Retrieved 5 chunks:
  [1] "Employees get 15 vacation days" ← RELEVANT ✅
  [2] "Benefits package overview"       ← RELEVANT ✅
  [3] "Office dress code policy"        ← NOT RELEVANT ❌
  [4] "Vacation accrual rate"           ← RELEVANT ✅
  [5] "IT password policy"              ← NOT RELEVANT ❌

Precision@5 = 3 relevant / 5 total = 0.60 (60%)

WEIGHTED CONTEXT PRECISION (considers ranking):
  Position 1: relevant → 1/1 = 1.0
  Position 2: relevant → 2/2 = 1.0
  Position 3: not relevant → 2/3 = 0.67 (skip)
  Position 4: relevant → 3/4 = 0.75
  Position 5: not relevant → skip

Average precision = (1.0 + 1.0 + 0.75) / 3 = 0.917

High precision: Retrieved docs are relevant (low noise)
Low precision: Retrieved docs are off-topic (high noise)

Q81. What is Context Recall and how is it different from Precision?

▶ Answer Context Recall measures if all the ground-truth relevant information was captured in the retrieved context.

CONTEXT RECALL:
═══════════════════════════════════════════

Ground truth answer: "Employees get 15 vacation days,
                      accrue at 1.25 days/month,
                      and can carry over up to 5 days."

Retrieved context:
  [1] "Employees get 15 vacation days" ← covers statement 1 ✅
  [2] "Accrual rate is 1.25 days per month" ← covers statement 2 ✅
  [3] "Dress code: business casual" ← irrelevant
  [4] "IT policy" ← irrelevant
  # Missing: carryover information! ← statement 3 NOT covered ❌

Recall = 2 covered statements / 3 total statements = 0.67

PRECISION vs RECALL:
  High Precision + Low Recall:  Retrieves few but relevant docs (misses some facts)
  Low Precision + High Recall:  Retrieves everything but lots of noise
  Ideal: High Precision + High Recall → only relevant docs, covers all facts

Q82. What is Faithfulness in RAG evaluation?

▶ Answer Faithfulness measures whether the generated answer is supported by the retrieved context (no hallucinations).

FAITHFULNESS SCORING:
═══════════════════════════════════════════════

Retrieved Context: "The Eiffel Tower is 330m tall and was built in 1889."

Answer A: "The Eiffel Tower is 330m tall and was completed in 1889."
  → All claims supported by context → Faithfulness = 1.0 ✅

Answer B: "The Eiffel Tower is 330m tall and has 1710 steps."
  → "330m tall" ← supported ✅
  → "1710 steps" ← NOT in context ❌
  → Faithfulness = 1/2 = 0.5 ⚠️

Answer C: "The Eiffel Tower is 350m tall."
  → "350m" contradicts context (330m) ← direct contradiction ❌
  → Faithfulness = 0.0 ❌

CALCULATION:
Step 1: Decompose answer into atomic claims
Step 2: For each claim, check if context entails it
Step 3: Faithfulness = supported_claims / total_claims

Q83. What is Answer Relevance in RAG evaluation?

▶ Answer Answer Relevance measures whether the generated answer actually addresses the question (not whether it's factually correct, but whether it's ON TOPIC).

ANSWER RELEVANCE:
═════════════════════════════════════════════

Question: "What are the side effects of Aspirin?"

Answer A: "Aspirin can cause stomach upset, bleeding, and allergic reactions."
  → Directly answers the question ✅ → High relevance

Answer B: "Aspirin was developed by Bayer in 1897 and is widely used for pain."
  → Factually correct but doesn't answer "side effects" ❌ → Low relevance

MEASUREMENT METHOD (RAGAS):
1. Use LLM to generate N questions that the answer would answer
2. Compute cosine similarity between generated questions and original question
3. Average similarity = Answer Relevance score

High relevance: Answer directly addresses the question
Low relevance: Answer is off-topic (even if factually accurate)

Q85. What is MRR (Mean Reciprocal Rank) and NDCG?

▶ Answer

MEAN RECIPROCAL RANK (MRR):
═══════════════════════════════════════════
Measures how high the first relevant document appears in results

Query 1: Answer at rank 3 → RR = 1/3 = 0.33
Query 2: Answer at rank 1 → RR = 1/1 = 1.00
Query 3: Answer at rank 2 → RR = 1/2 = 0.50

MRR = (0.33 + 1.00 + 0.50) / 3 = 0.61

MRR = 1.0 → First result is always correct
MRR = 0.5 → Correct answer usually at rank 2

NDCG (Normalized Discounted Cumulative Gain):
═════════════════════════════════════════════
Considers GRADED relevance (not just binary relevant/not)

Relevance scores: [3, 2, 3, 0, 1, 2] (graded 0-3)
DCG = 3/log(2) + 2/log(3) + 3/log(4) + 0/log(5) + 1/log(6) + 2/log(7)
    = 3 + 1.26 + 1.5 + 0 + 0.39 + 0.71 = 6.86

Ideal DCG (best possible ranking) = IDCG
NDCG = DCG / IDCG (normalized to 0-1)

High NDCG → Highly relevant docs ranked first

Q92. What is Self-RAG and how is it different from standard RAG?

▶ Answer Self-RAG trains the LLM to decide when to retrieve, what to retrieve, and critique its own output using special reflection tokens.

SELF-RAG FLOW:
══════════════════════════════════════════════════════════════

Query: "What year was Marie Curie born?"

Step 1: RETRIEVE decision
  LLM generates [Retrieve] token
  → Does this query need retrieval? Yes (factual) → RETRIEVE
  → Is it a creative task? No retrieval needed

Step 2: Retrieve documents (only if [Retrieve] = Yes)

Step 3: ISREL — Is retrieved document relevant?
  LLM generates [IsRel] = relevant / irrelevant
  → If irrelevant: skip this document

  [Retrieve]         → Should I retrieve?
  [IsRel]            → Is doc relevant?

Q94. What is Multi-Hop RAG and when is it needed?

▶ Answer Multi-hop RAG handles queries requiring information from multiple documents chained together — you can't answer without combining facts from different sources.

MULTI-HOP RAG EXAMPLE:
══════════════════════════════════════════════════════════════

Query: "Who is the CEO of the company that acquired DeepMind?"

Hop 1: Retrieve → "DeepMind acquired by Google (Alphabet) in 2014"
                              ↓
Hop 2: Retrieved fact: "Alphabet Inc."
       New sub-query: "Who is the CEO of Alphabet Inc.?"
       Retrieve → "Sundar Pichai is CEO of Alphabet since 2019"
                              ↓
Final Answer: "Sundar Pichai (CEO of Alphabet, which acquired DeepMind)"

ITERATIVE MULTI-HOP PIPELINE:
═════════════════════════════════════════════════════

query = "Who is the CEO of the company that acquired DeepMind?"
context = []
max_hops = 3

for hop in range(max_hops):
    # Retrieve based on current query + accumulated context
    new_docs = retrieve(current_query)
    context.extend(new_docs)

    # LLM decides: can I answer now, or need another hop?
    decision = llm.decide(question=query, context=context)

    if decision.can_answer:
        return llm.answer(query, context)
    else:
        # Generate follow-up sub-query
        current_query = decision.next_query

Types of multi-hop reasoning:
  Bridge: A→B→C (each hop bridges to next)
  Comparison: Find facts about A AND B, then compare
  Intersection: Find entity that satisfies multiple constraints

Q98. What is Fusion RAG?

▶ Answer Fusion RAG generates multiple query variations, retrieves from each, then fuses all results using RRF (Reciprocal Rank Fusion).

Step 1: GENERATE MULTIPLE QUERIES

  Q1: "What are the health benefits of intermittent fasting?"
  Q2: "How does intermittent fasting affect weight loss?"
  Q3: "Intermittent fasting and metabolic health research"
  Q4: "Time-restricted eating scientific evidence"

  Q1 → [Doc A, Doc B, Doc C]
  Q2 → [Doc B, Doc D, Doc E]
  Q3 → [Doc A, Doc E, Doc F]
  Q4 → [Doc C, Doc F, Doc G]

  Doc B: appears in Q1(rank 2) + Q2(rank 1) → high RRF score ✅
  Doc A: appears in Q1(rank 1) + Q3(rank 1) → high RRF score ✅
  Doc G: only in Q4(rank 3) → lower RRF score

Step 4: TOP-K from fused results → LLM context

BENEFIT: Much better recall than single-query retrieval

Q103. How do you implement semantic caching in RAG?

▶ Answer Semantic caching stores results for queries and returns cached results for semantically similar (not just identical) new queries.

SEMANTIC CACHE ARCHITECTURE:
══════════════════════════════════════════════════════════════

WITHOUT SEMANTIC CACHE:
  "What is vacation policy?" → Full RAG pipeline → 450ms
  "Tell me about vacation days" → Full RAG pipeline → 450ms (again!)
  These are similar enough to share result!

WITH SEMANTIC CACHE:
  Query #1: "What is vacation policy?"
    → Cache MISS
    → Full RAG pipeline → 450ms
    → Store: {embedding: [...], result: "15 days..."} in cache

  Query #2: "Tell me about vacation days"
    → Embed query → Compare to cached embeddings
    → cos_sim("vacation days", "vacation policy") = 0.92 > threshold(0.88)
    → Cache HIT! Return stored result → 15ms ✅

IMPLEMENTATION:
from redis import Redis
import numpy as np

class SemanticCache:
    def __init__(self, threshold=0.88, ttl=3600):
        self.redis = Redis()
        self.threshold = threshold
        self.ttl = ttl

    def get(self, query_embedding):
        # Fetch all cached embeddings (or use Redis vector search)
        keys = self.redis.keys("cache:*")
        for key in keys:
            cached = self.redis.hgetall(key)
            cached_emb = np.frombuffer(cached['embedding'])
            sim = cosine_similarity(query_embedding, cached_emb)
            if sim > self.threshold:
                return cached['result']  # Cache hit!
        return None  # Cache miss

    def set(self, query_embedding, result):
        key = f"cache:{uuid.uuid4()}"
        self.redis.hset(key, mapping={
            'embedding': query_embedding.tobytes(),
            'result': result
        })
        self.redis.expire(key, self.ttl)

PRODUCTION CONSIDERATIONS:
  - Use Redis with RediSearch vector module
  - TTL based on data volatility (1hr for FAQs, 24hr for stable docs)
  - Cache invalidation when docs updated
  - Monitor cache hit rate (target >25% for common query workloads)

def reciprocal_rank_fusion(ranked_lists, k=60):
    """
    ranked_lists: list of lists of document IDs, ordered by rank
    Returns: dict of doc_id -> RRF score
    """
    scores = {}
    for ranked_list in ranked_lists:
        for rank, doc_id in enumerate(ranked_list):
            if doc_id not in scores:
                scores[doc_id] = 0
            scores[doc_id] += 1 / (k + rank + 1)

    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

# CROSS-ENCODER RERANKER IMPLEMENTATION
from sentence_transformers import CrossEncoder
from dataclasses import dataclass
from typing import List, Tuple
import numpy as np

@dataclass
class RerankedResult:
    text: str
    original_rank: int
    rerank_score: float
    new_rank: int

class CrossEncoderReranker:
    def __init__(self, model_name="cross-encoder/ms-marco-MiniLM-L-6-v2"):
        self.model = CrossEncoder(model_name)

    def rerank(
        self, 
        query: str, 
        documents: List[str], 
        top_n: int = 5
    ) -> List[RerankedResult]:
        """
        Rerank documents by relevance to query.

        Args:
            query: The search query
            documents: List of candidate document texts
            top_n: Number of top results to return

        Returns:
            List of RerankedResult objects sorted by score
        """
        if not documents:
            return []

        # Create query-document pairs
        pairs = [[query, doc] for doc in documents]

        # Score all pairs (cross-encoder reads both together)
        scores = self.model.predict(pairs)

        # Create result objects with original rank
        results = [
            RerankedResult(
                text=doc,
                original_rank=i,
                rerank_score=float(score),
                new_rank=0  # Will be set below
            )
            for i, (doc, score) in enumerate(zip(documents, scores))
        ]

        # Sort by rerank score
        results.sort(key=lambda x: x.rerank_score, reverse=True)

        # Assign new ranks
        for i, result in enumerate(results):
            result.new_rank = i + 1

        return results[:top_n]

# SEMANTIC CHUNKING IMPLEMENTATION
from sklearn.metrics.pairwise import cosine_similarity
import numpy as np
from typing import List
from openai import OpenAI

client = OpenAI()

def get_embedding(text: str) -> List[float]:
    response = client.embeddings.create(
        model="text-embedding-3-small",
        input=text
    )
    return response.data[0].embedding

def semantic_chunk(
    text: str,
    similarity_threshold: float = 0.6,
    min_chunk_size: int = 50,
    max_chunk_size: int = 500
) -> List[str]:
    """
    Split text into semantically coherent chunks.

    Algorithm:
    1. Split into sentences
    2. Embed each sentence
    3. Find similarity drops between consecutive sentences
    4. Split at breakpoints (where similarity drops below threshold)
    """

    # Split into sentences (simple approach)
    import re
    sentences = re.split(r'(?<=[.!?])\s+', text)
    sentences = [s.strip() for s in sentences if s.strip()]

    if len(sentences) <= 1:
        return [text]

    print(f"Processing {len(sentences)} sentences...")

    # Embed all sentences
    embeddings = [get_embedding(sent) for sent in sentences]
    embeddings = np.array(embeddings)

    # Compute consecutive similarities
    similarities = []
    for i in range(len(embeddings) - 1):
        sim = cosine_similarity([embeddings[i]], [embeddings[i+1]])[0][0]
        similarities.append(sim)

    # Find breakpoints where similarity drops significantly
    breakpoints = [0]  # Always start a new chunk at beginning
    for i, sim in enumerate(similarities):
        if sim < similarity_threshold:
            breakpoints.append(i + 1)
    breakpoints.append(len(sentences))

    # Build chunks from breakpoints
    chunks = []
    for i in range(len(breakpoints) - 1):
        start = breakpoints[i]
        end = breakpoints[i + 1]
        chunk_text = " ".join(sentences[start:end])

        # Enforce size constraints
        if len(chunk_text.split()) < min_chunk_size and chunks:
            # Merge with previous chunk if too small
            chunks[-1] += " " + chunk_text
        elif len(chunk_text.split()) > max_chunk_size:
            # Split if too large (simple split by words)
            words = chunk_text.split()
            mid = len(words) // 2
            chunks.append(" ".join(words[:mid]))
            chunks.append(" ".join(words[mid:]))
        else:
            chunks.append(chunk_text)

    return chunks


# Example usage

Machine learning is a subset of artificial intelligence. It enables computers 
to learn from data without being explicitly programmed. Neural networks are 
inspired by the human brain and form the basis of deep learning.

The stock market had a volatile session today. The S&P 500 fell 2.3% amid 
concerns about inflation. Technology stocks were hit hardest, with the Nasdaq 
dropping 3.1%.

Python is a versatile programming language. It is widely used in data science 
and machine learning. The language emphasizes readability and simplicity.
"""

chunks = semantic_chunk(text, similarity_threshold=0.5)

    print(f"\nChunk {i}: {chunk[:100]}...")

📋 ADDITIONAL 130+ QUICK Q&A RAPID FIRE

Q121. What is the difference between top-k and top-p in LLM generation? A: top-k limits vocabulary to K most likely tokens. top-p (nucleus sampling) selects from tokens whose cumulative probability exceeds p. For RAG, use temperature=0 for deterministic, grounded answers.

Q122. What is context window stuffing? A: Including too many retrieved chunks that overflow the LLM's context window, causing truncation or degraded performance.

Q123. What is a retrieval augmented fine-tuning (RAFT)? A: Fine-tune the LLM on (question, distractor_docs + relevant_doc, answer) triplets, teaching it to ignore irrelevant context and answer from the right document.

Q124. What is token budget optimization in RAG? A: Deliberately controlling how many tokens are used for context vs. generation, using compression, summarization, or truncation to stay within cost/latency budgets.

Q125. What is late chunking? A: Embed the full document first, then split the resulting embedding sequence into chunks. Preserves full-document context in each chunk's embedding (Jina's approach).

Q126. What is FLARE (Forward-Looking Active Retrieval)? A: LLM generates sentence-by-sentence; when confidence is low, it pauses, retrieves relevant docs, and continues with better context.

Q127. What is REALM (Retrieval-Enhanced Language Model)? A: End-to-end training where retriever and generator are jointly optimized, unlike RAG where retriever is often fixed.

Q128. What is DPR (Dense Passage Retrieval)? A: Facebook's bi-encoder trained specifically for QA retrieval using positive/negative passage pairs. One of the foundational dense retrieval models.

Q129. What is ColBERT? A: Late interaction model — encodes query and document independently into multi-vector representations, then computes relevance via max-similarity across token pairs. Higher quality than single-vector bi-encoders.

Q130. When would you use ColBERT vs standard bi-encoder? A: ColBERT when quality is critical and you can afford 10x storage (stores per-token embeddings). Standard bi-encoder for speed and storage efficiency.

Q131. What is SPLADE? A: Sparse + Dense hybrid model that learns sparse representations via BERT. Better than BM25 for semantic matching while still being sparse. Best of both worlds.

Q132. What is the two-tower model? A: Another name for bi-encoder. Two separate towers/encoders for query and document. Used in large-scale retrieval (Google, Facebook).

Q133. How do you handle code in RAG? A: Use AST-based chunking (split on functions/classes, not character count), specialized code embedding models (CodeBERT, UniXcoder), and treat code + docstrings together as one chunk.

Q134. What is a knowledge graph embedding? A: Embedding entities and relationships in a knowledge graph into vector space (TransE, RotatE) for completion and similarity tasks. Different from text embeddings.

Q135. What is retrieval consistency? A: Same query should return same/similar results reliably. ANN indexes are deterministic; only randomness from query expansion or MMR can affect consistency.

Q136. How do you handle ambiguous queries? A: 1) Detect ambiguity with LLM classifier. 2) Generate clarifying question. 3) Or: retrieve for all interpretations, present diverse results. 4) Show disambiguation options to user.

Q137. What is table-augmented generation (TAG)? A: RAG variant specifically designed for tabular data — retrieves relevant tables, not just text chunks, and uses table-aware LLM prompting.

Q138. What is KGRAG (Knowledge Graph RAG)? A: Hybrid approach combining knowledge graph traversal for structured facts with vector RAG for unstructured text. Best for complex entity-relationship queries.

Q139. What are the main differences between LlamaIndex and LangChain for RAG? A: LlamaIndex is more RAG-focused (better data connectors, indexing strategies, retrieval optimization). LangChain is more general-purpose (chains, agents, broader ecosystem). Both are production-ready; LlamaIndex often preferred for pure RAG applications.

Q140. What is semantic search vs full-text search? A: Semantic: "cat" finds "feline", "pet", "kitten" (meaning-based). Full-text: "cat" finds only documents containing "cat" (exact term). RAG uses semantic search; add full-text for keyword coverage.

Q141. What is a chunk hierarchy in LlamaIndex? A: Hierarchical node structure: root → sections → paragraphs → sentences. Allows retrieving at different granularities and navigating up/down the hierarchy.

Q142. How does streaming affect RAG UX? A: With streaming, user sees first token in 200ms instead of waiting 2s for complete answer. Dramatically improves perceived performance. Implement with streaming=True in LLM call + SSE/WebSocket on frontend.

Q143. What is an ensemble retriever? A: Combines multiple retrievers (BM25 + dense + MMR) and fuses their results. LangChain's EnsembleRetriever supports weighted combination.

Q144. What is contextual compression retriever? A: LangChain retriever that first fetches documents, then uses LLM to compress each doc to only the query-relevant part. Reduces context noise.

Q145. What is a parent document retriever? A: LangChain's implementation of small-to-big chunking: indexes small chunks but returns full parent documents. Best for balancing precision and context.

Q146. How do you implement fallback retrieval? A: Try vector search first; if similarity < threshold, fall back to BM25; if still no results, fall back to web search; if nothing found, return "I don't have this information."

Q147. What is the MMLU benchmark and how does it relate to RAG? A: Massive Multitask Language Understanding — tests LLM knowledge without retrieval. RAG systems should exceed base LLM MMLU scores on domain-specific tasks (that's the point of RAG).

Q148. What is the difference between open-book and closed-book QA? A: Open-book (RAG): LLM has access to documents, can look up answers. Closed-book: LLM uses only parametric (trained) knowledge. RAG = open-book exam.

Q149. How do you prevent the RAG system from being gamed by users? A: Input sanitization, query rate limiting, intent classification (block prompt injection attempts), output filtering (PII detection), and audit logging of all queries.

Q150. What is the document freshness problem? A: Retrieved documents may be outdated even if they're in the index. Solution: Include document date in metadata, add recency scoring, set TTL on indexed documents, real-time indexing for frequently updated content.

async def rag_stream_generator(query: str, retriever, llm):
    """Async generator for streaming RAG responses."""

    # Step 1: Retrieve (not streamed — must complete before generation)
    docs = await asyncio.to_thread(retriever.invoke, query)
    context = "\n\n".join([d.page_content for d in docs])

    # Step 2: Signal that retrieval is complete
    yield "data: {\"type\": \"retrieval_complete\", \"num_docs\": " + str(len(docs)) + "}\n\n"

    # Step 3: Stream generation
    prompt = ChatPromptTemplate.from_template(
        """Answer based ONLY on this context:
        {context}

        Question: {question}
        Answer:"""
    )

    messages = prompt.format_messages(context=context, question=query)

    # Stream LLM tokens
    async for chunk in llm.astream(messages):
        if chunk.content:
            # Server-Sent Event format
            yield f"data: {{\"type\": \"token\", \"content\": \"{chunk.content}\"}}\n\n"

    # Step 4: Send sources
    sources = [doc.metadata.get("source", "unknown") for doc in docs]
    yield f"data: {{\"type\": \"sources\", \"sources\": {sources}}}\n\n"
    yield "data: [DONE]\n\n"

def build_qdrant_filter(extracted_filters: dict) -> Filter | None:
    """Convert extracted filters to Qdrant filter object."""
    conditions = []

    for field, value in extracted_filters.items():
        if value is None:
            continue

        if isinstance(value, str):
            conditions.append(
                FieldCondition(key=field, match=MatchValue(value=value))
            )
        elif isinstance(value, dict):  # Range filter
            range_params = {}
            if "gte" in value:
                range_params["gte"] = value["gte"]
            if "lte" in value:
                range_params["lte"] = value["lte"]
            conditions.append(
                FieldCondition(key=field, range=Range(**range_params))
            )

    if not conditions:
        return None

    return Filter(must=conditions)

# RAG CONFIDENCE SCORING
from openai import OpenAI
import numpy as np

client = OpenAI()

class RAGConfidenceScorer:
    """
    Multi-signal confidence scoring for RAG responses.

    Signals:
    1. Retrieval confidence: max cosine similarity of retrieved chunks
    2. Context coverage: does retrieved context contain answer?
    3. LLM self-assessment: ask LLM to rate its confidence
    4. Answer consistency: multiple generations agree?
    """

    def retrieval_confidence(self, query_vector, retrieved_docs) -> float:
        """Confidence from retrieval similarity scores."""
        if not retrieved_docs:
            return 0.0
        scores = [doc.get('score', 0) for doc in retrieved_docs]
        # High max score + consistent scores = high confidence
        max_score = max(scores)
        score_std = np.std(scores)
        # Penalize if all scores are similarly low (no clear winner)
        return max_score * (1 - 0.3 * score_std)

    def context_relevance_check(self, query: str, context: str) -> float:
        """Use NLI or LLM to check if context contains answer."""
        prompt = f"""Does this context contain enough information to answer the question?

Context: {context[:1000]}
Question: {query}

Rate from 0.0 (no relevant info) to 1.0 (complete answer available).
Output ONLY a number between 0.0 and 1.0:"""

        response = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}],
            temperature=0,
            max_tokens=5
        )

        try:
            return float(response.choices[0].message.content.strip())
        except ValueError:
            return 0.5

    def self_assessed_confidence(self, query: str, answer: str, context: str) -> float:
        """Ask LLM to rate its own confidence."""
        prompt = f"""Given this context and question, rate how confident you are 
in the answer provided.

Context: {context[:500]}
Question: {query}
Answer: {answer}

Rate confidence 0.0-1.0. Consider:
- Is the answer fully supported by context? (if not, low confidence)
- Are there ambiguities? (if yes, lower confidence)
- Is the answer specific? (vague = lower confidence)

Output ONLY a number 0.0-1.0:"""

        response = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}],
            temperature=0,
            max_tokens=5
        )

        try:
            return float(response.choices[0].message.content.strip())
        except ValueError:
            return 0.5

    def compute_final_score(
        self, 
        query, answer, context, retrieved_docs, query_vector
    ) -> dict:
        """Weighted combination of all confidence signals."""

        ret_conf = self.retrieval_confidence(query_vector, retrieved_docs)
        ctx_rel = self.context_relevance_check(query, context)
        self_conf = self.self_assessed_confidence(query, answer, context)

        # Weighted average
        final_score = (
            ret_conf * 0.30 +     # 30% weight to retrieval
            ctx_rel * 0.40 +      # 40% weight to context quality
            self_conf * 0.30      # 30% weight to LLM self-assessment
        )

        confidence_label = (
            "HIGH" if final_score >= 0.80 else
            "MEDIUM" if final_score >= 0.60 else
            "LOW"
        )

        return {
            "score": round(final_score, 3),
            "label": confidence_label,
            "components": {
                "retrieval": round(ret_conf, 3),
                "context_relevance": round(ctx_rel, 3),
                "self_assessed": round(self_conf, 3)
            },
            "show_disclaimer": final_score < 0.70
        }

Q163. Compare BM25 vs TF-IDF for sparse retrieval.

▶ Answer

BM25 vs TF-IDF:
══════════════════════════════════════════════════════════════

TF-IDF:
  score = TF(t,d) × log(N / df(t))

  PROBLEM: TF grows linearly — a doc with "Python" 100 times scores
           much higher than one with "Python" 10 times, even if both
           are equally relevant. No saturation.
  PROBLEM: Doesn't normalize for document length — long docs always
           score higher.

BM25 (Better Matching 25):
  score = Σ IDF(qi) × [f(qi,d) × (k1+1)] / [f(qi,d) + k1×(1-b + b×|d|/avgdl)]

  k1 ∈ [1.2, 2.0]: Term saturation parameter
    → As term freq increases, score SATURATES (diminishing returns)
    → "Python" ×100 ≈ "Python" ×20 in score ✅

  b = 0.75: Length normalization
    → Penalizes very long documents (they have more term occurrences naturally)
    → Short docs with high term density score appropriately ✅

CONCRETE EXAMPLE:
  Doc A: "Python Python Python Python Python" (500 words)
  Doc B: "Python is a programming language" (10 words)
  Query: "Python"

  TF-IDF: Doc A scores much higher (raw frequency)
  BM25: Doc B scores higher (term appears in shorter, more focused doc)

  BM25 result is usually better for actual retrieval!

CONCLUSION: Always use BM25, not TF-IDF, for sparse retrieval.
Elasticsearch uses BM25 by default since version 5.0.

# INCREMENTAL INDEXING PIPELINE
import hashlib
import json
from datetime import datetime
from typing import Optional

class IncrementalIndexer:
    """
    Only re-index documents that have changed.
    Uses content hashing to detect changes.
    """

    def __init__(self, vector_store, doc_store, embedding_model):
        self.vector_store = vector_store
        self.doc_store = doc_store
        self.embed = embedding_model

        # Hash registry: {doc_id: {hash, indexed_at, chunk_ids}}
        self.hash_registry = {}  # In production: persist in Redis/PostgreSQL

    def compute_hash(self, content: str) -> str:
        return hashlib.sha256(content.encode()).hexdigest()

    def index_document(self, doc_id: str, content: str, metadata: dict):
        """Index only if content has changed."""

        new_hash = self.compute_hash(content)
        existing = self.hash_registry.get(doc_id)

        # Check if already indexed with same content
        if existing and existing['hash'] == new_hash:
            print(f"Skipping {doc_id}: no content change")
            return {"status": "skipped", "reason": "no_change"}

        # Delete old chunks if document existed before
        if existing:
            old_chunk_ids = existing.get('chunk_ids', [])
            if old_chunk_ids:
                self.vector_store.delete(ids=old_chunk_ids)
                print(f"Deleted {len(old_chunk_ids)} old chunks for {doc_id}")

        # Chunk the document
        chunks = self.chunk_document(content, doc_id, metadata)

        # Embed chunks in batch
        texts = [c['text'] for c in chunks]
        embeddings = self.embed.embed_documents(texts)

        # Store in vector DB
        chunk_ids = []
        for chunk, embedding in zip(chunks, embeddings):
            chunk_id = f"{doc_id}_chunk_{chunk['index']}"
            self.vector_store.upsert(
                id=chunk_id,
                vector=embedding,
                payload={**chunk['metadata'], 'text': chunk['text']}
            )
            chunk_ids.append(chunk_id)

        # Update hash registry
        self.hash_registry[doc_id] = {
            'hash': new_hash,
            'indexed_at': datetime.utcnow().isoformat(),
            'chunk_ids': chunk_ids,
            'chunk_count': len(chunk_ids)
        }

        print(f"Indexed {doc_id}: {len(chunk_ids)} chunks")
        return {"status": "indexed", "chunks": len(chunk_ids)}

    def bulk_index(self, documents: list) -> dict:
        """Process multiple documents, skip unchanged ones."""
        results = {"indexed": 0, "skipped": 0, "failed": 0}

        for doc in documents:
            try:
                result = self.index_document(
                    doc['id'], doc['content'], doc['metadata']
                )
                if result['status'] == 'indexed':
                    results['indexed'] += 1
                else:
                    results['skipped'] += 1
            except Exception as e:
                print(f"Failed to index {doc['id']}: {e}")
                results['failed'] += 1

        return results

    def chunk_document(self, content: str, doc_id: str, metadata: dict) -> list:
        """Simple fixed-size chunking (replace with your strategy)."""
        chunk_size = 512
        overlap = 64
        words = content.split()
        chunks = []

        for i in range(0, len(words), chunk_size - overlap):
            chunk_words = words[i:i + chunk_size]
            chunks.append({
                'text': ' '.join(chunk_words),
                'index': len(chunks),
                'metadata': {
                    **metadata,
                    'doc_id': doc_id,
                    'chunk_index': len(chunks),
                    'char_start': len(' '.join(words[:i]))
                }
            })

        return chunks

  Step 2: Create new index with new embedding model
  Step 3: Re-index ALL documents with new model → new index
  Step 4: A/B test: 10% traffic → new index, 90% → old index
  Step 5: Compare retrieval quality metrics (MRR, Hit Rate)
  Step 6: Gradual rollout: 10% → 25% → 50% → 100%
  Step 7: Decommission old index after 7 days

Q171. What is RAPTOR (Recursive Abstractive Processing for Tree-Organized Retrieval)?

▶ Answer

RAPTOR ARCHITECTURE:
══════════════════════════════════════════════════════════════

PROBLEM: Standard RAG retrieves individual chunks → misses 
big-picture understanding ("forest for the trees" problem)

RAPTOR SOLUTION: Build a tree of summaries at multiple levels

CONSTRUCTION:
─────────────

Raw document chunks (leaf nodes)
      │
      │ [Cluster similar chunks] → UMAP + GMM clustering
      ▼
Clusters of related chunks
      │
      │ [Summarize each cluster with LLM]
      ▼
Level-1 summaries (one per cluster)
      │
      │ [Cluster similar summaries, summarize again]
      ▼
Level-2 summaries (higher-level abstractions)
      │
      │ [Repeat until single root summary]
      ▼
Root summary (full document overview)

RETRIEVAL (two modes):
──────────────────────
Mode 1: Tree traversal (top-down)
  Query → match at root level → descend to relevant subtree → get leaves
  Good for: navigating large corpora hierarchically

Mode 2: Collapsed tree (flat search across all levels)
  Query → search ALL nodes (leaves + all summary levels)
  Return mix of specific chunks AND summaries
  Good for: queries needing both detail and overview

ADVANTAGE: Can answer both specific and abstract questions
  "What does section 3.2 say about vacation?" → leaf chunks
  "What are the main themes of this HR policy?" → root summary

RAG-FUSION (Shieh et al., 2024):

RRF across all 8 lists → final merged ranking

ADVANTAGE OVER STANDARD:

  RAG-Fusion: captures 8 lists (4 queries × 2 retrieval methods)

Q173. "You mentioned cosine similarity — how is dot product similarity different?"

▶ Answer

COSINE vs DOT PRODUCT SIMILARITY:
══════════════════════════════════════════════════════════════

Cosine Similarity:  cos(θ) = (A·B) / (|A| × |B|)
  - Measures ANGLE between vectors
  - Range: -1 to +1
  - LENGTH-INVARIANT: vector magnitude doesn't affect score
  - Use when: embedding magnitude shouldn't matter (most text search)

Dot Product:  A·B = |A| × |B| × cos(θ)
  - Measures both ANGLE and MAGNITUDE
  - Range: -∞ to +∞ (unbounded)
  - LENGTH-SENSITIVE: longer vectors score higher
  - Use when: vector magnitude encodes importance (some models trained with dot product)

PRACTICAL IMPACT:
  Most text embeddings (OpenAI, BGE) are normalized (|v|=1)
  → For normalized vectors: dot product = cosine similarity ✅

  When using normalized embeddings: dot product is FASTER (no division)
  OpenAI recommends: "For normalized vectors, use dot product"

  Raw (unnormalized) embeddings → always use cosine for safety

Q177. What is a document loader vs a document transformer?

A loader fetches raw content from a source (PDF, web, S3) and returns Document objects. A transformer processes existing Document objects (splitting, filtering, translating). In LangChain: PyPDFLoader = loader; RecursiveCharacterTextSplitter = transformer.

Q178. What is the difference between "stuff" and "map-reduce" chain types in RAG?

Stuff: stuff all retrieved chunks directly into one prompt — simple but fails if chunks exceed context window. Map-reduce: summarize each chunk independently (map), then combine summaries (reduce) — handles large contexts but loses cross-chunk relationships. Use "stuff" for <5 short chunks; map-reduce for many/long chunks.

Q179. How do you handle RAG for tabular data (e.g., CSV, database)?

Use Text-to-SQL for structured databases — the LLM generates SQL from natural language, executes against DB, formats results. For CSVs: use pandas agent or embed row-level serialized text. Pure vector search works poorly on tabular data; SQL is more precise for numeric/relational queries.

Q180. What is the difference between retrieval precision and generation precision?

Retrieval precision = how many retrieved chunks are relevant (measured against ground truth). Generation precision = how much of the generated answer is factually supported by context (faithfulness). A system can have high retrieval precision but low generation precision if the LLM hallucinates despite good context.

Q181. What is chunk poisoning in RAG security?

An attacker deliberately inserts documents into the knowledge base (or uploads via user-facing file upload) containing malicious content — either misinformation or prompt injection instructions. The RAG retrieves it, and the LLM acts on it. Prevention: document source validation, content scanning before indexing, user-uploaded docs sandboxed in separate namespaces.

Q182. What is the role of temperature in RAG generation?

Temperature controls creativity/randomness. In RAG, temperature=0 is strongly recommended because you want the model to stick closely to the provided context (deterministic, faithful). Higher temperatures increase risk of the model "wandering" away from the context and hallucinating.

Q183. What is query latency budget allocation in production RAG?

Distribute total latency budget across components. Example for 500ms SLA: Embedding (20ms) + Vector search (40ms) + Reranking (60ms) + LLM (320ms) + Overhead (60ms) = 500ms. If one component is over budget, optimize it or remove it. Always measure p99, not p50, for SLA planning.

Q184. How do you handle very short queries in RAG (e.g., "policy")?

Single-word queries produce poor embeddings (insufficient context). Strategies: (1) Query expansion — LLM generates: "What is the [policy] mentioned in our documentation?" (2) BM25 boost — keyword search with exact term often works better. (3) Ask for clarification: "Could you be more specific? Which policy are you asking about?"

Q185. What is the difference between open-domain and closed-domain RAG?

Open-domain: knowledge base covers broad, general topics (entire Wikipedia). Closed-domain: knowledge base is specific to a domain (one company's docs, one product's manuals). Closed-domain RAG is easier to build, evaluate, and secure. Open-domain RAG needs much higher recall and is harder to prevent hallucination.

Q186. What is a RAG pipeline stress test?

Systematic testing under production conditions: high concurrency (100 parallel requests), edge case queries (very long, very short, adversarial), large context windows, document diversity. Measures: latency degradation under load, accuracy under noise, failure rate, memory usage, cost per query.

Q187. What is the role of a reranker in improving faithfulness (not just relevance)?

Better-ranked context → LLM uses it more reliably. If the most relevant chunk is rank 5 in a list of 10, LLM may ignore it ("Lost in the Middle"). Reranking puts the best chunk at rank 1 → LLM definitely uses it → higher faithfulness. So reranking indirectly improves both retrieval quality AND generation faithfulness.

Q188. What are the best practices for RAG prompt versioning?

Treat prompts like code: (1) Store in version control (Git), not hardcoded. (2) Use a prompt management tool (LangSmith, PromptLayer). (3) A/B test before full rollout. (4) Tag each prompt version with evaluation scores. (5) Enable instant rollback (feature flag to switch prompt version).

Q189. How do you handle RAG in a low-resource language (e.g., Swahili, Bengali)?

(1) Use multilingual embedding model (BGE-M3 covers 100+ languages). (2) Consider cross-lingual retrieval — documents in Swahili, query in English, model handles mapping. (3) If documents and queries are same language, language-specific fine-tuned embedding beats multilingual. (4) OCR may be needed for non-Latin scripts (use Tesseract with correct language pack).

Q190. What is knowledge graph completion and how does it relate to RAG?

Knowledge graph completion fills in missing edges in a knowledge graph (predicting unknown relationships). In RAG context: if your knowledge graph has entities extracted from documents, KG completion can infer implicit relationships, improving Graph RAG's ability to answer multi-hop questions even when the explicit relationship isn't stated.

Q191. What is the "reference documents" pattern in RAG?

Instead of only returning generated text, always return the actual document IDs/chunks that supported the answer. This allows: (1) Users to verify answers. (2) Developers to debug retrieval. (3) Citation in reports. (4) Groundedness measurement without re-running evaluation.

Q192. When should you NOT use RAG?

(1) Simple, static factual questions where LLM is reliable. (2) Creative writing (retrieval constrains creativity). (3) Very small document sets (<10 docs) — just put all in system prompt. (4) Real-time streaming data (stock prices, live sports) — use direct API tools. (5) When sub-100ms latency is required — retrieval adds irreducible latency.

Q193. What is document reranking vs passage reranking?

Document reranking: rank whole documents by relevance to query. Passage reranking: rank individual passages/chunks. RAG uses passage reranking because we retrieve at chunk level. Document reranking is used when you need to select which documents to read further, then passage rerank within selected docs.

Q194. What is Chain-of-Thought (CoT) prompting in RAG?

Adding "Let's think step by step" or explicit reasoning steps to the RAG prompt, making the LLM reason through the context before answering. Improves accuracy on complex questions that require combining multiple facts from the context: "First, identify relevant facts from context... Then, calculate/compare... Finally, answer..."

Q195. What is the "generation with abstention" pattern?

Teaching the RAG system to abstain (refuse to answer) when confidence is below a threshold, rather than generating a low-quality or hallucinated answer. Better UX: "I don't have enough information about this" than a confidently wrong answer. Implement via: confidence scoring, NLI checking, or explicit prompt instruction.

Q196. How do you handle RAG for code documentation?

(1) Chunk at function/class level (not arbitrary character count). (2) Index: function signature + docstring + body separately. (3) Use code-specific embedding models (CodeBERT). (4) Store metadata: language, module, class name, parameters. (5) Hybrid search: exact function name (BM25) + semantic purpose (dense). (6) Return full function body (not just docstring).

Q197. What is the "frozen retriever" problem in end-to-end RAG training?

In most RAG systems, the retriever is frozen (not updated during LLM training). This means retriever and generator can diverge — generator learns to use certain context styles, but retriever doesn't adapt. Solutions: (1) Periodic retriever fine-tuning on new Q&A pairs. (2) End-to-end training (REALM, Atlas). (3) Retriever distillation from generator signals.

Q198. What is approximate vs exact nearest neighbor search, and when does exact matter?

Exact NN: compare to every vector, guaranteed correct (O(n) time). ANN: smart shortcuts, 99%+ correct, O(log n) time. Exact matters when: safety-critical applications (medical diagnosis, fraud detection) where a missed document could cause harm. ANN is fine for: knowledge base Q&A, customer support, most commercial RAG.

Q199. What is query routing in multi-index RAG?

When you have multiple indexes (by department, topic, or language), a router component decides which index(es) to query. Implemented as: LLM classifier ("this query is about HR topics → HR index"), rule-based keyword matching, or a trained classifier. Reduces irrelevant results from wrong indexes.

Q201. What is the MTEB benchmark and why is it important for embedding model selection?

MTEB (Massive Text Embedding Benchmark) evaluates embedding models across 56 tasks in 112 languages — retrieval, clustering, classification, semantic similarity, etc. It's the standard reference for comparing embedding models. Before selecting a model, check MTEB scores for your specific task type (especially "Retrieval" column) and language. Available at: huggingface.co/spaces/mteb/leaderboard.

Q202. What happens when your RAG system is asked the same question many times? How do you optimize?

(1) Exact cache: hash(query) → cache result, TTL = data staleness tolerance. (2) Semantic cache: embed query → similarity search in Redis → return cached result if similarity > 0.88. (3) Pre-computed answers: for top-100 FAQ queries, pre-generate and cache. (4) Query normalization: lowercase, strip punctuation before hashing to increase cache hit rate.

Q203. What is "knowledge boundary" enforcement in RAG?

Explicitly constraining the RAG system to only answer within its defined knowledge domain. Example: a legal document RAG that refuses to answer medical questions. Implementation: (1) Domain classifier on input — block off-topic queries. (2) Retrieval confidence threshold — no relevant docs found → "This is outside my knowledge area." (3) System prompt: "Only answer questions related to [DOMAIN]."

Q204. Describe a scenario where increasing top-K hurts RAG performance.

Retrieval of top-20 chunks vs top-3: The extra 17 chunks may include low-relevance content. This: (1) Increases input tokens → higher cost and latency. (2) Increases noise in context → LLM gets confused. (3) "Lost in the Middle" — relevant chunk gets buried. (4) Context window pressure. Counterintuitive result: lower top-K with better reranking often outperforms higher top-K without reranking.

Q205. What is the role of BM25 in the era of semantic search?

BM25 remains critical because: (1) Exact keyword matching: product codes, error codes, proper nouns, rare terms that semantic models don't understand. (2) Speed: BM25 is orders of magnitude faster than ANN. (3) No training needed: works zero-shot on any domain. (4) Complementary: fills the gaps where semantic search fails. Modern hybrid search = BM25 + dense embeddings, not one or the other.

Q206. How do you handle multilingual queries against a monolingual knowledge base?

(1) Translate query to the knowledge base's language, then retrieve. Best for small volume of non-primary-language queries. (2) Cross-lingual embedding model (BGE-M3, LaBSE) — maps queries in any language to same embedding space as the monolingual documents. (3) Multilingual knowledge base — index documents in multiple languages with language metadata. (4) Hybrid: detect language, route to best strategy.

Q207. What is a "retrieval head" in RAG architecture?

A specialized layer or module in the LLM that is specifically trained/adapted for retrieval tasks — attending to and extracting information from retrieved passages more effectively. Some architectures (FiD — Fusion-in-Decoder) process each retrieved document separately through the encoder, then fuse in the decoder, which is a form of retrieval-aware architecture.

Q208. When would you use MMR vs reranking?

MMR (Maximal Marginal Relevance): use when you want diversity — prevents returning 5 near-identical chunks. Best for: broad topic overviews, when multiple angles needed. Reranking: use when you want precision — selects the most relevant chunks regardless of diversity. Best for: specific factual questions where you want the best 5 matches. You can combine both: rerank for relevance, then apply MMR for diversity selection.

Q209. Describe how you'd implement RAG for a voice interface (voice-in, voice-out).

Pipeline: Voice → STT (Whisper) → Text query → RAG pipeline → Text answer → TTS (ElevenLabs, Azure Speech). Special considerations: (1) Voice queries tend to be conversational → normalize to formal text before retrieval. (2) RAG answers must be designed for listening, not reading (no markdown, no lists, natural spoken language). (3) Keep answers short — listening to 5 paragraphs is painful. (4) Latency is critical for voice UX — target <800ms from speech end to audio start.

Q210. What is the "context window optimization" strategy for RAG prompts?

Efficient use of the LLM's context window: (1) Compression: use an LLM to compress retrieved chunks to only query-relevant sentences. (2) Truncation: if context exceeds budget, drop lowest-ranked chunks. (3) Interleaving: place highest-ranked chunk first (not in middle). (4) Token counting: measure actual token count before sending, not just character count. (5) Reserve budget: reserve 300 tokens for the answer, don't let context crowd it out.

Q213. "Explain how you'd handle contradictory information across retrieved documents."

Strategy: (1) Detect: compare claims across chunks using NLI (entailment vs contradiction). Flag contradictions. (2) Source credibility: rank sources by authority (official policy v2024 > forum post 2019). (3) Temporal priority: more recent document usually wins (date in metadata). (4) Transparency to user: "I found conflicting information: Source A says X (2024), Source B says Y (2022). The more recent source suggests X." (5) Escalation: for critical domains (legal, medical), don't resolve contradictions autonomously — always surface them to the user.

Q214. "A new team member asks why you chose HNSW over IVF for your production vector index. What do you tell them?"

"For our workload of 5M vectors and 200 QPS with a 50ms search SLA, HNSW is the right choice because: (1) Latency: HNSW p99 latency is consistently <20ms; IVF can spike when query falls across cluster boundaries. (2) Recall: HNSW achieves 98% recall@10 at our settings; IVF needs more nprobe (slower) to match. (3) Dynamic updates: we add ~1000 new vectors per day — HNSW handles incremental inserts natively; IVF needs periodic retraining of cluster centroids. (4) Trade-off: HNSW uses ~3x more RAM than IVF+PQ, but we have sufficient RAM. If we hit 100M vectors or RAM constraints, we'd revisit IVF+PQ with quantization."

Q215. "How do you prevent a RAG system from becoming stale in a fast-moving domain like cybersecurity?"

(1) Real-time ingestion: subscribe to threat intelligence feeds (MISP, NVD CVE) → event-driven pipeline → indexed within minutes. (2) Freshness metadata: every chunk stores published_date + source. (3) Freshness scoring: boost recent documents in retrieval (last 30 days get 1.2x score multiplier). (4) TTL on embeddings: CVE data older than 180 days marked status=archived — retrieved only if no fresh alternative. (5) Web search augmentation: for breaking threats (<24h old), use web search tool as fallback. (6) Staleness alerts: if no documents indexed in last 24h → alert (pipeline failure likely). (7) Context date disclaimer: always include "Based on information as of [last_index_date]."
