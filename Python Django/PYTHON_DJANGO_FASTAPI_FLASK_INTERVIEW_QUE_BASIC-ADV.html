01SECTION 1: PYTHON FUNDAMENTALS & DATA MODEL

🟢 Beginner

Q1. How does Python manage memory, and what is reference counting?

▶ Answer Every object has a reference count; when it drops to zero, CPython frees the object immediately (deterministic for most objects, unlike a tracing-only GC). A separate cyclic garbage collector (generational, gc module) periodically finds and collects reference cycles (e.g., a.x = b; b.x = a) that ref-counting alone can't free.

a = [1,2,3]      # refcount 1
b = a            # refcount 2
del a            # refcount 1
del b            # refcount 0 -> freed immediately

💡 Memory trick: refcounting = instant cleanup for the normal case; gen-GC = safety net for cycles.

Q2. What is the GIL and why does it exist?

▶ Answer The Global Interpreter Lock allows only one thread to execute Python bytecode at a time per process, even on multi-core machines. It exists because CPython's memory management (refcounting) isn't thread-safe without it, and it simplifies the C API. Effect: CPU-bound multi-threaded Python code doesn't get parallel speed-up; I/O-bound code still benefits because the GIL is released during blocking I/O (and by C extensions that release it, e.g., NumPy).

🎯 Interviewer's intent: do you know why multi-threading doesn't parallelise CPU work in Python (and when it still helps).

Q3. Threading vs multiprocessing vs asyncio — when do you use each?

▶ Answer

Threading Multiprocessing Asyncio
Parallelism No (GIL) Yes (separate processes) No (single thread, concurrent)
Best for I/O-bound (network, disk) CPU-bound High-concurrency I/O (many connections)
Overhead Low High (process spawn, IPC/pickling) Very low per task
Shared memory Yes (with locks) No (needs IPC/shared memory) Yes (single thread, no races on plain code)
Web server fit WSGI workers (threads) WSGI workers (processes) ASGI (FastAPI, async Django views)

🔥 Since Python 3.13, an experimental free-threaded build (--disable-gil, PEP 703) can remove the GIL — a major but still-maturing change for true multi-threaded parallelism.

Q4. Explain Python's data model: what do `__init__`, `__new__`, `__repr__`, `__eq__`, `__hash__` do?

▶ Answer

class Point:
    def __new__(cls, *a, **kw):           # creates the instance (rarely overridden)
        return super().__new__(cls)
    def __init__(self, x, y):             # initialises the already-created instance
        self.x, self.y = x, y
    def __repr__(self):                   # unambiguous, dev-facing: repr(obj), debugger, REPL
        return f"Point({self.x!r}, {self.y!r})"
    def __str__(self):                    # readable, user-facing: str(obj), print(obj); falls back to __repr__
        return f"({self.x}, {self.y})"
    def __eq__(self, other):              # defines == ; without it, equality is identity (is)
        return isinstance(other, Point) and (self.x, self.y) == (other.x, other.y)
    def __hash__(self):                   # required if the object must go in a set/dict key
        return hash((self.x, self.y))     # MUST be consistent with __eq__

⚠️ Common mistake: defining __eq__ without __hash__ — Python sets __hash__ = None, making instances unhashable (can't be a dict key or set member).

Q5. What is the difference between `is` and `==`?

▶ Answer is compares identity (same object in memory); == compares value equality via __eq__. Small integers (-5 to 256) and interned strings are cached by CPython, so a is b can be True for equal small ints as an implementation detail — never rely on it; always use == for value comparison and is only for None/singleton checks (x is None).

Q6. Explain Python's argument-passing model ("pass by object reference").

▶ Answer Python passes the reference to the object, not a copy — but names are rebound, not the caller's variable. Mutating a mutable object (list, dict) inside a function is visible outside; reassigning the parameter name is not.

def f(lst): lst.append(4)          # mutates the same list object
def g(lst): lst = [9]              # rebinds the LOCAL name only — caller's list is untouched
a = [1,2,3]; f(a); print(a)        # [1, 2, 3, 4]
g(a);        print(a)              # still [1, 2, 3, 4]

Q7. Why is a mutable default argument a classic bug?

▶ Answer

def add_item(item, bag=[]):          # ⚠️ the list is created ONCE, at function-definition time
    bag.append(item)
    return bag

add_item("a")     # ['a']
add_item("b")     # ['a', 'b']  <- surprise! same list reused across calls

Fix: use None as the sentinel and create the mutable object inside the function body: def add_item(item, bag=None): bag = bag if bag is not None else [].

Q8. What is the difference between shallow copy and deep copy?

▶ Answer

import copy
original = {"nums": [1, 2, 3]}
shallow = copy.copy(original)          # or dict(original) / original.copy()
deep = copy.deepcopy(original)

shallow["nums"].append(4)              # mutates the SAME inner list -> original also changes
deep["nums"].append(5)                 # deep has its own independent copy

Shallow copy duplicates the outer container only; nested mutable objects are still shared references. Deep copy recursively duplicates everything.

Q9. What are Python's built-in scoping rules (the LEGB rule)?

▶ Answer Local → Enclosing (closures) → Global (module) → Built-in. Name lookup walks outward through these scopes. global and nonlocal keywords let you write to an outer scope instead of creating a new local binding.

x = "global"
def outer():
    x = "enclosing"
    def inner():
        nonlocal x          # without this, `x = ...` below creates a NEW local variable
        x = "modified"
    inner()
    print(x)                # "modified"
outer()

Q10. What is a closure, and what's the classic late-binding pitfall with loops?

▶ Answer A closure is a function that remembers variables from its enclosing scope even after that scope has returned.

def make_multiplier(n):
    return lambda x: x * n            # closes over `n`

times3 = make_multiplier(3)
times3(10)                            # 30

# ⚠️ late-binding pitfall:
funcs = [lambda: i for i in range(3)]
[f() for f in funcs]                  # [2, 2, 2] — all closures share the SAME `i`, evaluated at call time

fixed = [lambda i=i: i for i in range(3)]   # default arg captures value AT DEFINITION time
[f() for f in fixed]                        # [0, 1, 2]

Q11. Explain Python's numeric and string interning, and `sys.getsizeof` gotchas.

▶ Answer CPython caches small integers (-5..256) and simple identifier-like strings ("interning") as an optimisation — objects are reused rather than reallocated, which is why is can misleadingly succeed for equal values in that range. This is a CPython implementation detail, not part of the language spec; other implementations (PyPy) behave differently. Never depend on it in application logic.

02SECTION 2: FUNCTIONS, ITERATORS, GENERATORS & DECORATORS

🟡 Intermediate

Q12. Explain `*args`, `**kwargs` and keyword-only / positional-only parameters.

▶ Answer

def f(a, b, /, c, d=4, *args, e, f=6, **kwargs):
    #    ^positional-only    ^kw-only (after *args or bare *)
    ...

f(1, 2, 3, e=5)          # a=1 b=2 c=3 d=4 args=() e=5 f=6 kwargs={}
  • / marks everything before it positional-only (can't be passed by keyword) — useful for stable public APIs.
  • A bare * (or *args) marks everything after it keyword-only.
  • *args collects extra positionals into a tuple; **kwargs collects extra keywords into a dict.

Q13. What is the difference between an iterable and an iterator?

▶ Answer An iterable implements __iter__ and returns an iterator, which implements __next__ (raising StopIteration when exhausted) — and typically also __iter__ returning itself. Lists are iterable but are not iterators themselves (you can loop over the same list many times); calling iter(some_list) produces a fresh iterator each time.

class Countdown:
    def __init__(self, n): self.n = n
    def __iter__(self): return self
    def __next__(self):
        if self.n <= 0: raise StopIteration
        self.n -= 1
        return self.n + 1
list(Countdown(3))          # [3, 2, 1]

Q14. What is a generator, and how does `yield` differ from `return`?

▶ Answer A generator function contains yield and, when called, returns a generator object immediately without running any code — execution pauses at each yield and resumes on the next next() call, preserving local state between calls. return inside a generator raises StopIteration with the return value.

def read_large_file(path):
    with open(path) as f:
        for line in f:
            yield line.strip()          # one line in memory at a time, not the whole file

Generators are lazy and memory-efficient — essential for streaming large datasets, infinite sequences, and pipelines.

Q15. What is the difference between `yield` and `yield from`?

▶ Answer yield from delegates iteration to a sub-generator/iterable, forwarding its values (and propagating send()/exceptions/return value) without an explicit loop.

def inner():
    yield 1; yield 2
    return "done"

def outer():
    result = yield from inner()     # yields 1, 2, then result == "done"
    yield result

Without yield from you'd need for x in inner(): yield x and lose access to the sub-generator's return value.

Q16. Explain generator expressions vs list comprehensions — memory and performance trade-offs.

▶ Answer

squares_list = [x**2 for x in range(10**7)]      # builds the whole list in memory NOW
squares_gen  = (x**2 for x in range(10**7))      # lazy — computes each value on demand
sum(squares_gen)                                  # O(1) memory, single pass

Use a generator expression when you only need to iterate once (feeding sum, any, another loop); use a list when you need random access, multiple passes, or len().

Q17. What are decorators, and how do you write one that preserves metadata?

▶ Answer A decorator is a function that wraps another function, adding behaviour without changing its source.

import functools, time

def timed(func):
    @functools.wraps(func)              # preserves __name__, __doc__, etc. — omit this and debugging breaks
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
    return wrapper

@timed
def slow_add(a, b):
    time.sleep(0.1)
    return a + b

⚠️ Common mistake: forgetting functools.wraps — slow_add.__name__ would then be "wrapper", breaking introspection, docs and some frameworks' routing/DI that read function metadata.

Q18. How do you write a decorator that takes arguments?

▶ Answer

def retry(times=3, exceptions=(Exception,)):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            last_exc = None
            for attempt in range(times):
                try:
                    return func(*args, **kwargs)
                except exceptions as e:
                    last_exc = e
            raise last_exc
        return wrapper
    return decorator

@retry(times=5, exceptions=(ConnectionError,))
def fetch(): ...

Three levels: retry(times=5) → returns decorator → applied to fetch → returns wrapper. This is why a parametrised decorator needs one extra layer of nesting compared to a plain decorator.

Q19. What is a context manager, and how do `__enter__`/`__exit__` compare to `contextlib.contextmanager`?

▶ Answer

class ManagedFile:
    def __init__(self, path): self.path = path
    def __enter__(self):
        self.f = open(self.path)
        return self.f
    def __exit__(self, exc_type, exc_val, exc_tb):
        self.f.close()
        return False                     # False/None -> re-raise any exception; True -> suppress it

# equivalent, simpler for straightforward cases:
from contextlib import contextmanager
@contextmanager
def managed_file(path):
    f = open(path)
    try:
        yield f
    finally:
        f.close()                        # guaranteed even if the `with` body raises

with managed_file(p) as f: guarantees cleanup runs even on exception — the core value of context managers over manual try/finally scattered through code.

Q20. Explain Python's exception handling: `try`/`except`/`else`/`finally`, and exception chaining.

▶ Answer

try:
    result = risky()
except ValueError as e:
    handle(e)
except (TypeError, KeyError):
    handle_other()
else:                       # runs ONLY if no exception was raised
    log_success(result)
finally:                    # ALWAYS runs — cleanup, even if except/else re-raises
    cleanup()

raise NewError("context") from original_exc chains exceptions (__cause__), preserving the original traceback for debugging instead of hiding it. Bare except: catches everything including KeyboardInterrupt/SystemExit — almost always wrong; catch specific exception types.

03SECTION 3: OBJECT-ORIENTED PYTHON: CLASSES, DESCRIPTORS & METACLASSES

🔴 Advanced

Q21. Explain Python's Method Resolution Order (MRO) and the diamond problem.

▶ Answer Python uses C3 linearisation to produce a single, consistent method lookup order for multiple inheritance, avoiding the classic diamond ambiguity.

      A
     / \
    B   C
     \ /
      D

class A: 
    def greet(self): return "A"
class B(A): 
    def greet(self): return "B->" + super().greet()
class C(A): 
    def greet(self): return "C->" + super().greet()
class D(B, C): 
    def greet(self): return "D->" + super().greet()

D().greet()          # "D->B->C->A"
D.__mro__             # (D, B, C, A, object)

super() follows the MRO, not the literal parent class — each class's super() call chains to the next class in D's linearisation, which is why C.greet runs even though B doesn't explicitly call it.

Q22. What are `@property`, `@staticmethod` and `@classmethod`, and when do you use each?

▶ Answer

class Circle:
    def __init__(self, radius): self._radius = radius

    @property
    def radius(self): return self._radius

    @radius.setter
    def radius(self, value):
        if value < 0: raise ValueError("radius must be non-negative")
        self._radius = value

    @property
    def area(self): return 3.14159 * self._radius ** 2    # computed, read-only

    @staticmethod
    def is_valid_radius(r): return r >= 0                 # no self/cls — pure utility, grouped for organisation

    @classmethod
    def unit_circle(cls): return cls(radius=1)            # alternative constructor; respects subclassing

@property gives attribute-style access with validation; @staticmethod is just a namespaced function; @classmethod receives cls (not an instance) and is the idiomatic way to write alternative constructors that work correctly for subclasses too.

Q23. What are descriptors, and how does `@property` relate to them?

▶ Answer A descriptor is any object implementing __get__, __set__ or __delete__, placed as a class attribute; the descriptor protocol governs attribute access for instances. property is itself implemented as a descriptor. Descriptors power ORMs (Django model fields), functools.cached_property, and validation frameworks.

class PositiveNumber:
    def __set_name__(self, owner, name): self.name = "_" + name
    def __get__(self, obj, objtype=None):
        return getattr(obj, self.name, None)
    def __set__(self, obj, value):
        if value <= 0: raise ValueError(f"{self.name} must be positive")
        setattr(obj, self.name, value)

class Product:
    price = PositiveNumber()          # reusable validated field, just like a Django model field

p = Product(); p.price = 10           # calls PositiveNumber.__set__
p.price = -5                          # raises ValueError

Q24. What is a metaclass, and when would you actually use one?

▶ Answer A metaclass is "the class of a class" — type is the default metaclass; every class is an instance of some metaclass. Writing class Foo(metaclass=Meta): lets Meta.__new__/__init__ intercept class creation to auto-register subclasses, validate class bodies, or inject attributes.

class RegistryMeta(type):
    registry = {}
    def __new__(mcs, name, bases, ns):
        cls = super().__new__(mcs, name, bases, ns)
        if bases:                                  # skip the base class itself
            RegistryMeta.registry[name] = cls
        return cls

class Plugin(metaclass=RegistryMeta): pass
class CsvPlugin(Plugin): pass                       # auto-registered in RegistryMeta.registry

🎯 Interviewer's intent: "metaclasses are deep magic — Django's ModelBase and DRF's serializer metaclasses use them to collect fields declared in a class body." In practice, prefer class decorators or __init_subclass__ for 90% of these use cases — simpler and easier to reason about.

Q25. What does `__init_subclass__` do, and how does it compare to a metaclass?

▶ Answer __init_subclass__ is a classmethod hook, added in Python 3.6, that runs automatically whenever a subclass is defined — covering many metaclass use cases (registration, validation) without the complexity of writing a custom metaclass.

class Plugin:
    registry = {}
    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        Plugin.registry[cls.__name__] = cls

class CsvPlugin(Plugin): pass          # auto-registered — no metaclass needed

Q26. Explain `__slots__` — what problem does it solve?

▶ Answer By default, instances store attributes in a per-instance __dict__, which has memory overhead. __slots__ declares a fixed set of attributes, allocating fixed-size storage instead and disabling arbitrary new attributes and (by default) the instance __dict__.

class Point:
    __slots__ = ("x", "y")
    def __init__(self, x, y): self.x, self.y = x, y

p = Point(1, 2)
p.z = 3          # AttributeError — z is not in __slots__

Use for classes with millions of instances (memory-sensitive data structures) — meaningful memory savings, but loses dynamic attribute assignment and multiple inheritance with slots gets tricky.

Q27. Explain abstract base classes (ABCs) and `Protocol` (structural typing).

▶ Answer

from abc import ABC, abstractmethod
class Storage(ABC):
    @abstractmethod
    def save(self, key, value): ...
Storage()                              # TypeError: Can't instantiate abstract class

from typing import Protocol
class SupportsSave(Protocol):
    def save(self, key, value) -> None: ...

def persist(store: SupportsSave): ...  # any object with a matching save() satisfies this — no inheritance needed

ABC = nominal typing (must explicitly inherit, enforced at instantiation). Protocol = structural typing ("duck typing" checked by static tools like mypy) — an object satisfies it just by having the right shape, no inheritance required.

Q28. What is the dataclasses module, and how does it compare to plain classes / NamedTuple / Pydantic?

▶ Answer

from dataclasses import dataclass, field

@dataclass(frozen=True, order=True)
class Point:
    x: int
    y: int
    tags: list[str] = field(default_factory=list)   # avoids the mutable-default-argument bug

@dataclass auto-generates __init__, __repr__, __eq__ (and __lt__ etc. with order=True) from type-annotated fields.

04SECTION 4: ASYNC PYTHON & CONCURRENCY

🔴 Advanced

Q29. Explain the asyncio event loop model, `async def`, `await` and coroutines.

▶ Answer async def defines a coroutine function; calling it returns a coroutine object that does nothing until it's awaited or scheduled. The event loop runs one coroutine at a time on a single thread, switching at each await when that operation is waiting on I/O — this is cooperative multitasking, unlike OS-thread preemption.

Task A: await db.query() ──(suspends, gives loop control)──▶ Task B: await http.get() ──(suspends)──▶ Task C runs
                    ▲                                                    │
                    └──────────── result ready, resumes A ◀──────────────┘

import asyncio
async def fetch(url):
    async with session.get(url) as resp:
        return await resp.text()
async def main():
    results = await asyncio.gather(*(fetch(u) for u in urls))   # runs concurrently
asyncio.run(main())

Q30. What is the difference between concurrency and parallelism, and where does asyncio fit?

▶ Answer Concurrency: multiple tasks make progress by interleaving (not necessarily simultaneous) — asyncio and threading. Parallelism: tasks literally run at the same time on different cores — multiprocessing. Asyncio gives concurrency on I/O-bound work with very low overhead (thousands of coroutines on one thread) but zero parallelism for CPU-bound work — a single CPU-heavy coroutine blocks the whole event loop.

Q31. Why does a CPU-bound `async def` function block the entire event loop, and how do you fix it?

▶ Answer

async def bad_handler(request):
    result = cpu_heavy_computation()    # blocks the loop — NO other coroutine runs until this returns
    return result

async def good_handler(request):
    loop = asyncio.get_running_loop()
    result = await loop.run_in_executor(None, cpu_heavy_computation)   # offload to a thread/process pool
    return result

Any blocking call inside a coroutine — CPU work, a synchronous requests.get(), time.sleep(), blocking file I/O — freezes every other coroutine on that event loop. Use run_in_executor, asyncio.to_thread, or a process pool for CPU/blocking work; use async-native libraries (httpx, asyncpg, aiofiles) for I/O.

Q32. What do `asyncio.gather`, `asyncio.wait` and `TaskGroup` do differently?

▶ Answer

results = await asyncio.gather(t1(), t2(), t3())            # waits for all; one exception cancels? no — propagates after all complete by default

done, pending = await asyncio.wait([t1(), t2()], timeout=5)  # more control: timeout, return_when=FIRST_COMPLETED

async with asyncio.TaskGroup() as tg:                         # 3.11+, structured concurrency
    tg.create_task(t1())
    tg.create_task(t2())
    # any task failing cancels the SIBLINGS and raises an ExceptionGroup — much safer error handling

TaskGroup is the modern recommended pattern: it guarantees no task is silently orphaned and properly propagates/aggregates errors, unlike bare gather/create_task calls that are easy to leak.

Q33. What happens if you `await` a coroutine that raises, inside `gather`?

▶ Answer By default asyncio.gather(*aws) lets all awaitables run to completion; if any raises, the exception propagates once all are done (others aren't cancelled). Pass return_exceptions=True to instead get exceptions back as results in the list rather than raising. TaskGroup behaves differently: the first failure cancels sibling tasks immediately (fail-fast), which is usually what you want in production code.

Q34. Explain sync vs async database drivers and connection pooling in async web apps.

▶ Answer Blocking DB drivers (psycopg2, default mysqlclient) block the event loop — wrong choice under ASGI. Use async drivers (asyncpg, psycopg v3 async mode, motor for MongoDB) or an async ORM layer (SQLAlchemy 2.0 async, Django 4.1+ async ORM methods). Always use a connection pool sized to expected concurrency, since opening a new connection per request is slow and can exhaust the database's connection limit under load.

Q35. What is `async with` / `async for`, and when do you need them?

▶ Answer They're the async equivalents of with/for, used when __aenter__/__aexit__ or __anext__ themselves need to await (e.g., an async DB session that awaits acquiring a connection, or streaming rows from an async cursor).

async def get_users():
    async with async_session() as session:            # awaits connection acquisition
        result = await session.execute(select(User))
        async for row in result:                       # if streaming, awaits each fetch
            yield row

Q36. How do WSGI and ASGI differ, and why does it matter for framework choice?

▶ Answer

WSGI ASGI
Concurrency model One request per worker thread/process (sync) Async event loop — many concurrent requests per worker
Protocols HTTP only HTTP, WebSockets, HTTP/2, long-lived connections
Frameworks Flask, classic Django views FastAPI, Django (async views), Starlette
Servers Gunicorn, uWSGI Uvicorn, Hypercorn, Daphne, Gunicorn+Uvicorn workers

ASGI is the async successor to WSGI, standardising how async Python web servers talk to frameworks — needed for WebSockets, Server-Sent Events, and high-concurrency I/O-bound APIs.

05SECTION 5: TYPING, TESTING & TOOLING

🟡 Intermediate

Q37. What does Python's type-hinting system provide, and what doesn't it do?

▶ Answer Type hints (def f(x: int) -> str:) are not enforced at runtime by the interpreter — they're read by static checkers (mypy, pyright), IDEs, and frameworks like Pydantic/FastAPI that do validate at runtime by inspecting the annotations. Benefits: earlier bug detection, better autocomplete, self-documenting signatures, and enabling frameworks like FastAPI to auto-generate validation and OpenAPI schemas from your type hints.

from typing import Optional, Union
def get_user(id: int) -> Optional["User"]: ...     # Optional[X] == Union[X, None]
def parse(x: int | str) -> None: ...                # modern union syntax (3.10+)

Q38. Explain `Generic`, `TypeVar` and generic classes in Python typing.

▶ Answer

from typing import TypeVar, Generic

T = TypeVar("T")
class Stack(Generic[T]):
    def __init__(self) -> None: self._items: list[T] = []
    def push(self, item: T) -> None: self._items.append(item)
    def pop(self) -> T: return self._items.pop()

int_stack: Stack[int] = Stack()
int_stack.push(1)
int_stack.push("x")           # mypy flags this — expected int, got str

Q46. What are the main Python performance techniques for web backends?

▶ Answer

  1. Fix N+1 queries first — almost always the biggest win (see the databases section).
  2. Cache (in-process functools.lru_cache/cached_property, Redis/Memcached for shared cache).
  3. Async I/O for high-concurrency, I/O-bound endpoints.
  4. Offload CPU work to background workers (Celery/RQ) or a process pool — don't block request threads.
  5. Use C-accelerated libraries where hot: orjson/ujson for JSON, uvloop as the asyncio event loop, compiled serializers.
  6. Profile before optimising — Python's bottlenecks in web apps are overwhelmingly I/O (DB, network), not interpreter speed.
  7. Connection pooling for DB and HTTP clients (httpx.AsyncClient reused, not recreated per request).

Q47. What's the difference between `pip`, `venv`, `poetry`/`uv`, and why does dependency pinning matter?

Q51. What is Django's architecture, and how does the MVT pattern map to MVC?

▶ Answer Django calls itself MVT (Model-View-Template): the Model matches MVC's model (data layer); Django's View is a plain Python function/class that contains the controller logic (decides what data to fetch and which template to render); the Template is the presentation layer (matches MVC's "view"). Request ─▶ URLconf (urls.py) ─▶ View (views.py: business logic) ─▶ Model (ORM: fetch/save data)
                                        │
                                        ▼
                              Template (render HTML/JSON) ─▶ Response

Q52. Describe the Django request/response cycle end to end.

▶ Answer

1. WSGI/ASGI server receives HTTP request
2. Django's request middleware chain runs (top to bottom): security, session, auth, csrf, ...
3. URLconf resolves the path to a view function/class
4. View executes: reads request, queries models, applies business logic
5. View returns an HttpResponse (often via render() using a template, or a DRF Response)
6. Response middleware chain runs (bottom to top)
7. Response sent back to the client

Middleware wraps the entire view call, so it can act before AND after (and can short-circuit by returning a response early, skipping the view).

A project is a collection of apps (your own and third-party) plugged together via INSTALLED_APPS; the same app can in principle be reused across different projects.

Q60. What is the N+1 query problem, and how do you fix it in Django?

▶ Answer

# N+1: 1 query for articles + N queries (one per article) for author.name
for article in Article.objects.all():
    print(article.author.name)                 # each access triggers a new query

# Fixed: select_related does a SQL JOIN in ONE query (for FK / OneToOne)
for article in Article.objects.select_related("author"):
    print(article.author.name)                 # no extra query

# prefetch_related does a SEPARATE query then joins in Python (for M2M / reverse FK)
for article in Article.objects.prefetch_related("tags"):
    print([t.name for t in article.tags.all()])

🔥 The single most common Django performance interview question. select_related = SQL JOIN (single-valued relations); prefetch_related = extra query + Python-side join (multi-valued relations); use django-debug-toolbar or assertNumQueries in tests to catch N+1s before production.

Q61. Explain Django QuerySet laziness and when it actually hits the database.

▶ Answer QuerySets are lazy — building Article.objects.filter(...).exclude(...).order_by(...) executes no SQL until the queryset is evaluated: iterated, sliced with a step, len()'d, list()'d, bool()'d, or printed/repr'd. This lets you compose filters across functions cheaply and lets the ORM build one efficient query instead of running each step separately.

qs = Article.objects.filter(published=True)     # no query yet
qs = qs.filter(author=me)                        # still no query — just extends the SQL being built
articles = list(qs)                              # NOW the query runs

⚠️ Common mistake: calling list()/iterating the same unevaluated queryset repeatedly in a loop or view causes repeated identical queries — cache the evaluated result in a variable if reused.

Q64. How do database transactions and `atomic()` work in Django?

▶ Answer

from django.db import transaction

@transaction.atomic
def transfer_funds(from_acct, to_acct, amount):
    from_acct.balance -= amount
    from_acct.save()
    to_acct.balance += amount            # if this fails, the FIRST save is rolled back too
    to_acct.save()

# or as a context manager, with savepoints for nested atomic blocks:
with transaction.atomic():
    order = Order.objects.create(...)
    try:
        with transaction.atomic():       # nested -> becomes a SAVEPOINT
            charge_payment(order)        # if this fails, only this inner block rolls back
    except PaymentError:
        order.status = "payment_failed"
        order.save()

All statements inside atomic() commit together or roll back together — essential for multi-step writes that must be all-or-nothing (e.g., inventory decrement + order creation).

Q65. What is `select_for_update()`, and what problem does it solve?

▶ Answer

with transaction.atomic():
    account = Account.objects.select_for_update().get(id=account_id)   # row-level lock until transaction ends
    account.balance -= amount
    account.save()

Locks the selected row(s) at the database level so concurrent transactions trying to update the same row block/wait rather than racing — prevents lost updates (e.g., two simultaneous withdrawals both reading the same stale balance). Must be inside atomic(); watch for deadlocks if multiple code paths lock rows in different orders.

Q66. What are `F()` and `Q()` expressions used for?

▶ Answer

from django.db.models import F, Q

Article.objects.update(views=F("views") + 1)          # atomic DB-side increment — avoids read-then-write race
Article.objects.filter(Q(title__icontains="django") | Q(body__icontains="django"))   # OR condition
Article.objects.exclude(Q(status="draft") & ~Q(author=request.user))                 # complex boolean logic

F() references a database column value in an expression (computed in SQL, avoiding a race between reading a value in Python and writing it back). Q() builds complex boolean (AND/OR/NOT) filter expressions that plain keyword-argument chaining (which is always AND) can't express.

Q67. How do you avoid race conditions with `get_or_create` and unique constraints?

▶ Answer

# Not fully race-safe under high concurrency without a DB unique constraint:
obj, created = Model.objects.get_or_create(email=email, defaults={"name": name})

get_or_create is not atomic against a true race unless the field has a database-level unique constraint — otherwise two concurrent requests can both pass the get() check and both attempt create(), and Django handles this by catching the resulting IntegrityError and retrying the get() — but this behaviour depends on the constraint existing. Always back uniqueness assumptions with a real DB constraint (unique=True or UniqueConstraint), not just application logic.

Q68. How does Django's migration system detect and handle schema conflicts in a team?

▶ Answer Migrations are numbered per-app; when two branches each add a migration with the same "previous" dependency, merging creates two leaf migrations — Django detects this (makemigrations warns, showmigrations shows a fork) and you resolve it with python manage.py makemigrations --merge, which creates a merge migration depending on both leaves. Q69. What is the difference between `Model.save()` behaviour and `QuerySet.update()`/`bulk_update()`?

▶ Answer

Model.objects.filter(...).update(field="x")   # single SQL UPDATE, NO signals, NO save() override runs, no per-row Python

Q71. How does Django middleware work, and how do you write a custom one?

▶ Answer

class RequestTimingMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response          # called once, at server startup

    def __call__(self, request):
        start = time.perf_counter()
        response = self.get_response(request)      # everything AFTER this runs on the way back out
        response["X-Response-Time"] = f"{time.perf_counter() - start:.3f}s"
        return response

Middleware forms an onion: request-phase code (before get_response) runs top-to-bottom through MIDDLEWARE; response-phase code (after) runs bottom-to-top. Any middleware can short-circuit by returning a response without calling get_response, skipping the view and inner middleware entirely (used by auth/caching middleware).

Q72. Explain Django signals — how do they work, and what are their trade-offs?

▶ Answer

from django.db.models.signals import post_save
from django.dispatch import receiver

@receiver(post_save, sender=Order)
def send_confirmation_email(sender, instance, created, **kwargs):
    if created:
        send_email(instance.customer.email, template="order_confirmed")

Signals implement a publish-subscribe pattern decoupling the sender from the receiver — the model doesn't need to know who's listening. Trade-offs: they make control flow implicit and harder to trace/debug (a save() can trigger a chain of invisible side effects), execute synchronously by default (slow receivers slow down the request), and are silently skipped by bulk operations (update(), bulk_create()). Prefer explicit service-layer function calls for critical logic; reserve signals for genuinely decoupled, optional side effects — and offload slow work (emails, webhooks) to a background task from inside the receiver.

Q74. How do you invalidate cache correctly when underlying data changes?

▶ Answer Options: TTL-based (short timeout, accept staleness — simplest, works for most read-heavy, eventually-consistent data), explicit invalidation (delete/update the cache key in the same place the model is saved — via a signal or, more predictably, inside the service function that mutates data), and versioned keys (f"article:{id}:v{article.updated_at.timestamp()}" — old versions simply expire naturally, no explicit delete needed). Explicit signal-based invalidation is powerful but easy to miss for update()/bulk_update() calls that bypass signals — a common source of stale-cache bugs.

Q88. What is Flask's design philosophy, and how does it differ from Django?

▶ Answer Flask is a microframework: a thin core (routing, request/response, templating via Jinja2) with everything else — ORM, auth, admin, forms — left to your choice of extensions or your own code. Q94. How does Flask-SQLAlchemy manage sessions per request, and what's the common pitfall?

Q105. Implement an LRU cache from scratch (no `functools`) using a dict + doubly linked list.

▶ Answer

class Node:
    __slots__ = ("key", "value", "prev", "next")
    def __init__(self, key=None, value=None):
        self.key, self.value, self.prev, self.next = key, value, None, None

class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.cache = {}                              # key -> Node, for O(1) lookup
        self.head, self.tail = Node(), Node()         # sentinels — avoid None-checks at the boundaries
        self.head.next, self.tail.prev = self.tail, self.head

    def _remove(self, node):
        node.prev.next, node.next.prev = node.next, node.prev

    def _add_front(self, node):                        # front = most recently used
        node.next, node.prev = self.head.next, self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key: int) -> int:
        if key not in self.cache:
            return -1
        node = self.cache[key]
        self._remove(node)
        self._add_front(node)                           # touching it makes it most-recently-used
        return node.value

    def put(self, key: int, value: int) -> None:
        if key in self.cache:
            self._remove(self.cache[key])
        node = Node(key, value)
        self.cache[key] = node
        self._add_front(node)
        if len(self.cache) > self.capacity:
            lru = self.tail.prev                        # evict from the back = least recently used
            self._remove(lru)
            del self.cache[lru.key]

get and put are both O(1): dict gives O(1) lookup, doubly-linked list gives O(1) removal/insertion without shifting elements (unlike a plain list).

Q106. Implement a thread-safe rate limiter (token bucket) in Python.

▶ Answer

import time, threading

class TokenBucket:
    def __init__(self, rate: float, capacity: int):
        self.rate = rate                  # tokens added per second
        self.capacity = capacity
        self.tokens = capacity
        self.last_refill = time.monotonic()
        self.lock = threading.Lock()

    def _refill(self):
        now = time.monotonic()
        elapsed = now - self.last_refill
        self.tokens = min(self.capacity, self.tokens + elapsed * self.rate)
        self.last_refill = now

    def allow(self) -> bool:
        with self.lock:                    # protects the read-modify-write against concurrent threads
            self._refill()
            if self.tokens >= 1:
                self.tokens -= 1
                return True
            return False

# usage in a WSGI/Flask/Django view: if not bucket.allow(): return 429

time.monotonic() (not time.time()) avoids issues from system clock adjustments. For a multi-process deployment (multiple Gunicorn workers), this in-memory bucket won't share state — use Redis (INCR + EXPIRE, or a Lua script for atomicity) instead.

Q110. Implement JWT authentication (encode + verify) from first principles.

import jwt, datetime

SECRET, ALGO = "change-me-use-env-var", "HS256"

def create_access_token(user_id: int, expires_minutes: int = 30) -> str:
    payload = {
        "sub": str(user_id),
        "iat": datetime.datetime.utcnow(),
        "exp": datetime.datetime.utcnow() + datetime.timedelta(minutes=expires_minutes),
    }
    return jwt.encode(payload, SECRET, algorithm=ALGO)

def verify_token(token: str) -> int:
    try:
        payload = jwt.decode(token, SECRET, algorithms=[ALGO])   # verifies signature AND exp automatically
        return int(payload["sub"])
    except jwt.ExpiredSignatureError:
        raise AuthError("Token expired")

Q113. Write a decorator-based simple retry + circuit breaker for an external API call.

▶ Answer

import time, functools

class CircuitOpenError(Exception): pass

class CircuitBreaker:
    def __init__(self, failure_threshold=5, reset_timeout=30):
        self.failure_threshold, self.reset_timeout = failure_threshold, reset_timeout
        self.failures, self.state, self.opened_at = 0, "closed", None

    def __call__(self, func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            if self.state == "open":
                if time.monotonic() - self.opened_at > self.reset_timeout:
                    self.state = "half_open"                # try one test call
                else:
                    raise CircuitOpenError("Circuit is open — failing fast")
            try:
                result = func(*args, **kwargs)
            except Exception:
                self.failures += 1
                if self.failures >= self.failure_threshold:
                    self.state, self.opened_at = "open", time.monotonic()
                raise
            else:
                self.failures, self.state = 0, "closed"       # success resets the breaker
                return result
        return wrapper

@CircuitBreaker(failure_threshold=3, reset_timeout=15)
def call_payment_gateway(order): ...

Prevents a struggling downstream dependency from being hammered by retries across thousands of requests — once the failure threshold is hit, subsequent calls fail fast without even attempting the network call, until the reset timeout elapses.

Q117. What is CSRF, and how do Django, Flask and FastAPI each handle it?

▶ Answer CSRF tricks a logged-in user's browser into submitting a request to your site using their existing session cookie, without their intent (e.g., a hidden auto-submitting form on an attacker's page). Q124. Design a rate-limited, idempotent payment API endpoint.

▶ Answer

POST /payments  with header  Idempotency-Key: <client-generated UUID>

Q125. How do you handle a database migration on a large table with zero downtime?

▶ Answer

Adding a column with a default (large table):
  1. Add the column as NULLABLE, no default at the DB level (fast, metadata-only on Postgres 11+)
  2. Backfill in BATCHES via a data migration or management command (avoid one giant UPDATE locking the table)
  3. Once backfilled, add a NOT NULL constraint (or application-level default) in a separate migration

Renaming a column (breaking change for running old-code instances during rolling deploy):
  1. Add the NEW column
  2. Deploy code that writes to BOTH old and new columns, reads from old (dual-write)
  3. Backfill new column from old for existing rows
  4. Deploy code that reads from new, still writes both (verify)
  5. Deploy code that only uses new column
  6. Drop the old column in a later migration

The core principle: never require the old code and new code to disagree about the schema during a rolling deploy — every migration should be compatible with the previous deployed version of the application for the window between "migration applied" and "new code fully rolled out."

Q126. Your Celery task queue is backing up. How do you diagnose and fix it?

▶ Answer Check: worker count vs. task arrival rate (are you under-provisioned?), whether a subset of tasks are slow/hanging (blocking workers that could process other tasks — check for missing timeouts), whether a single queue is mixing fast and slow task types (a flood of slow tasks starves quick ones — use separate queues/routing by task type and priority), retry storms (a failing external dependency causing exponential retry pile-up), and broker health (Redis/RabbitMQ memory or connection limits). Fixes: separate queues per task class with dedicated worker pools, task_time_limit/task_soft_time_limit to prevent hangs, exponential backoff with a cap on retries, and autoscaling workers on queue depth.

Q130. Sync (WSGI) vs async (ASGI) — when does async actually give you a real benefit?

▶ Answer Async shines when a service is I/O-bound with high concurrency — many simultaneous slow network calls (calling several downstream APIs per request, WebSocket connections, long-polling, streaming). It gives little to no benefit for CPU-bound work, and can be a net negative if the team introduces subtly-blocking calls inside async def handlers (worse than sync, since it blocks the whole event loop, not just one thread). Rule of thumb: if your service is mostly "receive request → one DB query → return," sync WSGI with enough worker processes is simpler and performs comparably; async pays off as the number of concurrent slow I/O operations per request grows.

Q131. Celery vs FastAPI BackgroundTasks vs a lightweight queue (RQ/Dramatiq/arq) — how do you decide?

▶ Answer

  • RQ/Dramatiq/arq: simple Redis-backed queues, lower operational overhead than Celery, good for small-to-medium workloads needing retries/persistence without Celery's full feature surface.
  • Celery: the most feature-complete (complex workflows/chains, multiple brokers, scheduling via Celery Beat, mature monitoring via Flower) — worth its extra operational complexity once you need those features or already have Celery infrastructure.

🏭 Production

Q134. A Django app randomly raises "RecursionError" or hangs on certain requests. What do you check?

▶ Answer Likely a signal loop: a post_save receiver that itself calls .save() on the same instance without a guard, re-triggering the signal infinitely (or a deep chain of related signals). Check for save() calls inside post_save/pre_save receivers on the same model without an update_fields/flag guard, and circular ForeignKey/OneToOne relations with cascading signal handlers. Fix: use update_fields checks, a _updating guard flag, or move the logic out of the signal into an explicit method the caller invokes once.

Q135. "DatabaseError: connection already closed" / "OperationalError: server closed the connection unexpectedly" appears intermittently. What's going on?

▶ Answer Common causes: the DB connection idle-timed-out (common with CONN_MAX_AGE set too high relative to the database's own idle timeout, or a connection pooler like PgBouncer in transaction-pooling mode being incompatible with persistent connections), a connection held across a fork() (e.g., in a Celery worker or Gunicorn preload that opened a connection before forking — each forked process then shares a now-broken socket), or the database restarting. Fix: tune CONN_MAX_AGE sensibly (or 0 to disable persistent connections if using an external pooler), ensure DB connections are established after fork (lazy connection, pgbouncer in session mode, or Django's connection health checks), and add reconnect/retry logic for transient failures.

Q136. FastAPI/async endpoint hangs under load even though each request is fast individually. What do you check?

▶ Answer Almost always a blocking call inside async def starving the event loop — a sync DB driver, a synchronous requests.get(), time.sleep(), or CPU-heavy work with no run_in_executor. Since one blocking call freezes every concurrent request on that worker, symptoms appear as intermittent hangs correlated with load, not with any single request being slow in isolation. Audit every await-free line inside async def handlers for anything that could block, and check third-party library docs for whether they're actually async-native (requests is not; httpx is).

Q137. A DRF list endpoint returns different results/order across page requests, causing duplicate or missing items for a paginating client. Why?

▶ Answer Missing deterministic ordering. Without an explicit, unique order_by (or ordering in Meta), the database doesn't guarantee row order is stable across separate queries — especially under concurrent writes. PageNumberPagination computes offsets assuming a stable order; if rows shift between page 1 and page 2 requests, items can be skipped or repeated. Fix: always add a deterministic order_by (ideally ending in a unique tiebreaker like id) to any paginated queryset, or switch to CursorPagination (keyed on a stable, unique, sequential field) which is far more robust against concurrent inserts than offset-based pagination.

Q138. Memory usage of a Django/Celery worker keeps climbing over hours ("memory leak"). How do you diagnose?

▶ Answer Common Python-web-specific causes: query results or large objects accumulating in a long-lived cache/global without eviction, Django's DEBUG=True in production (it keeps every query in connection.queries for the life of the process — a classic and very common leak), circular references delaying (not preventing, but delaying) garbage collection under generational GC pressure, or a Celery task leaking file handles/connections it doesn't close. Diagnose with tracemalloc, objgraph (to find what's growing), and first rule out DEBUG=True — it's the single most common cause of this exact symptom in Django. For Celery, configure worker_max_tasks_per_child as a pragmatic mitigation while you find the root cause.

Q139. `pytest` tests pass individually but fail when run together as a suite. What's the likely cause?

▶ Answer Test isolation failure — shared mutable state leaking between tests: a module-level cache/global not reset between tests, database rows from one test visible to another (missing transaction rollback — check pytest-django's db/transactional_db fixture usage), a fixture with function scope accidentally reused as if it were session-scoped, or tests relying on execution order (test B assumes state test A happened to leave behind). Fix by making each test independently set up its own required state, using pytest-django's automatic transaction rollback per test, and running with pytest-randomly to surface order-dependent tests deliberately.

Q140. A Django migration fails partway through in production with a table left in a half-migrated state. How do you recover?

▶ Answer Check whether the failing migration was wrapped by an atomic transaction — by default, Django wraps each migration in a transaction on databases that support DDL transactions (PostgreSQL), so a failure should auto-rollback cleanly; MySQL does not support transactional DDL, so a partial failure there can genuinely leave a half-applied schema. Recovery: inspect django_migrations table to see what's recorded as applied vs. what actually exists in the schema, manually reconcile (apply the missing DDL by hand or fake the migration with --fake once the schema matches), and going forward, test migrations against a production-schema copy in staging before applying to production, and prefer PostgreSQL's transactional DDL guarantees where possible.

Q141. An endpoint works fine under one Gunicorn worker but breaks with multiple workers/processes. What's likely wrong?

▶ Answer Almost always shared in-process state assumed to be global but actually per-process: an in-memory cache (LocMemCache, a module-level dict used as a cache), an in-memory rate limiter/counter, or a background thread started per-worker that duplicates work N times instead of running once. With multiple worker processes, each has its own copy of any in-process Python state — there's no automatic sharing. Fix: move shared state to Redis/Memcached/the database, and ensure any "run once" startup logic (like a scheduler) uses a proper distributed lock or runs in a single dedicated process, not inside every web worker.

▶ Answer Weigh: is the current bottleneck actually I/O concurrency (many slow external calls per request) that async would meaningfully help, or is it something async doesn't fix (slow queries, missing caching, CPU-bound work)? What's the migration cost (rewriting sync code as async, re-testing everything, retraining the team) versus incremental fixes to the existing Flask app (adding caching, fixing N+1-equivalent issues, scaling out workers)? Is auto-generated OpenAPI docs and Pydantic validation valuable enough on its own to justify a switch? Often the pragmatic answer is: fix the actual bottleneck first with data, and only migrate frameworks if the data shows a structural limitation async would solve — not because FastAPI is newer.

Q145. How do you decide between Django's built-in ORM features and dropping to raw SQL?

▶ Answer Default to the ORM — it's safer (parameterised, less error-prone), portable across database backends, and integrates with migrations. Drop to raw SQL (.raw(), cursor.execute(), or a CTE/window function via RawSQL/django.db.models.expressions) when: the ORM genuinely can't express the query efficiently (complex window functions, recursive CTEs, database-specific features), you've measured that the ORM-generated query is meaningfully worse than hand-tuned SQL for a hot path, or you need a report-style query that's a poor fit for the ORM's object-mapping model. Always keep raw SQL parameterised and covered by tests, since it bypasses some of the ORM's safety nets.

Q146. What's your framework for deciding "is this a code problem or a data/infrastructure problem" when debugging a slow endpoint?

▶ Answer Measure before guessing: check the query count and total query time (debug toolbar / APM), check if it's dominated by one slow query (index/data problem) vs. many queries (N+1/code problem), check external call latency (network/dependency problem), and check CPU vs. wait time in a profiler (compute problem vs. I/O problem). The category tells you where to look: N+1 → code (add select_related); slow single query on huge data → data/index problem; high CPU → algorithmic/code problem; high wait with low CPU → I/O/infrastructure/external-dependency problem.

Q147. What does the GIL prevent?

▶ Answer True parallel execution of Python bytecode across threads within one process.

Q148. Mutable default argument — safe or not?

▶ Answer Not safe — it's created once at function-definition time and shared across calls; use None as a sentinel instead.

Q149. `is` vs `==`?

▶ Answer is compares identity; == compares value equality via __eq__.

Q150. What does `yield` do that `return` doesn't?

▶ Answer Pauses the function, preserving local state, and resumes on the next next() call instead of exiting.

Q151. `select_related` vs `prefetch_related`?

▶ Answer select_related = SQL JOIN for single-valued relations; prefetch_related = separate query + Python-side join for multi-valued relations.

Q152. What triggers a QuerySet to hit the database?

▶ Answer Iteration, list(), len(), bool(), slicing with a step, or printing/repr — not filtering/chaining alone.

Q153. `F()` expression — what problem does it solve?

▶ Answer Atomic, database-side value updates (e.g., views = F("views") + 1), avoiding a read-then-write race condition.

Q154. What does `select_for_update()` do?

▶ Answer Locks the selected rows at the database level until the enclosing transaction commits, preventing concurrent lost updates.

Q155. Why must a custom `AUTH_USER_MODEL` be set before the first migration?

▶ Answer Changing it later requires a risky manual data migration across every FK pointing to the user table.

Q156. DRF: `Serializer` vs `ModelSerializer`?

▶ Answer Serializer declares fields explicitly; ModelSerializer auto-generates fields (and validators) from a model.

Q157. What does a DRF Router do?

▶ Answer Auto-generates the URLconf for a ViewSet's standard CRUD actions (and @action-decorated custom routes).

Q158. Flask: what problem does the application factory pattern solve?

▶ Answer Enables multiple independently-configured app instances (crucial for testing) instead of one module-level global app.

Q159. What does `init_app()` let a Flask extension do?

▶ Answer Defer binding to a specific app instance, so the extension object can be created at import time and reused across factories.

Q160. FastAPI: what does `response_model` do besides documentation?

▶ Answer Validates and filters the returned data against the schema, preventing accidental leakage of extra fields.

Q161. FastAPI: sync `def` route vs `async def` route — how are they scheduled?

▶ Answer Sync def runs in a thread pool automatically; async def runs directly on the event loop.

Q162. What's the danger of a blocking call inside `async def`?

▶ Answer It blocks the entire event loop, freezing every concurrent request on that worker — worse than a plain sync function.

Q163. What does `Depends()` provide in FastAPI beyond just calling a function?

▶ Answer Automatic dependency-graph resolution, per-request caching, yield-based setup/teardown, and easy test overrides.

Q164. WSGI vs ASGI — key difference?

▶ Answer WSGI is synchronous, one request per worker; ASGI supports async concurrency plus WebSockets/HTTP2/long-lived connections.

Q165. What's the main risk of `BackgroundTasks` in FastAPI vs a real task queue?

▶ Answer No persistence or retry — if the process crashes or the task fails, the work is silently lost.

Q166. Why is `pickle.loads()` on untrusted input dangerous?

▶ Answer It can execute arbitrary code during deserialization — a classic insecure-deserialization vulnerability.

Q167. What does `functools.wraps` preserve in a decorator?

▶ Answer The wrapped function's __name__, __doc__ and other metadata, which frameworks/introspection rely on.

Q168. Why is `unique_together`/`UniqueConstraint` needed alongside `get_or_create` for true race safety?

▶ Answer Without a DB-level unique constraint, two concurrent requests can both pass the initial get() and both attempt create().

Q169. What's the core weakness of offset-based pagination under concurrent writes?

▶ Answer Rows can shift between page requests, causing skipped or duplicated items — cursor pagination avoids this.

Q170. What's the single most common cause of "memory leak" symptoms in a Django production process?

▶ Answer DEBUG=True left enabled, which accumulates every executed query in memory for the life of the process.

Q171. Why can't a plain in-memory cache (`LocMemCache`) work correctly across multiple Gunicorn workers?

▶ Answer Each worker process has its own separate memory — nothing is actually shared between them.

Q172. What is the "alg: none" JWT vulnerability?

▶ Answer Trusting a client-supplied algorithm header during verification instead of pinning the expected algorithm explicitly.

Q173. Celery task queue backing up — first thing to check?

▶ Answer Whether task types are mixed in one queue, letting slow tasks starve fast ones — route by queue/priority.
