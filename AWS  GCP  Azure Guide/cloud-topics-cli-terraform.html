1. Compute

AWSGCPAzure
EC2Compute EngineVirtual Machines

Purpose: Virtual servers for apps, APIs, databases you manage.
When to use: Need full OS control, legacy/lift-and-shift, GPU. Avoid for simple stateless apps (use containers/serverless).

Use case, when and why (per service)

AWS

Use cases: Web/app servers, self-managed databases, GPU/ML jobs, lift-and-shift of legacy apps
When to use: Need full OS control, special instance types (GPU, high memory), or custom agents
Why use: Widest instance choice, Spot and Savings Plans for cost, mature ecosystem (AMIs, ASG)

Azure

Use cases: Windows/Linux servers, SQL Server or SAP hosting, lift-and-shift
When to use: Windows-heavy estates, Hybrid Benefit licensing, Active Directory integration
Why use: Best fit for Microsoft licensing and Entra ID integration, scale sets and availability zones

GCP

Use cases: Custom VMs, batch/HPC, GPU workloads, lift-and-shift
When to use: Need OS control or custom machine shapes
Why use: Custom machine types (pay only for needed CPU/RAM), live migration, per-second billing

AWS

Policy and role required

AWS

You / CI: AmazonEC2FullAccess (least privilege: ec2:RunInstances, DescribeInstances, CreateTags, TerminateInstances) plus iam:PassRole to attach a role
Service role: Instance profile role, trust ec2.amazonaws.com; AmazonSSMManagedInstanceCore for Session Manager

Azure

You / CI: Virtual Machine Contributor plus Network Contributor for NIC/VNet
Service role: Managed identity on the VM, then grant it roles on what it reads

GCP

You / CI: roles/compute.instanceAdmin.v1 plus roles/iam.serviceAccountUser to attach a service account
Service role: VM service account with only the roles the app needs (avoid the default Editor account)

3. Networking

AWSGCPAzure
VPCVPCVirtual Network (VNet)

Purpose: Private network with subnets, routing and firewalls.
When to use: Always, for every workload. Avoid the default network in production.

Use case, when and why (per service)

AWS

Use cases: Isolating workloads, public/private subnets, connecting to on-prem (VPN, Direct Connect)
When to use: Always, before deploying any workload; never use the default VPC for production
Why use: Full control of IP ranges, routing, security groups and NACLs; regional with subnets per AZ

Azure

Use cases: Isolated networks, hub-and-spoke, peering, ExpressRoute/VPN to on-prem
When to use: Always; plan address space early because VNets are hard to re-address
Why use: Native NSGs, peering and Private Link integration with every Azure service

GCP

Use cases: Private networking for projects, Shared VPC across teams, hybrid links
When to use: Always; use custom-mode VPCs, not the auto-created default
Why use: Global VPC (one network spans regions), subnets are regional, simple multi-project sharing

Policy and role required

AWS

You / CI: AmazonVPCFullAccess (ec2:CreateVpc, CreateSubnet, CreateRouteTable, CreateSecurityGroup, ...)
Service role: Flow Logs role: trust vpc-flow-logs.amazonaws.com, logs:CreateLogStream, PutLogEvents

Azure

You / CI: Network Contributor on the resource group
Service role: None needed; NSG flow logs write to a storage account (needs access to it)

GCP

You / CI: roles/compute.networkAdmin; Shared VPC users need roles/compute.networkUser on the host project
Service role: None needed for plain VPC

AWSGCPAzure

Purpose: Managed relational database (backups, patching, failover handled).
When to use: Need SQL/transactions without running DB servers yourself.

Use case, when and why (per service)

AWS

Use cases: Transactional apps (OLTP), web backends, SaaS metadata (MySQL, PostgreSQL, SQL Server, Oracle, Aurora)

When to use: Need managed SQL for apps on Cloud Run, GKE or Compute
Why use: Simple setup, automatic backups/HA, private IP and a connector for secure access

5. Containers

AWSGCPAzure

Purpose: Store container images and run them without managing servers.
When to use: Packaged apps and APIs that need fast deploys and autoscaling.

AWS

7. Serverless

8. IAM and Security

AWSGCPAzure
IAMCloud IAMMicrosoft Entra ID + RBAC

Purpose: Control who/what can access which resources; workload identities.
When to use: Always. Use roles/identities, least privilege, no long-lived keys.

Use case, when and why (per service)

AWS

Use cases: Controlling who can do what; roles for EC2/Lambda/ECS; cross-account access
When to use: Always; use roles and temporary credentials, least privilege, no long-lived keys
Why use: Fine-grained policies, STS temporary credentials, permission boundaries, SCP guardrails

Azure

Use cases: Employee and app identity (Entra ID), RBAC on resources, managed identities
When to use: Always; use managed identities for apps and groups for people
Why use: Single identity for Microsoft 365 and Azure, Conditional Access, PIM for just-in-time access

GCP

Use cases: Controlling access to projects and resources; service accounts; Workload Identity
When to use: Always; bind roles to groups or service accounts at the lowest scope
Why use: Simple role bindings with inheritance (org, folder, project), Workload Identity Federation

Policy and role required

AWS

You / CI: IAMFullAccess is very broad; prefer iam:CreateRole, PutRolePolicy, AttachRolePolicy, PassRole limited by a permissions boundary

Azure

GCP

You / CI: roles/iam.securityAdmin or roles/resourcemanager.projectIamAdmin; roles/iam.serviceAccountAdmin for service accounts

AWS
