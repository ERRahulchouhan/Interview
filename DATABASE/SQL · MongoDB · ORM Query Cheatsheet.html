SQL · MongoDB · ORM — every query, side by side

ORM = Python SQLAlchemy 2.0 (session s). MongoDB = mongosh syntax (PyMongo uses the same names in snake_case).

Sample data — SQL tables: users(id, name, email, age, city), orders(id, user_id, amount, status). MongoDB collections: users, orders (with user_id). ORM models: User, Order. Imports: from sqlalchemy import select, update, delete, func, or_, and_, case, exists

Scaling: 1 million+ records, indexing & sharding

A million records is small for a modern database. Fix the basics first, then scale step by step.

1. Indexing (biggest win)

Without an index the database scans every row. Index columns used in WHERE, JOIN and ORDER BY. Don’t over-index, because every index slows inserts and updates. Check with EXPLAIN.

2. Pagination

OFFSET 900000 is slow because the database still walks past 900k rows. Use keyset pagination instead:

SQL
SELECT * FROM users
WHERE id > :last_id
ORDER BY id LIMIT 20;
MongoDB
db.users.find({_id:{$gt:lastId}})
  .sort({_id:1}).limit(20)
ORM
select(User).where(User.id > last_id)
  .order_by(User.id).limit(20)

3. Query hygiene

  • Select only the columns you need, avoid SELECT *.
  • Avoid N+1 queries in the ORM (use joins or eager loading).
  • Do heavy work in the database, not in Python loops.

4. Caching

Keep hot, rarely changing data in Redis or an in-memory cache so it doesn’t hit the database every time.

5. Read replicas

The primary handles writes and copies of it handle reads. Best when the app reads far more than it writes.

6. Partitioning

Split one big table into smaller pieces inside the same database, usually by date or range (for example one partition per month). Queries on recent data only touch the recent partition.

7. Archiving

Move old data (for example orders older than 3 years) to an archive table or cold storage.

8. Sharding (when one server is not enough)

Sharding splits data across multiple servers. Each server (shard) holds only part of the data.

  • Shard key: the field that decides which shard stores a record, such as user_id.
  • Hash sharding: the key is hashed, so data spreads evenly. Good load balance, poor for range queries.
  • Range sharding: for example users 1–1M on shard A, 1M–2M on shard B. Range queries are easy, but one shard can become a hotspot.
  • Pitfalls: a bad shard key creates hotspots, cross-shard joins are slow, cross-shard transactions are complex, and resharding later is painful.

MongoDB shard setup:

sh.enableSharding("shop")
sh.shardCollection("shop.users", { user_id: "hashed" })

What to use, in order

  2. Cache (Redis)
  3. Read replicas
  4. Partitioning + archiving

Sharding in simple words

The idea

Imagine one library with 10 million books. One librarian, one building, and it is getting slow and crowded. So you open 4 libraries, each holding some of the books. A rule decides which library has which book, for example by the first letter of the title. Each librarian now handles fewer books and fewer visitors.

That is sharding: you split one big database into smaller databases (shards) on different servers, and a rule (the shard key) decides where each record goes.

Why do it?

One server has limits: disk space, memory, CPU, and writes per second. A bigger server (vertical scaling) gets very expensive and still has a ceiling. Sharding adds more normal servers (horizontal scaling). Each shard holds less data, so queries and writes are faster and the load is shared.

When to do it?

Only after the simpler steps failed. Sharding is the last step, not the first. Do it when:

  1. Your data is too large for one server (many hundreds of GB to TBs).
  2. Write traffic is too high for one server, even after indexes, caching and good queries.
  3. Read replicas don’t help, because the problem is writes or data size, not reads.

When NOT to do it

  • You have around 1 million records. Indexes will be enough.
  • The app is slow because of missing indexes or bad queries. Fix those first.
  • Traffic is mostly reads. Use caching and read replicas.

Sharding adds complexity: cross-shard joins and transactions are hard, and changing the shard key later is painful.

How to do it, step by step

  1. Pick the shard key. This is the most important decision. Ask: “What field do most of my queries filter by?” Often it is user_id. A good key has many different values, spreads data evenly, and appears in most queries.
  2. Pick the method.
    • Hash sharding: hash(user_id) % number_of_shards. Even spread, slow range queries.
    • Range sharding: users 1–1M on shard A, 1M–2M on shard B. Easy range queries, but a shard can become a hotspot.
  3. Route queries. Every query should include the shard key so the system knows which shard to ask. MongoDB’s router (mongos) does this for you. In SQL, your app or a tool like Vitess or Citus does it.
  4. Plan for growth. Leave room to add more shards later.

Bad vs good shard key

KeyResult
country (bad)Most users sit in one or two countries, so one shard gets almost all the load (hotspot).
user_id hashed (good)Users spread evenly across all shards.

MongoDB example

sh.enableSharding("shop")
sh.shardCollection("shop.orders", { user_id: "hashed" })

MongoDB then splits the data and balances it between the shards automatically.

Rule to remember

Index first, then cache, then replicas, then partitioning, and shard last.

Production concepts (must know)

1. Connection pooling

Opening a new connection per request is slow, and databases have a maximum connection limit. A pool keeps a fixed set of connections open and reuses them.

ORM (SQLAlchemy)
create_engine(url, pool_size=10,
  max_overflow=20, pool_pre_ping=True,
  pool_recycle=1800)
MongoDB (PyMongo)
MongoClient(uri, maxPoolSize=50,
  serverSelectionTimeoutMS=5000)
Rule
pool size x app instances
  < DB max connections
(create the client once, not per request)

2. Security

Never build queries by joining strings with user input. Use parameters.

SQL
cur.execute(
 "SELECT * FROM users WHERE email=%s",
 (email,))   # never f"...{email}"
MongoDB
# NoSQL injection: user sends {"$ne": null}
email = str(body["email"])  # force a string
db.users.find_one({"email": email})
ORM
# safe by default (bound parameters)
select(User).where(User.email == email)
  • Give the app a least-privilege user (no DROP, no admin rights).
  • Turn on authentication (MongoDB), use TLS, and never expose the DB port to the public internet.
  • Keep passwords in environment variables or a secrets manager, not in code. Encrypt data at rest; hash passwords with bcrypt or argon2.

3. Migrations (schema changes)

Never change production tables by hand. Use versioned migrations (Alembic, Flyway; for MongoDB, versioned scripts). For zero downtime, change in small steps:

  1. Add the new column as nullable.
  2. Backfill old rows in small batches.
  3. Deploy code that uses the new column.
  4. Add constraints, and drop the old column in a later release.

Never rename or drop a column in the same release as the code change. Large ALTER TABLE on millions of rows can lock the table, so test it on a copy first.

4. Backup & recovery

mysqldump -u user -p shop > shop.sql
pg_dump -Fc shop > shop.dump
mongodump --db shop --out /backup/2026-11-10
  • Point-in-time recovery (PITR): keep binlogs (MySQL), WAL (Postgres) or the oplog (MongoDB) so you can restore to any minute.
  • RPO = how much data you can afford to lose. RTO = how long you can be down.
  • A backup you never restored is not a backup. Test restores regularly, and store copies in another region.

5. Replication & failover

Run at least 3 nodes (primary + 2 replicas, a MongoDB replica set, or a managed Multi-AZ service). If the primary dies, a replica is promoted automatically.

  • Replication lag: a replica can be a little behind. A user who just saved something may not see it if you read from a replica. Read important data from the primary.
  • MongoDB: writeConcern: {w: "majority"} makes a write safe against failover. readPreference chooses primary or secondary reads.

6. Transactions, isolation & deadlocks

  • ACID: Atomic, Consistent, Isolated, Durable. Use a transaction when several writes must succeed or fail together (money transfer, order + stock).
  • Isolation levels: Read Committed (common default), Repeatable Read, Serializable (safest, slowest).
  • Deadlock: two transactions wait for each other. Keep transactions short, update rows in the same order, and retry on a deadlock error.
  • MongoDB: a single document update is already atomic. Design documents so most work needs only one document, and avoid multi-document transactions when you can.

7. Schema design

  • SQL: normalize (no repeated data, use foreign keys). Denormalize only for proven read speed needs.
  • MongoDB embed vs reference: embed when data is read together and stays small (order + its items). Reference when data is large, shared, or grows without limit (user and all their logs).
  • Avoid unbounded arrays. A MongoDB document is limited to 16 MB.
  • Validate data in the database too:
db.createCollection("users", {validator: {$jsonSchema: {
  required: ["name","email"],
  properties: {age: {bsonType: "int", minimum: 0}}}}})

8. Data lifecycle

  • Soft delete: add a deleted_at column and filter on it instead of really deleting. Easy to undo, good for audit.
  • Auto-expire (MongoDB TTL index):
db.sessions.createIndex({createdAt: 1}, {expireAfterSeconds: 3600})
  • In SQL, use a scheduled job to archive or delete old rows in small batches.

9. Monitoring

-- MySQL
SET GLOBAL slow_query_log=1; SET GLOBAL long_query_time=1;
-- Postgres: enable pg_stat_statements
// MongoDB
db.setProfilingLevel(1, {slowms: 100})

Watch: queries per second, p95 latency, active connections, replication lag, disk space, cache hit ratio, slow queries. Set alerts before disk is full or connections run out.

10. Resilience in the app

  • Timeouts on every query, so one slow query doesn’t freeze the app.
  • Retries with backoff for temporary errors, and idempotency keys so a retry doesn’t create a duplicate order or payment.
  • Bulk operations: insert and update in batches (for example 1,000 at a time), not one by one and not millions at once.
  • Rate limiting and caching protect the database from traffic spikes.
  • Avoid N+1 queries (use joins or eager loading), and never run heavy reports on the primary. Use a replica.

11. Consistency trade-off (CAP)

When the network between servers breaks, you must choose: stay consistent (some requests fail) or stay available (some data may be stale). Banking-type data should choose consistency. Feeds, likes and counters can accept stale data.

SQL basics

WHERE vs HAVING?

WHERE filters rows before grouping. HAVING filters groups after GROUP BY, so it can use aggregates like COUNT(*).

INNER JOIN vs LEFT JOIN?

INNER returns only rows that match in both tables. LEFT returns all rows from the left table, with NULLs where the right side has no match. Use LEFT JOIN + WHERE right.id IS NULL to find rows with no match.

DELETE vs TRUNCATE vs DROP?

DELETE removes rows (can use WHERE, can roll back, logged row by row). TRUNCATE removes all rows fast and resets auto-increment, with no WHERE. DROP removes the whole table, structure included.

Primary key vs unique key vs foreign key?

Primary key: unique and not null, one per table. Unique key: unique values, can allow NULL, many per table. Foreign key: a column that points to the primary key of another table and keeps the data consistent.

UNION vs UNION ALL?

UNION removes duplicates (extra sort/work). UNION ALL keeps everything and is faster. Use UNION ALL when you know there are no duplicates or don’t care.

What is normalization? When do you denormalize?

Normalization removes repeated data by splitting it into related tables (1NF, 2NF, 3NF). It avoids update mistakes. Denormalize only when a read is too slow because of many joins and you have measured it.

What is a CTE and how is it different from a subquery?

A CTE (WITH name AS (...)) is a named temporary result you can reuse and read top to bottom. It is cleaner than nested subqueries and supports recursion (for example, tree or hierarchy data).

Indexes & performance

How does an index work? What is the cost?

It is a sorted structure (usually a B-tree) that lets the database jump to rows instead of scanning the table. Cost: extra disk space, and slower inserts, updates and deletes because the index must be updated too.

Clustered vs non-clustered index?

A clustered index decides the physical order of rows (one per table, usually the primary key). A non-clustered index is a separate structure with pointers to the rows (many per table).

What is the leftmost prefix rule for a composite index?

An index on (a, b, c) helps queries filtering on a, a,b or a,b,c, but not on b alone. Order columns by equality filters first, then range or sort.

Why might a query not use an index?

Function on the column (WHERE YEAR(date)=2026), leading wildcard (LIKE '%abc'), type mismatch (string vs number), low-selectivity column, or the planner thinks a scan is cheaper. Check with EXPLAIN.

A query is slow. How do you optimize it?

Run EXPLAIN, look for full scans, add or fix indexes, select only needed columns, remove N+1 patterns, rewrite subqueries as joins if needed, paginate with keyset, cache the result, and only then consider replicas or sharding.

OFFSET pagination vs keyset pagination?

OFFSET still walks past all skipped rows, so page 50,000 is slow. Keyset uses WHERE id > last_id ORDER BY id LIMIT 20 and stays fast on any page. Downside: no jump to an arbitrary page number.

Transactions

What is ACID?

Atomicity (all or nothing), Consistency (rules stay valid), Isolation (transactions don’t disturb each other), Durability (committed data survives a crash).

Isolation levels and the problems they prevent?

Read Uncommitted allows dirty reads. Read Committed prevents dirty reads. Repeatable Read also prevents non-repeatable reads. Serializable also prevents phantom reads, but is slowest. Higher level = safer but less concurrency.

What is a deadlock and how do you handle it?

Two transactions each hold a lock the other needs. The database kills one. Prevent it by keeping transactions short, locking rows in the same order, and retrying the failed transaction.

MongoDB

When would you choose MongoDB over SQL?

When the data is document-shaped and changes shape often, reads fetch a whole object at once, and you need easy horizontal scaling. Choose SQL when you need many joins, strict relations and multi-row transactions (payments, accounting).

Embed or reference?

Embed when data is read together and stays small and bounded (order + items). Reference when data is big, shared by many documents, or grows without limit (user + logs).

What is the aggregation pipeline?

A series of stages that transform documents: $match (filter), $group, $sort, $project, $lookup (join), $unwind, $limit. Put $match and $limit early so indexes are used and less data flows through.

What is the ESR rule for compound indexes?

Order index fields as Equality, then Sort, then Range. This lets MongoDB use the index for filter and sort together.

Replica set vs sharded cluster?

A replica set is copies of the same data for high availability and read scaling. A sharded cluster splits different data across shards for scaling size and writes. Production clusters usually have both (each shard is a replica set).

Does MongoDB support transactions?

Yes, multi-document ACID transactions since version 4.0 (replica sets) and 4.2 (sharded). They cost performance, so design documents so most operations touch a single document, which is already atomic.

What are write concern and read concern?

Write concern says how many nodes must confirm a write (w: "majority" is safe against failover). Read concern says what level of data a read can see (for example majority only returns data that won’t be rolled back).

ORM

What is the N+1 problem and how do you fix it?

You load 1 list of N parents, then run 1 extra query per parent to load children, giving N+1 queries. Fix with eager loading or joins: select(User).options(selectinload(User.orders)) in SQLAlchemy.

Lazy vs eager loading?

Lazy loads related data only when you access it (can cause N+1). Eager loads it up front with the main query. Use eager when you know you will need the related data.

What is a session, and flush vs commit?

A session tracks objects you changed (unit of work). flush sends the SQL to the database inside the open transaction. commit makes it permanent. rollback cancels it.

When would you skip the ORM and write raw SQL?

Complex reports, heavy bulk operations, window functions or database-specific features, or when the generated query is slow. Use parameters (text("... :id")) to stay safe from SQL injection.

Scaling & production

Sharding vs partitioning vs replication?

Partitioning: split one table into pieces inside one server. Replication: full copies on other servers (availability, read scaling). Sharding: split data across servers (scale size and writes).

How do you choose a shard key?

High cardinality (many distinct values), even distribution, and present in most queries. Avoid keys that grow in order (timestamp, auto-increment) with range sharding, because all new writes hit one shard. A hashed user_id is a common good choice.

Hash vs range sharding?

Hash: even spread, bad for range queries. Range: good for range queries, risk of hotspots.

You have 1 million records and the app is slow. What do you do?

Do not shard. Check slow queries, add indexes, use keyset pagination, remove N+1, add caching, then read replicas. 1 million rows is small for one database.

Users don’t see their own update right after saving. Why?

Probably replication lag: the write went to the primary but the read came from a replica that hasn’t caught up. Read recent or critical data from the primary, or use read-your-writes routing.

What is CAP theorem?

During a network partition you can have only one of consistency or availability. Money data should choose consistency. Feeds and counters can choose availability and accept stale data.

How do you make a migration with zero downtime?

Add a nullable column, backfill in small batches, deploy code that writes and reads it, then add constraints and drop the old column in a later release. Never rename or drop in the same release as the code change.

What is idempotency and why does it matter for writes?

Doing the same request twice has the same result as doing it once. With retries and timeouts, a client may send a payment twice. An idempotency key (unique per request) lets the server detect and ignore the duplicate.

The connection pool is exhausted. What do you check?

Connections not returned (missing close or commit), long-running transactions, pool size too small, too many app instances for the DB connection limit, or slow queries holding connections. Fix leaks first, then tune pool size and add timeouts.

Scenario questions

Production database suddenly became slow. What are your steps?
  1. Check what changed: recent deploy, new query, traffic spike, migration.
  2. Look at current activity: running queries, locks, blocked sessions, connection count.
  3. Check the slow query log or profiler for the top offenders, then EXPLAIN them.
  4. Check server resources: CPU, memory, disk I/O, disk space, replication lag.
  5. Quick fixes: kill the bad query, add the missing index, roll back the deploy, enable cache.
  6. Long-term: alerts, query review, load testing.
Design the data model for an e-commerce app.

SQL: users, products, orders (user_id, status, total), order_items (order_id, product_id, qty, price at purchase time). Index orders(user_id, created_at). Store the price in order_items so old orders don’t change when the product price changes.

MongoDB: embed items inside the order document ({user_id, items:[{product_id, qty, price}], total}), reference user_id and product_id.

Practice queries

Second highest salary
-- SQL (handles ties)
SELECT DISTINCT salary FROM emp
ORDER BY salary DESC LIMIT 1 OFFSET 1;

// MongoDB
db.emp.aggregate([{$group:{_id:"$salary"}},
  {$sort:{_id:-1}}, {$skip:1}, {$limit:1}])
Find duplicate emails
-- SQL
SELECT email, COUNT(*) c FROM users
GROUP BY email HAVING COUNT(*) > 1;

// MongoDB
db.users.aggregate([{$group:{_id:"$email", c:{$sum:1}}},
  {$match:{c:{$gt:1}}}])
Top 3 orders per user
-- SQL (window function)
SELECT * FROM (
  SELECT o.*, ROW_NUMBER() OVER (
    PARTITION BY user_id ORDER BY amount DESC) rn
  FROM orders o) t
WHERE rn <= 3;

// MongoDB
db.orders.aggregate([{$sort:{amount:-1}},
  {$group:{_id:"$user_id", top:{$push:"$$ROOT"}}},
  {$project:{top:{$slice:["$top",3]}}}])
Running total of order amount by date
-- SQL
SELECT created_at, amount,
  SUM(amount) OVER (ORDER BY created_at) AS running_total
FROM orders;
Delete duplicate rows but keep one
-- SQL (keep the lowest id)
DELETE FROM users WHERE id NOT IN (
  SELECT MIN(id) FROM (SELECT id, email FROM users) t
  GROUP BY email);
